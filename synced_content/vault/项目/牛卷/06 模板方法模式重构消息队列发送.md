> 面试考的是**"你为什么要重构消息发送，而不是会写 RocketMQ"**：模板方法能把"消息发送"这段**到处重复的胶水代码**抽成"父类定骨架 + 子类填差异"。面试重点在讲清——**哪些东西父类收敛、哪些东西子类定制、业务侧最后剩几行**。

## 一、一句话定位

> Restful 业务里发 RocketMQ 消息时，**Topic 解析、消息体构建、发送、日志打印、异常处理**这段代码在每个发消息的地方重复出现、还和业务逻辑纠缠在一起。用**模板方法模式**把"发送公共逻辑"收敛到抽象父类，业务侧只传一个事件、调一行 `sendMessage`，几十行胶水代码变两行。

## 二、项目技术路线

### 1. 业务背景 / 重构动机
- 优惠券分发有两种发送类型：**立即发送**走 MQ 实时执行；**定时发送**由 XXL-Job 定时扫描再投 MQ。
- 每次发消息时，`Topic 解析 → 构建消息体 → 发送 → 打印成功/失败日志` 逻辑散落各处、**与业务代码纠缠**，不利于维护和复用。
- 目标有二：**① 业务和消息发送解耦（最好业务只剩一行发送）；② 抽象消息发送逻辑（发送/日志公共，Topic 等差异由业务方自定义）。**

### 2. 模板方法模式是什么
- **行为型模式**：在父类的一个 `operation` 方法里定义**算法骨架**，把某些**步骤的实现延迟到子类**；子类不改结构，只重定义其中几个步骤。
- 两个核心特性：
  - **复用性**：父类定义公共实现（如发送接口 + 日志打印）；
  - **扩展性**：差异实现下沉到子类，调用时按子类自动分发。

### 3. 三层抽象（重构核心，记住这三个类）
1. **`BaseSendExtendDTO`**｜消息发送基础扩充属性实体：`eventName / topic / tag / keys / sentTimeout / delayTime`。
2. **`MessageWrapper<T>`**｜消息体包装器：`keys + message(T) + timestamp`，统一消息格式、规范一致。
3. **`AbstractCommonSendProduceTemplate<T>`**｜抽象发送模板（核心）：
   - **两个抽象方法（子类必须实现）**：`buildBaseSendExtendParam`（返回各类扩展参数）、`buildMessage`（构建 Spring 的 `Message<?>`，拼 keys 和 tag）。
   - **一个通用方法（骨架，父类写好）**：`sendMessage(事件)` → 拼 `topic:tag` 目标 → **判断延迟消息 or 普通消息**（`delayTime` 非空走 `syncSendDeliverTimeMills`，否则 `syncSend`）→ 统一打印成功/失败日志。

### 4. 具体生产者落地
- `CouponTaskActualExecuteProducer extends AbstractCommonSendProduceTemplate<CouponTaskExecuteEvent>`，只实现上面两个抽象方法：
  - `buildBaseSendExtendParam`：给 `eventName/keys/topic + ${unique-name:}占位符解析`；
  - `buildMessage`：`new MessageWrapper(keys, 事件)` 并设 `PROPERTY_KEYS` / `PROPERTY_TAGS`。
- 业务侧调用变成**两行**：
```java
CouponTaskExecuteEvent event = CouponTaskExecuteEvent.builder().couponTaskId(couponTaskDO.getId()).build();
couponTaskActualExecuteProducer.sendMessage(event);
```

### 5. 消费者同步改造
- 因消息体统一成了 `MessageWrapper<T>`，消费者泛型由 `RocketMQListener<某Event>` 改为 `RocketMQListener<MessageWrapper<某Event>>`，`onMessage` 里先 `messageWrapper.getMessage()` 取事件，再打日志。
- 附「消费端兜底动作」示例：`CouponTemplateDelayExecuteStatusConsumer` 消费后把指定券模板状态改为已结束。

## 三、面试回答主线（三段式）

**1. 一句话定位**
> "发 MQ 的代码到处重复、和业务纠缠。我用模板方法抽了一个抽象发送模板，父类收敛'骨架+日志+异常'，子类只填差异，业务侧发消息收敛成两行。"

**2. 讲清"抽了什么/哪里可变"**（核心，直接反应该模式你懂没懂）
> "模板方法 = **父类定骨架**（拼目标、选普通/延迟发送、统一日志），**子类定差异**（`buildBaseSendExtendParam` 告诉我要发哪个 topic、`buildMessage` 怎么构建消息体）。调用方一 EnterEvent 就出结果。"

**3. 落到业务效果 + 关联框架**
> "重构后业务代码从几十行胶水变两行。这个思想跟 Spring 的 `AbstractTemplate`（如 `JdbcTemplate`）、模板方法在框架里到处都是——平时写 REST 时的回调模板就是同一套路。"

## 四、必须能说出的记忆锚点

1. **父类收敛**：拼目标、普通 vs 延迟发送、日志、异常，全在骨架方法 `sendMessage` 里。
2. **子类定制**：`buildBaseSendExtendParam`（topic/tag/keys/超时/延迟）、`buildMessage`（消息体包装）。
3. **三个抽象类物**：`BaseSendExtendDTO`（参数实体）、`MessageWrapper<T>`（消息包装器）、`AbstractCommonSendProduceTemplate<T>`（发送模板）。
4. **复用 + 扩展** 双特性。
5. **业务侧两行**：`new 事件 → producer.sendMessage(事件)`。
6. **消费者同步**：泛型统一为 `MessageWrapper<某Event>`。

## 五、被追问清单（面试官会往这打）

### Q1：模板方法和"普通抽象类/继承"有什么区别？
**答**：模板方法不只是"继承复用"，它强调**父类提供一个**可调用的完整流程方法 `operation()`（算法骨架），子类只实现其中若干**步骤（让步点/hooks）**，不改这个骨架。面试要说清这三层：**结构稳定（骨架）+ 步骤可变（子类实现）+ 调用方只看入口**。而普通继承复用可能是为了共享字段/行为，不一定有"骨架方法 + 可变步骤"的结构。

### Q2：`sendMessage` 这个骨架方法里，哪些是固定、哪些是变化的？
**答**：固定的——拼 `topic:tag` 目标、根据 `delayTime` 是否为空选**延迟 or 普通发送**、成功/失败日志、异常上抛；变化的（抽象方法）——**参数实体**（eventName/topic/keys/延迟）与**消息体构建**。这样每次新增一种消息发送，只要 new 一个子类实现这两个抽象方法即可。

### Q3：为什么把消息体统一成 `MessageWrapper<T>`？有什么好处？
**答**：消息体统一格式（`keys + message + timestamp`），有三个好处：① 消费者侧泛型确定、能统一反解析；② **keys 贯穿生产/消费**，方便链路追踪与去重；③ **timestamp** 记录发生时刻，排查延时、做重试判断都有据可依。这也是"把 MQ 数据定义为**事件**（Event）"的原因——大多数时候 MQ 里不只有一个参数，事件化更规范、易扩展。

### Q4：这种"事件/生产者/消费者"的结构本质上是什么？
**答**（加分，展示你懂架构而不只是模式）：这是一套**以"事件"为契约的解耦**——生产者只认识 `Event` 和 `Producer`，消费者只认识 `Event`，两者**通过 MQ 的 topic 而非类直接耦合**。配合模板方法，把"发件习惯"统一收敛，属于**消息驱动 + 骨架归一**的工程范式。面试可提一句"这套写法在大型项目里很常见，本质是把重复的 broker 对接细节藏起来"。

### Q5：和策略模式 / 工厂 / 装饰器有什么区别？为什么这里选模板方法？
**答**（专治只会背名字，务必对比）：模板方法是**同一步骤序列用一套骨架、子类只替换其中某些片段**——结构相同、内容不同；策略是**整块算法在多个独立类里二选一（互斥换整体）**；工厂是**只负责"创建谁"**、不涉及流程；装饰器是**层层叠加增强**（不替换片段而是包裹）。本项目发消息的**步骤骨架固定、只是细节参数不同** → 天然是模板方法的领地，而不是策略（不是找一个替代的"整体发送算法"去 switch）。

### Q6：这和 Spring `JdbcTemplate` / RestTemplate 是不是一回事？
**答**：是。`JdbcTemplate.execute/call` 就是实践——"连接获取、事务、异常翻译"这类骨架放父类里，业务只传入一个回调（`PreparedStatementCallback` / `RowCallbackHandler`）实现可变步骤。面试能主动举这个例，说明你真见过风格一致的模板方法在框架里的落地，而非只在纸上背过。

## 六、代码记忆模板（背这份即可）

```java
// 1. 抽象发送模板：骨架方法收敛公共逻辑，两个抽象方法留给子类
public abstract class AbstractCommonSendProduceTemplate<T> {
    protected abstract BaseSendExtendDTO buildBaseSendExtendParam(T event); // 差异：topic/tag/keys/延迟
    protected abstract Message<?> buildMessage(T event, BaseSendExtendDTO p); // 差异：消息体打包

    public SendResult sendMessage(T event) {                    // 骨架：请求方只调这一个
        BaseSendExtendDTO p = buildBaseSendExtendParam(event);
        String dest = p.getTopic() + (StrUtil.isNotBlank(p.getTag()) ? ":" + p.getTag() : "");
        SendResult r;
        try {
            r = (p.getDelayTime() != null)
                    ? rocketMQTemplate.syncSendDeliverTimeMills(dest, buildMessage(event, p), p.getDelayTime())
                    : rocketMQTemplate.syncSend(dest, buildMessage(event, p), p.getSentTimeout());
            log.info("[生产者] {} 发送结果:{} keys:{}", p.getEventName(), r.getSendStatus(), p.getKeys());
        } catch (Throwable ex) {
            log.error("[生产者] {} 发送失败:{}", p.getEventName(), JSON.toJSONString(event), ex);
            throw ex;
        }
        return r;
    }
}

// 2. 业务侧只剩两行
CouponTaskExecuteEvent event = CouponTaskExecuteEvent.builder().couponTaskId(...).build();
couponTaskActualExecuteProducer.sendMessage(event);
```
