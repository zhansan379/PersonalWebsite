# 面试整理：Java 代码块四种类型

> 代码块是用一对 `{}` 括起来的一组语句。四种类型**用法和作用截然不同**，靠「定义位置 + 修饰符」区分。
> 一句话记忆：**位置和修饰符决定类型，类型决定它被编译到哪里去**——静态块进 `<clinit>`、构造块进 `<init>`、局部块只影响作用域、同步块变成一对 monitor 指令。

## 一、通用回答框架

不要平铺四种定义，按这个骨架说才有层次：

```
1. 先给统一定义 + 四个核心作用      ← 限定作用域 / 初始化 / 控制流程 / 线程同步
2. 按「定义位置 + 修饰符」两个维度分类   ← 体现你有判别标准，不是死记
3. 每类说：作用 + 典型场景
4. 主动交出执行顺序（必被问，抢答）
5. 升维到字节码：每种块最终去了哪里     ← 拉开差距的关键
```

**开场句模板：**
> 「代码块就是一对花括号括起来的语句组，核心作用有四个：限定变量作用域、进行初始化、控制流程、线程同步。按**定义位置和修饰符**可以分成四种：局部代码块、构造代码块、静态代码块、同步代码块。它们的本质区别在于**最终被编译到哪里**——这也是执行顺序的根本原因。」

## 二、四种类型对比表（核心）

| 类型 | 定义位置 | 修饰符 | 核心作用 | 执行时机 |
|---|---|---|---|---|
| **局部代码块**<br>（普通语句块） | **方法内部**或语句内部（循环、判断中） | 无 | **限定变量的生命周期和作用域**，避免变量污染 | 执行到该处时 |
| **构造代码块**<br>（实例初始化块） | **类内部、方法外部** | **无** `static` | **提取多个构造函数的公共初始化逻辑** | **每次** `new` 对象，在构造方法**之前** |
| **静态代码块**<br>（静态初始化块） | **类内部、方法外部** | **有** `static` | 初始化静态成员、一次性类级配置（加载驱动、读配置） | **类初始化时，仅一次** |
| **同步代码块** | **方法内部** | `synchronized(锁对象)` | **解决多线程并发安全**，同一时刻只允许一个线程进入 | 线程执行到该处并**抢到锁**时 |

> **判别口诀**：**在方法里 → 局部块**（带 `synchronized` → 同步块）；**在类里 → 看有没有 `static`**，有则静态块，无则构造块。

## 三、逐类要点

### 3.1 局部代码块

**作用**：变量出了花括号即失效，编译期就无法再访问，有助于**避免变量污染**。

```java
public void testMethod() {
    {
        int temp = 10;      // 作用域仅限于此花括号
        System.out.println(temp);
    }
    // int a = temp;        // 编译报错：temp 已失效
}
```

> `if`、`for`、`while` 后面的 `{}` 也属于此类，同时承担**控制流程**的职责。

**⚠️ 一个需要说准的点**（见第五节）：常见说法是「变量出了块就被释放，节省内存」。**更严谨的表述**是：局部变量在**栈帧的局部变量表**中占一个 slot，出了作用域后该 **slot 可以被后续变量复用**（编译器的槽复用优化），而不是「立刻被回收」。参见 [[编程/jvm/06 运行时数据区 栈 局部变量表]]。

### 3.2 构造代码块（实例初始化块）

**作用**：把多个构造方法**公共的初始化逻辑**提出来，避免重复代码。

```java
class Student {
    String name;
    int score;

    {   // 构造代码块：每次 new 都先执行
        this.score = 60;    // 所有学生默认及格分
    }

    public Student(String name) {
        this.name = name;
    }
}
```

**关键机制**：构造代码块**不是独立方法**，它在编译期被**编译进构造方法 `<init>`**，位置在 `super()` 调用**之后**、构造方法体**之前**。所以「先于构造方法执行」的本质是「被放到了构造方法的前半段」。

> 这一点在 [[编程/jvm/16 类的生命周期 初始化阶段]] 的 `DACBCB` 笔试题中已用 jclasslib 验证过。

### 3.3 静态代码块

**作用**：初始化静态成员变量、执行一次性的类级配置（加载数据库驱动、读取配置文件）。

```java
class DataSource {
    static String url;

    static {
        url = "jdbc:mysql://localhost:3306/test";
    }
}
// 第一次 new：静态块 → 构造方法
// 第二次 new：只有构造方法（静态块不再执行）
```

**三个必说的点：**

| 点 | 说明 |
|---|---|
| **只执行一次** | 类的初始化只发生一次，`<clinit>` 只被调用一次 |
| **⚠️ 准确的执行时机** | 是**类初始化阶段**（执行 `<clinit>`），**不是「类加载阶段」**——这是高频纠正点，见第五节 |
| **与静态变量赋值的顺序** | **按源码书写顺序**，不存在「变量总在静态块之前」 |

### 3.4 同步代码块

**作用**：保证同一时刻只有一个线程能进入该块操作共享数据。

```java
public void transferMoney(int amount) {
    synchronized (this) {       // 锁定当前对象
        if (balance >= amount) {
            balance -= amount;
        }
    }
}
```

**相比 `synchronized` 方法的优势**：**锁粒度更细**——只锁真正需要保护的几行，而不是整个方法，并发度更高，还能自由选择锁对象。

## 四、执行顺序（面试最高频）

### 4.1 结论

> **父类静态代码块 → 子类静态代码块 → 父类构造代码块 → 父类构造方法 → 子类构造代码块 → 子类构造方法**

**记忆口诀**：**「静态优先，父类优先，构造代码块先于构造方法」**

### 4.2 为什么是这个顺序（字节码本质，加分项）

这个顺序不用背，理解了编译结果就能自己推导：

| 代码块 | 被编译到哪里 | 由此决定的顺序 |
|---|---|---|
| **静态代码块** + 静态变量赋值 | **`<clinit>`**（类初始化方法） | 类初始化**先于**任何实例创建；且**子类初始化前必先初始化父类** → 父静态 → 子静态 |
| **构造代码块** + 实例变量赋值 | **`<init>`**（构造方法），位于 `super()` 之后、方法体之前 | 子类 `<init>` 第一件事是调 `super()`，父类那一整套（父构造块 + 父方法体）跑完才回来 → 父块 → 父方法 → 子块 → 子方法 |
| **局部代码块** | 无独立结构，只影响局部变量表 slot 的作用域与复用 | 顺序执行 |
| **同步代码块** | 一对 **`monitorenter` / `monitorexit`** 指令 | 抢到锁才进入 |

> **答题时主动说这段**：「顺序的根本原因是静态块进 `<clinit>`、构造块进 `<init>` 且位于 `super()` 之后，所以父类的整套实例初始化必然在子类之前完成。」

### 4.3 两条延伸结论

- **类的初始化只一次，构造方法每 `new` 一次执行一次** → 静态块只打印一次，构造块打印 N 次
- 同一类中**多个同类型代码块**按**定义顺序**依次执行

## 五、两个必须说准的表述（避坑 / 加分）

> 这两处是原始表述中容易被面试官抓住追问的地方，**换成准确说法就是加分项**。

| 常见说法 | 准确说法 |
|---|---|
| 静态代码块在**类加载时**执行一次 | 在**类的初始化阶段**（执行 `<clinit>`）执行一次。类生命周期是**加载 → 连接（验证/准备/解析）→ 初始化**，静态块属于**初始化**阶段，不是加载阶段。<br>说「类加载时」在口语中常被接受，但被追问「加载、连接、初始化哪个阶段」时必须答对。 |
| 局部变量出了花括号**就被释放，节省内存** | 它在**栈帧局部变量表**中占用 slot，出作用域后该 **slot 可被后续变量复用**。真正的价值是**限定作用域、避免变量污染和误用**，「省内存」只是槽复用带来的次要效果。 |

## 六、30 秒速答版

> 代码块是一对花括号括起的语句组，核心作用有四个：限定作用域、初始化、控制流程、线程同步。按定义位置和修饰符分四种：
> **局部代码块**在方法内，作用是限定变量作用域，避免变量污染；`if`/`for` 的花括号也算。
> **构造代码块**在类内、无 `static`，用来提取多个构造方法的公共初始化逻辑，每次 `new` 都执行，在构造方法之前——本质是编译期被塞进了构造方法 `<init>` 的前半段。
> **静态代码块**在类内、有 `static`，用来初始化静态成员或做一次性类级配置比如加载驱动，在**类的初始化阶段执行 `<clinit>`，只执行一次**。
> **同步代码块**用 `synchronized` 锁一个对象，保证同一时刻只有一个线程进入，比同步方法的锁粒度更细。
> 执行顺序是：父类静态 → 子类静态 → 父类构造块 → 父类构造方法 → 子类构造块 → 子类构造方法。口诀「静态优先，父类优先，构造代码块先于构造方法」。根本原因是静态块编译进 `<clinit>`、构造块编译进 `<init>` 且在 `super()` 之后。

## 七、高频追问预案

### 7.1 分类与机制方向

| 追问 | 回答要点 |
|---|---|
| 怎么快速判断一个块是哪种类型？ | **在方法里** → 局部块（带 `synchronized` 则同步块）；**在类里** → 有 `static` 是静态块，没有是构造块。 |
| 构造代码块和构造方法的关系？ | 构造块**不是独立方法**，编译期被并入 `<init>`，位于 `super()` 之后、构造方法体之前。用 jclasslib 看字节码可验证。 |
| 静态代码块和静态变量赋值谁先执行？ | **按源码书写顺序**，二者一起被合并进 `<clinit>`。没有「变量优先」这回事。 |
| 一个类有多个静态块怎么执行？ | 按**定义顺序**依次执行（同样合并进 `<clinit>`）。 |
| 构造代码块和实例变量初始化谁先？ | 同样按**源码顺序**，都被编译进 `<init>`。 |
| 静态代码块一定存在吗？ | 不一定。无静态块且无静态变量赋值、只声明不赋值、`static final` + 编译期常量，三种情况编译器**不生成 `<clinit>`**。见 [[编程/jvm/16 类的生命周期 初始化阶段]]。 |
| 代码块可以有返回值吗？ | 不能。代码块不是方法，没有返回值、没有参数、不能被显式调用。 |

### 7.2 执行顺序方向

| 追问 | 回答要点 |
|---|---|
| 完整执行顺序背一下？ | 父静态 → 子静态 → 父构造块 → 父构造方法 → 子构造块 → 子构造方法。 |
| 为什么父类构造方法在子类构造块之前？ | 子类 `<init>` 的第一条是 `super()`，父类整套实例初始化（父构造块 + 父方法体）执行完才返回，然后才轮到子类的构造块。 |
| 静态块为什么一定最先？ | 它属于**类初始化**，而类初始化必然发生在**任何实例创建之前**；且子类初始化前会先初始化父类。 |
| 静态块执行几次？构造块执行几次？ | 静态块**一次**（类初始化只一次）；构造块**每次 `new` 一次**。 |
| 给一段含 A/B/C/D 的代码写输出？ | 套用「静态优先 → 父优先 → 构造块先于构造方法」，注意类初始化只一次。经典答案形如 `DACBCB`，详见 [[编程/jvm/16 类的生命周期 初始化阶段]]。 |
| 静态块 + 构造块 + 构造方法 + 父子类，哪个最容易答错？ | **父类构造方法 vs 子类构造块**的相对顺序（父方法在前），以及**静态块只执行一次**。 |

### 7.3 静态代码块深入方向

| 追问 | 回答要点 |
|---|---|
| **静态块到底在类生命周期哪个阶段执行？** | **初始化阶段**（`<clinit>`）。加载→连接（验证/准备/解析）→初始化，静态块属最后一个。 |
| 静态块能访问非静态成员吗？ | **不能**。静态块随类初始化执行，此时**尚无对象存在**，非静态成员没有内存空间；也不能用 `this`/`super`。 |
| 静态块是线程安全的吗？ | **是**。JVM 用类初始化锁保证 `<clinit>` **只执行一次**且结果对其他线程可见——这正是**静态内部类式单例**天然线程安全的根本原因。 |
| 静态块里抛异常会怎样？ | 检查异常**必须在块内捕获**（无法向外声明）；运行时异常会被包装成 **`ExceptionInInitializerError`**，该类被标记为错误状态，后续使用抛 `NoClassDefFoundError`。 |
| 静态块典型应用场景？ | 加载 JDBC 驱动（`Class.forName`）、读取配置文件、初始化静态集合/缓存、注册工厂或枚举映射表、加载本地库 `System.loadLibrary`。 |
| 哪些操作会触发静态块执行？ | 访问静态变量/静态方法、`new` 对象、`Class.forName`、执行 `main` 所在类、子类初始化。**例外**：访问 `static final` 编译期常量**不触发**。 |
| `ClassLoader.loadClass()` 会执行静态块吗？ | **不会**，它只加载不初始化。`Class.forName` 默认会（三参重载可传 `false` 关闭）。 |

### 7.4 同步代码块方向

| 追问 | 回答要点 |
|---|---|
| 同步代码块 vs `synchronized` 方法？ | 块**锁粒度更细**、可自选锁对象；方法锁的是整个方法体（实例方法锁 `this`，静态方法锁 `Class` 对象）。 |
| 底层实现区别？ | 同步块编译成一对 **`monitorenter`/`monitorexit`** 指令（含异常路径的 monitorexit）；同步方法靠方法上的 **`ACC_SYNCHRONIZED`** 标志位，由 JVM 隐式加解锁。 |
| `synchronized(this)` 和 `synchronized(XXX.class)` 区别？ | 前者锁**当前实例**（不同对象互不影响）；后者锁**类对象**（全类唯一，所有实例共享一把锁）。 |
| 锁对象怎么选，有什么坑？ | 必须是**所有相关线程都能拿到的同一个对象**。坑：①不要锁 `String` 字面量或装箱缓存内的 `Integer`（可能被无关代码共享）；②不要锁**会被重新赋值的引用**（换了对象就等于换了锁）；③不要锁 `this` 后又把对象暴露给外部随意加锁。 |
| 同步块能保证可见性和有序性吗？ | 能。进入/退出 monitor 构成 happens-before，保证原子性、可见性、有序性。详见 [[编程/java并发编程/多线程/Java 多线程与 JMM]]。 |
| 同步块里能抛异常吗？锁会释放吗？ | 能抛；**异常退出时锁会自动释放**（编译器生成异常表和额外的 `monitorexit`），不会死锁。 |
| 锁的粒度越细越好吗？ | 不一定。过细会增加加解锁次数与竞争切换成本，且可能破坏**复合操作的原子性**（分成两个块反而出现中间态）。 |

### 7.5 陷阱题方向

| 追问 | 回答要点 |
|---|---|
| 局部代码块真的能节省内存吗？ | 严格说是**局部变量表的 slot 可被复用**，主要价值是限定作用域、避免变量污染，不是「立即回收内存」。 |
| 构造代码块和 `static` 块能互相访问对方的变量吗？ | 构造块**可以**访问静态成员（类已初始化）；静态块**不能**访问实例成员。 |
| `final` 实例变量可以在构造代码块里赋值吗？ | 可以。`final` 字段允许在**声明处、构造代码块、构造方法**中赋值（blank final），但只能赋一次。 |
| 代码块和方法的本质区别？ | 方法有名字、可被调用、可传参和返回值；代码块无名、由 JVM/编译器在固定时机自动执行，**不能显式调用**。 |
| 四种块能嵌套吗？ | 可以，例如静态块里写局部块、同步块里写局部块。但**静态块里不能出现实例成员**。 |
| 为什么有的资料说代码块只有三种？ | 分类口径不同：狭义只算**初始化相关**的（局部/构造/静态）；同步代码块严格说是**同步语句**而非初始化块，但面试答四种更完整，说明分类依据即可。 |
