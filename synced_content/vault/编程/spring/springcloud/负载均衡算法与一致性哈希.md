# 负载均衡算法与一致性哈希

> 负载均衡算法决定"**请求发给哪个节点**"，从**简单轮询**到**最小活跃数**各有取舍；要想"**同一个用户固定落到同一台服务器**"，用**一致性哈希**按客户端 IP/参数映射节点。核心主线：**选法看需求——均匀、带权重、还是粘会话。**

## 一、这是什么

回答"负载均衡算法"时，先列算法家族表，再就"如何固定一个用户"重点讲一致性哈希。

## 二、核心内容

### 2.1 常见负载均衡算法

| 算法 | 原理 | 特点/适用 |
| :--- | :--- | :--- |
| **简单轮询（Round Robin）** | 按顺序依次分发 | 不关心后端性能/负载，机器配置均匀时用 |
| **加权轮询** | 按性能设权重，权重高的分更多请求 | 性能不均时让高性能机器多干活 |
| **简单随机** | 随机分发 | 请求越多各服务器接收越平均 |
| **加权随机** | 按权重随机分发 | 结合权重 + 随机 |
| **一致性哈希** | 按客户端 IP/参数哈希取模映射 | **同一客户端/同参数请求固定到同一台服务器** |
| **最小活跃数** | 统计各服务器当前处理请求数，发给最少的 | 动态感知负载，负载均衡更贴合实时压力 |

### 2.2 如何"固定一个用户"？→ 一致性哈希

**需求**：某些场景需要一台客户端始终访问同一台后端（如会话保持、缓存一致性）。

**实现**：一致性哈希算法
1. 根据请求的**客户端 IP** 或**请求参数**通过哈希算法得到一个数值
2. 用该数值**取模映射**出对应的后端服务器
3. 保证**同一个客户端 / 相同参数的请求每次都使用同一台服务器**

```java
// 伪代码示意
int hash = clientIp.hashCode();          // 对客户端身份哈希
int nodeIndex = Math.abs(hash) % nodes.size(); // 取模映射节点
return nodes.get(nodeIndex);
```

> 进阶注：真正的一致性哈希使用**哈希环**（把节点和请求都映射到 0~2³²-1 的环上，请求沿环找到最近的节点），并引入**虚拟节点**缓解节点不均匀/增删节点时的大范围重映射。

## 三、可能追问

1. 「一致性哈希能保证后端节点扩容时请求不受影响吗？」→ 一致性哈希环 + 虚拟节点使增删节点只影响环上邻近的少量请求（优于 `hash % N` 全部重排）
2. 「为什么用哈希环而不用 hash % 节点数？」→ 节点增删时 `% N` 会让几乎所有映射失效，一致性哈希只影响局部
3. 「一致性哈希在哪些场景见过？」→ Redis 集群分片、Nginx 会话粘滞、Dubbo/Feign 负载均衡
4. 「简单轮询的缺点？」→ 不感知后端负载，性能差的机器也会被分到请求
5. 「最小活跃数和加权轮询怎么选？」→ 追求实时负载贴合用最小活跃数；已知稳定性能差异用加权
