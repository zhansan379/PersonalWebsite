# 堆 · 内存结构与 -Xms/-Xmx 调优

> 堆是**线程共享**的内存区域，存放所有 `new` 出来的对象，通常是 Java 程序中**占用空间最大**的一块。堆有 `used` / `total` / `max` 三个关键值：`total` 会随对象增多**动态扩展**直到 `max`。堆会溢出，抛 `OutOfMemoryError`。生产环境建议 **`-Xms` 与 `-Xmx` 设为相同值**，避免反复申请与收缩带来的开销。

> 来源：B站「基础篇-22-堆内存」（BV1r94y1b7eS）

## 一、堆是线程共享的内存区域

前面学的**程序计数器**和**栈**属于线程内部的数据区域，线程之间**不能共享数据**。接下来要学的三块区域则是**线程之间可以共享**的：

| 区域 | 线程私有/共享 | 页面 |
|---|---|---|
| 程序计数器 | 私有 | [[编程/jvm/05 运行时数据区 程序计数器]] |
| 虚拟机栈 / 本地方法栈 | 私有 | [[编程/jvm/06 运行时数据区 栈 局部变量表]]、[[编程/jvm/08 运行时数据区 栈 内存溢出与本地方法栈]] |
| **堆** | **共享** | 本页 |
| 方法区 | 共享 | 后续章节 |
| 直接内存 | 共享 | 后续章节 |

## 二、堆里存什么，怎么访问

创建出来的对象都位于堆上，**包括对象的属性**（如 `name="张三"`、`age=18`、`id=1`）。

要访问堆中对象的数据，需要把对象的**内存地址**保存在：

- **栈内存**中（局部变量）
- 或**静态变量**里

```java
public static void main(String[] args) {
    Student s1 = new Student();   // 对象在堆上，地址存入当前栈帧的局部变量 s1
    Student s2 = new Student();   // 同上，地址存入 s2
}
```

**这里引出了「堆为什么是共享的」**：

| 引用保存位置 | 能否跨线程访问该对象 |
|---|---|
| 局部变量（栈帧内） | ❌ 别的线程无法使用这两个对象 |
| **静态变量** | ✅ 不同线程之间可以共享这两个对象 |

所以堆内存本身属于线程之间**可以共享**的内存区域 —— 对象放在共享的堆上，能不能被其他线程访问到，取决于**引用存在哪里**。

> 这正是 [[编程/java并发编程/多线程/Java 多线程与 JMM]] 中「局部变量天然线程安全、成员变量和静态变量才是线程安全战场」的底层原因。

## 三、堆会不会溢出

### 3.1 实验设计

用 `new` 关键字不停创建对象放进集合，看堆最终会不会溢出、抛出什么错误：

```java
ArrayList<byte[]> list = new ArrayList<>();
while (true) {
    list.add(new byte[1024]);          // 每次循环放入 1KB
}
```

### 3.2 两次实验结果

| 每次放入 | 结果 |
|---|---|
| `new byte[1024]`（1KB） | 运行很久，控制台什么都没打印，程序仍在运行 —— **迟迟不溢出** |
| `new byte[1024 * 1024 * 100]`（100MB） | 很快自动终止，抛出错误 |

```
java.lang.OutOfMemoryError: Java heap space
```

### 3.3 两个结论

1. **堆内存是会溢出的**，溢出时抛出 `OutOfMemoryError`，并明确指出是堆内存溢出
2. 每次只加 1KB 时过了很久都不溢出，说明**虚拟机分配的默认堆内存相对来说比较大**

> **补充**：`OutOfMemoryError` 和栈的 `StackOverflowError` 一样属于 `Error` 而非 `Exception`，不应该去 catch 并试图恢复。完整错误信息里的 `Java heap space` 是定位关键 —— 它明确了是**堆**溢出，而不是方法区、直接内存或栈溢出。

## 四、三个关键值：used / total / max

虚拟机管理堆内存时有三个需要关注的值：

| 值 | 含义 | 举例 |
|---|---|---|
| `used` | 当前**已使用**的堆内存 | used = 100MB 说明已创建了 100MB 的对象 |
| `total` | 虚拟机**已分配的、可以使用**的堆内存 | total = 200MB，则还可再放 100MB |
| `max` | 虚拟机**允许分配的最大**堆内存 | max = 300MB，则 total 将来还能扩展到 300MB |

三者关系：`used ≤ total ≤ max`。

## 五、用 Arthas 监控堆内存

### 5.1 dashboard 命令

```
dashboard          # 默认每 5 秒刷新一次
dashboard -i 3000  # -i 指定刷新频率，单位毫秒，此处每 3 秒刷新
```

输出中 `memory` 一项就是内存结构，其中 `heap` 就是堆内存。示例读法：

```
used = 153M, total = 981M, max = 921M
→ 堆里已创建 153M 的对象
→ 还可以再放 981 - 153 = 828M
```

### 5.2 memory 命令（更简洁）

`dashboard` 里有线程、运行时参数等额外信息。**如果只关注内存结构**，直接输入：

```
memory
```

它本质上就是 `dashboard` 中 `memory` 标签下的内容，但**只展示一次**，不刷新。

### 5.3 让程序停下来便于观察

在代码里加一行 `System.in.read();` 让程序阻塞，直到在控制台输入任意内容 —— 这样才有时间挂载 Arthas 并观察。

实测一次结果：`used = 119M`、`total = 489M`、`max = 7G`。

**max = 7G 说明**：程序没有设置堆内存上限时，虚拟机给了一个默认上限（本机为 7G）。堆内存不够时会把 `total` 扩张，直到 `max` 为止 —— 这就是为什么前面每次只加 1KB 时，很久都不会溢出：**默认堆实在太大了**。

## 六、total 的动态扩展过程（实测）

在循环中每次放入 100MB 的数组，配合 `dashboard -i 1000`（每秒刷新）观察，可以清楚地看到 `total` 是怎么涨起来的：

```java
ArrayList<byte[]> list = new ArrayList<>();
while (true) {
    list.add(new byte[1024 * 1024 * 100]);   // 每次 100MB
    Thread.sleep(500);                       // 放慢，方便观察
}
```

观察到的变化规律：

```
初始：      used = 124M   total = 489M   max = 7G
放入 100M： used = 224M   total = 489M       ← used 涨，total 不变（够用）
再放 100M： used = 324M   total = 489M
再放 100M： used ≈ 424M   total = 589M       ← used 逼近 total，total 扩张 100M
继续……      used 每秒 +100M，total 也跟着往上涨（1G、2G……）
```

**结论**：

1. `used` 随对象创建线性增长
2. 当 `used` 接近 `total` 时，虚拟机**自动扩张 `total`**（申请更多内存）
3. `total` 的扩张上限是 `max`

## 七、溢出时机：used = total，但远小于 max

继续运行到最后，抛出 `OutOfMemoryError`。但**溢出瞬间的数据很反常识**：

```
第一次实测：used = 3G     total = 3G     max = 7G   → 溢出
第二次实测：used = 5.5G   total = 5.5G   max = 7G（使用率 76.59%）→ 溢出
```

`total` 明明还没涨到 `max`（还有 1.5G ~ 4G 的空间可以扩张），为什么就溢出了？

- 直接原因：`used` 已经等于 `total`，且这一次的分配请求（100MB）无法被满足
- 深层原因：**与垃圾回收器的行为、以及大对象的分配策略有关** —— 视频把这一点留到**垃圾回收章节**再讲

> **补充**：可以先记住一个直觉 —— 堆并不是「填满 max 才报错」。JVM 在抛 `OutOfMemoryError` 之前一定会先触发 GC 尝试回收；只有**GC 之后仍然无法为本次分配腾出足够（且足够连续）的空间**时才会抛错。加上本例每次要的是 100MB 这种大对象，对连续空间的要求更高，所以远未达到 `max` 就失败了。细节见后续 GC 章节。

## 八、参数配置：-Xmx 与 -Xms

### 8.1 默认值

| 值 | 默认大小 | 举例（32G 内存的机器） |
|---|---|---|
| `max`（最大堆） | **系统内存的 1/4** | 32G ÷ 4 = 8G |
| `total`（初始堆） | **系统内存的 1/64** | 32G ÷ 64 = 512M（实测约 489M） |

这解释了前面实测的 `max = 7G`、`total = 489M` —— 正是本机内存的 1/4 与 1/64。

> **补充**：这两个比例是 HotSpot 在被识别为 **server-class machine** 时的默认策略，并非硬性规定。JDK 8u191+ / JDK 10+ 在容器中会自动感知 cgroup 限额（`UseContainerSupport`），也可以直接用 `-XX:MaxRAMPercentage` / `-XX:InitialRAMPercentage` 按百分比设置，比写死 `-Xmx` 更适合容器化部署。

### 8.2 设置语法

| 参数 | 作用 |
|---|---|
| `-Xmx<size>` | 设置堆内存的**最大**大小（max） |
| `-Xms<size>` | 设置堆内存的**初始**大小（total） |

**单位规则**（与 `-Xss` 一致）：

| 写法 | 含义 |
|---|---|
| 不写单位 | 字节，且**必须是 1024 的倍数** |
| `k` / `K` | KB |
| `m` / `M` | MB |
| `g` / `G` | GB |

**取值限制**：

- `max` 必须**大于 2MB**
- `total`（初始堆）必须**大于 1MB**

示例：

```
-Xmx4g -Xms4g          # 最大堆和初始堆都是 4G
-Xmx100m               # 最大堆 100MB
```

## 九、为什么 Arthas 显示的值比设置的小

设置 `-Xmx4g -Xms4g` 后，用 Arthas 查看：

```
max = 3925M   total = 3925M     ← 不是 4096M（4G）
```

**原因**：Arthas 通过 **JMX**（Java Management Extensions）获取内存数据，而 JMX 统计的是**可以用来分配对象的内存**，并不等于 `-Xmx` 设置的整块堆空间 —— 堆里还有一部分空间被 GC 自身的机制占用。具体原因同样留到**垃圾回收章节**。

**要点**：看到监控值比设置值略小（4096M → 3925M）是**正常现象**，不是配置没生效。

## 十、工作中的建议：-Xms 与 -Xmx 设为相同值

**推荐做法**：

```
-Xms4g -Xmx4g          # 两者相同
```

**理由**：

1. 堆内存不够时，虚拟机需要**向操作系统申请**新内存来扩张 `total`；使用率下降时又会**收缩**
2. 这个「扩张 / 收缩」的过程本身有性能开销，还会引发 GC
3. 直接把初始值拉到最大值，**一次分配到位**，运行期间不再变动，性能更稳定

> **补充**：这也是绝大多数生产环境 JVM 参数的标配写法。除了避免动态调整开销，固定堆大小还让内存占用**可预测** —— 容器里给多少内存、`-Xmx` 设多少，一目了然，不会出现「压测时 total 才 500M，线上流量一上来堆疯狂扩张连带 GC 抖动」的情况。

## 十一、小结

1. 堆是**线程共享**的内存区域，存放 `new` 出来的所有对象及其属性，通常是占用空间最大的区域
2. 访问堆中对象要靠**栈里的局部变量**或**静态变量**保存的引用；只有静态变量（等共享位置）持有的引用才能真正被多线程共享
3. 堆**会溢出**，抛 `java.lang.OutOfMemoryError: Java heap space`
4. 三个关键值：`used`（已用） ≤ `total`（已分配） ≤ `max`（上限）
5. `used` 逼近 `total` 时，`total` 会**自动扩张**，上限是 `max`
6. 用 Arthas 的 `dashboard -i <毫秒>` 持续观察，或 `memory` 看一次快照
7. 溢出可能发生在 `total` **远小于** `max` 时（实测 5.5G / 7G 就溢出），与 GC 和大对象分配有关，细节见 GC 章节
8. 默认 `max` = 系统内存 **1/4**，默认 `total` = 系统内存 **1/64**
9. `-Xmx` 设最大堆、`-Xms` 设初始堆；单位 k/m/g，`max > 2MB`、`total > 1MB`
10. Arthas（JMX）显示值略小于设置值属正常（4g → 3925M）
11. **工作建议：`-Xms` = `-Xmx`**，避免反复扩张收缩的开销
