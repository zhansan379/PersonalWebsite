# 类加载器

> 类加载器（ClassLoader）负责在类加载过程中获取字节码并加载到内存。本章覆盖：类加载器的作用、四种常见类加载器、双亲委派机制、如何打破双亲委派，以及 JDK9 引入模块化后类加载器的变化。其中「双亲委派机制」和「如何打破」是常见面试题。

## 一、类加载器的作用

负责在类的加载过程中**获取类的字节码信息，并加载到内存中**。

**底层流程**：
1. 把文件中的类信息读取到内存，转换成 `byte[]` 数组；
2. 调用虚拟机底层方法，把字节数组传入虚拟机在**方法区**和**堆**上分别创建对象，保存这一类的信息。

## 二、类加载器的种类（4 种）

| 类加载器 | 加载什么 | 说明 |
|---|---|---|
| **启动类加载器**（Bootstrap） | 核心类 | JVM 核心类库 |
| **扩展类加载器**（Extension） | 扩展类 | 对核心类的一些补充，可理解成"通用"，但不重要 |
| **应用程序类加载器**（Application） | 应用 classpath 中的类 | **用得最多**：项目中的类 + 引用的第三方 jar 包中的类 |
| **自定义类加载器** | 自定义 | 需要**重写 `findClass` 方法**（注意是 `findClass`，不是 `loadClass`） |

> JDK9 及之后：扩展类加载器 → **平台类加载器**（Platform），启动类加载器改用 Java 实现。详见「五、JDK9+ 类加载器的变化」。

## 三、双亲委派机制

每个 Java 实现的类加载器中都保存了一个 `parent` 成员变量，代表它的父类加载器：

```
自定义类加载器 → 应用程序类加载器 → 扩展类加载器 → 启动类加载器
```

（扩展类加载器的 `parent` 虽为空，但底层实现有特殊逻辑，可理解为其父类是启动类加载器。）

**加载流程**：
1. 收到加载任务，先检查**自己是否加载过**——加载过则结束；
2. 没加载过，就**自底向上**一层层向父类加载器委派，查看它们是否加载过；
3. 查到最上层全部没加载过，再**自顶向下**逐个尝试加载（启动类加载器先加载 → 加载不了给扩展类加载器 → 再给应用程序类加载器，逐层向下）；
4. 若所有类加载器都加载不了，最终抛出加载失败异常。

**两大好处**：
1. **避免类被重复加载**；
2. **保证核心类一定由启动类加载器加载**——防止应用程序重写核心类并被加载造成不安全，提升安全性。

## 四、如何打破双亲委派机制（3 种）

| 方法 | 说明 |
|---|---|
| **① 重写 `loadClass`** | 不再实现双亲委派逻辑（把双亲委派的源码逻辑干掉） |
| **② SPI + 线程上下文类加载器** | JNDI、JDBC、JCE、JAXB、JBI 等框架使用 |
| **③ OSGi** | 实现一整套类加载机制，允许同级类加载器之间互相调用 |

> 面试重点掌握**前两种**；可结合底层源码细节与面试官深入分享。

## 五、JDK9+ 类加载器的变化

> 来源：B站「基础篇-17-JDK9之后的类加载器」（BV1r94y1b7eS）

### 5.1 JDK8 及之前

- 扩展类加载器、应用程序类加载器的源码都在 `Launcher.java` 类中，存放在 `rt.jar`（核心包）里；
- 两者都继承自 `URLClassLoader`——通过特定目录找到 jar 包以及 jar 包中的字节码文件；
- **本质：按 jar 包的位置去加载字节码文件**。

### 5.2 JDK9 及之后（引入模块化）

- 引入 **module 模块化**概念，Java 类不再存放在 jar 包中，而是放到一个个 `.jmod` 文件中，保存在 `jmods` 文件夹里；
- 类加载器由「从 jar 包加载」转变为「从 jmod 模块文件加载」。

### 5.3 具体变化

1. **启动类加载器改用 Java 编写**（不再用 C++），存放在 `ClassLoaders` 类中；后面讲到的其他类加载器也存放在这个类中；
2. 启动类加载器继承自 **`BuiltinClassLoader`**，其作用就是从 jmod 模块化文件中找到对应类的字节码文件（`BuiltinClassLoader` 实现了这套机制）；
3. **细节——获取启动类加载器仍返回 `null`**：JDK8 之前在 Java 代码中拿不到（返回 null）；JDK9 之后即使改用 Java 编写，依然返回 null。目的是保持统一、避免用户直接操作重要的启动类加载器，**提高类加载的安全性**；
4. **扩展类加载器 → 平台类加载器**（Platform）：也从模块中加载字节码，继承关系由 `URLClassLoader` 变为 `BuiltinClassLoader`；
5. 模块化设计本身具有扩展性，而扩展类加载器原本就是为了在核心类之外扩展类——所以理论上平台类加载器不再需要，但**为兼容老版本被保留**，自身没有特殊逻辑。将来想对 JDK 做扩展，应按**模块化思想**扩展，与平台类加载器关系不大；
6. **应用程序类加载器**：仅发生继承关系变化（`URLClassLoader` → `BuiltinClassLoader`），其余与之前版本区别不大。
