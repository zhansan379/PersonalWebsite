# 类的生命周期：概述与加载阶段

> 类的生命周期描述一个类**从被加载进内存、到程序运行中被使用、到最终被卸载**的完整过程。
> 一句话概括加载阶段：**类加载器把字节码信息读进内存，JVM 在「方法区」和「堆区」各建一个对象来保存类信息，而程序员平时用到的是堆里那个 `java.lang.Class` 对象。**


## 一、五阶段 vs 七阶段（第一个必答点）

```
加载 Loading → 连接 Linking → 初始化 Initialization → 使用 Using → 卸载 Unloading
                    │
                    └── 细分：验证 Verification → 准备 Preparation → 解析 Resolution
```

- **粗分五个阶段**：加载、连接、初始化、使用、卸载
- **细分七个阶段**：因为**连接阶段做的事情比较多**，被拆成验证、准备、解析三个小阶段
- 网上文章两种说法都有，**面试时主动说明「粗分五个、细分七个，区别只在连接阶段是否展开」**，这就是加分点

**各阶段的考查权重：**

| 阶段 | 熟悉度 / 考查权重 |
|---|---|
| 加载、连接 | 原理题重点 |
| **初始化** | **最重要**——唯一**程序员可以干涉**的阶段，笔试题几乎都出在这 |
| 使用 | 最熟悉（`new`、反射） |
| 卸载 | 属于垃圾回收范畴，单独讲 |

## 三、加载阶段四个步骤（核心答题骨架）

### 3.1 步骤一：通过全限定名获取二进制字节流

类加载器根据类的**全限定名**（包名 + 类名），通过**不同渠道**以**二进制流**的方式把字节码信息读入内存。

**「不同渠道」是本步骤的加分点**——JVM 设计之初就考虑了扩展性，不限于本地磁盘：

| 渠道 | 实际场景 |
|---|---|
| 本地磁盘的 `.class` 文件 | 最常见 |
| **内存中动态生成** | Spring 框架大量使用的**动态代理**，运行时生成的类也要被加载 |
| **网络传输** | 早期 Applet 小程序技术（已淘汰，但证明了扩展性设计） |
| 数据库等自定义来源 | 有些公司把类持久化到数据库，可在此步扩展 |

> 这一步**程序员可以用 Java 代码扩展**（自定义类加载器重写获取字节流的逻辑）。

### 3.2 步骤二：类加载器职责结束，JVM 接手

类加载器只负责**拿到类的信息**，拿到后它的职责就完成了，后续由 JVM 处理。

### 3.3 步骤三：在方法区创建 `InstanceKlass` 对象

JVM 把类信息保存到**方法区**，生成一个对象叫 **`InstanceKlass`**。

**两个必说的细节：**

1. **拼写为 `Klass`（K 打头）而非 `Class`**——目的是与源代码中 `class`（C 打头）做区分，它是**用 C++ 编写的对象**。
2. **方法区只是 JVM 规范里的一个「虚」概念**，不同虚拟机、甚至 HotSpot 的不同版本实现都不同：
   - 早期 JDK 版本 → **永久代（PermGen）**
   - 较新版本 → **元空间（Metaspace）**

**`InstanceKlass` 里存了什么：**

```
字节码文件本身的信息：基本信息、常量池、字段、方法、属性
      +
JVM 为实现特定功能额外保存的信息：虚方法表（实现多态用）等
```

### 3.4 步骤四：在堆区创建 `java.lang.Class` 对象

JVM 还会在**堆**里生成一份与方法区数据**类似**的对象，即大家熟知的 `java.lang.Class` 对象。

| 要点 | 说明 |
|---|---|
| **作用** | **反射**的入口：先拿到 `Class` 对象，再通过它获取方法、字段，然后做后续操作 |
| **位置** | 堆区，在**加载阶段**被创建 |
| **内容** | 字段、方法等开发者需要的信息 |
| **双向引用** | 与方法区的 `InstanceKlass` 通过引用**彼此关联**，可以互相找到 |
| **⚠️ 静态字段位置** | **JDK8 起，静态变量的真实数据存放在堆中这个 `Class` 对象里**；JDK8 之前才在方法区。网上很多文章仍说「在方法区」，是过时说法 |

## 四、灵魂拷问：为什么方法区和堆区要各建一个对象？

> 这是本节最容易被追问的设计题。只留方法区那份、反射也去读它，不是更省内存吗？

**两个原因（都要答）：**

**原因一：语言层面无法直接操作**
`InstanceKlass` 是**用 C++ 编写的对象**，Java 代码一般**不能直接操作 C++ 对象**。所以 JVM 在堆上创建了一个用 **Java 语言包装后**的 `java.lang.Class` 对象，让我们能在代码里拿到它。

**原因二：安全性——收窄开发者的可访问范围**
`Class` 对象包含的字段**少于** `InstanceKlass`。因为 `InstanceKlass` 里的信息**并非都需要暴露**，例如**虚方法表**是 JVM 底层实现多态用的，开发者完全不需要访问。

于是设计成：把 `InstanceKlass` 的数据复制到堆中一份，**剔除掉不需要暴露的内容**；开发者只访问堆里这个「洁净版」对象，上面那个不直接开放。**通过这个设计很好地控制了开发者访问数据的范围，提升了数据安全性。**

## 五、HSDB 工具验证（实践加分项）

用 JDK 自带的 **HSDB**（HotSpot Debugger）可视化查看 JVM 内存结构，验证上述结论。

**工具位置与启动：**

```bash
# 位于 JDK 的 lib 目录下：sa-jdi.jar
# 因为该 jar 内有多个启动类，不能用 java -jar，要用 -cp 指定启动类
cd $JAVA_HOME/lib
java -cp sa-jdi.jar sun.jvm.hotspot.HSDB
```

**验证步骤：**

1. 被监控程序：类中定义一个**静态变量** `i = 0`，`main` 里 `new` 出自身对象，用 `System.in.read()` 阻塞防止退出
2. `jps` 查看目标 Java **进程号**
3. HSDB → `File` → `Attach` → 输入进程号
4. `Tools` → **Object Histogram**（对象查看器），三列分别是：**对象大小 / 该类型对象个数 / 类名**
5. 搜索框输入类名 → 双击进入对象内部 → `Inspect` 查看详情
6. **反向查找链路**：对象 → 它的 `InstanceKlass`（方法区）→ 里面的引用 → `java.lang.Class` 对象（堆）→ 在其中看到 **静态变量 `i = 0`**

**⚠️ 两个实操坑：**
- **HSDB 版本必须与被监控程序的 JDK 版本一致**，否则会出现奇怪问题
- **HSDB 不会告诉你对象在哪块内存区域**，需要自己根据对象类型判断（`InstanceKlass` → 方法区，`java.lang.Class` → 堆）
- HSDB 对显示信息做了**简化**，看到的未必是完整信息

**验证结论**：加载阶段确实在方法区和堆区各创建了一个对象，且**静态变量存放在 `Class` 对象中**。

## 六、面试答题逻辑

### 6.1 「讲一下类的生命周期」四步框架

```
1. 先给定义：一个类从加载进内存 → 被使用 → 被卸载的全过程
2. 给阶段划分：粗分五阶段，细分七阶段（连接展开为验证/准备/解析）—— 主动说明两种说法的由来
3. 逐阶段给一句话作用，重点落在「初始化是唯一程序员可干涉的阶段」
4. 补一句关联价值：它是运行时常量池、类加载器、多态底层、类加密的基础
```

### 6.2 「一个类是如何被加载到虚拟机中的」四步框架

```
1. 类加载器按全限定名，通过不同渠道（磁盘/动态代理内存生成/网络/自定义）获取二进制流
2. 类加载器职责结束，JVM 接手
3. 方法区创建 InstanceKlass（C++ 对象，含基本信息/常量池/字段/方法/属性 + 虚方法表）
4. 堆区创建 java.lang.Class 对象（反射入口，JDK8 起静态变量存这里），两者双向引用
5. 主动补充：为什么要建两个 —— 语言隔离 + 安全性收窄访问范围
```

### 6.3 40 秒口述版

> 类的生命周期粗分五个阶段：加载、连接、初始化、使用、卸载；如果把连接展开成验证、准备、解析，就是常说的七个阶段。其中初始化是最重要的，因为它是唯一程序员能干涉的阶段。
> 加载阶段做四件事：类加载器按全限定名通过不同渠道拿到二进制流——不只是读磁盘文件，Spring 动态代理在内存里生成的类、网络传输的类都走这里；拿到后类加载器职责结束，JVM 在方法区创建一个 C++ 写的 `InstanceKlass` 对象，保存基本信息、常量池、字段、方法、属性，还有实现多态用的虚方法表；同时在堆里创建一个 `java.lang.Class` 对象，这是反射的入口，两者双向引用。要注意 JDK8 开始静态变量的数据是存在堆里这个 `Class` 对象中的，不是方法区。之所以要建两份，一是 Java 代码不能直接操作 C++ 对象，需要一层 Java 包装；二是出于安全，`Class` 对象裁剪掉了虚方法表这类开发者不该访问的信息。

## 七、高频追问预案

### 7.1 阶段划分方向

| 追问 | 回答要点 |
|---|---|
| 到底五个阶段还是七个阶段？ | 都对。连接阶段事情多，展开为验证/准备/解析即七阶段；不展开即五阶段。 |
| 哪个阶段最重要？为什么？ | 初始化。它是**唯一程序员可以干涉**的阶段（静态变量赋值、静态代码块），笔试题几乎都考它。 |
| 卸载阶段什么时候发生？ | 属于垃圾回收范畴：类的 `Class` 对象不再被引用、类加载器被回收时才可能卸载。 |

### 7.2 加载阶段方向

| 追问 | 回答要点 |
|---|---|
| 字节码只能从本地磁盘加载吗？ | 不是。JVM 设计时就留了扩展点：磁盘文件、内存动态生成（动态代理）、网络传输（Applet）、数据库等自定义渠道。 |
| Spring 动态代理生成的类怎么加载？ | 运行时在内存中生成字节码，类加载器按全限定名从内存读取二进制数据加载。 |
| 这一步程序员能扩展吗？ | 能，自定义类加载器重写获取字节流的逻辑，即**类的加密/解密防反编译**的落地点。 |
| `InstanceKlass` 为什么叫 Klass 而不是 Class？ | 它是 C++ 对象，用 K 打头与源码中 C 打头的 `class` 区分，避免混淆。 |
| `InstanceKlass` 里有什么？ | 字节码本身的四类信息（基本信息、常量池、字段、方法、属性）+ JVM 功能性信息（虚方法表等）。 |
| 方法区和永久代、元空间什么关系？ | 方法区只是**规范中的虚概念**；永久代（早期 JDK）和元空间（JDK8+）是 HotSpot 的两种**实现**。 |
| 为什么要在堆和方法区各建一个对象？ | ①`InstanceKlass` 是 C++ 对象，Java 代码不能直接操作，需要 Java 包装层；②安全性，`Class` 对象裁剪掉虚方法表等不该暴露的信息，收窄开发者访问范围。 |
| `Class` 对象和 `InstanceKlass` 谁字段多？ | `InstanceKlass` 多。`Class` 是它的**裁剪副本**。 |
| 两者怎么关联？ | **双向引用**，可以互相查找。 |
| **静态变量到底存哪？** | **JDK8 起在堆中的 `Class` 对象里**；JDK7 及以前在方法区（永久代）。网上说「静态变量在方法区」多为过时说法，可用 HSDB 验证。 |
| 反射为什么要先拿 `Class` 对象？ | `Class` 对象是类信息的 Java 侧入口，通过它才能获取 `Method`、`Field` 再做调用。 |
| 怎么证明你说的对象布局是真的？ | 用 JDK 自带 HSDB（`java -cp sa-jdi.jar sun.jvm.hotspot.HSDB`）attach 进程，Object Histogram 反向查找，能看到静态变量在 `Class` 对象中。 |

### 7.3 陷阱题方向

| 追问 | 回答要点 |
|---|---|
| 加载阶段会执行静态代码块吗？ | **不会**。静态代码块在**初始化阶段**（`<clinit>`）执行，加载阶段只是把信息读进内存。 |
| 加载阶段静态变量有值吗？ | 加载阶段还没有；**准备阶段**赋**零值**（默认值），**初始化阶段**才赋代码里写的值。 |
| 符号引用什么时候变直接引用？ | **连接的解析阶段**；但访问**其他类**的方法/属性时不在此阶段解析，留到运行时动态链接。 |
| 一个类会被加载几次？ | 同一个类加载器下只加载一次；**不同类加载器**加载同一个类会产生**不同的 `Class` 对象**（类的唯一性由「类加载器 + 全限定名」共同决定）。 |
