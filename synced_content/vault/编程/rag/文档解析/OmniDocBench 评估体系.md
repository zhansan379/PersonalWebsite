# OmniDocBench 评估体系

> 文档解析领域最全面的评估基准，从 v1.5 到 v1.6 的演进解决了**元素匹配偏差**和**困难样本覆盖不足**两大核心问题。

## 一、v1.5 的问题

### 1.1 匹配策略偏差

v1.5 采用**固定粒度的一对一元素匹配**，对输出分割与真值不同的系统进行隐性惩罚——即使解析内容完全正确。

典型案例：
- 多行公式被注释为跨越 k 行的单个块，但模型生成了 k 个独立块 → 分数从满分骤降至接近零
- 密集文本区域被注释为一个块，模型可能逐行预测甚至识别为表格 → 由于没有文本元素可匹配，得零分

这种**粒度依赖性**使得跨系统比较不可靠。

### 1.2 困难样本覆盖不足

通过数据引擎的大规模难度分层发现，被标记为"困难"的样本在 v1.5 评估集中几乎不存在。基准主要衡量中低难度文档上的性能，导致顶级模型分数紧密聚类，判别能力下降。

## 二、v1.6 的关键改进

### 2.1 MGAM：多粒度自适应匹配

核心原则：**保持真值不变，只在预测端寻找最优分割粒度**。

三阶段匹配流程：

| 阶段 | 操作 | 产出 |
|---|---|---|
| 1. 直接二部匹配 | 匈牙利算法在原始粒度下求解 P 和 G 的最优匹配 | 候选匹配 M₁ + 总分 S₁ |
| 2. 预测分割+匹配 | 以 LaTeX 换行分隔符拆分每个预测元素，重新匹配 | 候选匹配 M₂ + 总分 S₂ |
| 3. 分区枚举+匹配 | 枚举细粒度预测元素的所有连续子序列分区（2ⁿ⁻¹ 种），每种分区后匹配，选最佳 | 候选匹配 M₃ + 总分 S₃ |
| 全局最优选择 | 选 S₁/S₂/S₃ 中最高者 | 最终匹配 M* |

**密集文本匹配**：对文本元素复用 MGAM，如果模型将文本识别为表格，则将表格转回纯文本后纳入匹配管道，避免因格式偏好差异造成不公平惩罚。

使用 MGAM 后，评估变得**与输出粒度和格式偏好无关**。

### 2.2 三层评估协议

| 层级 | 页数 | 说明 |
|---|---|---|
| **Base** | 1,355 页 | 保留原始 v1.5 计算集，保持与历史结果的可比性 |
| **Hard** | 296 页 | 从数据引擎标记为困难的数据池中精选，覆盖复杂嵌套表、密集公式、非常规布局 |
| **Full** | 1,651 页 | Base + Hard 的完整集合 |

Hard 子集样本**完全排除在 MinerU2.5-Pro 的所有训练阶段之外**，由专业团队标注并进行标注者间交叉验证。

## 三、评分公式

总体得分 = 各子指标归一化后的加权平均：

| 子指标 | 度量 | 指标类型 |
|---|---|---|
| 文本识别 | 编辑距离 | ↓ |
| 公式识别 | CDM（字符检测匹配） | ↑ |
| 表格识别 | TEDS / TEDS-S | ↑ |
| 布局检测 | 类别 IoU | ↑ |
| 阅读顺序 | 编辑距离 | ↓ |

## 四、v1.6 揭示的关键洞察

### 4.1 Hard 子集的判别力

Base 子集上顶级模型分数紧密聚类（前6名在 1.70 分内），Hard 子集则能有效区分：

- MinerU2.5-Pro：Base→Hard 仅下降 **2.04 点**（90.39 → 88.35），稳健性最强
- GLM-OCR：Base 96.19（第1）→ Hard 92.01（第3），下降 **4.18 点**
- HunyuanOCR：下降 **9.76 点**

### 4.2 评测公平性修复

Gemini 3 Pro 在 v1.5 中因匹配偏差被显著低估，v1.6 校正后从 92.85/92.58 上升到与专业模型更接近的水平。

## 五、残留挑战

论文也坦诚指出了评估中的基本挑战：

1. **格式歧义**：相同内容可用多种等效符号表示（HTML vs. Markdown 表格、不同 LaTeX 命令）
2. **结构歧义**：相同视觉布局可用不同元素类型合法表示（例如双语单词列表作为逐行文本或两列表格）
3. **评估覆盖范围**：垂直领域（金融、法律、医疗）需要特定领域的评估集
4. **标注精度瓶颈**：随着模型接近人类水平，评估集标注本身的精度成为挑战
