# 线程池的工作原理和执行流程？

> 一句话定调：线程池为了**减少频繁创建/销毁线程的性能损耗**，用「**核心理念 + 一条四步流水线**」承载任务——核心线程优先 → 满了进**阻塞队列** → 队列满了才**扩容非核心线程** → 再满就**拒绝策略**兜底。四个要素（核心线程数、最大线程数、任务等待队列、拒绝策略）就是整条流水线的阀门；**核心线程数设为 0 也可以**——此时任务先入队、再按需创建一个临时线程来消费队列。

> **这道题对应的「答题主线」**，面试官问「介绍一下线程池的工作原理？」「线程池的执行流程？」，可以按这条主线串起来：
> 一句话定义（复用线程、控制并发，省创建销毁开销）→ 四步执行流程（核心是否满→入队→扩非核心→拒绝）→ 收回到四要素（core/max/队列/拒绝策略，详细参数见配套页）→ 补一个反直觉考点（corePoolSize=0 也能工作）。主线的「提前正常就绪」就落在源码判断里。

## 一、什么是线程池 & 为什么用它

线程池是为了**减少频繁创建和销毁线程带来的性能损耗**——每次 new Thread / 每次线程退出都有可观的开销，而任务提交是高频行为。线程池预先把有限个线程"养"起来复用，同时通过**限制并发数**避免无节制地占满系统资源。

**核心组成（四个要素）：** `corePoolSize`（核心线程数）、`maximumPoolSize`（最大线程数，含核心+非核心）、任务等待队列（`workQueue`）、拒绝策略（`handler`）。整条执行流程就是这四者如何协作。

## 二、核心内容：任务执行流程（四步流水线）

提交一个任务时，按下面的顺序**逐级"扩容"**：

```text
提交任务
  └─ ① 当前线程数 < 核心线程数 corePoolSize ？
       ├─ 未满 → 直接创建新核心线程执行     （优先用核心线程）
       └─ 已满 → 任务入队
            ├─ ② 队列未满 → 放进等待队列排队  （核心忙，先缓冲）
            └─ 队列已满 → 尝试创建非核心线程
                 ├─ ③ 当前线程数 < 最大线程数 maximumPoolSize ？
                 │    ├─ 未满 → 创建非核心线程执行
                 │    └─ 已达最大 → ④ 执行拒绝策略
                 └─ （配合触发拒绝策略的边界判断）
```

**逐级解释：**

1. **核心线程未满 → 直接创建核心线程执行**：核心线程是线程池"常驻"的劳动力，优先扩张到 corePoolSize，不会轻易回收。
2. **核心已满 → 任务入队**：核心线程都被占用时，新任务先进**阻塞队列**排队，等待有空闲核心线程来取，而不是立刻开新线程——用队列缓冲来平滑突发。
3. **队列已满 → 创建非核心线程**：队列也装满，说明任务量超出核心线程消化能力，才创建**非核心线程**（总数仍受 maximumPoolSize 上限约束，队列仅当 `offer` 失败即满时才会走到这步）。
4. **连最大线程数也达到 → 执行拒绝策略**：线程数封顶 + 队列满载，新的任务池子确实吃不下了，按配置好的 `handler` 处理（详见概念页「拒绝策略」一节）。

> 一句话记忆：**核心优先 → 队列缓冲 → 扩容临工 → 拒单**。前两级只动"已在编"的线程，后两级才真正扩力，最后兜底保护线程池不被击穿。

## 三、圈出来的考点：核心线程数设置为 0 可以吗？

**可以。** 核心线程数为 0 时，来了任务会**先加入任务队列**，同时判断当前工作的线程数是否为 0，为 0 则**创建一个（非核心）临时线程**来执行线程池的任务。

看源码即明——`execute()` 里会对工作线程数做判断：

```java
public void execute(Runnable command) {
    int c = ctl.get();
    // ① 若当前工作线程数 < corePoolSize → 尝试新建核心线程
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true)) return;
        c = recheck(c);
    }
    // ② 否则尝试放入工作队列；成功且无存活线程时，再补建一个临时线程
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command)) reject(command);
        else if (workerCountOf(recheck) == 0)        // 关键：没线程就补一个
            addWorker(null, false);                  // 以"非核心"(allowCoreThreadTimeOut语义)方式建
    }
    // ③ 入队失败（队列满）→ 尝试建非核心线程，仍失败则拒绝
    else if (!addWorker(command, false))
        reject(command);
}
```

- 当 `corePoolSize = 0`：第一分支不进，直接走第二分支——任务**先入队**，此时若 `workerCountOf == 0` 就 `addWorker(null, false)` 建一个非核心线程去**消费队列**。
- 这类"空转省心"的池（如 `newCachedThreadPool` 把核心设 0、用 `SynchronousQueue`）正是"**临时线程 + 空闲即回收**"的典型。

## 四、面试速答与追问预案

### 4.1 三十秒速答版

线程池复用有限线程、控制并发，省去频繁创建/销毁开销。执行四步：核心线程未满 → 直接建核心线程；已满 → 任务入阻塞队列；队列满 → 建非核心线程（不超最大线程数）；连最大也满 → 拒绝策略兜底。四个阀门就是 core、max、队列、拒绝策略。补充：核心线程数设 0 也合法——任务先入队、按需补建临时线程消费队列。

### 4.2 追问预案

**Q1：为什么核心线程满了不是先扩线程，而是先入队？**
**A**：核心线程是常驻的"正规军"，理论上应消化绝大部分任务；队列（缓冲）在突发高峰时平滑压力，避免为一次性流量频繁创建→回收线程。只有在队列这个缓冲区也满、确实持续忙不过来时，才扩张临时线程。

**Q2：先建线程还是先入队的边界到底怎么定？**
**A**：核心线程没满 → 直接建线程、不入队；核心满了 → 入队，此时队列 `offer` 成功就不建非核心线程，`offer` 失败（队列满）才建非核心。所以"队列在有界时才有意义"——无界队列永不满，非核心线程永远不会被创建。

**Q3：核心线程数设 0 有什么实际场景？**
**A**：典型如 `Executors.newCachedThreadPool`（core=0、max=Integer.MAX_VALUE、SynchronousQueue）：任务提交即尝试立即建临时线程干活、空闲 60s 自回收，适合大量短小、高弹性任务，缺点是最大线程无上限可能 OOM。

**Q4：入队后如果核心线程一直忙，谁会消费队列里的任务？**
**A**：线程池里的**空闲 Worker**——某个核心线程执行完当前任务后，会循环调用 `workQueue.take()/poll()` 从队列取下一个任务继续执行（`getTask()` 循环）。核心线程不空也不是立刻销毁，而是拉满队列持续干活。

**Q5：七参数的和拒绝策略细节在哪？**
**A**：七个参数（core/max/keepAliveTime/unit/workQueue/threadFactory/handler）的逐个详解与按业务定值经验见「参数设置经验」；拒绝策略四选（Abort/CallerRuns/Discard/DiscardOldest）见「线程池怎么使用」——本篇只讲执行流程这一条主线。
