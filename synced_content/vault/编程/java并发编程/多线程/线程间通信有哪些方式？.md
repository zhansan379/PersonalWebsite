# 线程间通信有哪些方式？

> 一句话概述：线程各跑各的无法协作，需要**通信**。从底层到高层分**四层**——① **共享内存**（共享变量 + `synchronized`/`volatile` 保证可见性）；② **等待/通知监视器**（`Object` 的 `wait/notify/notifyAll`、`Lock`+`Condition` 的 `await/signal`）；③ **阻塞队列** `BlockingQueue`（生产者-消费者天然适配）；④ **同步屏障工具**（`CountDownLatch`/`CyclicBarrier`/`Semaphore`）。最常考的是 wait/notify 细节：**谁醒、醒几个、怎么选**。

## 一、这是什么

线程之间要协作（传递数据、协调进度）就得通信。Java 从最底层的**共享内存**一路到高层的**并发工具**，提供了多层次的通信手段。按"由底到高、由简到繁"把方式**分层记忆**最清晰——低层越原始通用，高层越好用但有特定形态。面试先给这个四层框架，再逐个展开，比零散列方法强得多。

## 二、核心内容：四层通信方式

### 第 1 层 · 共享内存（最基础）

多个线程访问**同一个共享变量**传递信息，是所有通信的底层基础。为保证**可见性/原子性**，需配 `synchronized` 或 `volatile`。例：用 `volatile boolean` 让生产者改、消费者轮询看到：

```java
private static volatile boolean flag = false;   // volatile 保证跨线程可见

// 生产者线程 2 秒后改 flag
// 消费者线程 while(!flag) 自旋等到 flag 变 true 才继续
```

> 关键：共享变量本身是"数据通路"，但**可见性需要额外保证**——`volatile` 保证写立即可见；`synchronized` 还能保证原子性（复合操作）。

### 第 2 层 · 等待/通知（监视器机制）

让线程"等别人叫醒"，是**一对多的协调**，两大流派：

**① Object 的 `wait()/notify()/notifyAll()`** —— 基于对象监视器（锁）：

```java
synchronized (lock) { lock.wait(); }        // 消费者：释放锁进入等待

synchronized (lock) { lock.notify(); }      // 生产者：唤醒一个等待线程
// lock.notifyAll(); // 唤醒所有等待线程
```

**② `Lock` + `Condition` 的 `await()/signal()/signalAll()`** —— 更灵活（可多条件、可指定队列）：

```java
Lock lock = new ReentrantLock();
Condition condition = lock.newCondition();

lock.lock();
try {
    condition.await();      // 消费者：等待
    // 或 condition.signal();  // 生产者：唤醒
} finally {
    lock.unlock();
}
```

> 对比：`await/signal` 对应 `wait/notify`，但 `Condition` 支持 `lock.newCondition()` 多个条件队列精准唤醒、且不要求持有同一个 `synchronized` 块——是 `Lock` 对 `Object` 监视器的进阶。

### 第 3 层 · 阻塞队列 BlockingQueue（生产者-消费者）

线程安全的队列，**入队满时阻塞生产者、出队空时阻塞消费者**，天然实现"协作 + 缓冲"：

```java
BlockingQueue<Integer> queue = new LinkedBlockingQueue<>(1);
queue.put(1);   // 满则阻塞
int item = queue.take();  // 空则阻塞
```

> 适合"一批生产持续消费"的解耦场景，比手写 wait/notify 更安全省心——它内部就封装了 wait/notify 的锁 dance。

### 第 4 层 · 同步屏障工具（控制并发节奏）

三个 `java.util.concurrent` 工具，各自解决一种"多线程进度协调"：

| 工具 | 作用 | 语义 |
| :--- | :--- | :--- |
| `CountDownLatch` | 一个/多个线程**等待其他线程各自 countDown 后**再继续 | `countDown()` 减计数，`await()` 等到 0 |
| `CyclicBarrier` | 一组线程**互相等待到同一屏障点**后才放行 | `await()` 全到齐（可重置 / 带 barrierAction） |
| `Semaphore` | **限制同时访问资源的线程数** | `acquire()`/`release()` 借还许可 |

## 三、wait/notify 高频细节

> 这几个点是"线程间通信"题目的**深水区考点**，单独拎出来。

### 1. wait 状态的线程如何恢复到 RUNNABLE？

通过**外部事件触发/资源可用性变化**恢复，最典型是被其他线程 `notify()/notifyAll()` 唤醒。

> ℹ️ 注意：`Thread.State` 枚举中**没有 RUNNING 状态**，只有 `RUNNABLE`——它涵盖 OS 层的 **ready（就绪）和 running（运行）**两个子状态，面试别答错。

### 2. notify 和 notifyAll 的区别？

相同点：都在唤醒等待线程、**最多只有一个线程能获得锁**、**都不能控制哪个线程获得锁**。

- **`notify()`**：**只唤醒一个**，其余仍在 wait。风险：若被唤醒的线程结束前没再 notify，**其他线程可能永远没人唤醒**（只能等超时或被中断）。
- **`notifyAll()`**：**所有线程都退出 wait** 去竞争锁，只有一个能抢到；它执行完释放锁后，其余线程再一个个抢到继续。

### 3. notify 唤醒哪个线程？（HotSpot 实现）

`notify` 源码注释说选择是**任意的**（留给 JVM 决定）。主流实现 **HotSpot** 并非随机，而是**先进先出（FIFO）顺序唤醒**。

## 四、如何应用 / 面试怎么讲

**加分表达：**
- 先抛**四层通信框架**（共享内存 / 等待通知 / 阻塞队列 / 同步工具），体现"从底到高"的系统性，而非背 API。
- 主动点出每层的定位：**共享内存最通用但要自己保证可见性；wait/notify 协调性弱（锁定对象）；Condition 多条件精准；BlockingQueue 封装了 wait/notify 更安全；三工具各管一种节奏**。
- 在 wait/notify 细节上秀深水区：notify 只醒一个、notifyAll 醒全部去抢锁、HotSpot FIFO、"没有 RUNNING 只有 RUNNABLE"。
- 能讲 wait/notify 与 volatile 的分工：volatile 治"可见性/标志"，wait/notify 治"等待唤醒/阻塞"。

**追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| wait 和 sleep 区别？ | wait 释放锁、基于监视器、须在同步块内、靠 notify 唤醒；sleep 不释放锁、到时自动醒 |
| wait 状态的线程怎么醒？ | 靠其他线程 `notify()`/`notifyAll()` 唤醒（或超时/中断），回到 RUNNABLE |
| notify 和 notifyAll 区别？ | notify 只唤醒一个（其余可能永远等）；notifyAll 全部退出 wait 抢锁 |
| notify 唤醒的是哪个线程？ | 源码说任意、依赖 JVM；HotSpot 实现是 FIFO 顺序唤醒，非随机 |
| 为什么回不到 RUNNING 状态这么问？ | Thread.State 没有 RUNNING，只有 RUNNABLE（含 OS 的 ready+running 两个子状态） |
| 共享变量配合什么保证通信正确？ | 用 volatile 保证可见性、synchronized/锁保证原子性，否则读到脏值 |
| wait/notify 和 Lock/Condition 区别？ | Condition 可 newCondition() 多条件队列精准唤醒、不必非绑一个 synchronized；await/signal 对应 wait/notify |
| CountDownLatch、CyclicBarrier、Semaphore 各管什么？ | Latch=一批完成后放行；Barrier=互相等到齐；Semaphore=限量并发 |
| 生产者-消费者用哪种？ | 首选 BlockingQueue（封装了 wait/notify）；面试也可手写 wait/notify 展示底层理解 |
