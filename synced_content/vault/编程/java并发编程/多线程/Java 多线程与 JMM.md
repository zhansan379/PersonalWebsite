# Java 多线程与 JMM

> 多线程带来的一切麻烦，根子上是**共享内存**：线程各有自己的栈和程序计数器，但堆和方法区是共享的。JMM 就是规定「多线程访问共享变量时怎样才不出错」的一套规则，核心是**可见性、原子性、有序性**三个问题。

> **答题主线**：多线程为什么用（提升吞吐/响应）→ 共享什么、私有什么 → 由共享引出三类注意事项（线程安全 / 线程间通信 / 创建销毁成本）→ 线程安全为什么会出问题，需要 JMM 解释 → 可见性、原子性、有序性各自的成因与解法 → volatile 与 synchronized 的能力边界 → happens-before 是 JMM 的最终答案。

**为什么把多线程和 JMM 放在一篇里讲**：面试中它们几乎必然连着问 —— 「多线程要注意什么」答到「线程安全」，下一个问题就是「为什么会不安全」「volatile 能解决吗」，这已经进入 JMM 了。两者是同一条链的表层与底层。

## 一、多线程是什么

### 1.1 定义与价值

一个 Java 程序中同时运行多个线程，各自执行不同任务。价值有两个方向：

| 目标        | 场景                 | 说明           |
| --------- | ------------------ | ------------ |
| 提升**吞吐量** | CPU 密集型计算拆分到多核     | 充分利用多核，总耗时下降 |
| 提升**响应性** | 一个线程处理用户输入，另一个后台下载 | 慢操作不阻塞主流程    |

> 注意区分：**并发（Concurrency）**是多个任务交替推进，单核也能并发；**并行（Parallelism）**是真正同时执行，必须多核。多线程在单核上只是并发，不会让 CPU 密集型任务变快。

### 1.2 共享什么，私有什么

这张表是理解一切线程安全问题的起点：

| 区域       | 归属       | 内容                       |
| -------- | -------- | ------------------------ |
| 程序计数器    | **线程私有** | 当前执行的字节码指令地址，线程切换后恢复执行进度 |
| 虚拟机栈     | **线程私有** | 栈帧：局部变量表、操作数栈、动态链接、方法出口  |
| 本地方法栈    | **线程私有** | native 方法调用栈             |
| 堆        | **线程共享** | 对象实例、数组                  |
| 方法区（元空间） | **线程共享** | 类信息、常量池、静态变量             |

**结论**：局部变量天然线程安全（在私有栈上，且基本类型不逃逸）；**成员变量、静态变量、以及局部变量引用的堆对象**才是线程安全问题的战场。

> 详见 [[05 运行时数据区 程序计数器]] — 运行时数据区的线程共享/私有划分。

### 1.3 创建线程的四种方式

| 方式            | 写法                     | 特点                         |
| ------------- | ---------------------- | -------------------------- |
| 继承 `Thread`   | 重写 `run()`             | 占用继承名额，不推荐                 |
| 实现 `Runnable` | `new Thread(runnable)` | 无返回值，不能抛检查异常               |
| 实现 `Callable` | 配合 `FutureTask`        | **有返回值，可抛异常**，`get()` 阻塞获取 |
| 线程池           | `ThreadPoolExecutor`   | **生产环境唯一推荐**，复用线程          |

前三种严格说只是「定义任务」的方式，真正创建线程都靠 `new Thread().start()`；实际项目中都应通过线程池提交任务。

## 二、使用多线程要注意什么

三类问题，按面试出现频率排序。

### 2.1 线程安全：多个线程操作共享数据

经典例子：两个线程各给一个变量加 1，期望 +2，结果可能只 +1。

```java
private int count = 0;
public void increment() { count++; }   // 非原子操作
```

`count++` 实际是三步：**读取 → 加 1 → 写回**。线程 A 读到 10，还没写回，线程 B 也读到 10，两个线程各自算出 11 写回 —— 一次自增丢失。

**解法有三个层次**：

| 手段 | 例子 | 适用 |
|---|---|---|
| 加锁互斥 | `synchronized`、`ReentrantLock` | 通用，临界区较大时 |
| 原子类（CAS） | `AtomicInteger.incrementAndGet()` | 单变量自增，无锁性能更好 |
| 避免共享 | 局部变量、`ThreadLocal`、不可变对象 | **最优解 —— 没有共享就没有竞争** |

> 优先级：**能不共享就不共享 > 用原子类 > 加锁**。加锁是兜底手段，不是首选。

### 2.2 线程间通信：协作时的等待与唤醒

生产者-消费者场景，消费者必须等生产者准备好数据。用 `wait()` / `notify()` / `notifyAll()`：

```java
synchronized (lock) {
    while (queue.isEmpty()) {   // 必须是 while，不能是 if
        lock.wait();            // 释放锁并等待
    }
    Object data = queue.poll();
}
```

**三个必踩的坑**：

| 坑 | 说明 |
|---|---|
| 必须在 `synchronized` 块内调用 | 否则抛 `IllegalMonitorStateException` |
| 必须用 `while` 而非 `if` 判断条件 | 防**虚假唤醒（spurious wakeup）**：线程可能在未被 notify 的情况下醒来，醒来后必须重新检查条件 |
| 优先 `notifyAll()` 而非 `notify()` | `notify()` 随机唤醒一个，可能唤醒了「同类」而非等待方，导致**死等** |

**更推荐的做法**：直接用 `BlockingQueue`（如 `ArrayBlockingQueue`），它内部已用 `Condition` 实现好了阻塞语义，业务代码不必手写 wait/notify。

### 2.3 线程创建销毁成本：用线程池

创建线程要分配栈内存（默认 1MB）、注册到操作系统调度，是**重量级操作**。频繁创建销毁不仅慢，还可能因线程数失控导致 OOM。

**线程池七参数**：

| 参数 | 作用 |
|---|---|
| `corePoolSize` | 核心线程数，即使空闲也保留 |
| `maximumPoolSize` | 最大线程数 |
| `keepAliveTime` + `unit` | 非核心线程空闲存活时间 |
| `workQueue` | 任务等待队列 |
| `threadFactory` | 线程工厂，**用来自定义线程名，排查问题的关键** |
| `handler` | 拒绝策略 |

**执行流程（顺序极易记错）**：

```
提交任务
 → ① 核心线程未满？        → 创建核心线程执行
 → ② 队列未满？            → 入队等待          ← 注意：先入队，不是先扩线程
 → ③ 线程数 < max？        → 创建非核心线程执行
 → ④ 都满了               → 执行拒绝策略
```

**四种拒绝策略**：`AbortPolicy`（默认，抛异常）、`CallerRunsPolicy`（调用者线程自己执行，形成背压）、`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢弃最老任务）。

**为什么不用 `Executors` 工厂方法**：

| 工厂方法 | 隐患 |
|---|---|
| `newFixedThreadPool` / `newSingleThreadExecutor` | 用无界队列 `LinkedBlockingQueue`，任务堆积到 **OOM** |
| `newCachedThreadPool` | `maximumPoolSize = Integer.MAX_VALUE`，线程数失控 **OOM** |

**线程数怎么定**：

- CPU 密集型：`CPU 核数 + 1`
- IO 密集型：`CPU 核数 × (1 + 平均等待时间 / 平均计算时间)`，工程上常从 `2 × 核数` 起步压测调整

> 公式只是起点，**真实值必须压测得出**。这句话在面试中一定要说，否则显得只会背公式。

## 三、JMM：为什么线程会不安全

上一章说了「要加锁」，但**为什么不加锁就会错**？这就要下沉到 JMM。

### 3.1 抽象模型：主内存与工作内存

JMM 规定：所有共享变量存在**主内存**；每个线程有自己的**工作内存**，保存该线程用到的变量副本。线程对变量的所有操作必须在工作内存中进行，**不能直接读写主内存**。

```
线程 A 工作内存 ──┐
                 ├── 主内存（共享变量）
线程 B 工作内存 ──┘
```

> **重要澄清**：主内存/工作内存是 JMM 的**抽象概念**，不等于物理硬件。它们与堆、栈的划分不在一个层次；工作内存**可以**对应 CPU 缓存和寄存器，但 JMM 只是规范，不规定实现。面试中把「工作内存」直接说成「CPU 缓存」是不严谨的，说「可类比」才稳。

JMM 要解决的就是三个问题：**可见性、原子性、有序性**。

### 3.2 可见性：改了别人看不到

线程 A 改了变量，未及时同步回主内存；或线程 B 一直读自己工作内存的旧副本 —— 线程 B 看到的还是旧值。

**典型现象**：用一个普通 `boolean flag` 控制线程停止，主线程改成 `false`，工作线程可能永远读到 `true`，死循环不退出。

```java
private volatile boolean running = true;   // 去掉 volatile 可能永不停止
public void stop()  { running = false; }
public void work()  { while (running) { /* ... */ } }
```

**`volatile` 的可见性语义**：

- **写**：立即刷回主内存
- **读**：先让本线程该变量的缓存失效，强制从主内存重新读

保证可见性的三种手段：`volatile`、`synchronized`（解锁前必须刷回主内存）、`final`（初始化完成后不可变，天然可见）。

### 3.3 原子性：一个操作被拆开了

`i++` 不是一个操作而是三个（读、改、写），中间可被线程切换打断。

**JMM 的原子性保证范围**：

| 操作 | 是否原子 |
|---|---|
| 基本类型（`int`、`boolean` 等）的**单次读/写** | ✅ 是 |
| `long` / `double` 的读写 | ⚠️ **规范允许非原子**（可拆成两次 32 位操作）。64 位 JVM 实现上是原子的，但规范层面 `volatile long` 才有保证 |
| `i++`、`i += 1` 等复合操作 | ❌ 否 |

**解法**：`synchronized` / `Lock` 互斥，或 `AtomicInteger` 等原子类（底层 CAS）。

> **`volatile` 不保证原子性** —— 这是最高频的考点。`volatile int i` 的 `i++` 依然会丢更新，因为 volatile 只保证「读到最新值」，不保证「读改写」不被打断。

### 3.4 有序性：代码顺序被改了

编译器和 CPU 为了性能会重排指令，前提是**不改变单线程的执行结果**（`as-if-serial` 语义）。重排来自三个层面：编译器优化重排、指令级并行重排、内存系统重排。

单线程无感，多线程可能出事。**最经典的例子是双重检查锁单例（DCL）**：

```java
public class Singleton {
    private static volatile Singleton instance;    // volatile 不可省
    public static Singleton getInstance() {
        if (instance == null) {                     // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {             // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

`instance = new Singleton()` 分三步：**① 分配内存 → ② 初始化对象 → ③ 把引用指向内存**。②③ 可能被重排为 ③②。此时线程 B 在第一次检查处看到 `instance != null` 直接返回，**拿到的是尚未初始化完成的对象**，一调用就出错。

`volatile` 通过**内存屏障**禁止这种重排序，这才是 DCL 里 volatile 的真正作用 —— **不是为了可见性，是为了禁止重排序**。

### 3.5 volatile 与 synchronized 的能力边界

| 特性 | volatile | synchronized |
|---|---|---|
| 可见性 | ✅ | ✅ |
| 原子性 | ❌ | ✅ |
| 有序性 | ✅ 禁止重排序 | ✅ 互斥保证结果正确 |
| 阻塞 | 不阻塞 | 会阻塞 |
| 用途 | 状态标志位、DCL 单例 | 临界区保护 |

> 关于 synchronized 的「有序性」要讲准：它**不禁止临界区内部的重排**，而是通过「同一时刻只有一个线程进入」，使重排不影响最终结果 —— 相当于把临界区变成单线程语义。

### 3.6 happens-before：JMM 的最终答案

前面讲的都是现象和工具，JMM 真正的规范表述是 **happens-before**：如果操作 A happens-before 操作 B，那么 A 的结果对 B **可见**，且 A 在 B 之前执行。

它的价值是：**不用去推理缓存和重排的细节，只要能串起 happens-before 链，就能断定程序正确。**

天然成立的规则（重点记前四条）：

| 规则 | 内容 |
|---|---|
| 程序次序 | 单线程内，前面的操作 happens-before 后面的 |
| 监视器锁 | 解锁 happens-before 后续对同一把锁的加锁 |
| volatile | 对 volatile 的写 happens-before 后续对它的读 |
| 传递性 | A hb B，B hb C ⟹ A hb C |
| 线程启动 | `Thread.start()` happens-before 该线程的所有操作 |
| 线程终止 | 线程所有操作 happens-before 其他线程从 `join()` 成功返回 |

## 四、面试答题逻辑与追问预案

### 4.1 答题总框架

这两个题目都属于**开放式概念题**，最忌讳想到哪说到哪。用一条固定主线：

```
① 是什么：一句话定义                     ← 30 秒内给出，别铺垫
② 为什么用：吞吐 + 响应性                 ← 体现你知道目的不只是"快"
③ 问题从哪来：共享内存（私有 vs 共享表）    ← 关键转折，所有麻烦的根源
④ 三类注意事项：安全 / 通信 / 成本         ← 结构化，不要只答线程安全
⑤ 下沉原理：三大特性各自成因与解法         ← 这里进入 JMM
⑥ 收口：happens-before 是统一答案          ← 加分项
```

**核心心法**：**答「是什么」时就埋下「为什么」的钩子。** 说到「线程共享堆和方法区」，面试官自然会问「共享会有什么问题」，你就顺势进入线程安全和 JMM —— **主动引导话题走向自己准备充分的区域**。

### 4.2 两种时长的版本

**30 秒版（JMM）**

> JMM 是一套规定多线程如何访问共享变量的规则，解决三个问题：可见性 —— 线程改了别人看不到，volatile 让写立即刷回主内存、读强制重新加载；原子性 —— `i++` 是读改写三步会被打断，靠 synchronized 或原子类；有序性 —— 编译器和 CPU 会重排指令，volatile 用内存屏障禁止重排。规范层面的统一表述是 happens-before。

**2 分钟版（多线程）**

按 4.1 的六步走，其中第③步一定要点出「线程私有栈和程序计数器、共享堆和方法区」，第④步三条都要给，第⑤步至少讲清可见性和原子性的区别。

### 4.3 必须踩到的得分点

| # | 得分点 | 一句话表述 |
|---|---|---|
| 1 | 并发 ≠ 并行 | 单核只能并发，CPU 密集型任务在单核上多线程不会更快 |
| 2 | 私有 vs 共享 | 栈和程序计数器私有，堆和方法区共享 —— **一切线程安全问题的根源** |
| 3 | 局部变量天然安全 | 在私有栈上，不存在竞争 |
| 4 | 注意事项分三类 | 只答「线程安全」是不完整的，还有通信和创建成本 |
| 5 | `i++` 三步拆解 | 读、改、写，能被切换打断 |
| 6 | volatile **不保证原子性** | 最高频考点，一定要主动强调 |
| 7 | 主内存/工作内存是**抽象** | 不等于 CPU 缓存，只是"可类比" |
| 8 | DCL 里 volatile 是**防重排序** | 不是为了可见性 —— 区分度极高 |
| 9 | wait 必须配 `while` | 防虚假唤醒 |
| 10 | 不用 `Executors` 工厂方法 | 无界队列/无界线程数导致 OOM |
| 11 | 线程数公式只是起点 | 真实值必须压测 |
| 12 | happens-before | 收口概念，不必背全八条，讲清价值即可 |

### 4.4 加分点（主动抛出，制造追问）

- **`as-if-serial` 语义**：重排的前提是不改变单线程结果
- **重排的三个层面**：编译器优化、指令级并行、内存系统
- **`long` / `double` 的非原子性协定**：规范允许拆成两次 32 位操作
- **优先级排序**：避免共享 > 原子类 > 加锁 —— 体现你不是「一上来就 synchronized」
- **`threadFactory` 自定义线程名**：线上排查问题的实战细节，非常能体现有真实经验
- **`CallerRunsPolicy` 形成背压**：拒绝策略里唯一有「反压」语义的
- **`BlockingQueue` 替代手写 wait/notify**：知道有更好的工具

### 4.5 高频追问与应答

**A. 多线程基础**

| 追问 | 应答要点 |
|---|---|
| 进程和线程的区别？ | 进程是资源分配单位（独立内存空间），线程是 CPU 调度单位（共享进程内存）。切换成本：线程远低于进程 |
| `start()` 和 `run()` 的区别？ | `start()` 由 JVM 创建新线程再调 `run()`；**直接调 `run()` 就是普通方法调用，还在当前线程执行，没有并发**。`start()` 不能调用两次（抛 `IllegalThreadStateException`） |
| `sleep()` 和 `wait()` 的区别？ | `sleep` 是 Thread 静态方法，**不释放锁**，到时自动醒；`wait` 是 Object 方法，**释放锁**，需被 notify 唤醒，且必须在 synchronized 内 |
| 线程有哪几种状态？ | NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING、TERMINATED。注意 Java 把「就绪」和「运行」合并为 RUNNABLE |
| 怎么优雅地停止一个线程？ | 用 `volatile` 标志位 + 中断 `interrupt()`。**不要用 `stop()`**（已废弃，会直接释放锁导致数据不一致） |
| 线程抛出的异常怎么捕获？ | 线程内的异常不会传播到创建它的线程。用 `Thread.setUncaughtExceptionHandler`；线程池里用 `submit()` 提交的异常被封装在 `Future` 里，**必须 `get()` 才能看到**（这是线程池吞异常的常见坑） |

**B. 线程安全与锁**

| 追问 | 应答要点 |
|---|---|
| `synchronized` 有几种用法？锁的是什么？ | 修饰实例方法锁 `this`；修饰静态方法锁**类对象**；修饰代码块锁指定对象。**锁静态方法和锁实例方法互不影响**，是两把锁 |
| `synchronized` 的底层原理？ | 对象头 Mark Word + Monitor（`monitorenter` / `monitorexit` 指令）。锁升级：无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（内核态互斥）。偏向锁在 JDK 15 已默认禁用 |
| `synchronized` 和 `ReentrantLock` 怎么选？ | 默认用 `synchronized`（JVM 层面、自动释放、已优化得很好）。需要**可中断、可超时（`tryLock`）、公平锁、多条件队列（`Condition`）**时才用 `ReentrantLock`，并且**必须在 `finally` 里 `unlock()`** |
| `AtomicInteger` 的原理？有什么问题？ | CAS（比较并交换）+ 自旋。三个问题：**ABA**（用 `AtomicStampedReference` 加版本号解决）、**高竞争下自旋开销大**（JDK 8 用 `LongAdder` 分段累加缓解）、**只能保证单个变量原子** |
| 什么是死锁？怎么避免？ | 四个必要条件（互斥、持有并等待、不可剥夺、循环等待）。避免：**统一加锁顺序**（最实用）、用 `tryLock` 设超时、减小锁粒度。排查用 `jstack` 看线程 dump |
| `ThreadLocal` 原理？有什么坑？ | 每个 Thread 内有 `ThreadLocalMap`，key 是 ThreadLocal 的**弱引用**，value 是强引用。**线程池场景下线程复用，不 `remove()` 会内存泄漏 + 脏数据**，必须在 `finally` 里 `remove()` |

**C. JMM 深水区**

| 追问 | 应答要点 |
|---|---|
| volatile 能保证线程安全吗？ | **不能**，只保证可见性和有序性。`volatile int` 的 `i++` 依然丢更新。只适合「一写多读」的状态标志场景 |
| volatile 底层怎么实现的？ | 编译后插入**内存屏障**（LoadLoad / StoreStore / LoadStore / StoreLoad）。x86 上体现为 `lock` 前缀指令，它会把缓存行写回内存并使其他核的缓存失效（缓存一致性协议 MESI） |
| DCL 单例里 volatile 能不能去掉？ | 不能。`new` 分三步（分配内存、初始化、赋引用），后两步可能重排，另一线程会拿到**半初始化对象**。volatile 禁止重排序解决 |
| 有没有比 DCL 更好的单例写法？ | **静态内部类**（利用类加载的线程安全性，懒加载且无锁）或**枚举**（还能防反射和反序列化攻击） |
| 主内存、工作内存和堆栈是什么关系？ | **不是一个层次的概念**。堆栈是 JVM 运行时数据区的物理划分，主内存/工作内存是 JMM 为描述可见性而定义的抽象模型，二者不存在一对一映射 |
| happens-before 有哪些规则？ | 讲清前四条（程序次序、监视器锁、volatile、传递性）+ 说明其价值：不用推理缓存细节，能串成链就能证明正确性。不必硬背八条 |
| `final` 在并发下有什么语义？ | 构造函数中对 final 域的写，happens-before 后续对该对象引用的读 —— **保证拿到的对象 final 字段一定已初始化完成**，前提是构造期间 `this` 引用没有逸出 |

**D. 线程池**

| 追问 | 应答要点 |
|---|---|
| 线程池的执行流程？ | 核心线程 → **队列** → 非核心线程 → 拒绝策略。注意是**先入队再扩线程**，顺序很多人答反 |
| 核心线程数怎么设？ | CPU 密集 `核数+1`；IO 密集 `核数 × (1 + 等待/计算)`。**必须强调公式只是起点，要压测** |
| 为什么阿里规范禁止用 `Executors`？ | `newFixedThreadPool` 无界队列堆积 OOM；`newCachedThreadPool` 线程数无上限 OOM。应手动 `new ThreadPoolExecutor` 明确所有参数 |
| 线程池怎么优雅关闭？ | `shutdown()` 拒绝新任务、等已提交任务完成；`shutdownNow()` 尝试中断正在执行的任务。配合 `awaitTermination()` 设超时 |
| 提交任务用 `execute` 还是 `submit`？ | `execute` 无返回值、异常直接抛到 `UncaughtExceptionHandler`；`submit` 返回 `Future`、**异常被吞进 Future**，不 `get()` 就永远发现不了 |
