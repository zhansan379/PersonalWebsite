# 缓存雪崩、击穿、穿透是什么？怎么解决？

> 三者的区别就一条线：**雪崩 = 大面积 key 同时失效（或 Redis 宕机）；击穿 = 单个热点 key 失效；穿透 = 数据本身在缓存和 DB 中都不存在**。前两个是"**数据有，但缓存暂时没了**"，第三个是"**数据根本不存在**"，所以前两个靠"控制重建"解决，第三个靠"拦在门外"解决。

## 一、答题逻辑（骨架）

```
1. 先用一句话给三者的分界线            ← 面试官最想确认你没背混
2. 三行对比表（触发条件 / 数据是否存在 / 核心解法）
3. 逐个展开定义 + 解决方案
4. 收尾：分层防护体系（从入口到 DB 的五道闸）  ← 体现工程整体观
```

**关键心态**：这是**背诵型题目**，区分度不在"记不记得住"，而在：①**能不能一句话讲清三者区别**（最常见的追问就是"三者区别"）；②**能不能说出方案的代价**（互斥锁会阻塞、空值占内存、布隆有误判）。只列方案不谈代价 = 没实战过。

## 二、三者对比（先记这张表）

|            | 缓存雪崩                            | 缓存击穿              | 缓存穿透                 |
| ---------- | ------------------------------- | ----------------- | -------------------- |
| **触发条件**   | **大量**缓存数据同时过期，或 **Redis 故障宕机** | **某个热点** key 过期   | 访问的数据**既不在缓存也不在 DB** |
| **数据存不存在** | 存在（DB 里有）                       | 存在（DB 里有）         | **不存在**              |
| **压力来源**   | 全量请求打到 DB                       | 单点热 key 的高并发打到 DB | 恶意/异常请求打到 DB         |
| **核心解法**   | 过期时间打散、高可用集群                    | 互斥锁、热点不过期         | 参数校验、缓存空值、布隆过滤器      |
| **一句话记忆**  | 面塌了                             | 点破了               | 门没关                  |

> **击穿是雪崩的特例**（雪崩是"一片 key"，击穿是"一个热 key"），所以它们的解法有重叠（互斥锁、后台更新）。

## 三、逐个详解

### 3.1 缓存雪崩

**是什么**：当**大量缓存数据在同一时间过期（失效）**，或者 **Redis 故障宕机**时，如果此时有大量用户请求，都无法在 Redis 中处理，于是**全部请求直接访问数据库**，导致数据库压力骤增，严重的会造成数据库宕机，形成一系列连锁反应，造成整个系统崩溃。
![[Pasted image 20260815095017.png|497]]

**解决方案**：

| 方案 | 做法 | 注意 |
|---|---|---|
| **均匀设置过期时间** | 避免将大量数据设置成同一个过期时间，给过期时间**加上一个随机数**，保证数据不会在同一时间过期 | 最简单有效，成本最低 |
| **互斥锁** | 发现数据不在 Redis 里就**加互斥锁**，保证同一时间只有一个请求构建缓存（读 DB → 写 Redis），构建完成后释放锁。未获取到锁的请求，要么**等待锁释放后重新读缓存**，要么**返回空值或默认值** | ❗**必须设置锁超时时间**，否则第一个请求拿到锁后发生意外一直阻塞不释放，其他请求也一直拿不到锁，整个系统会出现**无响应**现象 |
| **后台更新缓存** | 业务线程不再负责更新缓存，**缓存不设有效期**（"永久有效"），更新工作交由**后台线程定时更新** | 要考虑缓存被**内存淘汰策略**踢掉的情况 |

> 补充（原文未覆盖但常被追问）：针对 **Redis 宕机型雪崩**，还需要**高可用集群**（主从 + 哨兵 / Cluster）、**持久化快速恢复**，以及 **服务熔断 / 限流降级**（Sentinel、Hystrix）和**本地缓存兜底**（Caffeine 二级缓存）。

### 3.2 缓存击穿

**是什么**：如果缓存中的**某个热点数据过期**了，此时**大量请求访问该热点数据**，就无法从缓存中读取，直接访问数据库，数据库很容易被高并发请求冲垮。

![[Pasted image 20260815094938.png|425]]

**解决方案**：

| 方案             | 做法                                                               |
| -------------- | ---------------------------------------------------------------- |
| **互斥锁**        | 保证同一时间只有一个业务线程（允许**一个请求**）重建缓存；未获取到锁的请求，要么等待锁释放后重新读缓存，要么返回空值或默认值 |
| **热点数据不设过期时间** | 由**后台异步更新**缓存；或在热点数据**即将过期前，提前通知后台线程**更新缓存并重设过期时间（逻辑过期思路）        |

### 3.3 缓存穿透

**是什么**：当用户访问的数据**既不在缓存中，也不在数据库中**，请求访问缓存时发现缺失，再去访问数据库也没有，**没办法构建缓存数据**来服务后续请求。大量这样的请求到来时，数据库压力骤增。
![[Pasted image 20260815095044.png|384]]
**解决方案**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **非法请求的限制** | 在 **API 入口处**判断请求参数是否合理：是否含非法值、字段是否存在，判断出恶意请求就直接返回错误，避免进一步访问缓存和数据库 | 第一道闸，成本最低 |
| **缓存空值或默认值** | 针对查询不到的数据，在缓存中设置一个**空值或默认值**，后续请求直接从缓存读到空值返回，不再查数据库 | 占内存；被海量随机 key 攻击时仍会撑爆 → 必须设**较短 TTL** |
| **布隆过滤器** | **写入数据库时用布隆过滤器做标记**；请求到来时，业务线程确认缓存失效后，通过查布隆过滤器**快速判断数据是否存在**，不存在就不查数据库。即使发生穿透，大量请求也只会查 Redis 和布隆过滤器，不会打到 DB。**Redis 自身支持布隆过滤器** | 有**误判率**、**不支持删除** |

## 四、收尾：分层防护体系

> 实际生产不是选一个方案，而是**五道闸层层拦截**：

```
① 入口层：参数校验、限流、鉴权          ← 挡住恶意请求（防穿透）
② 过滤层：布隆过滤器                    ← 挡住不存在的 key（防穿透）
③ 缓存层：空值缓存 + 随机 TTL + 热点不过期 ← 削峰（防穿透/雪崩/击穿）
④ 重建层：互斥锁 / 逻辑过期 + 异步重建    ← 控制回源并发（防击穿/雪崩）
⑤ 兜底层：熔断降级、本地缓存、Redis 高可用 ← 保住 DB（防雪崩）
```

## 五、30 秒速答版

> 三者区别在于"数据在不在"和"失效范围有多大"：**雪崩**是大量 key 同时过期或 Redis 宕机，全量请求压到 DB；**击穿**是单个热点 key 过期，高并发都去回源；**穿透**是查的数据缓存和 DB 里都没有，缓存永远建不起来。
> 解决上：雪崩靠**过期时间加随机值打散** + **互斥锁**限制重建 + **后台定时更新**，Redis 宕机那种还要靠**高可用集群和熔断降级**；击穿靠**互斥锁**或**热点 key 不设过期、后台异步续期**；穿透靠**入口参数校验** + **缓存空值（短 TTL）** + **布隆过滤器**。
> 注意互斥锁**一定要加超时时间**，不然持锁线程阻塞会导致整个系统无响应。

## 六、对方可能追问的问题

### 6.1 顺概念追

| 追问 | 答题要点 |
|---|---|
| **一句话说清三者区别** | 雪崩=**一片** key 没了；击穿=**一个热** key 没了；穿透=key **压根不存在**。前两个数据在 DB 里，第三个不在 |
| 穿透和击穿老记混，怎么记？ | **穿透**：穿过缓存又穿过 DB，两层都空 → 门没关；**击穿**：只击破缓存上"一个点" → 点破了 |
| 击穿和雪崩是一回事吗？ | 击穿是雪崩的**特例**（范围从"一片"缩到"一个热点"），所以互斥锁、后台更新两个方案通用 |

### 6.2 顺布隆过滤器追（最高频深挖点）

| 追问 | 答题要点 |
|---|---|
| **布隆过滤器原理？** | 一个**位数组** + **k 个哈希函数**。写入时把 k 个哈希位置全置 1；查询时若**任一位为 0 → 一定不存在**；若**全为 1 → 可能存在**（可能是别的 key 把这些位置置 1 了） |
| 为什么有误判？误判率怎么控制？ | **哈希冲突**导致位被别的元素置 1。误判率由**位数组长度 m** 和**元素数量 n**、**哈希函数个数 k** 共同决定，工程上按预估数据量和可接受误判率（如 1%）配置 |
| **只会误判"存在"，不会误判"不存在"** | 这正是它能用在这里的原因：**说不存在就绝对不存在**，可以放心拦；说存在则放行去查缓存/DB，最坏就是白查一次 |
| **为什么不支持删除？** | 多个元素**共享同一位**，把位清 0 会误伤其他元素。解法：**计数布隆过滤器**（位换计数器）或**布谷鸟过滤器**（Cuckoo Filter，支持删除） |
| 数据新增/删除时过滤器怎么同步？ | 新增数据时**同步写入过滤器**（可订阅 binlog 保证不漏）；删除只能靠**定期全量重建**（双 buffer 切换，避免重建期间不可用） |
| 用什么实现？ | Redis 的 **RedisBloom 模块**、Redisson 的 `RBloomFilter`、单机可用 Guava `BloomFilter` |

### 6.3 顺互斥锁追（第二高频）

| 追问 | 答题要点 |
|---|---|
| 互斥锁怎么实现？ | `SET key value NX EX 10`（**原子**加锁 + 过期）；value 存**唯一标识（UUID）**；释放时用 **Lua 脚本**比对 value 再删，避免误删别人的锁 |
| 锁超时了但业务没做完怎么办？ | **看门狗（watchdog）自动续期**（Redisson 默认 30s、每 10s 续期）；或把锁时间设为"业务最大耗时"的安全倍数 |
| 主从切换时锁会丢吗？ | 会。主节点加锁成功后未同步就宕机，从节点升主后锁**凭空消失**。这就是 **RedLock** 想解决的问题（但 RedLock 本身**存在争议**，Martin Kleppmann 与 antirez 有著名论战）；要绝对可靠应上 **ZooKeeper / etcd** |
| 大量线程等锁会不会拖垮服务？ | 会。所以要么 **tryLock 快速失败**并返回**默认值/降级数据**，要么**双重检查**（拿到锁后再查一次缓存，可能别人已经建好了），别让线程无限等 |
| 有没有不加锁的方案？ | **逻辑过期**：key **不设 TTL**，value 内部存一个 `expireTime` 字段；发现逻辑过期就**开异步线程重建，同时先返回旧数据**。牺牲一致性换取**绝对高可用**，秒杀/大促常用 |

### 6.4 顺工程实践追

| 追问 | 答题要点 |
|---|---|
| **热点 key 怎么发现？** | Redis 自带 `--hotkeys` / `MONITOR`（生产慎用）、`OBJECT FREQ`（LFU 模式）；更常见是**业务埋点 + 实时流计算**（Flink）做热点探测 |
| 热点 key 除了击穿还有什么问题？ | **数据倾斜**：单个 slot / 节点被打爆。解法：**key 打散**（`key#1..key#N` 多副本随机读）、**本地缓存**（Caffeine）挡在 Redis 前面 |
| 「后台更新缓存 + 永不过期」有什么坑？ | 缓存可能被 **内存淘汰策略**踢掉（`maxmemory-policy`：`noeviction`/`allkeys-lru`/`volatile-lru`/`allkeys-lfu` 等 8 种）。所以后台线程还要**兜底检测 key 是否还存在**，不存在立即重建 |
| 雪崩发生时怎么保住 DB？ | **限流 + 熔断降级**（Sentinel）、**DB 连接池上限**、**多级缓存**（本地 + Redis）、非核心功能直接降级返回兜底数据 |
| 缓存预热是什么？ | 系统上线/大促前**主动把热点数据加载进缓存**，避免冷启动瞬间全部穿到 DB——这是雪崩的**事前预防**手段 |
| 这三个问题和一致性问题什么关系？ | 一致性关注"**缓存里的值对不对**"，这三个关注"**缓存挡不挡得住流量**"，是两个正交维度 → 见 [[编程/数据库/redis/场景题/如何保证 redis 和 mysql 数据缓存一致性问题？]] |
