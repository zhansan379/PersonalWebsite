# Claude Code 上下文工程

> 上下文工程是 Claude Code 能力的隐形支柱——模型的决策质量完全取决于它看到了什么上下文。系统必须在有限的上下文窗口内，决定哪些信息保留、哪些压缩或丢弃。

## 🎯 答题逻辑（骨架）

```
1. 先定位矛盾（别急着讲技巧）        ← 15 秒，证明你知道这题的约束是什么
   ├─ 约束 A：窗口有限，消息只增不减
   └─ 约束 B：system + tools 就有 50-100K token，必须吃到
              前缀缓存；而前缀缓存要求「字节级完全一致」
   结论：所有设计都是「带着镣铐跳舞」——既要给模型最好的上下文，
         又不能打破缓存
2. 讲组装：按「变化频率」分层          ← 证明布局不是随手拼字符串
   system（从不变，静态/动态边界切割）→ tools → messages（只在尾部增长）
   反直觉点：CLAUDE.md、记忆、技能都不在 system 里，
             而是 messages 里的 <system-reminder> 附件
3. 讲增长控制：五级渐进式压缩流水线    ← 证明你知道压缩不是「满了就总结」
   Tool Result 裁剪 → History Snip → Microcompact
   → Context Collapse → Autocompact，成本从零到一次完整 API 调用
4. 讲缓存保护：三断点缓存链 + 四层防御  ← 证明你看到了 2 和 3 是一对矛盾
   压缩要改历史 = 动前缀 = 缓存全失效；所以 Microcompact 要么
   等缓存冷了再改，要么走 cache_edits 不破坏缓存
5. 讲动态信息怎么进来                 ← 证明你懂「注入通道」这个抽象
   <system-reminder> 统一通道 + 记忆预取（生成时并行搜盘）+ 增量注入去重
6. 收口到设计原则                     ← 拔高
   memoize 保幂等、渐进式降级、投影式可回退、缓存感知的注入顺序
```

**关键心态**：这题考的**不是"你怎么写提示词"，而是"你有没有真的运维过长会话 Agent"**。面试官在听两件事：你会不会把上下文当成一个只增不减的字符串拼接；你知不知道「省 Token」和「保缓存」是互相打架的。会被判定为没实操过的答法有三种：「上下文满了就让模型总结一下历史」（把五级流水线塌缩成一级，且忽略摘要本身要花一次 API 调用）、「把 CLAUDE.md 和记忆放进系统提示词里」（直接毁掉全局缓存共享）、「缓存就是把提示词存起来省钱」（说不出失效规则）。

**分水岭术语**：**前缀缓存字节级一致**、**`cache_control` 缓存断点**、**静态/动态边界（`__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__`）**、**渐进式压缩 / `cache_edits`**、**`<system-reminder>` 注入通道**、**投影式折叠（Context Collapse）**。这几个词能自然说出来，基本判定你读过实现；只会说「压缩历史 + 向量检索记忆」就是纯 API 使用者。

## 一、核心概念

### 1.1 上下文窗口 = 办公桌

把上下文窗口想象成一张办公桌：桌面有限，必须把最重要的文档放在手边，其他的归档到抽屉里。上下文工程就是这套"文档管理系统"：

- **上下文构建**：决定桌上放什么
- **压缩**：什么时候把旧文档收进抽屉
- **持久化与恢复**：如何让归档的文档在需要时快速取回

### 1.2 前缀缓存的镣铐

Claude Code 每次 API 请求，系统提示词 + 工具定义就有 **50-100K token**。为避免每次都从零处理，它依赖服务端的 **前缀缓存（KV Cache）**。

但前缀缓存有一个硬约束：**前缀必须字节级完全一致才能命中**。任何一个字节的变化都会导致整个前缀的缓存失效。这给上下文工程带来了"带着镣铐跳舞"的感觉——每个设计决策都必须同时满足两个目标：**给模型最好的上下文**，同时**不打破缓存**。

## 二、上下文构建全景

每次 API 调用前，Claude Code 将模型需要的所有信息组装成一个完整请求。Claude API 的请求体有三个顶级字段：`system`（系统提示词数组）、`tools`（工具 schema 数组）、`messages`（消息数组）。

下表总结了各组件在一个会话中的**变化特征**及其缓存策略：

| 组件 | 在请求中的位置 | 会话内变化频率 | 说明 |
|---|---|---|---|
| 核心系统指令 | `system`（边界前） | **从不**——所有用户所有会话完全相同 | 全局缓存，全球共享 |
| 动态系统指令 | `system`（边界后） | **从不**——因用户而异但 session 内固定 | 会话开始时确定 |
| 工具 schema | `tools[]` | **极少**——MCP 重连或 Tool Search 发现新工具时 | 延迟加载减少变动 |
| CLAUDE.md + 日期 | `messages[0]` | **从不**——会话开始时 memoize 计算一次 | 包裹在 system-reminder 中 |
| 用户消息 + 模型回复 | `messages` | **每轮增长** | 压缩机制控制增速 |
| 工具调用 / 结果 | `messages` | **每次工具执行后增长** | 旧结果可被 Microcompact 清理 |
| 记忆文件 | `messages`（附件） | **按需**——相关记忆被发现时注入，去重 | 每会话最多 60KB |
| 技能 / MCP 指令 | `messages`（附件） | **增量**——只在列表变化时注入 delta | 不重复发送已知内容 |

> **关键设计**：记忆、技能、MCP 指令**不在系统提示词中**，而是作为 `<system-reminder>` 附件消息注入到消息数组中。这样它们可以按需、增量地注入，不会破坏系统提示词的缓存。CLAUDE.md 和日期虽然也是"元信息"，但放在消息数组第一条而非系统提示词中——因为 CLAUDE.md 内容因项目而异，放在系统提示词中会降低缓存共享率。

### 2.1 系统提示词组成

系统提示词是上下文中最稳定的部分——它定义模型"是谁"以及"该怎么做"。下面是一次 API 请求中 `system` 字段的完整结构：

```
system — 系统提示词数组（多个 TextBlock 拼接）
┌──────────────────────────────────────────────────────┐
│ [0] 归属头 (Attribution Header)            不缓存    │
│ [1] CLI 前缀 (交互模式 / -p 模式指令)       不缓存    │
│ ─── 静态内容 ─────────────────────── 🔒 global ──── │
│ [2] 核心指令 + 工具描述 + 安全规则 + 行为准则         │
│     （所有用户完全相同）                               │
│ ─── __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__ ──────────── │
│ ─── 动态内容 ─────────────────────── 不缓存 ─────── │
│ [3] 输出风格、语言偏好、MCP 指令等                    │
│     （因用户/会话而异）                                │
└──────────────────────────────────────────────────────┘

tools — 工具 schema 数组
┌──────────────────────────────────────────────────────┐
│ 内置工具 (Read, Edit, Bash, Grep, Write, Glob...)    │
│ MCP 工具 (用户安装的，可能标记 defer_loading 延迟加载) │
│ 最后一个工具 ← 标记 cache_control 作为缓存断点        │
│ ── 断点之后 ──                                        │
│ 服务端工具 (advisor 等，开关不影响缓存)                │
└──────────────────────────────────────────────────────┘

messages — 消息数组
┌──────────────────────────────────────────────────────┐
│ [User]  <system-reminder>                             │
│           CLAUDE.md 内容 + 当前日期                    │
│         </system-reminder>                 (isMeta)   │
│ [User]  用户第 1 条消息                                │
│ [Asst]  模型回复（可能包含 tool_use 块）               │
│ [User]  tool_result 结果                               │
│ [User]  附件消息（每条都是独立的 isMeta 用户消息）：    │
│          ├ <system-reminder> 记忆文件内容 </...>       │
│          ├ <system-reminder> 可用技能列表 </...>       │
│          ├ <system-reminder> 延迟工具发现结果 </...>   │
│          └ <system-reminder> MCP 指令增量 </...>       │
│ ...（消息不断增长，直到压缩机制介入）                   │
└──────────────────────────────────────────────────────┘
```

关键设计要点：

- **静态/动态边界**：`__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 哨兵将系统提示词切成两半。边界之前的核心指令使用 `scope: 'global'` 缓存，**全球共享**——没有这个切割，所有用户都得各自缓存一份完全相同的内容；边界之后是用户专属的动态内容，不缓存或 `scope: 'org'`
- **Section 缓存策略**：大多数 section（工具描述、安全规则）是稳定的，首次计算后缓存到 `/clear` 或 `/compact` 才刷新；少数依赖实时 feature flag 的 section 每轮重新计算，如果值变了会**破坏前缀缓存**
- **优先级链**：系统提示词的最终内容不是"选一个"，而是根据当前运行模式**逐级裁决**。先搞清涉及的几个概念：

  | 概念 | 是什么 | 谁/什么时候触发 |
  |---|---|---|
  | **override** | 一个完全独立的提示词字符串，绕过所有正常逻辑 | Claude Code 自己设置。SDK 嵌入模式（第三方调用 Claude Code API）和 `/loop` 循环模式会用。比如 `/loop` 下模型只需要"重复执行任务"，不需要工具描述、安全规则等全套提示词 |
  | **custom** | 用户通过 `--system-prompt "xxx"` 传入的额外指令 | 用户在命令行手动指定。典型用途：`--system-prompt "用中文回复"`、`--system-prompt "不要用 emoji"`。本质是"在标准提示词之上叠加个人偏好" |
  | **agent** | 用户定义的、有独立身份和提示词的子 Agent | 项目里配置了自定义 Agent（如 `.claude/agents/` 下的代码审查 Agent、测试 Agent）。每个 Agent 自带 `getSystemPrompt()`，定义了该 Agent 的专属行为指令。在普通模式下替换默认提示词，在 Proactive 模式下追加 |
  | **Proactive 模式** | Claude Code 的一种自主运行模式（Feature-gated） | 模型不再等待用户每条指令，而是自主规划并执行多步任务。此时默认提示词已经是"自主 Agent 身份 + 记忆 + 环境"的精简版——所以 agent 提示词是**追加**而非替换，相当于在通用自主能力上加领域专长 |

  这些概念在 `buildEffectiveSystemPrompt()` 中按以下优先级裁决（源码见 [[raw/编程笔记/claude源码解析/源代码/systemPromptSections.ts]]）：

  ```typescript
  // 0. 有 override？直接返回，连 append 都不加——真正的完全替换
  if (overrideSystemPrompt) {
    return [overrideSystemPrompt]
  }

  // 1. 协调器模式？用协调器专用提示词 + append，跳过后续所有
  if (COORDINATOR_MODE && !mainThreadAgentDefinition) {
    return [coordinatorPrompt, ...append]
  }

  // 2. Proactive 模式 + 有 Agent？Agent 追加到 default 后面（不是替换）
  if (agentSystemPrompt && isProactiveActive()) {
    return [...defaultSystemPrompt, agentPrompt, ...append]
  }

  // 3. 普通模式：agent / custom / default 三者互斥，只选一个
  return [
    agentSystemPrompt
      ? agentPrompt           // 有 Agent → 用 Agent，custom 被忽略
      : customSystemPrompt
        ? customPrompt        // 有 custom → 替换 default
        : defaultPrompt,      // 都没有 → 标准提示词
    ...append,                // append 始终垫底
  ]
  ```

  几个反直觉的细节：

  | 细节 | 说明 |
  |---|---|
  | **agent 和 custom 互斥** | 如果你定义了一个 Agent 又传了 `--system-prompt`，后者会被**静默忽略**——Agent 优先级更高 |
  | **override 连 append 都不加** | `/loop` 模式是完全替换，连底线规则都不保留 |
  | **Proactive 模式下 agent 行为不同** | 不是替换默认提示词，而是**追加**——先有通用自主能力，再叠加上 Agent 的领域指令 |
  | **append 在除 override 外的所有路径都生效** | coordinator、agent、custom、default 都会带 append |

### 2.2 系统上下文（getSystemContext）

被 memoize 缓存，每会话只计算一次。核心实现：

- **Git 状态**：5 个 git 命令 **并行执行**（`Promise.all`），结果截断至 2000 字符
- **Disclaimer 免责声明**：明确告诉模型"这是会话开始时的快照，不会实时更新"，防止模型幻觉
- **条件跳过**：CCR（远程）模式或禁用 git-instructions 时跳过

### 2.3 用户上下文（getUserContext）

memoize 缓存，包含：

- **CLAUDE.md 内容**：通过多层发现机制加载的项目级指令
- **当前日期**：ISO 格式

### 2.4 CLAUDE.md 发现机制

发现顺序（从远到近，后加载的优先级更高）：

1. MDM 管理策略文件
2. 用户主目录 `~/.claude/CLAUDE.md`
3. 项目文件（从 CWD 向上遍历目录树）
4. 本地文件 `CLAUDE.local.md`（不提交到 git）
5. `--add-dir` 显式附加目录

支持 `@include` 指令引用其他文件（`@./path`、`@~/path`、`@/path`）。

### 2.5 上下文注入顺序

系统上下文**后置**于系统提示词，用户上下文**前置**于消息——此顺序兼顾了缓存效率：系统提示词最稳定，放在最前面有利于缓存命中。

## 三、消息历史管理

### 3.1 消息规范化（normalizeMessagesForAPI）

消息发送前的关键处理步骤，解决内部格式与 API 要求的差异：

| 步骤 | 问题 | 处理 |
|---|---|---|
| 附件重排序 | 附件可能出现在任意位置 | 向上冒泡至 tool_result/assistant 之前 |
| 过滤虚拟消息 | 内部临时消息不应进入 API | 移除 `isVirtual` 标记的消息 |
| 构建错误→块类型映射 | 过大文件重复发送 | 从后续消息中剥离对应媒体块 |
| 剥离内部元素 | tool_reference 等 API 不理解 | 移除内部跟踪标记 |
| thinking/signature 处理 | 部分模型不支持 | 根据模型能力剥离 |
| 合并分裂消息 | 并行工具调用产生同 ID 多消息 | 按 message.id 合并 |
| 验证修复配对 | tool_use / tool_result 可能不配对 | 为孤儿 block 生成合成对应项 |

### 3.2 压缩边界

Autocompact 后在消息列表中插入 `compact_boundary` 标记，后续 API 调用只发送边界之后的消息。

## 四、五级压缩流水线

设计哲学：**渐进式压缩**——先用成本最低的手段释放空间，只在必要时才动用更重的武器。

```
消息列表 →  1. Tool Result 预算裁剪
         →  2. History Snip 剪裁
         →  3. Microcompact 微压缩
         →  4. Context Collapse 上下文折叠
         →  5. Autocompact 自动全量压缩
```

### Level 1: Tool Result 预算裁剪

- **零延迟、零成本**（纯本地操作）
- 工具结果超过 `maxResultSizeChars`（默认 50,000 字符）时，持久化到磁盘
- 上下文只保留 2KB 预览 + 持久化路径引用
- 模型可通过 Read 工具随时获取完整内容

### Level 2: History Snip

- Feature-gated 功能
- 从历史消息中剪裁冗余部分释放 Token
- 释放量传递给后续 autocompact 阈值检查

### Level 3: Microcompact

清理历史中不再需要的旧工具结果。有**两条互斥路径**：

| | 基于时间（缓存冷） | 缓存编辑（缓存热） |
|---|---|---|
| 触发条件 | 距上次消息超过阈值 | 工具数量超过阈值 |
| 操作方式 | 直接修改消息内容 | `cache_edits` API 块 |
| 对缓存影响 | 无需考虑（缓存已过期） | **完全不破坏缓存** |
| API 调用 | 零 | 零（捎带在下次请求中） |

### Level 4: Context Collapse

- **投影式压缩**：创建消息的只读折叠视图，**不修改原始消息**
- 类比数据库的 View：底层数据不变，查询时看到过滤/转换后的视图
- 可回退，优于 Autocompact 的不可逆性
- 在约 **90%** 上下文利用率时触发，**同时抑制 Autocompact**

### Level 5: Autocompact

最后手段，fork 子 Agent 调用 API 生成对话摘要。触发条件（5 个全部满足）：

1. 递归守卫（不是 compact 查询源自己触发）
2. 三重开关检查（环境变量 + 用户配置）
3. 非 Reactive-only 模式
4. 非 Context Collapse 模式
5. Token 阈值达标

压缩采用"分析-摘要"两阶段模式：先写 `<analysis>` 草稿（推理过程），再生成 `<summary>`。最终只保留 `<summary>` 进入上下文（经典 Chain-of-Thought Scratchpad 技术）。

**压缩后恢复**：自动恢复最近 5 个文件、已激活技能、延迟工具/MCP 指令等，是长对话保持连贯性的关键。

**熔断器**：连续 3 次 autocompact 失败则停止重试。

## 五、Token 预算管理

本页只记与上下文组装直接相关的三点，完整的预算模型（双层预算、有效窗口公式、三层水位线、常量表、续写机制）见 [[04 Token 预算管理]]。

### 5.1 Token 估算算法

核心思路：用 API 返回的精确 `usage` 数据作为锚点，只对锚点后的新增消息做粗略估算（字符数 × 4/3）。误差从可能的 30%+ 降到通常 <5%，无需额外 API 调用。

> 算法的三步实现（`tokenCountWithEstimation()`）见 [[04 Token 预算管理#六、Token 估算：不调 API 也能算]]。

### 5.2 输出 Token 预留

`max_output_tokens` 默认值覆盖 p99 输出需求（p99 = 4,911 tokens）；当模型因 `max_tokens` 截断时自动升级到 `ESCALATED_MAX_TOKENS = 64,000`（MOT 恢复机制）。

> 为什么默认值不该手动调大、以及 slot 资源预留的原理，见 [[04 Token 预算管理#1.3 为什么 maxOutputTokens 默认只有 8K？]]。
>
> ⚠️ 待核对：本页源材料记 Sonnet 默认 `max_output_tokens = 16,000`，[[04 Token 预算管理]] 记 **8K**（且"8K 覆盖 99% 需求"的论证只对 8K 成立）。两处疑似源材料版本不同，需回 raw 核对后统一。

### 5.3 Task Budget 跨压缩结转

每次压缩前捕获 `finalContextTokensFromLastResponse()`，压缩后从剩余量中扣除——server 不知道压缩前的上下文有多大，`taskBudgetRemaining` 告诉它这些 Token 已被"花掉"。

> 结转的动机、完整算例与续写时的上下文重放见 [[04 Token 预算管理#七、剩余预算：Agent 的 "氧气表"]]。

这个可控的缓存取决于模型服务商，deepseek就不支持手动控制

### 6.1 三层缓存链

```
[system 块 ← cache_control] [tools ← cache_control] [历史消息... ← cache_control]
 ~~~~~~缓存命中~~~~~~         ~~~~~~缓存命中~~~~~~         ~~~~~~缓存命中~~~~~~
```

三个断点串联实现**全链路缓存**：持续 20 轮的对话，第 21 轮只需处理最新增量。
我猜测这个所谓的cache_control的作用是遇到这个标记就缓存一下。

### 6.2 四层防御

| 层次 | 机制 | 解决的问题 |
|---|---|---|
| 第一层 | 系统提示词分割 | 静态部分 global 缓存（全球共享），动态部分不缓存 |
| 第二层 | 会话级锁存 | TTL 资格和 beta header 在会话开始时锁定，防止中途翻转 |
| 第三层 | 排列策略 | 可选工具放断点之后，MCP 工具延迟加载 |
| 第四层 | 缓存断裂检测 | 两阶段快照对比，自动归因断裂原因 |

### 6.3 MCP 工具的隐藏代价

只要安装了**任何一个 MCP 工具**，系统提示词缓存就从 `global`（全球共享）降级为 `org`（组织内共享）。

> 降级的机制原因（MCP 工具列表会话内可能变化，破坏跨组织缓存基础）见 [[05 System Prompt 缓存与动态组装#模式 1：MCP 工具存在时]]。

## 七、system-reminder 注入机制
模型通过训练知道 `<system-reminder>` 内的内容是系统自动注入的元数据，而不是用户的直接输入。`<system-reminder>` 标签是统一的系统信息注入通道：

- 包装 CLAUDE.md 内容、当前日期、记忆文件、技能列表等
- 在消息流的任意位置注入，不混淆"发言者"身份
- 相邻的 system-reminder 会被合并到邻近 tool_result 中

## 八、记忆预取

在模型生成响应的同时**并行搜索**相关记忆文件，隐藏磁盘 I/O 延迟。使用 `using` 语法确保资源清理，去重防止同一文件被多次注入。

## 九、设计洞察

1. **Memoize 保证幂等性**：`getSystemContext` 和 `getUserContext` 每会话只计算一次
2. **渐进式压缩**：从零成本裁剪到全量摘要，大部分对话永不触发 Autocompact
3. **投影式折叠的可逆性**：Context Collapse 不修改原始消息，可安全回退
4. **缓存感知的上下文组装**：注入顺序考虑缓存命中率
5. **Token 估算的锚点策略**：精确值锚点 + 增量估算
6. **会话级锁存的务实取舍**：牺牲灵活性换缓存稳定性
7. **MCP 工具越少，缓存效率越高**

## ⚡ 30 秒速答版

> Claude Code 的上下文工程要同时满足两个互相打架的目标：**在有限窗口里给模型最好的上下文**，同时**不打破前缀缓存**——因为它的 system + tools 就有 **50-100K token**，而前缀缓存要求**前缀字节级完全一致**才命中，改一个字节后面全部重算。
>
> 所以整个请求是**按"变化频率"分层组装**的：`system` 最稳定放最前，还用一个**静态/动态边界哨兵**把它切成两半，静态那半可以 **global 全球共享缓存**；`tools` 在中间，最后一个工具上打 **`cache_control` 断点**，可选工具和 MCP 工具放断点之后；`messages` 只在**尾部增长**。反直觉的是 **CLAUDE.md、记忆、技能列表都不在系统提示词里**，而是作为 `messages` 里的 **`<system-reminder>` 附件消息**注入——这样能按需、增量注入而不动前缀。
>
> 增长控制用的是**五级渐进式压缩流水线**：先零成本地把超大工具结果**落盘只留 2KB 预览**，再 History Snip 剪裁，再 **Microcompact** 清理旧工具结果，到约 **90%** 利用率做 **Context Collapse 投影式折叠**（只做只读视图、不改原消息、可回退），实在不行才 **Autocompact** —— fork 一个子 Agent 调 API 写 `<analysis>` 再出 `<summary>`，只把 summary 放回上下文。
>
> 关键洞察是：**压缩和缓存是一对矛盾**——改写历史消息就等于改前缀，缓存全废。所以 Microcompact 有两条互斥路径：**缓存已经冷了**就直接改消息内容，**缓存还热**就走 `cache_edits` API 块，**完全不破坏缓存**。压缩的时机本身是缓存状态的函数，这是我觉得最漂亮的设计。

## 💬 对方可能追问的问题

### 顺着前缀缓存追（概率最高，也最容易问深）

| 追问 | 答题要点 |
|---|---|
| 前缀缓存的失效规则到底是什么？ | **从请求最开头逐字节匹配的最长公共前缀**。命中只发生在 `cache_control` 标记的断点位置，且**断点之前的所有内容必须完全一致**。位置 i 改了一个字节 → **i 之后的全部缓存作废**，前面的仍可用。所以它是「前缀」缓存不是「片段」缓存，**没有中间插入、没有局部更新** |
| 为什么系统提示词必须放最前面而且必须稳定？ | 这是失效规则的**直接推论**：缓存只能从头往后匹配，谁放在前面谁就成为所有后续内容的「地基」。system 是唯一在**整个会话里从不变**的部分，放最前 → 它后面的 tools 和历史消息才有机会被缓存；反过来如果把「当前日期」「记忆内容」这类会变的东西放进 system，等于**每轮都换地基，后面全部重算**——这就是为什么 CLAUDE.md 和日期宁可放 `messages[0]` 也不放 system |
| 那 CLAUDE.md 放 messages[0] 不也是每个项目都不一样吗？ | 是，但**代价的作用范围完全不同**。放 system 里会让 system 这个 50-100K 的块**降级为项目专属**，全球共享率归零；放 messages[0] 只影响消息数组这一段，system 和 tools 的缓存照样命中。同理它被 memoize，**会话开始只算一次**，之后不变 |
| 静态/动态边界具体解决什么？ | 系统提示词里混着「所有用户完全相同」的核心指令 + 工具描述 + 安全规则，和「因用户/会话而异」的输出风格、语言偏好、MCP 指令。用 `__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__` 哨兵一刀切开：边界前 `scope: 'global'` **全球共享**，边界后不缓存或 `scope: 'org'`。没这一刀，每个用户都要各自缓存一份完全一样的内容 |
| 为什么 MCP 工具要延迟加载、要放断点之后？ | MCP 工具列表**会话内可能变化**（重连、Tool Search 发现新工具），一变就动了 tools 的字节。放在 `cache_control` 断点**之后**，变动就不影响断点之前的缓存。另外只要装了**任何一个** MCP 工具，系统提示词缓存就从 `global` **降级为 `org`** —— 结论：MCP 工具越少缓存效率越高 |
| 会话级锁存锁的是什么？为什么要锁？ | 锁的是 **TTL 资格和 beta header**，在会话开始时确定后中途不再翻转。因为这些是请求级参数，中途变化会**破坏前缀缓存**；宁可牺牲灵活性换缓存稳定性。同理，少数依赖实时 feature flag 的 section 每轮重算，值一变就会断缓存 |
| 缓存断裂了怎么排查？ | 系统内置**缓存断裂检测**：做**两阶段快照对比**，自动归因是哪一段变了。工程上排查顺序就是按前缀从前往后：system 静态段 → 动态段 → tools → messages |

### 顺着五级压缩流水线追

| 追问 | 答题要点 |
|---|---|
| 为什么要分五级，一个 Autocompact 不够吗？ | 因为**成本差好几个数量级**。Level 1 是纯本地操作、**零延迟零成本**；Level 3 Microcompact **零 API 调用**（捎带在下次请求里）；只有 Level 5 要 **fork 子 Agent 真调一次 API**，还不可逆。设计哲学是**渐进式降级**：先用最便宜的手段释放空间，**大部分对话永远走不到 Autocompact** |
| Level 1 具体怎么做的？为什么它最优？ | 工具结果超过 `maxResultSizeChars`（默认 **50,000 字符**）就**持久化到磁盘**，上下文只留 **2KB 预览 + 文件路径引用**。妙处在于**信息没丢**——模型想看完整内容随时 Read 回来。这是「**把上下文当缓存、把磁盘当主存**」的思路 |
| Microcompact 的两条路径为什么要分？ | 因为**要不要顾及缓存取决于缓存还热不热**。距上次消息超过阈值 → 缓存本来就过期了 → **直接改消息内容**，没有负担；缓存还热（按工具数量阈值触发）→ 改内容会毁掉缓存 → 走 **`cache_edits` API 块**，**完全不破坏缓存**。两条路径都是**零 API 调用** |
| Context Collapse 的「投影式」是什么意思？ | 创建消息的**只读折叠视图**，**不修改原始消息**——类比数据库的 **View**：底层数据不变，查询时看到过滤/转换后的结果。好处是**可回退**，优于 Autocompact 的不可逆。触发点约 **90%** 上下文利用率，并且**同时抑制 Autocompact**（否则两个机制会互相踩） |
| Autocompact 为什么要「分析-摘要」两阶段？ | 先写 `<analysis>` 做推理草稿，再产出 `<summary>`，**最终只有 `<summary>` 进上下文**。本质是经典的 **Chain-of-Thought Scratchpad**：让模型有地方想清楚该保留什么，但不让思考过程占用宝贵的上下文预算 |
| 压缩之后模型会不会「失忆」？ | 会，所以有**压缩后恢复**：自动恢复**最近 5 个文件**、已激活技能、延迟工具与 MCP 指令等。这是长对话保持连贯性的关键——纯摘要会丢掉「我正在改哪个文件」这类工作状态 |
| Autocompact 的触发条件？失败了怎么办？ | **5 个条件全部满足**才触发：递归守卫（compact 查询自己不能再触发）、三重开关检查（环境变量 + 用户配置）、非 Reactive-only 模式、非 Context Collapse 模式、Token 阈值达标。失败有**熔断器：连续 3 次失败就停止重试**，避免在压缩上无限烧钱 |
| 压缩边界怎么实现的？ | Autocompact 后在消息列表插入 **`compact_boundary` 标记**，后续 API 调用**只发送边界之后的消息**。注意这也意味着压缩会重置消息段的缓存 |

### 顺着上下文组装与 system-reminder 注入追

| 追问 | 答题要点 |
|---|---|
| 为什么用 `<system-reminder>` 这个标签？ | 模型**经过训练知道**这个标签里是系统自动注入的元数据，**不是用户的直接输入**。所以它可以在消息流的**任意位置注入而不混淆「发言者」身份**——这是一条统一的系统信息注入通道，包装 CLAUDE.md、日期、记忆文件、技能列表、延迟工具发现结果、MCP 指令增量 |
| 记忆是怎么进上下文的？ | 作为 `messages` 里的**附件消息**按需注入，不是塞进 system。而且做**去重**（同一文件不重复注入）、有**容量上限**（每会话最多 **60KB**）。技能和 MCP 指令是**增量注入 delta**，只在列表变化时发，不重复发已知内容 |
| 什么是记忆预取？为什么能提速？ | 在**模型生成响应的同时并行搜索**相关记忆文件，把磁盘 I/O 延迟藏在模型的生成时间里。实现上用 `using` 语法确保资源清理 |
| 系统上下文（git 状态等）怎么处理的？ | `getSystemContext` 被 **memoize，每会话只算一次**（保证幂等 + 不破缓存）；**5 个 git 命令并行执行**（`Promise.all`），结果**截断到 2000 字符**；还带一段 **disclaimer 明确告诉模型这是会话开始时的快照、不会实时更新**——这是**主动防幻觉**，否则模型会以为看到的是当前分支状态 |
| 消息发给 API 之前做了什么处理？ | `normalizeMessagesForAPI`，解决内部格式和 API 要求的差异。值得说的几条：**附件向上冒泡**到 tool_result/assistant 之前、过滤 `isVirtual` 虚拟消息、**并行工具调用产生的同 ID 多消息按 message.id 合并**、以及**校验 tool_use / tool_result 配对，为孤儿 block 生成合成对应项**（不配对 API 直接报错，这是 Agent 里非常常见的线上故障） |
| 系统提示词的 override / custom / agent 优先级？ | `buildEffectiveSystemPrompt()` 逐级裁决：**override 直接返回，连 append 都不加**（`/loop`、SDK 嵌入用）→ 协调器模式 → **Proactive 模式下 agent 是追加**（默认提示词已是自主 Agent 身份，再叠领域专长）→ 普通模式下 **agent / custom / default 三者互斥**，有 Agent 时 `--system-prompt` 会被**静默忽略** |

### 顺着工程落地与你的项目追（最容易露馅）

| 追问 | 答题要点 |
|---|---|
| 你自己做 Agent 时怎么设计上下文布局？ | 说一条可执行的规则：**按变化频率从低到高排列，只在尾部追加**。稳定的 system + 工具 schema 在前并打缓存断点；会变的（时间、检索结果、用户偏好）一律往后放或走独立注入消息；**绝不在前缀中间插入内容** |
| 那如果必须更新前面的信息，比如当前时间？ | 两个办法：① **会话开始时锁定一次**（memoize），会话内不更新，并加 disclaimer 告诉模型这是快照；② 如果真要实时，**放到消息数组尾部注入**，让它落在缓存断点之后。绝不放 system |
| 大工具结果（比如全量日志）怎么处理？ | 抄 Level 1：**落盘 + 只留预览 + 给路径**，让模型按需 Read 回来。这比直接截断好，因为**信息可恢复**；也比全量塞进去好，因为不挤占预算 |
| 什么时候该压缩，怎么定阈值？ | 分级：**工具结果超限立即裁剪**（无条件）；到高水位（如 ~90%）做**可回退的折叠**；只在实在不够时做**不可逆的摘要**，且摘要后要**主动恢复工作状态**（最近文件、激活的技能）。精确的水位线与预算公式见 [[编程/agent/上下文与记忆/04 Token 预算管理]] |
| 你怎么知道当前用了多少 Token？每轮都调 count API 吗？ | 不用。用 **API 返回的精确 `usage` 作为锚点**，只对锚点之后的新增消息做**粗略估算（字符数 × 4/3）**，误差从可能的 30%+ 降到通常 **<5%**，且**零额外 API 调用**。这是「精确锚点 + 增量估算」的通用套路 |
| 输出 Token 要预留多少？ | `max_output_tokens` 默认值按覆盖 **p99 输出需求**来定（**p99 ≈ 4,911 tokens**），而不是拍脑袋给个大值；真被 `max_tokens` 截断了才自动升级到 **`ESCALATED_MAX_TOKENS = 64,000`**（MOT 恢复机制）。为什么不该一开始就调大，见 [[编程/agent/上下文与记忆/04 Token 预算管理]] |
| 压缩了之后 server 端的预算怎么对得上？ | **Task Budget 跨压缩结转**：压缩前捕获 `finalContextTokensFromLastResponse()`，压缩后从剩余量里扣掉。因为 **server 不知道压缩前的上下文有多大**，必须由 `taskBudgetRemaining` 告诉它「这些 Token 已经花掉了」，否则续写时预算会算错 |
| 这套东西换到别的模型服务商还成立吗？ | 部分成立。**「前缀稳定 + 尾部增长」是所有前缀缓存的共性**；但**手动缓存控制不是通用能力**——`cache_control` 这类显式断点取决于服务商，比如阿里百炼有 Context Cache 可控，DeepSeek 是自动的、不支持手动控制。所以设计上要把「布局稳定」当第一性原则，把「显式断点」当可选优化 |

### 高频陷阱题

1. **「上下文不够了，直接让模型总结一下历史不就行了？」** → 这就是 Level 5 Autocompact，是**最后手段**而不是第一手段。它要 **fork 子 Agent 真调一次 API**（有延迟有成本）、**不可逆**、**会重置消息段缓存**、还可能丢工作状态所以需要额外的恢复逻辑。前面四级（落盘裁剪、Snip、Microcompact、投影式折叠）都是**零 API 调用**的，能解决绝大多数情况。
2. **「把 CLAUDE.md / 项目规则放进系统提示词最合理吧？」** → **反了**。CLAUDE.md **因项目而异**，放进 system 会让那 50-100K 的 system 块失去**全球共享缓存**资格。正确做法是放 `messages[0]`，用 `<system-reminder>` 包裹，把「因人而异」的代价限制在消息数组里。
3. **「缓存就是把提示词存下来省钱，改改中间内容不影响吧？」** → 影响，而且是**灾难性的**。前缀缓存是**从头逐字节匹配**的，改动位置之后的**全部作废**。所以「在历史中间删掉一个旧工具结果」这种看起来最省 Token 的操作，其实是最贵的——这正是 Microcompact 要么等缓存冷、要么走 `cache_edits` 的原因。
4. **「Context Collapse 既然不改原始消息，那它是不是不破坏缓存？」** → 别这么说。它的卖点是**可回退/可逆**（只读投影视图，原消息完好），明确保证「完全不破坏缓存」的是 **Microcompact 的 `cache_edits` 路径**。把两件好事混为一谈会被追穿。
5. **「压缩机制越多越好，全打开是不是最省？」** → 不是，机制之间会**互相干扰**。所以 Context Collapse 触发时会**主动抑制 Autocompact**，Autocompact 的触发条件里也明确包含「非 Context Collapse 模式」和**递归守卫**（压缩请求自己不能再触发压缩）。多级压缩的难点在**互斥与优先级**，不在单个算法。
6. **「装几个 MCP 工具而已，无非多点 token 吧？」** → 隐藏代价大得多：只要装了**任何一个** MCP 工具，系统提示词缓存就从 `global` **降级为 `org`**，共享面从全球缩到组织内。这也是为什么 MCP 工具要 `defer_loading` 延迟加载、并排在 `cache_control` 断点**之后**。
