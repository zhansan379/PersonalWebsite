# Agent 记忆机制

> 大模型没有记忆——每次 API 调用都是完全独立的。所谓的"记忆"，本质上是代码侧的把戏：把对话历史塞进 messages 数组重新发送。如何塞、塞多少、塞多久，就是 Agent 记忆机制要回答的问题。
>
> **本页定位**：记忆机制的**全局视角与决策框架**。各子机制的深挖在「上下文与记忆」子目录下，本页只给结论与链接，不重复展开。

## 🎯 答题逻辑（骨架）

```
1. 先否定前提：模型没有记忆              ← 证明你知道"记忆"是代码侧的把戏，不是模型能力
   每次 API 调用完全独立 → 所谓记忆 = 把历史重新塞进 messages 数组
2. 点出真正的矛盾：信息保留 vs 成本控制    ← 证明你知道这题的张力在哪，而不是背名词
   历史每轮都要整份重发 → 每多一轮，多付一份输入 Token 的钱和延迟
3. 拆成两个维度：选什么 + 怎么送          ← 证明你有框架
   ├─ 策略层（选什么）：完整历史 / 滑动窗口 / Token 截断 / 摘要压缩 / 混合策略
   └─ 工程层（怎么送）：上下文构建位置 → 分级压缩 → 前缀缓存 → 存储分层
4. 给出生产级默认答案                    ← 证明你落过地，敢给具体选型
   混合策略（早期摘要 + 最近 N 轮完整）+ Redis 热数据设 TTL + MySQL 冷归档
5. 主动暴露坑与边界                      ← 辩证思维，顺手抢占下一个问题
   全量摘要不可逆 / 前缀缓存要字节级一致 / 单纯按时间衰减很粗糙 / 多租户与脱敏
```

**关键心态**：这题考的是**系统设计取舍**，不是术语背诵——面试官在听你有没有"**预算意识**"和"**缓存意识**"这两根弦。只答「用滑动窗口保留最近 N 轮」就收尾，或者把记忆说成模型自带能力、说"上下文不够就摘要"却讲不出触发条件和不可逆性，基本会被判定为没实操过。

**分水岭术语**：**混合策略**、**有效窗口（200K 标称 ≈ 180K 可用）**、**渐进式压缩 / 不可逆**、**前缀缓存字节级一致**、**增量注入（只发 delta）**。这五个词能自然说出来，就说明你算过预算、也被缓存失效坑过。

## 一、问题的本质

### 1.1 模型没有记忆

每次 API 请求都是**完全独立**的。模型不保存任何对话状态——没有上一轮的概念，不知道你是谁，不记得三秒前说了什么。ChatGPT 等产品显得有记忆，只是因为前端把完整对话历史塞进了 messages 数组。

**类比**：大模型像一个极其聪明但患有严重失忆症的专家——每次找他，都需要把之前聊过的内容全部重新说一遍。

### 1.2 记忆的代价

```
单轮对话：
messages = [system, user]

多轮对话（第20轮）：
messages = [system, user₁, assistant₁, user₂, assistant₂, ..., user₂₀]
```

轮次 | 单轮增量 | 累计历史 Token
---|---|---
第 1 轮 | ~200 | 200
第 5 轮 | — | ~1,200
第 10 轮 | — | ~2,500
第 20 轮 | — | ~5,000
第 50 轮 | — | ~10,000+

**每多一轮，就多一份输入 Token 的费用和延迟。**

## 二、要考虑哪些问题

### 2.1 信息保留 vs 成本控制

这是最根本的张力。保留全部历史 = 信息零丢失但 Token 无限膨胀。丢弃历史 = 省钱但模型可能"失忆"，给出矛盾或错误的回答。

核心问题不是"要不要保留"，而是**哪些值得保留、哪些可以丢弃、丢弃后如何补偿**。

### 2.2 长期记忆 vs 短期精度

| | 长期记忆 | 短期记忆 |
|---|---|---|
| 形式 | 摘要、关键事实 | 最近 N 轮完整对话 |
| 优势 | Token 少、覆盖全局 | 细节完整、理解当前语境 |
| 劣势 | 丢失细节、不可回查 | Token 占用大 |

**关键判断**：什么时候把短期记忆"归档"为长期记忆？

触发条件通常有三种：按轮数（每 N 轮）、按 Token 阈值（历史超过 M）、按话题切换（检测到新话题）。

### 2.3 跨会话持久化

用户关闭浏览器、第二天重新打开，之前的对话还在吗？

| 方案 | 效果 | 代价 |
|---|---|---|
| 不持久化 | 每次都是新对话 | 用户需要重复描述问题 |
| 存 Redis 设 TTL | 30 分钟内回来能继续 | 过期后丢失 |
| 存数据库永久保留 | 永远能找回历史 | 存储成本、隐私风险 |

**取舍取决于场景**：客服场景 30 分钟 TTL 够用；个人助理可能需要永久记忆。

### 2.4 多租户隔离

用户 A 的记忆绝不能泄露给用户 B。实现层面：
- 会话 ID 绑定用户 ID
- 查询记忆时强制带用户过滤条件
- 日志和监控数据同样需要隔离

### 2.5 敏感信息

对话中可能出现手机号、身份证、密码、银行卡号。存储记忆时必须处理，三条路径：**脱敏**（掩码）、**加密**（整条消息加密存储）、**不入库规则**（匹配到敏感信息直接不存）。金融、医疗等合规行业对这一点有硬性要求。

> 具体做法与访问控制见 [[02 多轮对话记忆设计#4.2 敏感信息处理]]。

### 2.6 记忆衰减：越旧越不重要？

直觉上，越早的消息越不重要。但实际上：
- 用户在对话开头说的核心目标，可能在 20 轮后仍然关键
- 中间某个确认过的决定，后续操作依赖它
- 单纯按时间丢弃，"最重要的那条"可能恰恰是最早那几条

**单纯按时间衰减是粗糙的**。更理想的做法是提取关键事实（用户意图、已确认决定、未解决问题），而不是一刀切丢弃早期消息。

## 三、解决方案全景

记忆机制有两个维度：**选什么**（策略层——哪些信息值得保留）和**怎么送**（工程层——如何组装、压缩、缓存这些信息）。两者缺一不可。

### 3.1 上下文构建：记忆如何送达模型

选好了要保留什么，下一步是**把它放在请求的什么位置**。放错位置会破坏缓存、混淆角色、白白浪费 Token。

一次 API 请求有三个顶级字段，各有不同的稳定性特征：

```
system ─── 系统提示词（最稳定，跨请求不变）
  ├── 核心指令 + 工具描述 + 安全规则  ← global 缓存，全球共享
  └── 动态内容（用户偏好、MCP 指令）  ← 因用户而异

tools ─── 工具 schema（极少变化）
  └── 最后一个工具标记 cache_control 断点

messages ─── 消息数组（每轮增长，变化最快）
  ├── 记忆文件（按需注入，<system-reminder> 包装）
  ├── 技能列表 / MCP 指令（增量注入，不重复发送已知内容）
  └── 对话历史（用户消息 + 模型回复 + 工具结果）
```

**构建原则**：

| 原则 | 为什么 |
|---|---|
| **稳定内容放前面** | 前缀缓存要求字节级完全一致才能命中。系统提示词最稳定，放最前面最大化缓存收益 |
| **变动内容放后面或附件** | CLAUDE.md、记忆文件、技能列表会变化，放消息数组中作为附件注入，不破坏系统提示词缓存 |
| **增量注入，不重复** | 技能列表只在变化时注入 delta，已知内容不重复发送——省 Token 且不破坏缓存 |
| **用 `<system-reminder>` 隔离** | XML 标签创建语义边界，模型知道这是系统元信息而非用户输入，不会混淆发言者身份 |

详见 [[03 Claude Code 上下文工程#二、上下文构建全景]]；`<system-reminder>` 的实现位点与注入内容清单见 [[Agent 系统设计的三维框架：Prompt-Context-Harness#4.5 Claude Code 的 System Reminder 机制]]。

### 3.2 记忆选择策略：保留什么、丢弃什么

确定了"怎么送"，回到"选什么"——五种策略，从简单到复杂：

| 策略 | 做法 | Token 控制 | 信息保留 | 适用 |
|---|---|---|---|---|
| **完整历史** | 全部保留 | 无 | 完整 | ≤5 轮简单 FAQ |
| **滑动窗口** | 只保留最近 N 轮 | 按轮数 | 丢早期 | 大多数客服 |
| **Token 截断** | 设 Token 上限，从新到旧保留 | 精确控制 | 丢早期 | 消息长度差异大 |
| **摘要压缩** | 用 LLM 压缩早期对话 | 大幅压缩 | 保留关键 | 长对话需记忆 |
| **混合策略** ⭐ | 早期→摘要 + 最近 N 轮→完整 | 精确可控 | 长+短期兼顾 | 生产级推荐 |

每种策略的详细实现、消息结构、Prompt 模板、N 值经验与代码示例见 [[02 多轮对话记忆设计#一、五种记忆策略]]。

### 3.3 Token 预算与上下文压缩

策略选好了，但对话一直在增长——**什么时候触发压缩、用什么手段压、压完怎么恢复**，还要考虑"压缩请求本身会不会也爆了"。

三条结论先记住：

- **可用空间远小于标称窗口**：200K 窗口要先扣掉输出预留，有效上限约 180K；系统提示词、工具定义、用户上下文再占掉一大块。
- **压缩是分级的，不是一刀切**：先用零成本手段（裁剪、清理旧工具结果），实在不行才调 API 做全量摘要；全量摘要**不可逆**，是最后手段。
- **压缩提示词不给长度限制**：只规定"必须覆盖哪些内容"，因为隐含目标是**信息保真 > 长度压缩**。

**五级渐进式压缩速查**：

| 级别 | 手段 | 成本 | 可逆 | 触发条件 |
|---|---|---|---|---|
| **Level1** | Tool Result 预算裁剪：大结果写磁盘，上下文只留预览 | 零延迟、零 API | ✓ | 工具结果超字符阈值 |
| **Level2** | History Snip：从历史消息中剪裁冗余部分 | 零 API | ✓ | Feature-gated |
| **Level3** | Microcompact：清理旧工具结果，热缓存时不破坏前缀缓存 | 零 API | ✗ | 时间间隔或工具数量超阈值 |
| **Level4** | Context Collapse：投影式折叠，创建只读折叠视图，不修改原始消息 | 零 API | ✓ | 高上下文利用率 |
| **Level5** | Autocompact：fork 子 Agent 生成整个对话摘要 | 1 次 API | ✗ | 接近有效窗口上限 |

> 精确的水位线数值与常量、有效窗口计算公式、Autocompact 的 fork 原理与熔断机制、压缩提示词的完整设计，见 [[04 Token 预算管理]] 与 [[03 Claude Code 上下文工程#四、五级压缩流水线]]。
>
> ⚠️ 待核对：[[Agent 系统设计的三维框架：Prompt-Context-Harness#3.3 Claude Code 的三层压缩（最精细）]] 给出的是**三层**分类法（MicroCompact / Session Memory Compact / Full LLM Compact），与本页的五级流水线不兼容，疑似源材料版本不同，需回 raw 核对后统一。

### 3.4 前缀缓存：让重复计算变免费

上下文构建和压缩解决了"送什么"的问题，但每次请求服务端都要对 50-200K token 的输入做 KV Cache 计算。如果每次从头算，延迟和成本都不可接受。

**前缀缓存原理**：服务端记住上一次请求的 KV Cache 结果，下次请求前缀一致时直接复用，只处理新增部分。硬约束是——**前缀必须字节级完全一致才能命中**，任何一个字节的变化都会导致该位置之后的所有缓存失效。

**对记忆设计的实践启示**：

- 保持对话连续（普通用户缓存 TTL = 5 分钟，离开太久缓存过期）
- 减少 MCP 工具安装（会缩小缓存共享范围，见下方决策表第 6 行）
- 固定模型，不要中途切换（不同模型缓存空间独立）

> 三层缓存链结构、四层防御手段、缓存断裂检测见 [[03 Claude Code 上下文工程#六、前缀缓存策略]]；三种分块模式与 TTL 决策的机制层解释见 [[05 System Prompt 缓存与动态组装#六、缓存策略：三种分块模式]]。

### 3.5 存储方案

**推荐**：Redis 做主存储（热数据，设 TTL）+ MySQL 做归档（冷数据，对话结束后异步写入）；开发调试用内存即可。

> 内存 / Redis / MySQL 在性能、持久化、分布式、过期清理、实现复杂度上的完整对比见 [[02 多轮对话记忆设计#三、存储方案]]。

## 四、设计决策框架

设计记忆机制时，需要在七个维度上做决策。每个维度互相关联——比如选了"摘要压缩"策略，就要配套考虑"摘要请求本身会不会爆上下文"。

| 决策维度         | 你的选项                                                        | 选型依据                                                                      | 踩坑提醒                                                     |
| ------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------- |
| **1. 记忆策略**  | 完整历史 / 滑动窗口 / Token截断 / 摘要 / 混合                             | ≤5轮→完整历史；宽话题→滑动窗口；深长线→混合策略（摘要+最近N轮）                                       | 混合策略看似万能，但摘要压缩本身要调 API，低频对话场景成本反而不如滑动窗口                  |
| **2. 上下文构建** | 放在 system / messages 附件 / 增量注入                              | 稳定内容放 system（享受缓存）；变动内容放 messages 附件（不破坏缓存）；频繁变动内容增量注入（只发 delta）          | 把 CLAUDE.md 放在 system 里会破坏全球缓存——所有用户都得各自缓存一份相同内容         |
| **3. 输出预留**  | 8K / 64K / 自定义                                              | 默认值覆盖 p99 需求；被截断时自动升级重试                     | 设太大浪费服务端 slot 资源，设太小模型被频繁截断。不要手贱改成 32K"以防万一"             |
| **4. 压缩选择**  | Microcompact / AutoCompact / Context Collapse / 手动 /compact | Microcompact 成本最低先上；Autocompact 是最后手段；Context Collapse 可逆、优先于 Autocompact | Autocompact 不可逆——原始消息被摘要替换后无法恢复。连续失败会熔断，不会无限重试        |
| **5. 压缩提示词** | 给长度限制？给内容要求？                                                | **不给长度限制，给内容覆盖要求**——告诉模型"必须覆盖什么"，不要求"缩到多短"                         | 加长度限制会导致模型为了凑字数而丢弃关键信息。信息保真 > 长度压缩                       |
| **6. 缓存策略**  | global / org / 不缓存                                          | 无 MCP 工具→系统提示词静态部分用 global（全球共享）；有 MCP→降级为 org                            | 装一个 MCP 工具就从 global 降为 org，缓存共享范围从全球缩到组织。**精简 MCP 工具安装** |
| **7. 存储**    | 内存 / Redis / Redis+MySQL                                    | 开发→内存；生产→Redis 热数据 TTL + MySQL 冷数据归档；合规→加密+脱敏+访问日志                        | Redis 设 TTL 但别太短——用户去倒杯水回来对话就丢了体验很差。30 分钟起步              |

### 决策路径速查

```
记忆策略怎么选？
  ≤5 轮 → 完整历史，到此为止
  >5 轮，宽话题 → 滑动窗口或 Token 截断
  >5 轮，深长线 → 混合策略（摘要 + 最近 N 轮）

上下文怎么放？
  稳定不变 → system（prefix cache 最大化）
  因项目而异 → messages 附件，不碰 system
  频繁变动 → 增量注入，只发 delta

压缩什么时候触发？
  高利用率     → Context Collapse（可逆，优先）
  接近有效上限 → Autocompact（不可逆，最后手段）
  连续失败     → 熔断，提示用户手动 /compact

缓存 TTL？
  普通用户 5 分钟 → 别中断对话超过 5 分钟，回来要重建
```

## ⚡ 30 秒速答版

> 大模型本身**没有记忆**，每次 API 调用都是完全独立的；所谓的记忆就是代码侧把对话历史重新塞进 **messages** 数组。所以这题的本质是**信息保留和成本控制的张力**——历史每轮都要整份重发，每多一轮就多付一份输入 Token 和延迟。
>
> 我会分两个维度回答：**选什么**和**怎么送**。选什么是策略层，从完整历史、滑动窗口、Token 截断、摘要压缩到**混合策略**——早期对话压成摘要、最近 N 轮保留完整，生产级一般就选混合。
>
> 怎么送是工程层：稳定内容放 **system** 吃**前缀缓存**，会变的（CLAUDE.md、记忆文件）放 messages 附件并用 `<system-reminder>` 隔离，频繁变的做**增量注入只发 delta**；上下文涨上来走**渐进式压缩**——先零成本手段裁剪工具结果、清理旧结果，最后才调 API 做全量摘要，因为全量摘要**不可逆**。
>
> 还要注意标称 200K 窗口扣掉输出预留后**有效只有约 180K**。存储上 Redis 存热数据设 TTL、MySQL 归档冷数据，再加**多租户隔离**和**敏感信息脱敏**。

## 💬 对方可能追问的问题

### 顺着"为什么需要记忆"追（概率最高）

| 追问 | 答题要点 |
|---|---|
| 模型真的完全没记忆？那 ChatGPT 的"记忆"功能是什么？ | 模型层**完全无状态**，不知道你是谁、不记得上一轮。产品层的"记忆"是把关键事实抽出来存库，下次请求再**注入** system 或 messages——本质仍是代码侧注入，不是更新权重 |
| 多轮对话的 Token 是怎么涨的？ | 单次请求随历史**线性**增长，但因为每轮都重发全部历史，整场会话的累计花费是前缀的重复求和。量级参考：第 5 轮约 1.2K、第 20 轮约 5K、第 50 轮 1 万+ |
| 为什么不能简单"越旧越先丢"？ | 单纯按时间衰减很粗糙：开头说的核心目标 20 轮后仍关键，中间确认过的决定后续操作还依赖它。正确做法是**提取关键事实**（用户意图、已确认决定、未解决问题），而不是一刀切丢早期消息 |
| 什么时候把短期记忆"归档"成长期记忆？ | 三种触发条件：按**轮数**（每 N 轮）、按 **Token 阈值**（历史超过 M）、按**话题切换**（检测到新话题）。长期记忆是摘要/关键事实，Token 少但丢细节、不可回查；短期是最近 N 轮完整对话，细节全但占 Token |

### 顺着记忆策略选型追

| 追问 | 答题要点 |
|---|---|
| 五种策略你怎么选？ | ≤5 轮的简单 FAQ→完整历史；话题宽、不需要深记忆→滑动窗口；消息长度差异大→按 Token 截断；长对话且要记住前情→摘要压缩；生产级默认→**混合策略**（早期摘要 + 最近 N 轮完整） |
| 为什么按 Token 截断比按轮数更好？ | 轮数不等于长度——一条粘贴进来的日志可能顶十轮闲聊。设 Token 上限、从新到旧保留，才能**精确控制**预算 |
| 混合策略是不是万能？ | ❌ 摘要压缩本身要**调一次 API**。低频对话场景这笔成本可能反而高于直接用滑动窗口，所以要按对话频次和深度选，别默认上混合 |
| 摘要的提示词要不要限制长度？ | **不给长度限制，只给内容覆盖要求**——告诉模型"必须覆盖哪些内容"，不要求"缩到多短"。加长度限制会让模型为凑字数丢关键信息，隐含目标是**信息保真 > 长度压缩**（五种策略的实现细节、Prompt 模板与 N 值经验见 [[编程/agent/上下文与记忆/02 多轮对话记忆设计]]） |

### 顺着上下文构建与压缩追（最容易露馅）

| 追问 | 答题要点 |
|---|---|
| 记忆到底放 system 还是 messages？ | 按**稳定性**分层：核心指令 / 工具描述 / 安全规则最稳定 → system，享受缓存；CLAUDE.md、记忆文件、技能列表会变 → messages 附件注入；频繁变动 → **增量注入只发 delta**，不重复发送已知内容 |
| 把 CLAUDE.md 放进 system 有什么问题？ | 破坏**全球缓存**——它因项目而异，一旦进 system，所有用户都得各自缓存一份相同结构的前缀，共享收益归零 |
| 为什么注入的记忆要用 `<system-reminder>` 包起来？ | XML 标签创建**语义边界**，让模型知道这是系统元信息而非用户输入，不会**混淆发言者身份** |
| 200K 窗口就能塞 200K 历史吗？ | ❌ 先扣**输出预留**，有效上限约 **180K**；再扣系统提示词、工具定义、用户上下文，真正留给历史的远小于标称值。输出预留也不要手贱调大——设太大浪费服务端 slot、挤占输入，设太小频繁被截断 |
| 压缩为什么要分级？说说层次 | 原则是**先零成本、后花钱**：L1 Tool Result 预算裁剪（大结果写磁盘、上下文只留预览，可逆）→ L2 History Snip → L3 Microcompact（清旧工具结果，热缓存时**不破坏前缀缓存**）→ L4 Context Collapse（只读折叠视图、不改原始消息、**可逆**）→ L5 Autocompact（fork 子 Agent 做全量摘要，1 次 API、**不可逆**，最后手段，连续失败会**熔断**并提示手动 /compact） |
| 前缀缓存的硬约束是什么？对记忆设计什么启示？ | 前缀必须**字节级完全一致**才命中，任何一个字节变化会让该位置之后的缓存全部失效。启示：保持对话连续（普通用户 TTL 约 5 分钟）、**精简 MCP 工具安装**（装了会从 global 缓存降级为 org，共享范围从全球缩到组织）、固定模型不要中途切换 |

### 顺着存储、合规与你的项目追

| 追问 | 答题要点 |
|---|---|
| 生产上记忆存哪里？ | **Redis 做主存储**放热数据并设 TTL + **MySQL 做归档**放冷数据，对话结束后**异步**写入；开发调试用内存就够 |
| TTL 设多久？ | **30 分钟起步**。太短会出现"用户去倒杯水回来对话就没了"；客服场景 30 分钟够用，个人助理可能需要永久记忆，代价是存储成本和隐私风险 |
| 多租户怎么保证记忆不串号？ | 三件事：会话 ID **绑定用户 ID**、查询记忆时**强制**带用户过滤条件、日志和监控数据同样做隔离 |
| 对话里出现手机号、银行卡号怎么处理？ | 三条路径：**脱敏**（掩码）、**加密**（整条消息加密存储）、**不入库规则**（命中敏感规则直接不存）。金融、医疗等合规行业是硬性要求 |
| 你项目里具体怎么设的？ | 必须给得出**具体选型 + 理由**：记忆策略与 N 值、归档触发条件（轮数 / Token 阈值 / 话题切换）、存储分层与 TTL、以及压缩之后出过什么问题（比如摘要丢了关键决定）怎么补的——这一问是区分"看过文章"和"上过线"的地方 |

### 高频陷阱题

1. **「上下文窗口越来越大，记忆管理是不是就不需要了？」** → ❌ 不是。标称 200K 有效只有约 **180K**，而且每轮都要整份重发历史，窗口变大只是让你**更贵更慢**，成本和延迟的矛盾不会消失。
2. **「上下文不够就上摘要压缩」** → 顺序错了。摘要要**调 API 有成本**，而且全量摘要**不可逆**（原始消息被替换后无法恢复）。正确顺序是先零成本手段（裁剪工具结果、清旧结果、可逆的折叠），Autocompact 是**最后一级**。
3. **「越旧的消息越该先丢」** → ❌ 直觉是错的。最早那几条往往是核心目标，中途确认过的决定后续还在依赖，按时间一刀切正好丢掉最重要的。应该按**关键事实**保留而不是按时间。
4. **「记忆是模型自己记住的吧？」** → ❌ 模型**完全无状态**。所有"记忆"都是代码侧把历史或抽取出的事实重新注入 messages，模型权重从不改变。
5. **「存进 Redis 就算持久化了吗？」** → ❌ 设了 TTL 的 Redis 是**易失的热存储**，过期即丢。要永久找回必须 MySQL 归档，同时要承担存储成本和隐私合规风险。
6. **「Context Collapse 和 Autocompact 差不多，先上哪个都行？」** → ❌ 关键差别是**可逆性**：Context Collapse 只做投影式折叠、不修改原始消息，所以**优先**；Autocompact 不可逆，只在接近有效窗口上限时才用。
