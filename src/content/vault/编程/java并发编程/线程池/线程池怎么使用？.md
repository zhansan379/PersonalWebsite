# 线程池怎么使用？

> 一句话概述：线程池核心作用是**复用线程、控制并发数**，避免频繁创建销毁线程带来的开销。使用分两个层次——**简单场景**用 `Executors` 工具类一条快速建池（共 5 种快捷线程池：**Fixed 固定数量 / Cached 弹性无限 / Single 单线程保序 / Scheduled 定时周期**，但多为**无界队列 + 线程数失控**，阿里手册**明令禁止**，复杂业务应**手动 `new ThreadPoolExecutor`** 配 7 参数精准控制 + 有界队列 + 有意义的线程名 + 主动监控）。提交任务有两种：`submit`（可提交 Callable 拿返回值、能捕获异常）和 `execute`（只能跑 Runnable、异常直接抛）。定时/周期任务用 `ScheduledExecutorService` 的 `schedule` 族。用完要 `shutdown` 关闭，防线程泄漏。

## 一、这是什么

这是"线程池怎么用"的上手篇，与"参数怎么设"（见相关页面）互补——本篇讲**流程与 API**，参数篇讲**每个数字怎么定**。核心脉络：建池（Executors / ThreadPoolExecutor 两档）→ 提交（submit / execute 两种）→ 关闭（shutdown / shutdownNow）。

## 二、核心内容：怎么用

### 第 1 步 · 建池：简单场景用 Executors

`Executors` 工具类快速创建，适合简单场景不用手配复杂参数。比如固定 3 个线程的池，处理一批异步任务、兼顾返回值：

```java
// 创建固定3个线程的线程池
ExecutorService fixedThreadPool = Executors.newFixedThreadPool(3);

// 提交Runnable任务 无返回值
for (int i = 0; i < 5; i++) {
    int taskNum = i;
    fixedThreadPool.submit(() -> {
        System.out.println("当前线程 " + Thread.currentThread().getName() + " 处理任务 " + taskNum);
        try {
            Thread.sleep(1000); // 模拟任务执行耗时
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    });
}

// 提交Callable任务 有返回值
Future<Integer> future = fixedThreadPool.submit(() -> {
    Thread.sleep(500);
    return 100 + 200; // 任务返回结果
});

// 获取Callable任务的返回值 会阻塞直到任务完成
try {
    Integer result = future.get();
    System.out.println("任务返回结果: " + result);
} catch (Exception e) {
    e.printStackTrace();
}

// 任务执行完后关闭线程池 避免资源泄露
fixedThreadPool.shutdown();
```

> ⚠️ **Executors 快捷方法的隐患**：如 `newCachedThreadPool` 可能创建大量线程导致 OOM；`newScheduledThreadPool` 的 `maximumPoolSize` 为 `Integer.MAX_VALUE` 且内部用**无界 `DelayedWorkQueue`**，任务堆积时可能 OOM。**复杂业务场景更推荐 ThreadPoolExecutor 手动配置。**

### 补充 1.1 · Executors 的五种快捷线程池

`Executors` 一共提供 **5 个快捷方法**，每一种其实都只是**特定参数组合的 ThreadPoolExecutor**：

| 快捷方法                                 | 类型                                | 核心/最大线程数                    | 工作队列                                                 | 特点与坑                                                                                                        |
| :----------------------------------- | :-------------------------------- | :-------------------------- | :--------------------------------------------------- | :---------------------------------------------------------------------------------------------------------- |
| `newFixedThreadPool(n)`              | **FixedThreadPool**               | 核心=最大=n（数量固定）               | **无界 `LinkedBlockingQueue`(容量 `Integer.MAX_VALUE`)** | 线程数从 0 增到 n 后**固定**，超出处理能力的任务全丢进队列等待；一旦消费跟不上生产，无界队列**无限堆积 → OOM**（阿里手册禁用首要对象）                               |
| `newCachedThreadPool()`              | **CachedThreadPool**              | 核心=0 / 最大=MAX_VALUE（理论上无上限） | **`SynchronousQueue`（容量 0）**                         | 只**中转/传递**不存储，每来一个任务若无空闲线程就**立即新建线程**；空闲线程 60s 回收。做法：**quick hire 高并发瞬时大量提交会狂建成百上千线程，直接资源耗尽 → OOM**（阿里手册禁用） |
| `newSingleThreadExecutor()`          | **SingleThreadExecutor**          | 唯一 1 个                      | 无界 `LinkedBlockingQueue`                             | 只用唯一线程执行，一旦异常会**自动新建一个线程接续**；单线程天然保证**按提交顺序执行**，适合任务须严格按序的场景（多线程并行池不保证顺序）                                   |
| `newScheduledThreadPool(n)`          | **ScheduledThreadPool**           | n 个核心                       | **无界 `DelayedWorkQueue`(MAX_VALUE)**                 | 支持**定时/周期**执行（如每隔 10s 执行一次）；maximum=MAX_VALUE 且无界队列，任务堆积**也可能 OOM**                                         |
| `newSingleThreadScheduledExecutor()` | **SingleThreadScheduledExecutor** | 唯一 1 个                      | 无界 `DelayedWorkQueue`                                | `ScheduledThreadPool` 的特例（单线程版定时池）                                                                          |

> 一句话区分：**Fixed** 固定数量、**Cached** 弹性无限、**Single** 单线程保序、**Scheduled** 定时周期（+Single 版本）。阿里手册禁用的共性根源 = **无界队列 + 线程数失控** → 两种 OOM。

### 补充 1.2 · 为什么阿里手册禁止 Executors，要求手动 new ThreadPoolExecutor

`Executors` 是帮我们快速建池的"捷径"，但《阿里巴巴 Java 开发手册》**明令禁止**用它创建线程池，而应**手动 `new ThreadPoolExecutor`**——这条铁律背后是大量生产事故（最典型就是上面 Fixed/Cached 的 OOM）。理由有三：

1. **参数要按自己的场景定**：核心线程数、最大线程数、线程回收策略、工作队列类型、拒绝策略，都应根据业务并发情况评估，一般要求**有界队列 + 可控线程数**，确保线程池行为符合需求——`Executors` 的"默认参数"往往是坑。
2. **一定要起有意义的线程名**：任何自定义线程池都应指定有意义的名字（`threadFactory`）。查问题时总要抓**线程栈**（线程暴增/死锁/CPU 占满/异常），有语义的线程名一眼就能定位是哪个池出问题。
3. **主动监控线程池状态**：线程池"任劳任怨、默默无闻"，除非触发拒绝策略，否则压力再大都不抛异常。若能提前观察到**队列积压**、**线程数快速膨胀**，往往能提早发现问题、避免故障扩大。

## 第 2 步 · 建池：复杂业务用 ThreadPoolExecutor

手动创建需指定 **7 个核心参数**，理解它们才能用好。比如适合 **IO 密集型**任务的池（线程数可多些，一般取 CPU 核数×2）：

```java
// 获取CPU核心数 用于合理设置线程数
int corePoolSize = Runtime.getRuntime().availableProcessors() * 2;

// 手动配置线程池
ThreadPoolExecutor threadPool = new ThreadPoolExecutor(
    corePoolSize, // 核心线程数 线程池长期维持的最小线程数
    corePoolSize * 2, // 最大线程数 线程池能容纳的最多线程数
    60L, // 空闲线程存活时间 超过核心线程数的空闲线程 多久后销毁
    TimeUnit.SECONDS, // 存活时间单位
    new ArrayBlockingQueue<>(100), // 任务阻塞队列 核心线程忙时 新任务存这里
    Executors.defaultThreadFactory(), // 线程创建工厂 用于设置线程名 优先级等
    new ThreadPoolExecutor.AbortPolicy() // 拒绝策略 队列满且线程数达最大时 如何处理新任务
);

// 提交任务的两种方式 这里用execute提交Runnable（无返回值 不能捕获异常）
threadPool.execute(() -> {
    System.out.println("IO任务执行中 " + Thread.currentThread().getName());
    // 模拟IO操作 比如数据库查询 网络请求
});

// 关闭线程池 推荐用shutdown 等待已提交任务完成后再关闭
threadPool.shutdown();
// 若需要强制关闭 可调用shutdownNow 会中断正在执行的任务 返回未执行的任务
// List<Runnable> unExecutedTasks = threadPool.shutdownNow();
```

**关键细节：**
- **拒绝策略有四种**：默认 `AbortPolicy`（直接抛异常）、`CallerRunsPolicy`（让提交任务的主线程自己执行，缓解压力）、`DiscardPolicy`（直接丢弃新任务）、`DiscardOldestPolicy`（丢弃队列里最旧任务再提交新任务）。要根据业务选——**核心业务不能丢任务，就别用 Discard 相关策略**。

### submit 与 execute 的区别

`submit` 能提交 `Callable` 有返回值，还能通过 `Future` **捕获任务执行中的异常**；`execute` 只能提交 `Runnable`，异常会直接抛出。例如捕获能力：

```java
// submit捕获异常
Future<?> future = threadPool.submit(() -> {
    int i = 1 / 0; // 模拟异常
});
try {
    future.get();
} catch (ExecutionException e) {
    System.out.println("任务执行异常: " + e.getCause()); // 捕获到算术异常
}
```

### 补充 · 定时任务调度：ScheduledExecutorService

要定时/周期执行任务时，用 `ScheduledExecutorService`——Java 并发包中**增强版的定时任务调度管理器**，继承自 `ExecutorService`，功能是**给定延迟后执行任务、或周期性重复执行任务**。相比传统 `Timer` 它是首选工具。

**核心特性与优势：**
- **基于线程池，性能更优**：背后是线程池，能高效管理和复用线程；一个任务执行异常**不会影响其他任务的调度**，而 `Timer` 可能因此整体停止。
- **调度方式更灵活**：支持单次延迟、固定频率、固定延迟等多种模式。
- **线程安全**：相比非线程安全的 `Timer`，更适合现代多线程复杂应用。

**核心调度方法（三选一）：**

| 方法 | 含义 | 说明 |
| :--- | :--- | :--- |
| `schedule(task, delay, unit)` | **延迟执行一次** | 指定延迟后执行一次 |
| `scheduleAtFixedRate(task, initDelay, period, unit)` | **固定频率执行** | 初始延迟后按固定间隔 `period` 重复——**无论任务执行多久**，下次都按固定时间表启动 |
| `scheduleWithFixedDelay(task, initDelay, delay, unit)` | **固定延迟执行** | 下次在**上一次执行结束后**再等固定 `delay` 才开始 |

> 区分：**FixedRate = 按"开始时刻"排班**（到点就启，可能并发堆积）；**FixedDelay = 按"结束时刻"顺延**（串行不重叠，任务慢则整体拉长）。

**创建与使用：** 用 `Executors.newScheduledThreadPool(n)` 创建：

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2); // 2线程的调度池

Runnable task = () -> System.out.println("任务执行，时间：" + System.currentTimeMillis());

scheduler.schedule(task, 3, TimeUnit.SECONDS);            // 延迟3秒执行一次
scheduler.scheduleAtFixedRate(task, 1, 5, TimeUnit.SECONDS);   // 延迟1s后每5s一次(固定频率)
scheduler.scheduleWithFixedDelay(task, 1, 2, TimeUnit.SECONDS); // 延迟1s后,每次执行完隔2s再执行(固定延迟)

// 合适的时机关闭线程池
// scheduler.shutdown();
```

**重要注意事项：**
1. **相对时间**：所有延迟/周期都是**相对时间**（如"5秒后"），而非绝对时刻（如"10:00:00 执行"）；要调度到未来某日期，需计算当前与目标的时间差。
2. **任务异常**：周期任务里若抛出**未捕获异常**，该任务的后续调度会被取消——所以任务内部要妥善处理异常。
3. **资源释放**：不用时调 `shutdown()`/`shutdownNow()` 关闭，释放线程（与上节关闭纪律一致）。

> ⚠️ 与前面 Executors 隐患呼应：`newScheduledThreadPool` 的 `maximumPoolSize` 为 `Integer.MAX_VALUE` 且内部用**无界 `DelayedWorkQueue`**，任务堆积时也可能 OOM，复杂场景仍建议手动 `ThreadPoolExecutor` 配定时参数。

## 三、核心原则 / 使用纪律

- **不能创建后不关闭**：否则线程池一直占用线程，导致**线程泄漏**，JVM 无法退出。
- **任务队列容量要合理**：太大可能导致**内存溢出**，太小容易触发**拒绝策略**。
- **线程数按任务类型调整**：**CPU 密集型**（复杂计算）线程数不宜过多，一般和 CPU 核心数相当，避免线程切换开销；**IO 密集型**可多设些线程，因为线程大部分时间在等待 IO 完成。

## 四、如何应用 / 面试怎么讲

**加分表达：**
- 先给"**建池 → 提交 → 关闭**"三段式流程，回答不散；再用一档对比把 `Executors`（简单但可能 OOM）和 `ThreadPoolExecutor`（7 参数可控）区分开——体现"知道快捷方式和它的代价"。
- 主动点出 **submit vs execute** 的核心差异（能否返回结果、能否捕获异常），并配一个"`get()` 抛 `ExecutionException` 包装任务内异常"的例子——这是多数人答不上来的亮点。
- 谈关闭要带上**纪律**（不 shutdown 会线程泄漏）和 **shutdown vs shutdownNow 选型**，串起生命周期闭环。

**追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| Executors 快捷方法有什么坑？ | newCachedThreadPool 可致大量线程 OOM；newFixedThreadPool/newScheduledThreadPool 用无界队列任务堆积可致 OOM；故复杂业务建议手动 ThreadPoolExecutor |
| submit 和 execute 区别？ | submit 可提交 Callable 有返回值、返回 Future 可 get 捕获 ExecutionException 包的任务内异常；execute 只能跑 Runnable、异常直接抛 |
| 线程池 7 参数是哪 7 个？ | corePoolSize、maximumPoolSize、keepAliveTime、时间单位、工作队列、线程工厂、拒绝策略 |
| 为什么推荐 shutdown 而非 shutdownNow？ | shutdown 让已提交任务跑完再停，优雅；shutdownNow 强中断且只能靠 interrupt（可能无效），返回未执行任务需妥善处理 |
| 四种拒绝策略怎么选？ | AbortPolicy(默认抛异常)/CallerRuns(调用线程执行)/Discard/DiscardOldest；核心业务不容丢任务就别用 Discard 系列 |
| 不关闭线程池会怎样？ | 常驻线程不释放，造成线程泄漏，JVM 无法正常退出（非守护线程） |
| CPU 密集和 IO 密集线程数？ | CPU 密集≈核数（防线程切换开销）；IO 密集=核数×2 或更高（大部分时间在等 IO） |
| Future.get() 为什么能捕获任务内异常？ | 任务抛出的异常被 Future 包装成 `ExecutionException`，`get()` 抛出来可 `getCause()` 拿到原始异常 |
| 定时任务怎么调度？ | 用 `ScheduledExecutorService`：`schedule` 延迟一次 / `scheduleAtFixedRate` 按开始时刻固定频率（可能堆积并发） / `scheduleWithFixedDelay` 按结束时刻顺延（串行不重叠） |
| FixedRate 和 FixedDelay 区别？ | FixedRate 按"开始时刻"排班到点就启、任务慢会排队；FixedDelay 按"上次结束"顺延、串行不重叠 |
| 周期任务抛异常会怎样？ | 抛未捕获异常后该任务后续调度被取消，须在任务内自行 catch |
