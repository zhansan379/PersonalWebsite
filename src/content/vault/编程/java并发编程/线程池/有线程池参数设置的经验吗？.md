# 有线程池参数设置的经验吗？

> 一句话概述：线程池参数核心是**五件套**——`corePoolSize`（核心线程数）、`maximumPoolSize`（最大线程数）、`keepAliveTime`（非核心线程空闲回收）、**工作队列**、**拒绝策略**。起点是 **corePoolSize 按类型估算**：CPU 密集 → CPU核数+1（避免过多线程抢 CPU），IO 密集 → CPU核数×2（或更高，看 IO 等待时间）；再由具体业务场景调整队列与拒绝策略。

## 一、这是什么

这是一套**根据实际业务场景给 ThreadPoolExecutor 配参数的经验**，通常考的是：corePoolSize 怎么估、什么时候用有界/无界队列、不同业务在"队列缓冲"还是"直接扩容线程"之间如何取舍、拒绝策略怎么选。下面先给估算原则，再用**三种典型场景**把完整参数串起来。

## 二、核心内容

### corePoolSize 的估算经验

先把任务类型分清楚，才能定线程数：

**CPU 密集型**——任务的大部分时间在**占用 CPU** 做逻辑运算/数学计算/内存处理，几乎不等待外部资源，CPU 使用率一直很高。常见例子：
- 大规模矩阵运算、机器学习模型推理。
- 音视频编解码（转码）。
- 复杂的数学公式计算（如蒙特卡洛模拟）。
- 使用 Stream 对大 List 进行 map/filter 复杂聚合计算。
- 数据加密/解密（如 AES/RSA 非对称加解密）。

**IO 密集型**——任务的大部分时间在**等待网络响应 / 磁盘读写**，这段时间里 CPU 处于空闲等待状态（`WAITING`/`TIMED_WAITING`）。常见例子：
- 微服务调用：Service A 调用 Service B 的 RESTful API / Dubbo / gRPC。
- 数据库操作：执行复杂 SQL 查询（MySQL/PostgreSQL），等待索引检索和网络传输数据。
- 缓存操作：批量查询 Redis 或 Memcached。
- 文件操作：读取/写入大型本地文件（如 Excel 导入导出）。
- 消息消费：Kafka/RabbitMQ 消费者拉取并处理消息，但处理逻辑含外部 API 调用。

两种类型的估算：
- **CPU 密集型**：`corePoolSize = 可用CPU核数 + 1`——避免过多线程竞争 CPU（加 1 是为应对偶尔的阻塞/页面缺失导致的一个线程挂起，保证 CPU 不打满或空转）。
- **IO 密集型**：`corePoolSize = 可用CPU核数 × 2`（或更高）——IO 等待时线程会让出 CPU，可开更多线程并发等待，吞吐更高；具体看 IO 等待时间占比。

### 三种典型场景配置对比

| 场景 | 特点 | core/max | 队列 | 回收 | 拒绝策略 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **电商瞬时高并发** | 瞬时高并发、任务处理时间短 | 16 / 32 | `SynchronousQueue`（不缓存任务） | 非核心 10s 回收 | `AbortPolicy`（直接拒绝） |
| **后台数据处理** | 稳定流量、任务长（秒级）、容延迟 | 8 / 8（禁扩容） | `ArrayBlockingQueue`（有界 1000） | 不回收 | `CallerRunsPolicy`（调用线程执行） |
| **微服务 HTTP 请求** | IO 密集型、依赖下游 RT | 16 / 64 | `LinkedBlockingQueue`（有界 200） | 非核心 60s 回收 | 自定义（重试/降级） |

### 场景一：电商（瞬时高并发、任务短）

```java
new ThreadPoolExecutor(
    16, // corePoolSize = 16（假设8核CPU × 2）
    32, // maximumPoolSize = 32（突发流量扩容）
    10, TimeUnit.SECONDS, // 非核心线程空闲10秒回收
    new SynchronousQueue<>(), // 不缓存任务, 直接扩容线程
    new AbortPolicy()       // 直接拒绝, 避免系统过载
);
```

**说明**：使用 `SynchronousQueue` 确保任务直达线程、避免队列延迟；拒绝策略快速失败，前端返回"活动火爆"提示，结合降级策略（如缓存预热）。

### 场景二：后台数据处理（稳定流量、任务长、容延迟）

```java
new ThreadPoolExecutor(
    8, // corePoolSize = 8（8核CPU）
    8, // maximumPoolSize = 8（禁止扩容, 避免资源耗尽）
    0, TimeUnit.SECONDS, // 不回收线程
    new ArrayBlockingQueue<>(1000), // 有界队列, 容量1000
    new CallerRunsPolicy()  // 队列满后由调用线程执行
);
```

**说明**：固定线程数避免资源波动，队列缓冲任务，拒绝策略兜底；配合监控告警（如队列使用率 > 80% 触发扩容）。

### 场景三：微服务 HTTP 请求（IO 密集、依赖下游 RT）

```java
new ThreadPoolExecutor(
    16, // corePoolSize = 16（8核 × 2）
    64, // maximumPoolSize = 64（应对慢下游）
    60, TimeUnit.SECONDS, // 非核心线程空闲60秒回收
    new LinkedBlockingQueue<>(200), // 有界队列容量200
    new CustomRetryPolicy() // 自定义拒绝策略（重试或降级）
);
```

**说明**：根据下游 RT（响应时间）调整线程数，队列防止瞬时峰值；自定义拒绝策略将任务暂存 Redis，异步重试。

## 三、如何应用 / 面试怎么讲

**加分表达：**
- 张口先给 corePoolSize 的**两种估算口诀**（CPU 密集 = 核数+1、IO 密集 = 核数×2），体现"有方法而不只是背参数"。
- 会解释**队列 vs 扩线程**的取舍：任务要快并发高 → 用不缓存队列直接开线程（如 SynchronousQueue）；任务长、允许排队 → 用有界队列缓冲，避免创建过多线程。
- 主动谈**拒绝策略的兜底思路**：快速失败 vs 调用线程执行 vs 自定义降级，配合监控告警形成闭环，是这道题的最高分表达。
- 记住**五件套 + 三场景**就能覆盖绝大部分线程池参数题。

**追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| corePoolSize 为啥 CPU 密集核数+1？ | 避免过多线程抢 CPU；+1 应付一个线程偶发阻塞/缺页导致的 CPU 空转 |
| IO 密集为什么核数×2？ | IO 等待时线程释放 CPU，可多开线程并发等待，吞吐更高；具体看 IO 等待占比 |
| 什么时候用无容量队列（SynchronousQueue）？ | 任务处理极快、要立刻被线程执行、不想排队积压；配合扩容与快速拒绝 |
| maximumPoolSize = corePoolSize 是什么思路？ | 固定线程池，禁扩容，避免资源被突发流量打爆；靠有界队列缓冲 + 拒绝策略兜底 |
| 线程池的队列和 maximum 谁先用满？ | 先 core 满 → 任务进队列 → 队列满才会创建非核心线程直到 maximum；所以队列很长时 maximum 可能被"饿着" |
| 拒绝策略有哪些、如何选？ | AbortPolicy（默认抛异常）、CallerRuns（调用线程执行）、DiscardPolicy/DiscardOldest（丢弃）；按"宁可失败快速提示/宁可慢不能丢"取舍 |
| keepAliveTime 设多久合理？ | 非核心线程空闲多久回收；突发流量场景设短（如10s）快速释放资源，慢下游场景设长（如60s）避免反复创建销毁 |
| 核心线程会不会被回收？ | 默认不会，核心线程常驻；可 `allowCoreThreadTimeOut(true)` 让核心线程也按空闲回收 |
| 队列选有界还是无界？ | 生产最好**有界**（如 LinkedBlockingQueue(200)），无界会无限积压任务、拖垮内存，也更难监控 |
