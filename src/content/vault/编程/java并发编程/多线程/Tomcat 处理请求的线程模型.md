> **这道题对应的「答题主线」**，面试官问「Tomcat 是怎么用线程处理请求的？」，可以按这条主线串起来：
> Tomcat 两大核心（Connector 管网络 / Container 管业务）→ 四步流水线（Acceptor 收连接 → Poller 用 NIO 监控 I/O → Worker 线程池读请求+解析+调 Servlet → 返回响应并放回线程池）→ 同步请求模型本质（一个请求一生由一个 Worker 负责）→ 关键参数（maxThreads 默认 200 / acceptCount 排队 / 队列满拒绝）→ 升华（Servlet 3.0 异步：Worker 把耗时业务委托给应用自定义业务线程池后立即释放，才是真正独立的业务线程池）。

## 一、Tomcat 的两大核心：连接器与容器

为高效工作，Tomcat 在架构上做明确分工：

- **连接器（Connector）**：负责底层网络通信（TCP/IP），监听端口、接收外部请求。
- **容器（Container）**：负责业务逻辑，即执行我们编写的 Servlet，处理请求并生成响应。

## 二、请求处理流程：分工明确的流水线

一个 HTTP 请求到达时，涉及多种线程分工协作：

1. **接收连接（Acceptor 线程）**：在端口（如 8080）上等待新连接，默认只有一个，只负责收连接，不处理请求。
2. **监控事件（Poller 线程）**：连接建立后 Acceptor 不直接处理，而是交给 Poller。Poller 用 NIO 的 `Selector` **非阻塞监控**连接上的 I/O 事件（如请求数据是否可读）。默认最多 2 个。
3. **执行业务（Worker 线程）**：Poller 检测到请求数据就绪后，把「读取请求、解析 HTTP 协议、调用 Servlet 执行业务逻辑」等所有后续工作封装成任务，提交给 **Worker 线程池**执行。
4. **返回响应**：业务逻辑执行完毕后，Worker 线程负责把响应写回客户端，然后自身释放回线程池，等待处理下一个请求。

这个模型通常叫**「同步请求模型」**——**一个请求从进入 Tomcat 到响应返回，整个生命周期都由一个 Worker 线程负责**。

## 三、Worker 线程池：并发处理的核心

`maxThreads` 指的就是这个 Worker 线程池的最大容量：

- **默认大小**：`maxThreads` 默认 **200**。
- **如何设置**：在 `conf/server.xml` 中修改，例如调大到 500。
- **处理机制**：当请求并发量超过 `maxThreads`，新请求进入等待队列（由 `acceptCount` 参数控制）；队列满了之后新连接可能被拒绝。

## 四、重要补充：Servlet 3.0 异步处理

从 Servlet 3.0 规范起，Tomcat 支持**异步 Servlet**。它允许 Worker 线程接收到请求后，把耗时的业务逻辑**委托给应用自己定义的业务线程池**执行，而 Worker 线程立即释放，回到 Tomcat 线程池。

优点：显著提高 Worker 线程利用率，从而提升系统整体吞吐量。但这是**非默认行为**，需要主动编码实现。

它独立于 Tomcat 之外、是应用自建的线程池，只在用 Servlet 3.0 异步特性时才会接触到。

## 五、调试实战：为什么打断点时请求会变「串行」处理

> 现象：并发请求调试时，必须处理完一个才能执行下一个——这是「串行」假象。结合上面的线程模型，原因**有直接关系，罪魁祸首极大概率是 IntelliJ IDEA 默认的断点挂起策略**（`Suspend: All`），它往往比线程池配置更能直接造成串行。

### 5.1 根本原因：IDEA 默认挂起「所有线程」

直接双击行号打的普通断点，默认 `Suspend: All`——命中时 **IDEA 会挂起整个 JVM 进程中的所有线程**，包括：

- 处理当前请求的 **Worker 线程**；
- 监听新连接的 **Acceptor 线程**；
- 监控网络事件的 **Poller 线程**。

Acceptor 和 Poller 被冻结后，Tomcat 根本**无法从端口读取任何新请求的数据**，更别说分配新线程。所以哪怕 `maxThreads` 配了 500，断点命中期间也全都处于「冻结」状态，**必须点 Resume 让所有线程解冻后，下一个请求才能进来并得到处理**。

### 5.2 改成只挂起「当前线程」会怎样

右键断点，把 `Suspend` 从 `All` 改为 `Thread`：

- 只有处理当前请求的那个 Worker 线程被暂停；
- **Acceptor 和 Poller 依然在运行**，Tomcat 仍能接收新请求，并在线程池里**分配另一个空闲的 Worker 线程**去处理第二个请求。

**但即便改成 `Thread`，以下两种情况第二个请求依然会「卡住」**：

- **遇到同步锁（Synchronized/Lock）**：业务代码里有全局锁（如操作同一静态变量、数据库连接池耗尽等）。第一个请求线程在断点处暂停、却依然持有这把锁；第二个请求线程进来尝试获取同一把锁 → 获取不到 → 阻塞等待 → 表现得像「必须等第一个处理完」。
- **线程池已满**：`maxThreads` 故意设为 1，或 200 个线程都被其他长时间运行的任务占满，新请求自然只能排队等待。

### 5.3 实操建议

- **排查断点类型**：断点小红点图标右下角没有特殊标记通常就是 `All`。**调试多线程/并发问题时，右键断点强制 `Suspend -> Thread`**，对服务器的干扰最小。
- **留意阻塞代码**：就算改了断点策略，若第二个请求仍卡死，要留意断点所在那一行是否操作了共享资源（数据库连接、Redis 连接、全局锁对象）。

**一句话总结**：IDEA 默认的「挂起全部」策略冻结了 Tomcat 的接收线程（Acceptor），这比线程池配置更能直接导致「串行处理」现象；把它改成「挂起当前线程」就能恢复多线程并行处理的特性。

## 六、面试速答与追问预案

### 6.1 三十秒速答版

Tomcat 用一个共享 Worker 线程池处理所有请求（含 HTTP 解析 + 业务逻辑），默认 200。流程是 Acceptor 收连接 → Poller（NIO）监控 → Worker 池执行 → 返回响应，属同步请求模型。若要独立业务线程池，需用 Servlet 3.0 异步。

### 6.2 追问预案

**Q1：Acceptor 为什么只需要一个？它怎么忙得过来？**
**A**：Acceptor 只做「接受连接」这一件很轻的事，不会卡在真正的 I/O 读写上——它把连接交给 Poller（代码上通常通过内部队列 `setSocketOptions` 转交）。正因为收连接成本极低，一个 Acceptor 足够，不需要多个。

**Q2：Poller 的意义是什么？不用它行不行？**
**A**：Poller 用 NIO 的 `Selector` 把「监听一堆连接上是否来了数据」这个阻塞等待改成非阻塞多路复用；Linux 底层对应 `epoll`。它让 Tomcat 只靠少量线程（默认 2 个）就能同时盯住成千上万条连接的 I/O 事件，这是高并发下省线程的关键。若用旧版 BIO 模型，则每个连接都要占一个线程，扩展性差。

**Q3：请求量超过 maxThreads 会发生什么？**
**A**：超额请求先进入等待队列（由 `acceptCount` 限定），队列也满了之后，再来的新连接会被拒绝（操作系统层面直接拒绝 accept）。不会像无界队列那样无限堆积导致内存耗尽，但用户会看到连接失败/超时。

**Q4：maxThreads 设多大合适？**
**A**：没有统一值，取决于每个请求的 CPU 密集/IO 密集性质、机器核数、业务 RT。经验方向：请求多是 IO 阻塞在外部（数据库、远程调用）时，可适当调大的同时要配合业务线程池；请求是纯 CPU 算力时，线程数≈核数。盲目调大反而因线程切换上下文损耗、内存占用升高而降低吞吐。**本质是对调用链上游响应慢的容忍度 + 资源预算的权衡**。

**Q5：同步请求模型哪里不好？Servlet 3.0 异步怎么治？**
**A**：同步模型下，Worker 线程会「抱住」一个请求直到响应返回；如果业务慢（如调第三方 API 阻塞），Worker 就被长期占用、快速耗尽 200 个线程，后续请求排队/被拒，吞吐骤降。Servlet 3.0 异步让 Worker 收到请求后把耗时逻辑交给**应用自建的业务线程池**，自己立刻放回 Tomcat 池继续接新请求——把「Tomcat Worker 线程」从业务耗时中解放出来。

**Q6：和 Netty / Reactor 线程模型有什么关系？**
**A**：Acceptor、Poller（NIO Selector）、Worker 池的划分，本质是**Reactor 多线程模型**的一个实例——主 Reactor 收连接（Acceptor）、多路复用分发事件（Poller）、worker 线程池执行业务（Worker）。Netty 的 `boss`/`worker` 事件循环、Spring WebFlux 的 Reactor 都是同一思路。理解 Tomcat 这层，对迁移到自研网络框架（netty 手写 RPC）是直接铺垫。
