# Java 中有哪些常用的锁，在什么场景下使用？

> 答题主线：Java 锁先按**竞争处理方式**分两大类——**悲观锁**（默认可能被抢，先加锁：synchronized、ReentrantLock、ReadWriteLock）和**乐观锁**（不预锁，更新时用版本号/CAS 校验有没有被改）。synchronized 内部按竞争激烈程度又分**锁升级**（无锁→偏向→轻量→重量）；另有按等待方式的**自旋锁**。面试扯清这 5 类"是什么 + 各自场景"，就覆盖了 90% 的锁问题。

## 一、四步回答骨架

1. **定调（先给分类框架）**：Java 锁最常见的切分是**悲观锁 vs 乐观锁**——悲观锁默认"很可能被抢"，访问前先加锁把资源捂住（`synchronized`、`ReentrantLock`、`ReadWriteLock`）；乐观锁默认"不太会被抢"，不加锁，只在更新时用版本号/CAS 校验有没有被别人改过。先把这两类立住，再往里填具体实现。
2. **悲观锁三剑**：**`synchronized`**（JVM 内置关键字，自动获取/释放，方法/代码块），按竞争激烈分层为锁升级（无锁→偏向→轻量→重量）；**`ReentrantLock`**（显式锁，`lock()/unlock()`，多出可中断、可定时等待、公平/非公平）；**`ReadWriteLock`**（读读共享、读写/写写互斥，读远多于写的场景并发度最高）。
3. **乐观锁**：不锁资源，靠**版本号或时间戳**（配 CAS）在更新时检测是否已被并发修改；适合读多写少、冲突率低的场景。
4. **补自旋锁**：等待时**不放弃 CPU、持续循环**重试 CAS，适合锁持有时间极短的短临界区；但过度自旋浪费 CPU，需权衡。

## 二、核心内容：五种常用锁的机制与场景

### 1. synchronized（内置锁 / 悲观锁）

JVM 内置的加锁机制，作用在**方法或代码块**上。进入时线程获取关联对象的锁，离开时自动释放；其他线程想拿同一把锁就被阻塞直到释放。加锁时按竞争程度有**四个级别**：
- **无锁**：无竞争，直接访问；
- **偏向锁**：只有一个线程反复进入同步块、无其他线程竞争时启用，减少加锁开销；
- **轻量级锁**：其他线程来争但竞争不激烈，用线程栈上的数据结构实现，避免落到操作系统级；
- **重量级锁**：竞争激烈，才升级为操作系统级的互斥锁（开销最大）。

> 场景：并发读写同一代码块的常规互斥场景，用 synchronized 最省事（自动释放、不易出错）。

### 2. ReentrantLock（显式锁 / 悲观锁）

`java.util.concurrent.locks.ReentrantLock`，需**手动 `lock()`/`unlock()`**（务必 finally 释放）。比 synchronized 多的能力：
- **可中断**的锁等待（`lockInterruptibly`）；
- **可超时**等待（`tryLock(timeout)`）；
- **公平锁选项**：`new ReentrantLock(true)` 按请求顺序分配锁，保证公平但可能拉长等待；非公平（默认）不保证顺序，减少锁竞争、性能更高，但可能让某些线程**饥饿**。

> 场景：需要可中断/可超时/公平控制、或更精细的 Condition 控制时选用；普通互斥用 synchronized 即可。

### 3. ReadWriteLock（读写锁 / 悲观锁）

`java.util.concurrent.locks.ReadWriteLock` 接口：**允许多个读取者同时访问**，但**只允许一个写入者**（写时排斥所有读写）。这是"读读并发、写互斥"。

> 场景：**读远多于写**的场景（如缓存、配置读取），同一时刻可放多个线程进来读，明显提高并发性。

### 4. 乐观锁 vs 悲观锁

- **悲观锁**：访问数据前先锁定，假设最坏情况（数据很可能被其他线程改）。`synchronized`、`ReentrantLock` 都是悲观锁。适合**写多冲突多**的场景，把并发冲突提前挡住。
- **乐观锁**：不锁定资源，靠**版本号/时间戳**（或用 CAS）在更新时检查数据是否已被其他线程修改，没被改才提交。适合**读多写少、冲突率低**的场景，避免锁带来的阻塞开销。

### 5. 自旋锁

线程在等待锁时**持续循环检查锁是否可用**，而不放弃 CPU、不阻塞。通常用 **CAS** 实现（循环尝试 CAS 直到成功）。

> 场景：**锁等待时间很短**时，自旋比"挂起→唤醒"的线程切换更省；但如果锁老不放，长时间自旋白白占用 CPU，浪费资源。

## 三、如何应用 / 面试怎么讲

**加分表达：**
- 一上来就抛"**悲观/乐观**"这根主线把锁分成两大类，再往里填实现，比零散背类名高级——体现你有体系而不是背清单。
- 给**选型判断**：悲观锁里普通互斥默认 synchronized（简单不易错），要可中断/超时/公平才上 ReentrantLock，**读远多于写用 ReadWriteLock**；乐观锁适合读多写少冲突低。把"场景"和"锁"一一对上，是这道题真正的得分点。
- 能点出**锁升级**（无锁→偏向→轻量→重量）说明你懂 synchronized 不是"一上来就重量级"，而是按竞争动态伸缩——体现对 JVM 优化的理解。
- 自旋锁主动谈**取舍**（短临界区才值、过度自旋浪费 CPU），比单纯报名字更能体现工程判断。

**追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| synchronized 的锁升级完整路径？ | 无锁 → 偏向锁（单线程反复进） → 轻量级锁（有轻度竞争，栈上自旋） → 重量级锁（竞争激烈转 OS 互斥锁）；竞争越激烈开销越大，JVM 按需升级 |
| 偏向锁什么时候用？ | 一个线程反复进入同步块、无其他线程竞争时，减少无竞争下的加锁开销（本质是"念旧"，认准第一次的线程） |
| 轻量级锁为什么比重量级快？ | 轻量级锁用线程栈上的结构+自旋，不切换到操作系统内核级互斥锁，避免用户态/内核态切换开销 |
| 什么时候升级成重量级锁？ | 轻量级锁自旋失败、竞争持续激烈时，升级为 OS 互斥锁（阻塞挂起） |
| ReentrantLock 和 synchronized 怎么选？ | 普通互斥用 synchronized（自动、不易错）；需要**可中断/可定时/公平锁/多 Condition** 才用 ReentrantLock |
| 公平锁和非公平锁各适合什么？ | 公平保"先来后到"但吞吐低、可能拉长等待；非公平允许插队、减少锁竞争吞吐高，但极端可能饥饿；默认非公平 |
| ReadWriteLock 什么时候用？ | **读多写少**、允许多线程同时读；若写频繁，读写锁的读锁反而成为瓶颈，不如普通互斥锁 |
| 悲观锁和乐观锁怎么选？ | 悲观锁适合**写多冲突多**（提前挡住竞争）；乐观锁适合**读多写少、冲突低**（免阻塞开销）；乐观锁在高冲突下不断重试反而更差 |
| 乐观锁怎么判断被改了？ | **版本号**（Integer 版本+1，更新时比较）或**时间戳**，配 CAS 原子更新；版本不符则放弃或重试 |
| 自旋锁什么时候划算？ | 锁持有时间很短（临界区极小）时，自旋免去挂起/唤醒的线程切换；否则白转浪费 CPU |
| 和 volatile 的关系？ | volatile 只保证可见性、禁重排，**不保证原子性**、不能替代锁；只适合单个读写的标志位，多步操作仍需锁 |
