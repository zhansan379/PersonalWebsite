# 乐观锁的实现方式及 CAS 的缺点和解决？

> 一句话定调：乐观锁认为竞争不总是发生，**不强持锁（无锁）**，把"读-比较-替换"作为原子操作去改内存变量，失败就重试/处理冲突。实现乐观锁有三条路：**CAS（原子类）、版本号控制、时间戳**。而乐观锁的基石 CAS 有**三大缺点**：ABA 问题、自旋长时间不成功费 CPU、只能保证单个共享变量的原子性；也正因 CAS 依赖**循环重试**，高并发下大量自旋会浪费 CPU，所以**不能用 CAS 取代所有锁**。Java 用 **AtomicStampedReference（带版本号 Stamp）** 从根上解决 ABA。

> **这道题对应的「答题主线」**，面试官问「乐观锁怎么实现？CAS 有什么缺点、怎么解决？」，可以按这条主线串起来：
> 一句话定义（无锁 + CAS 原子修改 + 失败重试）→ 三种实现方式（CAS / 版本号 / 时间戳）→ 聚焦最优的 CAS，讲透三大缺点（ABA / 自旋费CPU / 仅单变量）→ 由此反问"为什么不能全用 CAS"（自旋在低竞争好、高竞争 CPU 浪费）→ 落点 ABA 的 Java 解法（AtomicStampedReference 带 Stamp 比对值+版本号）。

## 一、乐观锁的实现方式

乐观锁认为并发竞争**不总是发生**，因此**不需要持有锁**：把「比较-替换」两个动作作为一个原子操作尝试改内存变量，失败表示冲突，进入相应的重试逻辑。实现乐观锁有三种方式：

**1. CAS（Compare And Swap）操作**

CAS 是乐观锁的基础。Java 提供 `java.util.concurrent.atomic` 包，含各种原子变量类（`AtomicInteger`、`AtomicLong`），这些类用 CAS 实现线程安全原子操作，可用来实现乐观锁。

**2. 版本号控制**

增加一个**版本号字段**记录数据更新时的版本，每次更新递增版本号。更新数据时同时比较版本号：若当前版本号与更新前获取的一致，则更新成功，否则失败（说明已被别人改过）。

```
读数据（获取版本号）→ 业务计算 → 更新时检查版本号是否一致 → 一致则更新并版本号+1；不一致则重试/失败
```

**3. 时间戳**

用**时间戳**记录数据的更新时间。更新时比较时间戳：若**当前时间戳大于数据的时间戳**，说明数据已被其他线程更新，更新失败。

## 二、CAS 的三大缺点

**1. ABA 问题**

在 CAS 更新过程中，读取到的值是 A、准备赋值时仍是 A，但**实际上 A 曾变 B 又变回 A** —— 这个中途变化 CAS 感知不到，就叫 ABA。

- 大部分场景下 ABA 不影响并发的最终效果；
- Java 用 **`AtomicStampedReference`** 解决：加入**预期标志**和**更新后标志**两个字段，更新时不光检查值、还要检查当前标志是否等于预期标志，全部相等才更新。

**2. 循环时间长、开销大**

自旋 CAS 如果长时间不成功，会给 CPU 带来很大的开销。

**3. 只能保证一个共享变量的原子操作**

只对一个共享变量操作可以保证原子性，多个则不行；多个可以用 `AtomicReference` 处理，或使用锁（`synchronized`）实现。

## 三、为什么不能所有锁都用 CAS

CAS 基于**循环重试**机制：若一直未能成功，线程会一直**自旋重试、占用 CPU 资源**。在**高并发**情况下，大量线程自旋会导致 CPU 资源浪费。这与悲观锁的"阻塞挂起"不同——阻塞会把线程让出 CPU，而自旋死磕不放 CPU。所以：

- 低竞争 / 短临界区：CAS 自旋划算；
- 高竞争 / 长临界区：大量自旋白烧 CPU，不如阻塞式锁（synchronized/Lock）。

因此 CAS **不是万能替代**，需要按竞争程度选型。

## 四、CAS 的 ABA 问题及 Java 的解决

**问题复现**：变量值在操作过程中先被其他线程从 A 改 B、又被改回 A，CAS 无法感知中途变化，误判为"未变更"。例如：

1. 线程 1 读变量为 A，准备改为 C；
2. 此时线程 2 将变量 A→B→A；
3. 线程 1 的 CAS 执行时发现仍是 A，认为没变就更新了 C——**中间状态丢失**。

**Java 的解决**：工具类在 CAS 操作中增加**版本号（Stamp）或标记**，每次修改都更新版本号，使即使值相同也能识别变更历史。典型是 **`AtomicStampedReference`**——通过比对值和版本号识别 ABA：

```java
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);

// 尝试修改值并更新版本号
boolean success = ref.compareAndSet(100, 200, 0, 1);
// 前提：当前值=100 且 版本号=0，才会更新为（200, 1）
```

`compareAndSet(期望值, 新值, 期望版本号, 新版本号)` 要求**值 + 版本号同时匹配**才更新，从而把 ABA 拦下来。

## 五、面试速答与追问预案

### 5.1 三十秒速答版

乐观锁无锁、用 CAS 原子比较替换实现。三种方式：CAS、版本号、时间戳。CAS 三大缺点：ABA（用 AtomicStampedReference 带版本号解决）、自旋费 CPU、只能保证单变量。正因 CAS 靠循环重试，高竞争下大量自旋浪费 CPU，所以不能全用 CAS，需按场景与悲观锁互补。

### 5.2 追问预案

**Q1：为什么说 CAS 是乐观锁的基础？**
**A**：乐观锁的核心就是"不加锁、改时校验是否被改"，CAS 用硬件/原子的 compare-and-swap 一步完成"比较 + 替换"，无锁又能保证原子性，正是乐观锁的原子落地手段。`atomic` 包各种原子类都基于它。

**Q2：版本号和时间戳两种乐观锁实现有什么区别？**
**A**：都是加一个"变更标识"用于更新时比对。版本号是递增整数，更新时要求取到的版本号没变；时间戳用最后更新时间，当前时间超过记录时间戳认为已被改。本质思路相同，只是用数字递增还是用时间表示"版本"。

**Q3：ABA 在什么场景下会出问题？为什么说大部分场景无所谓？**
**A**：ABA 若只影响"最终取到的值"通常无碍（最终值正确即可）；但涉及**有状态中间过程**（如栈/链表操作、依赖值的"次数"）时可能出错。`AtomicStampedReference` 用引用 + 版本号兜底。

**Q4：CAS 循环自旋和阻塞谁好？**
**A**：取决于竞争。低竞争/短临界区自旋可能更快（省去线程切换）；高竞争/长临界区自旋白烧 CPU，阻塞式（synchronized/Lock 挂起让出 CPU）更合适。所以"不全用 CAS"正是要按场景权衡。

**Q5：为什么 CAS 只能保证一个变量？多个怎么处理？**
**A**：CPU 的 CAS 指令原子范围是单个内存位置；多个变量无法一并原子比较替换。可把多个变量包进一个对象用 `AtomicReference` 整体 CAS，或用锁 `synchronized` 覆盖多变量操作。
