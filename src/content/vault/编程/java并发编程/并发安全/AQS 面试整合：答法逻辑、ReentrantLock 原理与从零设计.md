# AQS 面试整合：答法逻辑、ReentrantLock 原理与从零设计

> 答题主线：真正的 AQS 打法**先给大局观、别长篇大论**——AQS 是封装"等待/唤醒/排队"的抽象框架，靠 **volatile state + FIFO 双向等待队列**实现线程安全抢资源；它只管排队细节，**加不加锁、怎么加锁由实现类决定**。然后落到 ReentrantLock 把加锁/解锁完整走一遍，再反推"为什么这么设计"，最后和 synchronized 拉开对比。来源：三支 B 站字幕（AVQ 核心原理 / 一分钟答法 / 当面设计 AQS）。

## 一、四步回答骨架

1. **先给大局观（一句话收住）**：AQS 是 `java.util.concurrent` 里的抽象同步框架，核心作用是**统一封装现成的等待/唤醒/排队机制**；底层靠一个 **volatile 的 state 变量 + FIFO 队列**实现线程安全的资源抢夺。`state` 表示资源状态（如独占锁 0=没人占、1=被占），线程抢不到锁就被挂进队列排队；队列是 **CLH 变体的双向链表**，节点里记录线程信息和等待状态。
2. **点破分工（句句是得分）**：**AQS 不负责"加不加锁"这件事**——它只帮你处理线程排队的细节；怎么加锁、怎么释放由实现类自己决定。`ReentrantLock`、`CountDownLatch`、`Semaphore` 都是基于它实现不同的锁语义。说完这一句面试官就同意你有大局观。
3. **走一遍实现（落一个具体例子）**：以 ReentrantLock 串起完整流程——**加锁**：CAS 把 state 从 0 改 1 + 记 `exclusiveOwnerThread`；抢不到 → 不死心再试（判 state / 判自己是不是持锁线程实现可重入）→ 仍失败 → 封 Node 进双向队列 → `LockSupport.park` 挂起。**解锁**：state 归 0 + 清空持锁线程 + `unpark` 唤醒队列中头节点的后继。
4. **拉高收尾（设计动机 + 对比）**：反推为什么这么设计——`state` 用 int 才能表达 Semaphore 的多线程许可、ReentrantLock 的可重入计数；"要不要锁"抽象成 `tryAcquire` 留给子类（模板方法模式）。最后拉开两张对比：**独占(ReentrantLock) vs 共享(Semaphore)**、**ReentrantLock vs synchronized**、以及**为何不用 OS mutex**。

## 二、核心内容

### 1. 面试正确打法：先给大局观，点到为止（视频2）

> 别一上来就"同锁入队、信号量、同步器"一顿输出，容易把面试官绕睡；关键是**让他听完第一句就点头**。记住这几点就够：
> - AQS 本质是**抽象框架**，封装了线程排队和资源控制；
> - 核心是 **state + FIFO 等待队列**；
> - 真正的**锁逻辑交给实现类自己定**。
>
> 这就是拿分打法。随后面试官多半会引申"那 ReentrantLock 里具体怎么实现的"，再往下讲。

### 2. 通过 ReentrantLock 完整走一遍 AQS（视频1）

AQS 里有**两样极重要的东西**：① **双向链表队列**——每个线程被封装成 Node（前驱 / 线程 / 后继，所以是双向）按 **FIFO 先进先出**排队；② **int 成员变量 state**——用 volatile 修饰保证多线程可见性，默认 0，等于 1 时表示锁被占有。

ReentrantLock 内有个继承 AQS 的 `Sync` 抽象类，下面两个实现类：**`NonfairSync`（非公平）和 `FairSync`（公平）**。默认 new ReentrantLock() 创建的是 **非公平锁**。

#### 加锁流程（非公平锁，两线程为例）

| 步骤              | 动作                                                                                     |
| :-------------- | :------------------------------------------------------------------------------------- |
| 1. 线程一 `lock()` | CAS 原子性把 state 改为 1 → 成功                                                               |
| 2.              | 设置 `exclusiveOwnerThread = 线程一`（记录持锁线程）                                                |
| 3. 线程二 `lock()` | CAS 把 state 改 1 → 失败（已被线程一占用）                                                          |
| 4. 不死心还想试       | 再读一次 state 判断是否 0 → 不是；再判 `exclusiveOwnerThread` 是不是自己 → 是线程一不是线程二 → 失败（**这步正是实现可重入**） |
| 5. 构建 Node      | 造一个"线程二节点" + 一个**空的哨兵节点**作为头节点；头尾指针先指向哨兵，再把线程二节点挂到哨兵之后                                 |
| 6. 循环判断         | 只看**当前节点的前驱是否为头节点**（保证只有头节点的后继第一个节点才有资格抢锁）→ 是 → 再读 state 仍为 1 → 仍失败                    |
| 7. 挂起           | `LockSupport.park()` 把线程二挂起，安静待在队列里等着                                                  |

#### 解锁流程（唤醒线程二）

| 步骤                | 动作                                     |
| :---------------- | :------------------------------------- |
| 1. 线程一 `unlock()` | 检查 `exclusiveOwnerThread` 是否自己 → 是     |
| 2.                | state 改回 0                             |
| 3.                | `exclusiveOwnerThread` 置 null          |
| 4.                | 判断头节点必须存在                              |
| 5.                | `LockSupport.unpark()` 唤醒头节点的后继节点（线程二） |

线程二被唤醒后：因为它是在一个**死循环里被 park** 挂起的，唤醒后继续跑循环——判前驱是头节点 → 是 → 读 state 是 0 → 是 → CAS 改 1 → 设 `exclusiveOwnerThread = 线程二` → **把自己晋升为新的头节点**、置空旧头节点里的线程、并把旧头节点的后继置空（**方便 GC 回收**）→ 加锁成功。

> **非公平体现在哪**（大白话比喻：追女神"回首掏"）：线程一解锁、线程二被唤醒时，若正好有个线程三也来加锁抢 CAS——**很可能线程三比线程二先把 state 改成 1**。明明线程二先排队等着，却被后来的线程三插队抢到，这就是**非公平锁**。

#### 公平锁的不同点

线程三加锁时**多了一个判断**：若**头节点已存在后继节点，且该后继节点中的线程不是当前线程**，就不能去改 state，只能把自己封成 Node 放进队列排队。→ 这就是公平锁的"先来后到"。

### 3. 从零设计一个并发工具类：预判 AQS（视频3）

> 面试深水区常问"**让你实现一个并发工具类，会考虑哪些问题？**"——顺着想一遍，你就把 AQS 设计出来了。

**第一步 · 怎么表示共享资源被占用 → state。**
`state=0` 空闲、`state=1` 被占，这是 lock 的思想。但**为什么 state 不能是 boolean、必须是 int**？想两种场景：
- **场景A（多线程做客）**：共享资源可同时被 3 个线程访问 → state 最多为 3 → 这就是 **Semaphore** 的"剩余许可证"思想；
- **场景B（递归/重入）**：当前线程要多次访问资源，访问一次 state+1、释放一次 state-1，**减到 0 才代表空闲** → 这就是 **ReentrantLock 可重入**的思想。

**第二步 · 可见性和原子性。** 多线程读 state → 加 `volatile` 保可见性；多线程改 state → 用 **CAS** 保原子性。

**第三步 · CAS 失败怎么办？** 不能一直自旋空转（浪费 CPU）→ 把失败的线程**阻塞**住，等资源空了再唤醒。

**第四步 · 怎么高效管理一堆等待线程？** 把线程包装成 Node，用**双向链表实现一个先进先出等待队列**：CAS 失败 → 入队并阻塞；资源释放 → 唤醒队里节点去改 state。

> 到这儿你已经设计出一个简单的并发工具类了。

**第五步 · API 怎么设计？想上层业务怎么调用。**
- 业务只想"**尝试**获取资源，拿不到就干别的事" → 设计 `tryAcquire()`，返回 true/false；
- 业务"**必须**拿到资源才能继续，否则一直等" → 设计 `acquire()`，无返回值，拿不到就阻塞到成功。

→ 你**预判了 AQS 的设计**。对照 AQS 源码：`tryXxx` 方法里没实现、直接抛异常，**因为不同工具类抢资源的方式不同，开放给子类重写，AQS 只关心"有没有抢到"**；`acquire` 内部就是"先 tryAcquire，拿不到就入队阻塞"，本质是**模板方法模式**。

### 4. ReentrantLock vs synchronized（视频3）

| 维度 | ReentrantLock | synchronized |
| :--- | :--- | :--- |
| 底层基础 | 基于 AQS（有 `tryAcquire`） | JVM 关键字 |
| **能否尝试加锁** | 有 `tryLock()`，抢不到可转做其他操作 | 无，抢不到只能阻塞 |
| **公平性** | 有公平锁/非公平锁（默认非公平） | 只有非公平 |
| 条件队列 | 可 `new` 多个 `Condition`，配合 `signal` 做精细唤醒 | 每个锁对象一个 `wait/notify` |

**锁监视器的对比（条件队列）**：synchronized 的监视器有持有区（放抢锁失败线程）和等待区（放通信时主动放弃锁的线程）。ReentrantLock 下：没拿到锁的线程进 **AQS 等待队列**；拿到锁但需要等资源落位、调用 `await` 主动放锁的线程，则进 **Condition 的条件队列**——而且可以 new **多个** Condition，用不同 Condition 的 `signal` 实现**更精细的唤醒通知**。这是两者另一处关键不同。

### 5. 独占模式 vs 共享模式、为何不用 OS mutex（视频3）

**独占模式**：只允许单线程独占资源，适用互斥场景（如 ReentrantLock）。`acquire`/`tryAcquire` 对应 `lock`/`tryLock`；state=0 空闲、加锁 CAS 改 1、重入一次 +1、释放一次 -1，**减到 0 完全释放后唤醒队列里线程重新抢锁**。

**共享模式**：多个线程可同时共享资源，适用协作场景（如 Semaphore、CountDownLatch）。Semaphore 的 state 代表"剩余许可证":初始化为 N，获取递减、减到 0 新线程入队等待，释放递增。CountDownLatch 的 state 代表"剩余任务数"，`countDown` 递减，**归零唤醒所有 await 线程**。

**为何不直接用操作系统 mutex？** ① 直接用 OS mutex 走**内核态/系统调用**，每次加锁解锁都要**用户态↔内核态切换，开销大**；AQS 用用户态的 CAS + 队列管理能减少开销。② AQS 是抽象工具，子类能自定义公平策略、独占/共享模式，**Java 层可灵活扩展**；OS mutex 无法在 Java 层面扩展。

## 三、如何应用 / 面试怎么讲

- **先给大局观再下沉**：第一句只说"state + FIFO 队列 + 抽象框架、锁交给实现类"，让面试官点头；等他追问"ReentrantLock 里具体怎么实现"再往下走。**千万别一上来倒实现细节**。
- **主动点破分工**：强调"AQS 只管排队、不管加锁"——这是判断你真懂 vs 背书的分水岭。
- **会把设计反推**：能解释"为什么 state 是 int 不是 boolean、为什么 tryXxx 只抛异常、为什么用队列而非 OS mutex"，面试官会觉得你不只是会用，还能自己设计。
- **善用大白话比喻**：非公平锁像"追女神回首掏"（后来的线程三插队），讲出来很有画面感、显易懂。
- **拉开对比收尾**：独占/共享、ReentrantLock vs synchronized、OS mutex，把知识串成网。

**追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| AQS 核心原理一句话怎么答？ | 抽象同步框架，用 volatile state + FIFO CLH 变体双向等待队列做线程安全抢资源；它只封装排队/阻塞/唤醒，加锁逻辑交给子类 |
| 面试官为什么不让细讲？ | 容易把面试官绕进去；先给大局观（三句话），等追问再下沉到 ReentrantLock |
| state 为什么是 int 不是 boolean？ | 要表达两种扩展：Semaphore 多线程许可(state 可>1)、ReentrantLock 可重入计数(重入+1/释放-1)；boolean 表达不了 |
| 可重入锁怎么实现的？ | state = 重入次数，加锁判持锁线程是自己就 state+1，解锁 -1，减到 0 才真正释放 |
| 非公平锁体现在哪？ | 线程释放时队头线程刚要 CAS，前来的新线程可插队先把 state 抢走（回首掏） |
| 公平锁 vs 非公平锁差在哪？ | 公平锁 tryAcquire 多一步：头节点已有非当前线程的后继就不抢、直接入队；非公平一来就 CAS 抢 |
| ReentrantLock 和 synchronized 区别？ | AQS-based 所以有 tryLock、有公平/非公平锁、可多个 Condition 精细唤醒；synchronized 全无且集合都非公平 |
| AQS 为什么不用 OS mutex？ | 避免用户态↔内核态切换开销；且 AQS 可在 Java 层自定义公平/模式，OS mutex 不可扩展 |
| tryAcquire 为什么直接抛异常？ | 不同的锁/协作工具抢资源方式不同，放给子类重写；AQS 只关心抢没抢到（模板方法模式） |
| 独占模式和共享模式区别？ | 独占：单线程（ReentrantLock），state 0/1 或重入次数；共享：多线程（Semaphore 许可数、CountDownLatch 倒数），state 递增/递减 |
| 没抢到锁的线程怎么被唤醒？ | 入队 + `LockSupport.park` 挂起；释放时 state 归 0 后 `unpark` 唤醒头节点后继，被唤醒线程继续死循环自旋抢锁 |
