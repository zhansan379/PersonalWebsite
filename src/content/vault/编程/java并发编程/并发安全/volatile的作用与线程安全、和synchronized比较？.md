# volatile 的作用、指令重排序与线程安全、和 synchronized 比较？

> 一句话定调：volatile 是一个**轻量级同步机制**，有**两个作用**——① **保证可见性**（写立即刷主存、读直接从主存取）；② **禁止指令重排序**（通过内存屏障实现）。但它**只保证可见性、不保证原子性，因此不能完全保证线程安全**（如 `i++` 复合操作仍需要锁）。设计上它解决"变量在多线程下的可见性与有序性"，synchronized 解决"共享资源的互斥与原子性"——能力边界不同。

> **这道题对应的「答题主线」**，面试官问「volatile 的作用、能否保证线程安全、和 synchronized 的区别？」，可以按这条主线串起来：
> 两个作用（可见性 + 禁止重排序）→ 能力边界（只保可见、不保原子 → 复合操作不安全）→ 底层机制（JMM 4 种内存屏障 + volatile 插入策略 + x86 的 lock 前缀）→ 指令重排序原理（单线程结果不变 / 数据依赖不重排）→ 与 synchronized 对比（可见性 vs 互斥原子性、轻量 vs 重量、适用场景）收尾。

## 一、volatile 的作用：两个

**1. 保证变量对所有线程的可见性**

当一个变量被声明为 volatile，它的**写操作会立即刷新到主存**，**读操作会直接从主存读取**，从而确保多线程环境下对该变量访问的可见性——一个线程修改了 volatile 变量的值，其他线程能立刻看到，不受各自线程工作内存的影响。

**2. 禁止指令重排序优化**

volatile 在 Java 中主要通过**内存屏障**来禁止特定类型的指令重排序。

### 1.1 四种内存屏障与插入策略

JMM 实际定义了 4 种内存屏障：`LoadLoad`、`StoreStore`、`LoadStore`、`StoreLoad`。Java 编译器对 volatile 操作的标准插入策略：

1. **volatile 写之前插 `StoreStore` 屏障**：防止前面的普通写被重排序到 volatile 写之后；
2. **volatile 写之后插 `StoreLoad` 屏障**：防止 volatile 写与后面可能出现的 volatile 读/写重排序，**开销最大**的屏障；
3. **volatile 读之后插 `LoadLoad` 屏障**：防止 volatile 读与后面的普通读重排序；
4. **volatile 读之后插 `LoadStore` 屏障**：防止 volatile 读与后面的普通写重排序。

**x86 平台的落地**：volatile 写实际通过 **`lock` 前缀指令**（如 `lock addl $0,0(%rsp)`）实现，可同时充当 StoreLoad 屏障——因为 x86 本身的内存模型已隐含了 LoadLoad、StoreStore、LoadStore 的保证。

## 二、指令重排序的原理

为提升性能，处理器和编译器常对指令重排序，但必须满足两个条件：

1. **在单线程环境下不能改变程序运行的结果**；
2. **存在数据依赖关系的不允许重排序**。

所以重排序**不会影响单线程**结果，**只会破坏多线程的执行语义**。

**例子**：设 A 与 C 有数据依赖、B 与 C 也有数据依赖。最终指令序列中 C 不能被重排序到 A 和 B 前面（否则结果改变）；但 A 和 B 之间没有数据依赖，编译器和处理器可以重排 A、B 的执行顺序。正是这种"无依赖可重排、有依赖不可乱排"的缝隙，在多线程下可能造成可见性问题——volatile 的内存屏障正是为封堵这些重排序而设。

## 三、volatile 能否保证线程安全？

**不能完全保证。** volatile 能保证**可见性**，但不能保证**原子性**：

- 当一个线程修改 volatile 变量的值，其他线程能立即看到最新值，避免数据不一致——这是可见性带来的好处；
- 但 volatile **不能解决复合操作**问题：如 `i++` 并非原子操作，多个线程同时对 i 自增，volatile 无法保证线程安全；
- **复合操作仍需 `synchronized` 或 `Lock`** 保证原子性与线程安全。

## 四、volatile 和 synchronized 的比较

| 维度 | volatile | synchronized |
| :--- | :--- | :--- |
| **解决的问题** | 变量的**可见性 + 有序性**，确保修改对其他线程可见 | 多线程访问共享资源时的**竞态条件 / 数据不一致**，保证线程安全 |
| **机制** | **轻量级**同步：可见性 + 禁止重排序 | **排他性**同步：同一时刻只允许一个线程访问共享资源 |
| **互斥性** | 无互斥，非排它 | 有互斥，排它 |
| **原子性** | 不保证（复合操作不安全） | 保证（代码块/方法级原子） |
| **用法** | 只修饰变量，声明 volatile 即可 | 修饰方法或代码块 |
| **读/写** | 读直接读主存、写立即刷回主存，不用本地缓存 | 加锁清工作内存读主存，释放锁写回主存 |

> **能力边界一句话**：volatile 是解决"变量在多线程下的可见性与有序性"的轻量机制；synchronized 是解决"共享资源竞态与一致性"的排他互斥机制。能保证可见性 → 但不能保证原子性 → 复合操作仍要锁。

## 五、面试速答与追问预案

### 5.1 三十秒速答版

volatile 两个作用：保证可见性（写刷主存、读读主存）+ 禁止指令重排序（内存屏障）。它只保可见、不保原子，所以 v**olatile 不能完全保证线程安全**——`i++` 等复合操作仍需 synchronized/Lock。synchronized 是排它互斥、保证原子性；volatile 是轻量可见性机制。适用：状态标志、单写多读的双重检查锁（DCL）。

### 5.2 追问预案

**Q1：volatile 为什么不能保证原子性？**
**A**：可见性只解决"读到最新值"；原子性解决"读-改-写一步完成不被打断"。`i++` 是读、自增、写三步，两个线程可能同时读到旧值、各自 +1 后写回，最后只 +1。volatile 不锁互斥，无法阻止这种交错，故复合操作仍需锁。

**Q2：两种条件下为什么重排序只破坏多线程语义、不影响单线程？**
**A**：重排序的前提就是在单线程内不改变结果（条件 1），所以单线程无论怎么排最终结果不变；而多线程下，无依赖的语句在不同线程交错执行、配合可见性缺失，可能导致结果与直觉不符。这就是为什么要用内存屏障在关键点卡住重排。

**Q3：volatile 适合什么场景？**
**A**：适合"一写多读"或只是当状态标志的场景，如 `volatile boolean running` 中断标志、DCL 中单例的 instance 字段（保证完全初始化的对象对读线程可见）。不适合"多个线程同时读写同一值做计算"的复合场景。

**Q4：DCL 为什么要用 volatile 修饰 instance？**
**A**：防止**半初始化对象**被发布——普通引用下，构造过程与赋引用可能被重排序，读线程拿到引用却看到未构造完成的对象。volatile 禁止该重排 + 保证可见性，确保赋值发生在完全构建之后。

**Q5：volatile 读写和 synchronized 谁先谁后？能否互相替代？**
**A**：不能替代。volatile 是 synchronized 的**轻量级补充**，只解决可见性/有序性，无原子性；synchronized 保证原子 + 可见 + 有序、但更重（锁）。能用 volatile 的场景用 volatile（轻、无锁竞争），需要原子性时升级为 synchronized/Lock。
