# Agentic RAG 综述

> Agentic RAG 是 RAG 的最新范式，通过引入自主 Agent 实现动态决策和工作流程优化，取代了传统的静态检索管线。

## 〇、为什么会有这些架构？—— 一个 Problem-Driven 的故事

RAG 的演进不是论文灌水堆出来的，每一代架构都是在解决上一代**真实踩过的坑**。下面从问题出发，用大白话把这条演进线串起来。

### 起点：LLM 会胡说八道

LLM 的知识截止于训练数据，问它"公司最新的报销政策是什么"，它要么不知道，要么瞎编（幻觉）。于是有了最朴素的思路：**把相关文档塞进 prompt，让 LLM 照着回答**。这就是 Naïve RAG。

### 第一坑：关键词对不上意思

Naïve RAG 用 TF-IDF / BM25 做关键词匹配。用户问"怎么提升团队战斗力"，文档里写的是"组织效能优化方法论"，关键词完美错开，啥也检索不到。

**→ 解决方案：密集检索（Dense Retrieval）**

Advanced RAG 用 DPR 把查询和文档都映射到**向量空间**。"战斗力"和"效能"虽然字面不同，但在语义空间中距离很近。向量检索解决了"**意思相近但用词不同**"的匹配问题。

**实际例子**：用户搜"减肥方法"，向量检索能找回"科学减重指南"——关键词没一个对得上，但语义完全相关。

那为什么还要保留稀疏检索（BM25）？因为向量检索也有盲区——搜"Transformer 架构"这种精确术语时，BM25 直接命中关键词往往更准。所以 Modular RAG 提出**混合检索**：稀疏负责精确匹配，密集负责语义泛化，两者互补。

### 第二坑：一个问题需要跨文档拼图

用户问"A 公司的 CEO 是谁，他之前在哪家公司任职"。这个问题的答案不在**一个**文档里——需要先从文档 A 找到 CEO 的名字，再用这个名字去文档 B 查他的履历。

**→ 解决方案：多跳检索（Multi-hop Retrieval）**

Advanced RAG 引入多跳机制：第一跳检索"公司 CEO"，拿到人名；第二跳以这个人名为查询，检索其履历。本质上是让检索过程**像人一样迭代推进**，而不是寄希望于一个文档恰好包含所有答案。

**实际例子**："治疗 2 型糖尿病的一线药物有什么副作用？"→ 第一跳找到一线药物名称（如二甲双胍）→ 第二跳检索该药物的副作用。没有多跳，系统拿不到第一步的结果，第二步根本无从查起。

### 第三坑：实体之间的关系被忽略了

多跳检索能串起事实链，但它还是把文档当**孤立的文本块**。有些信息天然是**图状的**——实体之间存在复杂关联。

比如：论文 A 引用了论文 B，论文 B 反驳了论文 C，三篇论文的作者分别属于不同机构。用文本检索，这种引用关系、归属关系、因果关系全部丢失。

**→ 解决方案：Graph RAG**

用图数据结构显式建模实体（节点）和关系（边）。当一个查询涉及"谁引用了谁""A 药物的禁忌症有哪些""这个法条被哪些判例援引过"时，系统不是去搜文本相似度，而是**沿着图的边遍历**，天然支持关系推理。

**实际例子**：医生问"这位患者服用了 A 药和 B 药，有危险吗？"Graph RAG 从知识图谱中找到：A 药和 B 药共享代谢酶 CYP3A4 → 合用会导致药物浓度升高 → 有中毒风险。这是纯文本相似度检索完全做不到的——相似度检索只会分别找到 A 药的文档和 B 药的文档，但**不会推理它们之间的关系**。

### 第四坑：相似度高 ≠ 有用

这是最关键的一个坑。向量检索返回的是"和查询最相似的 Top-K 文档"，但**相似 ≠ 相关**。

用户问"Python 的 GIL 如何影响多线程性能"，系统可能返回一篇"Python GIL 的历史由来"——相似度很高（大量词汇重叠），但实际上用户要的是**性能影响机制**，不是历史故事。

单纯的相似度只看向量距离，不知道**这篇文档到底有没有回答用户的问题**。

**→ 解决方案：批判/评估模块（Critic / Relevance Assessment）**

Corrective RAG 和 Agent-G 都引入了一个评估环节：检索到文档后，先由一个专门的模块判断"这些文档真的有用吗？"如果不够好，触发查询改写或外部搜索，而不是硬着头皮拿不相关的文档去生成。

**实际例子**：用户问"2025 年新能源汽车补贴政策有哪些变化"，系统检索到的 Top-3 文档都是 2023 年的政策。Critic 评估后发现时效性不满足 → 触发网络搜索获取最新政策 → 基于新文档生成回答。没有评估环节，系统会自信地拿两年前的过期信息给出"看似正确、实则错误"的答案。

### 第五坑：不是所有问题都值得大动干戈

有了上述能力后，系统每条查询都走完整的检索-评估-重写-多跳流水线。但"今天天气怎么样"这种问题，花半秒钟联网就行；"请分析全球气候变化对保险业的系统性影响"才值得深度检索。

**→ 解决方案：自适应路由（Adaptive RAG）**

在入口处放一个轻量级分类器，先判断问题复杂度。简单问题直接让 LLM 回答或做单步检索，复杂问题才启动多步推理流水线。本质上是**把算力花在刀刃上**。

### 第六坑：现实场景不只是"回答问题"

走到这里，RAG 已经能很好地回答各种复杂问题了。但企业场景里，用户的需求往往不是"回答一个问题"，而是**完成一个文档任务**。

比如会计拿到 100 张发票，ta 要的不是"这张发票的金额是多少"，而是：解析所有发票 → 提取关键字段 → 与采购订单核对 → 标记异常 → 生成付款建议。这是**多步骤、有状态、需要业务规则**的工作流。

**→ 解决方案：Agentic 文档工作流（ADW）**

ADW 把检索从"回答问题"升级为"执行文档工作流"：维护处理状态、协调多个 Agent 各司其职、应用领域业务规则、输出结构化结果。RAG 是"我问你答"，ADW 是"我把一堆文档交给你，你帮我把事办了"。

### 总结：演进不是堆名词，是填坑

```
坑1：关键词对不上 → 密集检索（语义匹配）
坑2：一个文档装不下 → 多跳检索（迭代推进）
坑3：关系丢了 → 图结构（显式建模实体关系）
坑4：相似≠有用 → Critic 评估（检索后质量判断）
坑5：简单问题大炮打蚊子 → 自适应路由（按需检索）
坑6：不只是回答问题 → ADW（端到端文档工作流）
```

每一次演进都是因为上一代的架构在真实场景中**摔了一跤**。理解了这些坑，才能真正理解为什么需要这些看似复杂的设计。

## 一、这是什么

Agentic RAG（Agentic Retrieval-Augmented Generation）是将自主 Agent 引入检索增强生成系统的新范式。不同于以往 RAG 依赖预设的静态检索管线，Agentic RAG 让 Agent 根据查询内容**动态决定**检索什么、从哪里检索、检索几次、以及如何整合信息。

核心论文：[[raw/编程笔记/rag/七大Agentic RAG框架技术解析 1|Agentic Retrieval-Augmented Generation: A Survey on Agentic RAG]] (arXiv:2501.09136, 2025)

## 二、RAG 发展历程

RAG 经历了五个主要发展阶段：

| 阶段               | 核心特点                       | 主要局限                    |
| ---------------- | -------------------------- | ----------------------- |
| **Naïve RAG**    | 基于关键词检索（TF-IDF/BM25），静态数据集 | 缺乏语义理解，输出碎片化，难以扩展       |
| **Advanced RAG** | 密集向量搜索（DPR），上下文重排，多跳检索     | 计算开销大，大规模场景可扩展性有限       |
| **Modular RAG**  | 混合检索策略，可组合流程，外部工具集成        | 复杂度提高，需要更多工程投入          |
| **Graph RAG**    | 图数据结构捕获实体关系，支持多跳推理         | 依赖高质量图数据，集成复杂           |
| **Agentic RAG**  | Agent 自主决策，动态路由，迭代细化       | 系统设计更复杂，对 Agent 协调能力要求高 |

### Naïve RAG

最基础的 RAG 实现。用 TF-IDF 或 BM25 做关键词检索，从静态数据集取回文档，直接拼接到 prompt 中让 LLM 生成。**优点是简单易实现**，但检索只看词汇匹配、不看语义，回答常常不连贯。

### Advanced RAG

引入**语义理解**。用 DPR（Dense Passage Retrieval）将查询和文档映射到同一向量空间，通过向量相似度检索，再用神经排序模型重排结果。支持多跳检索（从文档 A 找到线索再检索文档 B）。

### Modular RAG

将检索和生成流程拆成**独立可替换的模块**。核心创新：
- **混合检索**：稀疏检索（BM25）+ 密集检索（DPR）并行使用
- **工具集成**：接入外部 API、数据库、计算工具
- **可组合流程**：检索器、生成器等组件可按需替换和重组

### Graph RAG

用**图数据结构**表达实体间的关系和层次。通过图的节点连通性和路径检索来做多跳推理。适用于医疗诊断、法律研究等需要关系推理的场景。**关键瓶颈**：需要高质量图数据，非结构化场景难以应用。

### Agentic RAG

最新范式，核心突破是引入**自主 Agent**。Agent 不再执行固定流程，而是根据查询动态调整策略：选择数据源、迭代细化查询、评估检索质量、必要时触发外部搜索。

## 三、七大 Agentic RAG 架构

### 3.1 Single-Agent（路由器模式）

单个 Agent 集中管理检索、路由和整合。Agent 接收查询后分析类型，从结构化数据库（Text-to-SQL）、语义搜索（向量检索）、网络搜索、推荐系统等选项中**动态选择**最合适的数据源，然后将结果传递给 LLM 合成回答。

**适用场景**：工具和数据源数量有限的简单场景。

### 3.2 Multi-Agent（多智能体协作）

将职责**分配给多个专门 Agent**，由一个协调 Agent 统一调度。每个 Agent 专注一类数据源或任务：
- Agent 1：处理结构化查询（SQL 数据库）
- Agent 2：管理语义搜索（PDF、文档等非结构化数据）
- Agent 3：网络搜索和 API 调用
- Agent 4：推荐系统

各 Agent **并行执行**检索，最后由 LLM 将所有结果合成完整回答。

**适用场景**：需要同时查询多种异构数据源的复杂场景。

### 3.3 层次化 Agentic RAG

Agent 按**层级结构**组织。顶级 Agent 评估查询复杂度并做战略决策（优先哪些数据源），然后将任务**委派**给下层的专门 Agent。下层 Agent 独立执行后，结果由上层聚合合成。

**与 Multi-Agent 的区别**：Multi-Agent 是平级分工，层次化是有决策层级的上行下派。顶级 Agent 做的是"该优先查什么"的**策略判断**，而不只是"把任务分给谁"。

### 3.4 Corrective RAG（自我纠正）

引入**自我纠正机制**，核心由五个 Agent 组成：

1. **上下文检索 Agent**：从向量库检索初始文档
2. **相关性评估 Agent**：评估检索结果质量，标记不相关文档
3. **查询细化 Agent**：重写查询以提高检索精度
4. **外部知识检索 Agent**：文档不足时触发网络搜索
5. **回答合成 Agent**：整合所有验证过的信息生成最终回答

**核心思路**：检索→评估→如果不满意→细化查询重新检索→如果还不够→外部搜索。形成闭环的质量保证。

### 3.5 Adaptive RAG（自适应）

根据查询复杂度**动态选择策略**，用一个小型分类器模型预判查询类型：

- **简单查询**（如"水的沸点"）：**跳过检索**，直接用 LLM 知识回答，节省成本
- **中等查询**（如"最新电费账单"）：单步检索
- **复杂查询**（如"某城市十年人口变化及原因"）：多步迭代检索

**核心价值**：对简单问题不做无谓检索，在成本和回答质量之间取得平衡。

### 3.6 Graph-Based Agentic RAG（Agent-G）

将**图知识库**与非结构化文档检索结合。核心组件：

- **检索器库**：一组专门 Agent，动态选择图数据或文本数据
- **批评模块（Critic）**：验证检索结果的相关性和质量，标记低置信度结果
- **反馈循环**：通过迭代验证和重新查询细化检索
- **LLM 整合**：将验证后的结构化+非结构化数据合成回答

**适用场景**：医疗（疾病-症状映射）、法律等同时需要结构化关系和非结构化文本的领域。

### 3.7 Agentic 文档工作流（ADW）

ADW 是 RAG 的**最远延伸**，不只检索信息，而是完成整个文档处理链路：

1. **文档解析**：用企业级工具（如 LlamaParse）提取结构化字段
2. **状态维护**：跨多步工作流追踪文档处理进度
3. **知识检索**：从外部知识库获取参考信息
4. **Agent 协调**：应用业务规则、多跳推理、生成建议
5. **可操作输出**：生成结构化的报告和建议

**与传统 RAG 的关键区别**：RAG 的目标是"回答一个问题"，ADW 的目标是"完成一个文档任务"（如发票处理、合同审查），中间需要维护状态和执行多步业务逻辑。

### 三种范式对比

| 维度 | 传统 RAG | Agentic RAG | ADW |
|---|---|---|---|
| 目标 | 回答查询 | 动态检索+推理 | 端到端文档任务自动化 |
| 检索方式 | 静态管线 | Agent 动态决策 | 多步协调+状态管理 |
| 输出 | 文本回答 | 增强的回答 | 结构化报告/可操作建议 |
| 状态管理 | 无状态 | 有限状态 | 全链路状态追踪 |

## 四、关键洞察

1. **RAG 不会消亡，而是进化**：Agentic RAG 不是对 RAG 的替代，而是 RAG 的自然演进——从静态管线走向动态决策系统
2. **Agent 的核心价值是动态路由**：不是"查得更准"，而是"知道该查什么、什么时候查、查到什么程度算够"
3. **不同架构适配不同复杂度**：从单 Agent 路由到多层次协调到 ADW，选择取决于查询复杂度、数据源多样性和任务目标
4. **评估和纠正闭环是关键**：Corrective RAG 和 Agent-G 的 Critic 模块说明，**检索后的质量判断**比检索本身更需要智能化
