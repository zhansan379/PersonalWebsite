# RAG 综述（2024 经典论文）

> 同济 & 复旦联合出品：系统梳理 RAG 的三代范式、三大核心组件、评估体系及未来方向。是理解 RAG 技术全景的必读综述。

核心论文：[[raw/编程笔记/rag/ai_latex_trans_arxiv_2312.10997v5_2139274b-004c-4ba4-ad6a-6db43a64734e-trans.pdf|Retrieval-Augmented Generation for Large Language Models: A Survey]] (arXiv:2312.10997v5)

## 〇、这篇论文做了什么

这篇综述覆盖了 100+ 篇 RAG 研究，用一个统一框架把散落的技术点串了起来：

- **三代范式**：Naive RAG → Advanced RAG → Modular RAG，每代解决上一代的瓶颈
- **三维剖析**：把 RAG 拆成检索、生成、增强三个核心组件，每个组件详解技术路线
- **完整评估**：覆盖 26 个下游任务、近 50 个数据集，梳理了四大评估工具
- **未来判断**：RAG vs 长上下文、鲁棒性、多模态等 7 个方向的前瞻分析

## 一、三代 RAG 范式

论文最核心的贡献是提出了 RAG 的三代范式分类，这个框架已经成为行业的通用语言。

### 1.1 Naive RAG（朴素 RAG）

最原始的"检索-读取"流程：索引 → 检索 → 生成。

- **索引**：原始数据（PDF/HTML/Word）清洗 → 分块 → Embedding → 向量数据库
- **检索**：用户查询向量化 → 计算与块的相似度 → 取 Top-K
- **生成**：查询 + 检索结果拼接为 prompt → LLM 生成回答

Naive RAG 的三大痛点：
1. **检索问题**：精度和召回率不足，关键信息遗漏
2. **生成问题**：幻觉（生成检索上下文不支持的答案）、毒性、偏见
3. **增强障碍**：多源信息集成困难，冗余导致重复回答，单一检索对复杂问题不够

### 1.2 Advanced RAG（高级 RAG）

在 Naive RAG 基础上，围绕**检索前**和**检索后**两个环节做了优化：

**检索前优化**：
- 数据粒度控制（滑动窗口、细粒度分割）
- 索引结构优化（分层索引、元数据附加）
- 查询优化（查询重写、查询扩展、查询变换）

**检索后优化**：
- **重排序（Rerank）**：把最相关的内容移到 prompt 的前端，解决 LLM"迷失在中间"的问题
- **上下文压缩**：用小型语言模型删除不重要的 token，在保持信息完整性的同时缩短上下文

### 1.3 Modular RAG（模块化 RAG）

不再是一条固定的链式管线，而是**可替换、可组合的模块系统**。核心创新有两层：

**新增模块**：
| 模块 | 功能 | 代表方法 |
|---|---|---|
| Search | 跨搜索引擎、数据库、知识图谱直接搜索 | KnowledGPT |
| Memory | 利用 LLM 记忆池指导检索，自增强 | Self-Mem |
| Routing | 根据查询选择最优检索路径 | 语义路由/元数据路由 |
| Predict | 直接让 LLM 生成上下文，减少冗余噪声 | GenRead |
| Task Adapter | 为下游任务定制零样本/少样本 prompt | UPRISE, PROMPTAGATOR |

**新模式**（不再只是"检索→读取"）：

- **重写-检索-读取**：LLM 先重写查询再检索（RRR）
- **生成-读取**：LLM 直接生成上下文替代检索（GenRead）
- **迭代检索-生成**：检索和生成交替进行，互相增强（ITER-RETGEN）
- **自适应检索**：根据场景自主决定是否检索（FLARE, Self-RAG）

这三代范式的关系是**递进继承**，不是互相替代。Modular RAG 建立在 Advanced 和 Naive 的基础上。

## 二、三维核心剖析

论文将 RAG 系统拆为三个可以独立优化的维度：

### 2.1 检索（Retrieval）— 找什么、怎么找

**检索源**：

| 数据类型 | 来源 | 挑战 |
|---|---|---|
| 非结构化文本 | Wikipedia、领域语料 | 应用最广泛，但覆盖面受限 |
| 半结构化数据 | PDF（文本+表格） | 分块可能割裂表格，语义搜索困难 |
| 结构化数据 | 知识图谱（KG） | 信息精确，但构建维护成本高 |
| LLM 生成内容 | 模型自身知识 | 新颖方向，生成上下文有时比检索更准 |

**检索粒度**（从细到粗）：词项 → 短语 → 句子 → **命题（Proposition）** → 块 → 文档。其中"命题"是 DenseX 提出的概念——每个命题封装一个独立事实，在精度和完整性之间取得平衡。

**索引优化**：
- 分块策略：大块捕获更多上下文但有噪声；小块更干净但丢失上下文。Small2Big 方案用小句子检索、用前后文补充
- 元数据附加：页码、文件名、时间戳等，支持过滤和时间感知检索。还可以人工构造摘要和假设性问题（反向 HyDE）
- 结构索引：父子关系的分层索引；知识图谱索引（KGP，连接多文档间的段落和结构关系）

**查询优化**：
- **查询扩展**：多查询并行执行；子问题分解（Least-to-Most）；CoVe 验证链减少幻觉
- **查询变换**：查询重写（RRR）；后退式问题（Step-back）；HyDE（构造假设答案→基于答案嵌入找相似文档）
- **查询路由**：元数据过滤、语义路由、混合路由

**嵌入模型**：
- 稀疏编码（BM25）+ 密集检索（BERT 架构）互补
- 主流模型：AngIE, Voyage, BGE，基于多任务指令微调
- 微调嵌入：领域数据集微调、LLM 监督信号微调（LSR）、RLHF 风格强化学习微调

### 2.2 生成（Generation）— 怎么用、怎么调

**上下文策展**：检索后的文档不能直接塞给 LLM。

- **重排序（Rerank）**：规则方法（多样性、MRR）或模型方法（SpanBERT、Cohere rerank、bge-reranker、GPT）
- **上下文选择/压缩**：LLMLingua 用小模型删除不重要的 token→人看不懂但 LLM 能理解的形式；Filter-Reranker 范式用小模型当过滤器、大模型做重排序；LLM 自身评估（如 Chatlaw 中 LLM 自评引用法条的相关性）

**LLM 微调**：
- 领域数据微调补充知识
- 适配数据格式和输出风格
- 强化学习对齐人类/检索器偏好
- 检索器-生成器协同微调（RA-DIT，用 KL 散度对齐评分函数）

### 2.3 增强（Augmentation）— 查几次、怎么迭代

论文总结了三种增强过程：

| 模式        | 机制                    | 代表方法            | 适用场景                   |
| --------- | --------------------- | --------------- | ---------------------- |
| **一次检索**  | 标准流程，检索一次后生成          | 大多数 RAG 系统      | 简单事实查询                 |
| **迭代检索**  | 检索→生成→再检索→再生成，交替多次    | ITER-RETGEN     | 需要"检索增强生成、生成增强检索"的协同任务 |
| **递归检索**  | 基于先前结果逐步细化搜索查询，形成反馈循环 | IRCoT, ToC      | 用户需求不明确、信息高度专业化        |
| **自适应检索** | LLM 自主判断何时需要检索、何时停止   | FLARE, Self-RAG | 避免不必要的检索，灵活控制          |

**自适应检索的关键机制**：
- FLARE：监控生成过程的置信度（词条概率），低置信度时自动触发检索
- Self-RAG：引入"反射标记"——模型自省地决定是否检索（retrieve 标记）并进行自我批评（critic 标记）

## 三、评估体系

### 3.1 下游任务与数据集

RAG 的核心任务仍是 QA，但已扩展到 26 个任务、近 50 个数据集：

| 任务类型 | 代表数据集 | 说明 |
|---|---|---|
| 单跳 QA | Natural Questions, TriviaQA, SQuAD | 最基础，一张文档能回答 |
| 多跳 QA | HotpotQA, 2WikiMultiHopQA, MuSiQue | 需要跨文档推理 |
| 长文本 QA | ELI5, NarrativeQA, ASQA | 需要综合大量材料 |
| 领域 QA | Qasper（科学）、COVID-QA、CMB（医疗） | 专业领域 |
| 对话生成 | Wizard of Wikipedia | RAG 增强对话 |
| 信息抽取 | WikiEvent, RAMS, T-REx | 事件抽取、关系抽取 |
| 代码搜索 | CodeSearchNet | RAG 用于代码 |
| 事实验证 | FEVER, PubHealth | 核查事实真伪 |
| 推理 | HellaSwag, CSQA, GSM8K | 常识/复杂/数学推理 |

### 3.2 三个质量分数 + 四个基本能力

**三个质量分数**（评估 RAG 输出质量）：
- **上下文相关性**：检索内容是否精准、无冗余
- **答案忠实度**：答案是否基于检索上下文，有无编造
- **答案相关性**：答案是否直接回答了问题

**四个基本能力**（评估 RAG 鲁棒性）：
- **噪声鲁棒性**：面对不相关文档是否不受干扰
- **否定拒绝**：检索内容不够时，能否识别并拒绝回答（而不是硬编）
- **信息集成**：能否从多个文档中合成信息
- **反事实鲁棒性**：能否识别并忽略文档中的已知错误

### 3.3 四大评估工具

| 工具 | 定位 | 评估维度 |
|---|---|---|
| RGB | Benchmark | 噪声鲁棒性、否定拒绝、信息集成、反事实鲁棒性 |
| RECALL | Benchmark | 反事实鲁棒性 |
| RAGAS | 自动化工具 | 上下文相关性、忠实度、答案相关性 |
| ARES | 自动化工具 | 同上，但用 LLM 做评判 |
| TruLens | 自动化工具 | RAG 三元组（相关性、忠实度、答案质量） |
| CRUD | Benchmark | 创意生成、知识密集型 QA、纠错、摘要 |

## 四、七个未来方向

1. **RAG vs 长上下文**：LLM 上下文窗口扩展到 200K+ token 后，RAG 还有必要吗？论文的判断是**有必要**——分块检索提升推理速度；检索过程可观测、可验证；长上下文仍是黑盒。同时超长上下文也为 RAG 处理更复杂的问题提供了新机会。

2. **RAG 鲁棒性**：噪声文档反而可能提升准确率 30%+（反直觉发现），说明需要专门的检索-生成集成策略。

3. **混合方法**：RAG + 微调的最佳组合方式（顺序/交替/端到端）有待探索。用小模型做轻量级评估器是趋势（如 CRAG）。

4. **RAG 缩放定律**：LLM 有明确的缩放定律，但 RAG 的缩放行为尚不明确。有趣的是"逆缩放定律"——小模型可能优于大模型。

5. **生产级 RAG**：检索效率、大数据集召回率、数据安全（防止 LLM 泄露文档源/元数据）是工程关键挑战。生态工具（LangChain, LlamaIndex, Flowise AI）正在向定制化、简化、专业化趋势分化。

6. **多模态 RAG**：从文本扩展到图像（RA-CM3, BLIP-2）、音频（GSS, UEOP）、视频（Vid2Seq）、代码（RBPS, CoK）。

7. **评估方法需跟上**：RAG 发展迅速，评估体系要同步演进，确保性能评估准确且有代表性。

## 五、与 Agentic RAG 的关系

这篇论文发表于 2024 年初，系统梳理了 RAG 的基础架构，但它覆盖到的最前沿是 Modular RAG 中的自适应检索（FLARE, Self-RAG），尚未涉及 2025 年兴起的 Agentic RAG。可以把这篇论文理解为**RAG 地基**，而 [[编程/rag/Agentic RAG 综述|Agentic RAG]] 是建造在地基上的新一代。

关键对应关系：
- 论文中的**自适应检索**（Self-RAG 的反射标记）→ Agentic RAG 中 Agent 自主决策的原型
- 论文中的**模块化检索模式**（路由、迭代、递归）→ Agentic RAG 中多 Agent 协作的前身
- 论文中的**查询路由** → Agentic RAG 中 Single-Agent 路由模式的基础
