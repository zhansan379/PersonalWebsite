# 面试整理：为什么用 BigDecimal 不用 double？

> 这是**场景题 + 原理题**的混合考题，考的是你能不能讲清「**为什么浮点数会丢精度 → 底层是二进制表示 → BigDecimal 怎么解决 → 使用时有哪些坑**」这条完整链路。电商/支付/对账场景几乎是必考。
> 一句话记忆：**二进制不能精确表示所有小数（就像十进制表示不了 1/3），double 跑二进制运算必然有舍入误差；金钱计算要求精确，所以用 BigDecimal——它是十进制 + 整数数组实现，精确且可控舍入。**

## 一、回答逻辑（五步骨架）

```
1. 一句话点破原因：double 用二进制浮点，无法精确表示很多十进制小数
2. 底层原理：二进制小数 = 1/(2^n) 的和，0.1 表示不了
3. 给出复现：0.05+0.01 输出 0.060000000000000005（直接写例证）
4. 引出 BigDecimal：十进制 + 任意精度，怎么解决
5. 抛出使用要点 + 坑：必须用字符串构造、scale、舍入模式、不可用 equals 比较
```

**开场句模板：**
> 因为 double 做的是**二进制浮点运算**，而**二进制没法精确表示 0.1 这样的十进制小数**（就像十进制也精确表示不了 1/3），所以运算必然产生舍入误差。金融、金额计算要求精确，所以用 BigDecimal——它是**十进制定点数**，能精确表示并对舍入规则做显式控制。

## 二、核心原理（得分点）

### 2.1 为什么 double 会丢精度（机理）

- 计算机用二进制存浮点数：能精确表示的是能用 **`1/(2^n)` 累加**拼出来的数（如 `0.5=2⁻¹`、`0.25=2⁻²`、`0.125=2⁻³`）。
- `0.1` 无法写成有限个 `1/(2^n)` 之和 → 在二进制下是**无限循环小数**，只能截断存储 → 产生舍入误差。
- 类比干扰项：十进制表示不了 `1/3 = 0.3333...`，本质同一个道理。

**必背复现例：**
```java
System.out.println(0.05 + 0.01);    // 0.060000000000000005
System.out.println(1.0 - 0.42);     // 0.5800000000000001
System.out.println(4.015 * 100);    // 401.49999999999994
System.out.println(123.3 / 100);    // 1.2329999999999999
```

### 2.2 BigDecimal 怎么解决（机制差异）

| 维度 | double | BigDecimal |
|---|---|---|
| 进位制 | **二进制浮点**（IEEE 754） | **十进制**定点数 |
| 内存 | 8 字节，二进制近似 | 不可变对象 + **BigInteger 整数部分 + scale 小数位**，任意精度 |
| 精确性 | 不精确，舍入误差累积 | 精确十进制，误差可控 |
| 舍入 | 交给硬件规则（不可控） | **显式指定舍入模式**（RoundingMode） |
| 适用 | 科学计算、性能敏感、近似即可 | 金额、对账、需要精确的结果 |

> **加分表述**：BigDecimal 本质是**「整数 × 10⁻ˢᶜᵃˡᵉ」** 的数学表示，把运算还原成整数运算（scale 对齐后加减、乘法、除法带舍入），数字完全按十进制走，所以不会引入二进制浮点的误差。这也是它能存储任意精度十进制数的原因。

## 三、使用 BigDecimal 的关键点（面试真正的加分段）

| 要点 | 说明 | 反例 / 正确写法 |
|---|---|---|
| **必须用字符串构造** | `new BigDecimal("0.1")` 才精确；直接 `new BigDecimal(0.1)` 会把 double 已经丢了精度的值**再放大** | ❌ `new BigDecimal(0.1)` → 0.1000000000000000055511…<br>✅ `new BigDecimal("0.1")` → 精确 0.1 |
| **加减乘** | `add` / `subtract` / `multiply`，**BigDecimal 不可变，返回新对象** | `num1.add(num2)` 要接收返回值，别只调不接 |
| **除法的坑** | 无限循环小数除法不指定精度会抛 `ArithmeticException: Non-terminating decimal expansion` | 除法必须传 `(val, scale, RoundingMode)` |
| **舍入模式** | 八种 `RoundingMode`，金额最常见的 `HALF_UP`（四舍五入） | `setScale(2, RoundingMode.HALF_UP)` |
| **比较用 `compareTo` 而非 `equals`** | `equals` 比较 scale（0.1 != 0.10）；`compareTo` 只比数值 | 判断对等用 `a.compareTo(b) == 0` |

## 四、高频追问预测

### 4.1 原理方向

| 追问 | 回答要点 |
|---|---|
| double 到底吃什么亏？ | 二进制表示不了 0.1 这类小数，运算结果有舍入误差；且误差会**累积**，多次运算差别更大。 |
| 为什么二进制表示不了 0.1？ | 0.1 = 1/10，分母 10 = 2×5，含质因数 **5**，所以不能写成有限个 `1/(2^n)` 之和；而 0.5、0.25、0.125 分母只有 2，能精确表示。 |
| 那十进制不也表示不了 1/3？ | 对，原理同理。区别在于计算机**底层就按二进制存储** double，所以 0.1 从存入那一刻就失真了；十进制是人类视角，BigDecimal 用字符串/整数保存十进制语义，绕开了底层二进制近似。 |
| 是不是所有 double 小数都不精确？ | 不是所有。**分母只含 2 的幂**的数是精确的（0.5、0.25、2 的负幂组合）；含其他质因数（如 3、5、7…）的才不精确。 |
| double 什么时候能用？ | 精度要求不高、性能敏感、范围大的科学计算；图形/物理/算法里没关系。金额类、身份标识、比较相等一律用 BigDecimal 或整数存厘/分。 |

### 4.2 BigDecimal 使用方法方向

| 追问 | 回答要点 |
|---|---|
| 为什么 `new BigDecimal(0.1)` 还是不精确？ | 因为 **0.1 已经是 double 类型，其二进制值本身就不精确**（近似 0.1000000000000000055511…），构造函数只是把它如实搬进来。用**字符串** "0.1" 才能按精确的十进制注册。 |
| 除法不指定参数会怎样？ | 除不尽（无限循环小数）时抛 `ArithmeticException`（Non-terminating decimal expansion）。必须传 `(除数, scale, roundingMode)`。 |
| `equals` 和 `compareTo` 区别？ | `equals` 要求数值**和 scale 都相等**（`0.1` vs `0.10` 不相等）；`compareTo` 只看数值大小。**用 BigDecimal 判断相等应优先 `compareTo`**，否则 `HashMap`/`HashSet` 里会踩坑。 |
| 怎么转成正常 double / 字符串输出？ | `doubleValue()`（会再丢一次精度）、`toString()` / `toPlainString()`（去掉科学计数法）。展示用 `toPlainString`。 |
| 性能如何？会不会太慢？ | 比 double 慢几个数量级（不可变对象 + BigInteger 运算 + 每次分配新对象）。这也是**能用 double 就别滥用的原因**——精确和性能是权衡。高并发计费可能拆成整数（分/厘）或特化工具。 |

### 4.3 实战 / 场景结合

| 追问 | 回答要点 |
|---|---|
| 电商金额为什么不能用 double？ | 0.05 + 0.01 在 double 里 = 0.060000000000000005，一旦涉及下单、优惠、对账，误差会累积成**无法下单 / 对账不平 / 利润算错**，并发越高危害越大。 |
| 金额有没有更好的存法？ | 有：整数（**分/厘**）存数据库 + 运算，性能最好；或 BigDecimal 存 `decimal(20,2)`。别用 float/double 当货币。 |
| BigDecimal 存数据库用什么类型？ | MySQL 用 `DECIMAL(M,D)` 精确十进制类型，与 BigDecimal 一一对应，不会丢精度；不要用 `DOUBLE/FLOAT` 存金额列。 |
| 和 float 比呢？float 更糟？ | 是。float 只有约 7 位有效十进制，double 约 15 位，float 精度更低、误差更大，金额场景同样禁用。 |
| 与之前类型转换的"精度损失"呼应？ | 类型转换那里的 `double→int` 截断小数、`float` 丢尾数，本质都是**浮点表示能力有限**；BigDecimal 是在"源头"用十进制表示法消除误差，而不是事后补救。 |
| 为什么 BigDecimal 加 `scale` 字段？ | 记录小数位数，用于对齐运算、控制 `setScale` 舍入结果，也是 `equals` 区分 0.1/0.10 的原因。 |
| BigDecimal 是线程安全 / 不可变吗？ | **不可变**：每个运算返回新对象，原对象不变。因此多个线程共享同一 BigDecimal 引用是安全的（读安全，写=产生新对象）。 |

## 五、口述版答案（40 秒）

> 用 BigDecimal 不用 double，是因为 double 做**二进制浮点运算**会丢精度。计算机用二进制表示小数，只能精确表示 `1/(2^n)` 的和，而 **0.1 这种分子分母含其他质因数的数，在二进制里是无限循环小数**，存进去就被截断，于是 `0.05 + 0.01` 得出 `0.060000000000000005`。金额计算一旦有这种误差，就会出现下单、对账问题。BigDecimal 是**十进制定点数**，内部用整数加 scale 表示数值，运算走十进制，所以精确可控。但用它有几个关键点：**必须用字符串构造**，`new BigDecimal(0.1)` 会把已经失真的 double 再放大；**除法要指定 scale 和舍入模式**否则可能抛异常；**比较要用 compareTo 而不是 equals**，因为 equals 会连小数位一起比。更工程化的做法是金额直接**用整数存分**，或数据库用 DECIMAL 类型。
