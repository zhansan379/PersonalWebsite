# 面试整理：装箱与拆箱

> 这是 Java 基础面试的**必问题 + 坑题高发区**，考的核心是「**编译器到底替你把代码改成了什么样**」——Is写 `Integer i = 10` 你以为轻松，其实背后是 `Integer.valueOf(10)`。追问会一路滑向 `IntegerCache`、`==` 比较、空指针。一句话提分点：**能不能说出自动装箱的"编译器替换"本质 + IntegerCache 的范围**。
> 一句话记忆：**装箱 = 基本类型 → 包装类的编译器自动替换（本质是 `valueOf`），拆箱 = 包装类 → 基本类型的自动替换（本质是 `.xxxValue()`）；缓存只对 -128~127 生效。**

## 一、回答逻辑（四步骨架）

```
1. 一句话定调 + 给代码例子：什么是装箱拆箱
2. 揭示本质：是编译器的「语法糖」，替换成 valueOf / xxxValue
3. 分类说清发生时机：赋值时、方法调用时
4. 抛出坑 + 引导追问：IntegerCache、== 比较、NPE、循环性能
```

**开场句模板：**
> 装箱是把基本类型转成对应的包装类对象，拆箱是反过来。它们本质上是**编译器的语法糖**——装箱会被替换成 `Integer.valueOf(...)`，拆箱会被替换成 `.intValue()`，从 JDK5 开始自动完成，无需手写转换。但它有几个坑：缓存范围、`==` 比较、循环里反复装箱、以及拆箱发生空指针。

## 二、回答要点

### 2.1 本质与时机（得分点）

| 发生时机 | 例子 | 编译器实际行为 |
|---|---|---|
| **赋值时** | `Integer i = 10;` | 装箱 → 替换为 `Integer.valueOf(10)` |
| **赋值时拆箱** | `int n = i;` | 拆箱 → 替换为 `i.intValue()` |
| **方法调用** | `show(3)`（参数是 Integer） | 实参需装箱 → `valueOf(3)` |
| **方法返回** | `int result = show(3)`（返回 Integer） | 返回值需拆箱 → `.intValue()` |

> 一句话讲点透 vs 手动版对比（JDK5 前的写法）：手动 `Integer.valueOf(3)` / `.intValue()`，JDK5 起编译器代劳。

### 2.2 核心坑一：`IntegerCache` 缓存（最高频得分点）

- 自动装箱 `Integer.valueOf(int)` 会先查**缓存** `IntegerCache`，命中直接返回**缓存里的同一个对象**。
- **缓存范围：-128 ~ 127**（默认，可通过 `-XX:AutoBoxCacheMax` 调大，仅对 Integer）。
- 超出范围才 `new Integer(...)` 新建对象。
- 由此引出最常见的 `==` 比较题：**范围内 == 是 true，范围外 == 是 false**。

### 2.3 核心坑二：循环里反复装箱（性能）

```java
Integer sum = 0;
for (int i = 1000; i < 5000; i++) {
    sum += i;   // 每次都：拆箱 sum.intValue() + i，再装箱 Integer.valueOf(result)
}
```
- `sum += i` 实际是 `sum = sum + i`：先**拆箱**做加，再**装箱**存回。
- 由于循环里数值超 cache 范围，**每次都 new 一个新 Integer 对象**，几千次循环就产生几千个对象，加重 GC、影响性能。
- **教训**：正确声明变量类型（用 `int`），避免隐式反复装箱。

## 三、最容易错的对比 / 陷阱

| 场景 | 结果 | 解释 |
|---|---|---|
| `Integer a=127; Integer b=127; a==b` | **true** | 都在 IntegerCache 范围内，同一对象 |
| `Integer a=128; Integer b=128; a==b` | **false** | 超出缓存，各 new 一个对象 |
| `Integer a=127; int b=127; a==b` | **true** | 有基本类型参与时 a 会被**拆箱**比较数值 |
| `new Integer(100) == new Integer(100)` | **false** | 显式 new 不走缓存 |
| `null 参与拆箱` | **NPE** | `int x = someInteger;` 若 someInteger 为 null → `NullPointerException` |
| 循环里 `Integer sum += i` | 创建大量对象 | 见 2.3 |

## 四、高频追问预测

### 4.1 缓存 / 相等判断方向（必考）

| 追问 | 回答要点 |
|---|---|
| IntegerCache 范围多大？能改吗？ | 默认 **-128~127**；可用 `-XX:AutoBoxCacheMax=xxx` 调整上限（仍受下限 -128 约束），仅 Integer 有此配置，Long/Short/Character 固定缓存。 |
| 为什么 -128~127 要缓存？ | 老生常谈但正确：这个区间装箱**高频**（如循环计数的常见取值），缓存避免频繁 new 对象，提升性能、减少 GC。 |
| `==` 比较对象到底比什么？ | 对引用类型比**引用地址**（是否同一对象）；对基本类型比**数值**。Integer 与 int 混合比较时先拆箱再比值。 |
| 那对象相等怎么比？ | 用 `equals()` 比数值；Integer 的 `equals` 内部就是 `intValue() == ...` 比较值。 |
| 除了 Integer 还有哪类缓存？ | `IntegerCache`、`LongCache`、`ShortCache`、`ByteCache`、`CharacterCache`（0~127）——byte/short/int/long 都在 -128~127，char 0~127。Float/Double **无缓存**（浮点按数值语义）。 |

### 4.2 拆箱 NPE 方向

| 追问 | 回答要点 |
|---|---|
| 拆箱会抛什么异常？ | `NullPointerException`。拆箱调用 `.intValue()`，包装类引用为 `null` 时调用方法即 NPE。`Integer x = null; int y = x;` 崩溃。 |
| 哪些地方最容易踩拆箱 NPE？ | ① 自动拆箱赋值 `int y = x`；② `Integer` 参与运算符（`x + 1` 会拆箱）；③ 三目运算符（两个分支类型不一时），如 `Integer n = flag ? 1 : null` 编译期把 null 强拆；④ 方法返回值 Integer 赋给 int。 |
| 数据库/ORM 里为什么常见？ | `null` 从 DB 读到包装类字段，在参与比较/运算时拆箱就 NPE；这也是 MyBatis/JPA 字段映射容易踩的坑。 |

### 4.3 性能方向

| 追问 | 回答要点 |
|---|---|
| 自动装箱对性能的影响？ | 主要来自**对象创建**：每次装箱可能 new 新对象（超缓存时），大量发生会加重 GC。拆箱本身走指令，代价小。 |
| 避免性能问题的写法？ | 优先用**基本类型**；确需包装类时用 `Integer.valueOf` 复用缓存；集合容器（List<Integer>）不得不用包装类时，尽量批量且避免循环内重复装箱。 |
| `new Integer(int)` 还能用吗？ | **已废弃**（JDK9 @Deprecated）。应统一用 `Integer.valueOf(int)` 或自动装箱，后者走缓存更省内存语义也更安全。 |
| 为什么还要有包装类？ | ① 泛型只能接收引用类型（`List<int>` 不行）；② 需要 `null` 语义（表缺失）；③ 提供工具方法（`parseInt`、`String.valueOf`、比较、常量）。 |

### 4.4 与类型转换 / 字符串联动

| 追问 | 回答要点 |
|---|---|
| Integer 和 int 是同一个吗？ | 不是。int 是基本类型（栈上/局部变量存值），Integer 是包装类（对象，存引用 + 堆上对象）；自动机制只在赋值和运算时出现。 |
| 字符串转 int 的方法？ | `Integer.parseInt("123")`（返回 int，严格解析非数字抛 `NumberFormatException`）；`Integer.valueOf("123")`（返回 Integer，同样抛异常）。 |
| 包装类还和 JVM 哪里相关？ | 涉及类型转换、常量池、以及前面学的大整数/精度议题的收尾呼应；本质都是"基本类型 ↔ 引用类型"的桥接设计。 |

## 五、口述版答案（40 秒）

> 装箱是把基本类型转成包装类，拆箱是反过来，二者是**编译器的语法糖**。手写的话装箱是 `Integer.valueOf(10)`、拆箱是 `.intValue()`，JDK5 起自动完成。它主要在**赋值和方法调用**时触发。但有几个关键考点：第一，**装箱会命中 IntegerCache 缓存**，范围默认 **-128~127**，在这个范围内多次装箱返回同一个对象，所以 `Integer a=127; Integer b=127; a==b` 是 true；一旦超过 128 就各自 new 对象，`==` 就是 false——比较对象相等要用 equals。第二，**拆箱可能空指针**，`Integer` 为 null 时任何拆箱操作（赋值、运算）都会抛 NPE。第三，**循环里反复装箱**，比如 `Integer sum=0;` 在一个几千次的循环里 `sum += i`，每次都要先拆箱再加再装箱，而值大多超出缓存，就会创建几千个新对象影响性能，所以应该用基本类型 `int`。另外 `new Integer(int)` 在 JDK9 已废弃，要统一用 `Integer.valueOf`。
