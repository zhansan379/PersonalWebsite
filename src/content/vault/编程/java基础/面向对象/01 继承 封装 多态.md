# 继承 封装 多态

> 面向对象三大特性：**继承**复用代码、**封装**隐藏细节只暴露接口、**多态**用相同接口在不同实例上产生不同行为。其中多态是重点——它靠「继承/接口实现 + 重写 + 向上转型」三者共同实现，也是绝大多数设计模式的底层支撑。
>
> 第六章把多态从**语言层**推到**工程层**：在 Spring 里「一个接口多个实现」会多出一个语言层没有的问题——**容器该注入哪一个**，这是接口多态最常踩坑的地方。

## 一、三大特性速览

| 特性 | 一句话 | 核心价值 |
|---|---|---|
| 继承 | 子类获得父类的属性与方法 | **复用代码** |
| 封装 | 属性和方法结合在一起，只暴露接口供外部交互 | **增强安全性**、简化编程 |
| 多态 | 相同接口、不同实例、不同操作 | **扩展性**与**解耦** |

## 二、封装

把**属性和方法结合在一起**，对外只暴露必要的接口，内部实现细节隐藏。

- **增强安全性**：外部无法随意修改内部状态，只能通过约定好的接口操作；
- **简化编程**：调用方只需关心"能做什么"，不必关心"怎么做"。

## 三、继承

子类继承父类，直接获得父类的属性和方法，从而**复用代码**。

继承同时也是**多态的前提之一**——只有存在父子（或接口与实现）关系，才可能发生"子类替换父类"。

## 四、多态

### 4.1 多态分为哪两种

| 类型 | 实现方式 | 确定时机 |
|---|---|---|
| 静态多态 | **重载**（overload） | **编译时** |
| 动态多态 | **重写**（override）、**接口实现** | **运行时** |

> 面试常见追问：**「子类替换父类靠什么实现？」** → 答**运行时多态**，依靠 **重写 + 继承 / 接口 + 向上转型**，**和重载无关**。

### 4.2 重写 vs 重载

| | 重写（override） | 重载（overload） |
|---|---|---|
| 参数 | **相同参数**，子类重写父类方法 | **不同参数** |
| 绑定时机 | 运行时（看实际对象类型） | 编译时即可确定调用哪个方法 |
| 作用 | 同一接口、不同实例产生不同行为 | 同一方法名因参数不同而实现不同逻辑 |

**重写实现动态多态的例子**：

```java
// 接口：定义发声标准
interface Animal {
    void makeSound();
}

// Dog 实现接口
class Dog implements Animal {
    @Override
    public void makeSound() {
        System.out.println("汪汪");
    }
}

// Cat 实现接口
class Cat implements Animal {
    @Override
    public void makeSound() {
        System.out.println("喵喵");
    }
}

// 测试
public class Test {
    public static void main(String[] args) {
        // 接口引用指向实现类
        Animal a1 = new Dog();
        Animal a2 = new Cat();
        a1.makeSound(); // 汪汪
        a2.makeSound(); // 喵喵
    }
}
```

同一行 `makeSound()` 调用，因实际对象不同而输出不同结果——这就是动态多态。

### 4.3 向上转型（自动转型，常用）

**定义**：**父类 / 接口引用 = 子类对象**，编译器自动完成，无需强转。

```java
Animal animal = new Dog(); // 向上转型
```

**特点**：

1. **安全无异常**；
2. 只能调用父类 / 接口中**存在的方法**，**不能直接调用子类独有的方法**。
   例：`Dog` 有专属方法 `guard()`，则 `animal.guard()` 直接**编译报错**。

**作用**：实现多态，统一管理所有子类，通用方法统一调用。

### 4.4 向下转型（强制转型，有风险）

**定义**：把向上转型后的父类引用，**强制转回子类类型**。

```java
Animal animal = new Dog();
Dog dog = (Dog) animal; // 向下强制转型
dog.guard();            // 此时可以调用 Dog 独有方法
```

**风险**：如果引用实际指向的对象**不是**目标子类，会抛出 `ClassCastException` 类型转换异常。

> 实践建议：向下转型前先用 `if (animal instanceof Dog)` 判断，避免运行时异常。

## 五、多态解决的核心问题

1. **扩展性**：新增子类 / 实现类，无需修改原有调用代码，符合**开闭原则**；
2. **代码解耦**：上层只依赖父类 / 接口，不依赖具体实现类（**依赖倒置**）；
3. **消除分支判断**：不用大量 `if / else / switch` 判断类型，靠多态自动匹配逻辑；
4. **代码复用**：统一一套调用规范，不同业务各自实现，统一入口调用；
5. 是大量**设计模式**（策略、模板、工厂、装饰器等）的底层核心支撑。

## 六、接口多态的工程落地：Spring 多实现注入

前面讲的都是**语言层**的多态：接口引用指向不同实现，运行时决定行为。但在 Spring 项目里，「接口 + 多实现」会多出一个语言层没有的问题——**容器该把哪个实现注进来**。

### 6.1 问题现场：从「唯一匹配」到「启动失败」

以 `QueryRewriteService`（查询改写策略接口）为例。当 `rewrite/` 包下只有 `MultiQuestionRewriteService` 一个 `@Service` 实现时，按类型注入能**唯一匹配**，一切正常：

```java
@Service
@RequiredArgsConstructor
public class StreamChatPipeline {
    private final QueryRewriteService queryRewriteService; // 唯一实现，注入成功
}
```

一旦再加一个实现（比如 `LlmRewriteService`），启动就直接失败：

```
NoUniqueBeanDefinitionException: expected single matching bean but found 2:
multiQuestionRewriteService,llmRewriteService
```

> ⚠️ 关键认知：这是**启动期（容器初始化）报错，不是运行期**——容器根本起不来，不存在「跑到那行代码才炸」。好处是这类问题在本地/测试环境必然暴露，不会漏到线上偷偷降级。

### 6.2 Spring 的候选解析顺序（四步）

按类型找到多个候选后，Spring 依次尝试：

| 顺序 | 机制 | 说明 |
|---|---|---|
| 1 | `@Primary` | 候选中**有且只有一个**标了它就选它；标了两个 → 依然报错 |
| 2 | `@Priority(n)` | JSR-250 的 `javax.annotation.Priority`（Jakarta 下为 `jakarta.annotation.Priority`），**n 越小优先级越高**；只能标在类上，不能标在 `@Bean` 方法上 |
| 3 | **按名字回退** | 用**字段名 / 构造器参数名**去匹配 bean name |
| 4 | 都不满足 | 抛 `NoUniqueBeanDefinitionException` |

**第 3 步最容易被误解成「Spring 很智能」**，其实它是**巧合生效**——只有名字**完全相等**才算匹配：

- 字段叫 `queryRewriteService`，恰好有个 bean 也叫 `queryRewriteService`（类名首字母小写）→ 匹配上；
- 但上面例子里字段叫 `queryRewriteService`，而实现类的 bean name 是 `multiQuestionRewriteService` → **匹配不上**，所以照样抛异常。

> 别指望「名字差不多」能救你。也正因为这条规则如此脆弱，**不要把它当作一种设计手段**——它只该是你排查报错时的解释，而不是你依赖的机制。

### 6.3 四种处理方式

**方式一：`@Primary`——有明确默认实现时最简单**

```java
@Service
@Primary
public class MultiQuestionRewriteService implements QueryRewriteService { ... }
```

**方式二：`@Qualifier`——在注入点显式指定**

```java
private final @Qualifier("multiQuestionRewriteService") QueryRewriteService queryRewriteService;
```

⚠️ 配合 `@RequiredArgsConstructor` 时有个**隐蔽坑**：Lombok 生成构造器时**默认不会把 `@Qualifier` 拷到构造器参数上**，注解等于白写。必须在 `lombok.config` 中显式声明：

```properties
lombok.copyableAnnotations += org.springframework.beans.factory.annotation.Qualifier
```

**方式三：`@ConditionalOnProperty`——配置驱动，同一时刻只有一个 bean 存在**

```java
@Service
@ConditionalOnProperty(
        name = "ragent.rag.rewrite.strategy",
        havingValue = "multi-question",
        matchIfMissing = true)
public class MultiQuestionRewriteService implements QueryRewriteService { ... }
```

注意这是 **Spring Boot** 的注解（不属于 Spring Core）。`matchIfMissing = true` 表示配置项缺失时也生效，用于兜底默认策略。这个思路和项目里已有的 `ragConfigProperties.getQueryRewriteEnabled()` 开关一致，适合「两种改写策略二选一」。

**方式四：注入 `List` / `Map`——需要运行期动态选择时**

```java
private final Map<String, QueryRewriteService> rewriteServices; // key = bean name
```

多个实现**全部注入**，由自己按条件挑。`List<QueryRewriteService>` 的顺序可用 `@Order` / `Ordered` 控制。这是**策略模式**在 Spring 里最标准的写法。

### 6.4 四种方式怎么选

| 方式 | 决策时机 | 适用场景 | 主要代价 |
|---|---|---|---|
| `@Primary` | 编译期写死 | 有一个公认的默认实现 | 另一实现虽存在却**永远不会被用到**，容易让人困惑「为什么我写的实现没生效」 |
| `@Qualifier` | 编译期写死 | 不同注入点要用不同实现 | Lombok 需额外配置；注入点散落各处，不好统一管理 |
| `@ConditionalOnProperty` | **启动期**由配置决定 | 策略二选一，改配置 + 重启即可切换 | 同一时刻只有一个 bean，无法运行期切换 |
| `List` / `Map` 注入 | **运行期**动态决定 | 按租户 / 场景 / 请求参数路由 | 所有实现都会被实例化；选择逻辑要自己写 |

**就 `QueryRewriteService` 这个场景的判断**：它是个策略接口（`rewrite` / `rewriteWithSplit` 两档，外加 `default` 方法兜底）。如果真要加第二个实现，倾向**方式三 `@ConditionalOnProperty`**——改写策略是**启动期确定的配置**，不需要运行期切换，比 `@Primary` 更**显式**。`@Primary` 的问题在于：另一个实现虽然存在却永远不会被调用，排查时很浪费时间。

如果将来需要**按租户 / 场景运行期路由**，再换成**方式四的 `Map` 注入**。

> 这一节正是第五章「消除分支判断」和「依赖倒置」的真实落地：`StreamChatPipeline` 只依赖 `QueryRewriteService` 接口，具体用哪个实现交给容器和配置决定，上层代码一行都不用改。

## 七、面试速答

| 问题 | 答案要点 |
|---|---|
| 什么是多态？子类替换父类靠什么实现？ | **运行时多态**；依靠**重写、继承 / 接口、向上转型**；**与重载无关** |
| 多态分为哪两种？ | **静态多态**（重载，编译时）、**动态多态**（重写 / 接口实现，运行时） |
| 重写和重载的区别？ | 重写：参数相同、子类覆盖父类、运行时绑定；重载：参数不同、编译时确定 |
| 向上/向下转型的区别？ | 向上自动且安全但无法调用子类独有方法；向下需强转，类型不符抛 `ClassCastException` |
| 一个接口两个实现，Spring 注入会怎样？ | 按类型有 2 个候选 → 依次走 `@Primary` → `@Priority` → **字段名/参数名匹配 bean name** → 都不满足抛 `NoUniqueBeanDefinitionException`；而且是**启动期**报错，容器起不来 |
| `@Primary` 和 `@Qualifier` 的区别？ | `@Primary` 标在**实现类**上，声明「我是默认」，全局生效；`@Qualifier` 标在**注入点**上，声明「我要哪个」，粒度更细、优先级更高 |
| 用了 `@RequiredArgsConstructor` + `@Qualifier` 为什么没生效？ | Lombok 默认不把 `@Qualifier` 拷到构造器参数上，需在 `lombok.config` 加 `lombok.copyableAnnotations += ...Qualifier` |
| 想在运行期按条件切换实现怎么做？ | 注入 `Map<String, T>`（key 为 bean name）或 `List<T>`，自己按条件挑——**策略模式**在 Spring 里的标准写法 |
| 多个实现但只想让一个存在，怎么做？ | `@ConditionalOnProperty` 配置驱动，同一时刻只注册一个 bean；比 `@Primary` 更显式，避免「另一个实现永远不被调用」的困惑 |
