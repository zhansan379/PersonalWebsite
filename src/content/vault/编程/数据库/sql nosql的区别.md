# SQL 与 NoSQL 的区别

> 这道题**不是考定义，是考选型思维**。正确的答法是：先用一句话讲清「数据模型」的本质差异，再用 **数据模型 → 一致性（ACID/BASE）→ 扩展性 → 查询能力** 四个维度展开，每个维度都挂一个业务场景，最后收在「不是替代关系，而是按场景混用」。只背「MySQL 是关系型、MongoDB 是非关系型」会被判定为没有工程经验。

## 一、答题逻辑（骨架）

```
1. 定义 + 代表产品          ← 30 秒，证明基本概念清楚
2. 抛出选型框架（四维度）    ← 主动给结构，抢夺主导权
   ├─ 数据模型 / Schema
   ├─ 一致性：ACID vs BASE
   ├─ 扩展性：水平扩展难易
   └─ 查询能力与生态
3. 每个维度配场景           ← 银行 vs 社交 vs 缓存，证明有落地思考
4. 收尾：混合持久化          ← 拉高层次，堵住"到底选哪个"的追问
```

**关键心态**：面试官想听的是「什么场景选什么，为什么」，而不是「谁更好」。任何绝对化表述（"NoSQL 性能更好"）都会招来反驳式追问。

## 二、核心答题点

### 2.1 定义与代表产品

|        | SQL（关系型）                                   | NoSQL（非关系型）                      |
| ------ | ------------------------------------------ | -------------------------------- |
| 代表     | SQL Server、Oracle、MySQL(开源)、PostgreSQL(开源) | MongoDB、Redis、HBase、Neo4j        |
| 数据形态   | **结构化数据**，逻辑上是行列二维表：列 = 属性，行 = 数据实体        | JSON 文档、哈希表、列族、图等**非二维表**形式      |
| Schema | **写时约束**（schema-on-write），先建表后写数据          | **读时解释**（schema-on-read），字段可动态增减 |
| 关系     | 表之间有外键、可 JOIN                              | 数据间**无关系**，靠嵌套或应用层聚合             |

> 加分点：NoSQL 全称是 **Not Only SQL**，不是"不用 SQL"，它是对关系模型的**补充**而非取代。

### 2.2 维度一：ACID vs BASE（最重要）

- **关系型支持 ACID**：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。
- **NoSQL 多采用更宽松的 BASE**：基本可用（Basically Available）、软状态（Soft state）、最终一致性（Eventually consistent）。

**判断方法：问自己「这个业务能不能容忍短暂不一致」**

| 场景 | 能否容忍不一致 | 选型 |
|---|---|---|
| 银行转账、订单支付、库存扣减 | ❌ 不能，一笔钱可能被用两次 | 优先 **SQL** |
| 社交动态、点赞数、feed 流 | ✅ 能，一条状态在不同用户处差几秒读到不影响使用 | 优先 **NoSQL** |

### 2.3 维度二：扩展性

- **NoSQL 数据之间无关系 → 天然易水平扩展**，可扩展能力被做进了架构层面。例：Redis 自带**主从复制、哨兵模式、切片集群（Cluster）**三种形态。
- **关系型数据之间存在关联性 → 水平扩展难**，一旦拆到多机就要解决：
  - **跨服务器 JOIN**（数据不在同一节点）
  - **分布式事务**（2PC / TCC / 本地消息表）
  - 分库分表后的**全局 ID、跨片分页、聚合查询**

> 所以关系型的常规扩展路径是「先垂直（加配置）→ 读写分离 → 最后才分库分表」，而 NoSQL 一开始就是加节点。

### 2.4 维度三：查询能力与生态

| | SQL | NoSQL |
|---|---|---|
| 查询语言 | 标准化 SQL，复杂多表关联、聚合、子查询强 | 各家 API 不统一，复杂关联弱（常需反范式冗余） |
| 数据校验 | 数据库层保证（类型、非空、外键） | **责任转移到应用层** |
| 生态 | 成熟（BI、报表、ORM、DBA 工具链） | 分散，运维经验依赖具体产品 |

### 2.5 收尾（必说）

> "实际项目里两者不是二选一，而是**混合持久化（Polyglot Persistence）**：核心交易数据放 MySQL 保证 ACID，热点读用 Redis 做缓存，全文检索交给 ES，日志/埋点这类海量弱一致数据走 MongoDB 或 HBase。选型看的是**这份数据的一致性要求、访问模式和体量**，不是看数据库本身好坏。"

## 三、30 秒速答版

> SQL 就是关系型数据库，MySQL、PostgreSQL 这些，数据是行列二维表的结构化形式，支持 ACID；NoSQL 是非关系型，MongoDB、Redis 这些，存储形式是文档、哈希表等，一般用 BASE 模型，只保证最终一致性。
> 选型主要看三点：一是**一致性要求**，银行支付必须 ACID 选 SQL，社交动态可以容忍延迟选 NoSQL；二是**扩展性**，NoSQL 数据无关系所以水平扩展容易，关系型要解决跨库 JOIN 和分布式事务；三是**查询复杂度**，多表关联分析 SQL 更强。
> 实际是混着用的，核心数据 MySQL，缓存 Redis，检索 ES。

## 四、对方可能追问的问题

### 4.1 顺着 ACID 追（概率最高）

| 追问                | 答题要点                                                                            |
| ----------------- | ------------------------------------------------------------------------------- |
| ACID 四个特性分别是什么？   | 原子性=全成功或全失败；一致性=事务前后数据合法；隔离性=并发事务互不干扰；持久性=提交后不丢                                 |
| MySQL 靠什么实现 ACID？ | 原子性→**undo log** 回滚；持久性→**redo log** + WAL；隔离性→**MVCC + 锁**；一致性是前三者共同保证的结果      |
| 隔离级别有哪些？MySQL 默认？ | 读未提交/读已提交/**可重复读（MySQL 默认）**/串行化；对应脏读、不可重复读、幻读；RR 下用 **间隙锁** 解决幻读               |
| BASE 和 CAP 是什么关系？ | CAP：一致性/可用性/分区容错，P 必选，所以在 C 和 A 之间取舍；BASE 是 **AP 方向的工程妥协**，用最终一致换可用性            |
| NoSQL 一定不支持事务吗？   | ❌ 陷阱题。**MongoDB 4.0 起支持多文档 ACID 事务**，Redis 有 MULTI/Lua 的弱事务。差别在于「事务是否是设计核心」而非有无 |

### 4.2 顺着扩展性追

| 追问 | 答题要点 |
|---|---|
| 为什么 NoSQL 容易水平扩展？ | 数据无关联 → 可按 key **分片（Sharding）**，任意一条请求只落单节点，无需跨节点 JOIN 和分布式事务 |
| 关系型数据库如何扩展？ | 主从复制 → 读写分离 → 垂直分库 → 水平分表（ShardingSphere / MyCat）；代价是全局 ID（雪花算法）、跨库分页、分布式事务 |
| 分布式事务怎么解决？ | 2PC/XA（强一致、性能差）、**TCC**、**Seata AT 模式**、**本地消息表 + MQ 最终一致**（最常用） |
| Redis 集群怎么分片？ | Cluster 用 **16384 个哈希槽**，CRC16(key) % 16384 定位节点；不是一致性哈希 |
| MySQL 单表多少数据要考虑分表？ | 经验值**千万级**开始关注（B+ 树层高与索引内存占用），但真实阈值取决于行宽和查询模式，别背死数字 |

### 4.3 顺着底层原理追

| 追问 | 答题要点 |
|---|---|
| 为什么 NoSQL 写入通常更快？ | 很多 NoSQL 用 **LSM Tree**（顺序追加 + 后台 compaction，写快、有读放大/写放大），MySQL InnoDB 用 **B+ 树**（原地更新，读稳定、随机写慢） |
| MySQL 为什么用 B+ 树而不是 B 树/哈希？ | 非叶子节点不存数据 → 层高更低、一次 IO 载入更多索引；叶子节点双向链表 → **范围查询和排序快**；哈希不支持范围 |
| Redis 为什么快？ | 纯内存 + 单线程避免锁竞争 + **IO 多路复用** + 高效数据结构（SDS/跳表/ziplist） |

### 4.4 顺着落地场景追（最容易露馅）

| 追问 | 答题要点 |
|---|---|
| 你项目里用了什么？为什么？ | 必须准备**具体的一句话理由**：如"用户/订单在 MySQL 因为要事务；会话和热点配置在 Redis 因为 QPS 高且可重建；文档分块的向量检索在向量库因为要 ANN" |
| MySQL 加了 Redis，一致性怎么保证？ | **Cache Aside**（读时回填、写时删缓存）为主；延迟双删、订阅 binlog（Canal）异步更新兜底；承认这是**最终一致** |
| 什么时候必须引入 NoSQL？ | ①海量弱一致数据（日志、埋点）②高 QPS 热点读（缓存）③schema 频繁变动（爬虫、多源异构数据）④特定查询模型（全文检索→ES、关系网络→图库） |
| NoSQL 的代价是什么？ | 无 JOIN 需**反范式冗余**（更新时要多处同步）、数据校验落到应用层、缺少统一查询语言、运维/人才成本高 |
| 听说过 NewSQL 吗？ | **TiDB、OceanBase、CockroachDB**：既要 ACID 又要水平扩展，用 Raft 多副本 + 自动分片；是这道题的"第三条路" |

### 4.5 高频陷阱题

1. **"关系型数据库能存 JSON 吗？"** → 能。MySQL 5.7+ / PostgreSQL 的 **JSON/JSONB 字段** 已经能处理半结构化数据，所以"要存 JSON 就必须上 MongoDB"是错的。
2. **"NoSQL 性能一定比 SQL 高吗？"** → 不一定。单机简单点查 Redis 快是因为**内存**而非"非关系"；同样是磁盘存储、同样是主键查询，MySQL 并不慢。性能差异来自**存储介质、数据模型和一致性代价**。
3. **"NoSQL 是不是没有 Schema？"** → 是「Schema 灵活」不是「无 Schema」，Schema 只是从数据库转移到了**应用代码里**，写得不好会变成隐式脏数据。
