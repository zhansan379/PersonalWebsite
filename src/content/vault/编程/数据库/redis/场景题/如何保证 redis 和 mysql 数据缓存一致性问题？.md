# 如何保证 Redis 和 MySQL 数据缓存一致性问题？

> 标准答法：**读用旁路缓存（Cache Aside），写用「先更新 DB，再删除缓存」**。但真正的高分点在于先定性——**缓存是牺牲强一致性来换性能的，这由 CAP 理论决定，缓存属于 AP**；所以正确的目标不是"强一致"，而是"**通过补偿方案做到最终一致**"。

## 一、答题逻辑（骨架）

```
1. 先亮出结论方案：读 Cache Aside，写 先更新 DB 再删缓存   ← 30 秒给答案，不绕
2. 定性：缓存牺牲强一致换性能，属 CAP 的 AP               ← 关键升华，把题目从"技术"抬到"取舍"
   → 推论：需要强一致的业务，本来就不该用缓存
3. 承认延迟客观存在 + 过期时间兜底（太短/太长的坏处）
4. 但可以做到最终一致 → 删除缓存失败的两个补偿方案
   ├─ 消息队列重试（侵入业务代码）
   └─ 订阅 binlog（Canal + MQ，业务无侵入）
5. 对比取舍，说明你项目里选了哪个、为什么
```

**关键心态**：这题最容易掉进「无限追问一致性漏洞」的陷阱——面试官会不停问"那这种并发情况呢"。**主动承认「不可能强一致，只能最终一致 + 过期时间兜底」，反而能终结追问**。硬说自己的方案能强一致，一定会被问死。

## 二、核心答题点

### 2.1 基本策略：旁路缓存（Cache Aside）

之所以叫“旁路”，是因为缓存不参与业务的主流程，应用程序直接与数据库交互，缓存只是挂在旁边作为“加速器”使用。

| 操作 | 做法 |
|---|---|
| **读数据** | 查 cache → **命中**直接返回；**不命中**从 DB 加载数据到 cache 再返回 |
| **写数据** | **先更新 DB，再删除缓存** |

### 2.2 定性：缓存本质是「牺牲强一致换性能」

- 缓存通过牺牲强一致性来提高性能，这是由 **CAP 理论**决定的：缓存系统适用的场景就是**非强一致性场景，它属于 CAP 中的 AP**。
- **推论**：如果需要数据库和缓存数据保持**强一致**，就**不适合使用缓存**。
- 所以用缓存提升性能，**就是会有数据更新的延迟**。设计时要结合业务仔细思考是否适合用缓存。

### 2.3 过期时间是最后的兜底（必须设置）

缓存**一定要设置过期时间**，太短或太长都不好：

| | 坏处 |
|---|---|
| **太短** | 请求较多地落到数据库上，**失去了缓存的优势** |
| **太长** | 脏数据使系统长时间处于延迟状态；长时间没人访问的数据一直占内存不过期，**浪费内存** |

> 这条常被忽略但很重要：**即使所有补偿手段都失败了，过期时间也能保证数据最终收敛**。答题时一定要说。

### 2.4 达成最终一致：删除缓存失败的两个方案

「先更新 DB，再删缓存」的风险是**第二步删除失败**，缓存留下脏数据。两种补偿方案：

#### 方案一：消息队列重试

将第二个操作（删除缓存）要操作的数据**加入消息队列**，由消费者来操作：

- 删除缓存**失败** → 从消息队列中**重新读取数据，再次删除缓存**（重试机制）；重试超过一定次数仍不成功，**向业务层发送报错信息**。
- 删除缓存**成功** → 把数据从消息队列中移除，避免重复操作；否则继续重试。

> **缺点：对业务代码产生较多侵入。**

#### 方案二：订阅 MySQL binlog（Canal）

「先更新数据库」成功后必然产生一条变更日志记录在 **binlog** 里，于是可以**订阅 binlog 拿到要操作的数据，再执行缓存删除**。阿里巴巴开源的 **Canal** 就是基于这个实现的。

**Canal 工作原理**：

```
Canal 伪装成 MySQL 从节点
   → 向 MySQL 主节点发送 dump 请求
   → MySQL 推送 binlog 给 Canal
   → Canal 解析 binlog 字节流，转为结构化数据
   → 投递到 MQ，供下游订阅
```

落地方式：把 binlog 采集发送到 **MQ 队列**，编写一个缓存删除消费者订阅 binlog，根据更新 log 删除缓存，并通过 **ACK 机制**确认处理这条更新 log，从而保证缓存一致性。

> **优点：业务代码零侵入**（业务只管写 DB，缓存删除完全由旁路链路负责）。

### 2.5 两方案对比

| | MQ 重试 | 订阅 binlog（Canal） |
|---|---|---|
| 业务侵入 | **较大**（要在业务里发消息） | **无侵入** |
| 可靠性 | 依赖业务代码正确发消息 | 以 binlog 为准，**不会漏** |
| 额外组件 | MQ | Canal + MQ |
| 延迟 | 较低 | 多一跳，略高 |
| 适用 | 改造成本低、系统简单 | 缓存场景多、多个下游都要感知变更 |

## 三、30 秒速答版

> 读走**旁路缓存**：命中返回，不命中读 DB 回填缓存。写走**先更新 DB，再删除缓存**。
> 但要先说清一点：**缓存本来就是牺牲强一致换性能的，属于 CAP 里的 AP**，所以目标是最终一致而不是强一致；真要强一致就不该用缓存。
> 为了让它最终一致，做三件事：①**所有缓存都设过期时间兜底**；②删缓存失败用 **MQ 重试**，超过次数就告警；③更彻底的做法是**订阅 binlog（Canal + MQ）**异步删缓存，业务代码零侵入。

## 四、对方可能追问的问题

### 4.1 顺策略选择追（几乎必问）

| 追问 | 答题要点 |
|---|---|
| **为什么是删除缓存，而不是更新缓存？** | ①**懒加载**思想：删了之后有人读才回填，避免更新了半天没人读，白做功；②**并发写会导致脏数据**：A、B 同时更新，两条"更新缓存"的到达顺序可能与"更新 DB"的顺序相反，缓存留下旧值；③更新缓存若涉及多表聚合计算，**代价远大于删除** |
| **为什么是先更新 DB 再删缓存，而不是先删缓存再更新 DB？** | 「先删缓存再更 DB」不一致窗口**大**：A 删缓存 → B 读未命中，从 DB 读到**旧值写回缓存** → A 才更新 DB → 缓存长期是旧值（窗口 = 一次 DB 写的耗时）。<br>「先更 DB 再删缓存」窗口**极小**：只有"B 读到旧值"和"B 写缓存"之间恰好插入 A 的删除，才会出问题，而**读 DB 通常比写 DB 快得多**，概率很低 |
| 那「先更新 DB 再删缓存」还是有漏洞？ | **承认它有**（这是唯一正确的回答）。理论上无法完全避免，靠**过期时间兜底 + 业务可容忍**解决。追求零漏洞只能加分布式锁把读写串行化，**代价是缓存的性能优势全丢** |
| **延迟双删是什么？** | 「先删缓存 → 更新 DB → **睡一会儿 → 再删一次缓存**」。第二次删是为了清掉"更新期间被并发读回填的旧值"。**延迟多久？** 要略大于"一次读 DB + 写缓存"的耗时；有主从时还要**大于主从复制延迟**。缺点是这个时间**只能靠经验估**，所以不如 binlog 方案优雅 |
| 四种双写顺序哪种最好？ | 先更 DB 后删缓存（**最优，业界主流**）> 延迟双删 > 先删缓存后更 DB > 更新缓存（最差） |

### 4.2 顺架构与主从追

| 追问                | 答题要点                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------- |
| **读写分离时会有什么新问题？** | 更新主库并删缓存后，请求打到**还没同步完的从库**，读到旧值又回填缓存 → 又脏了。解法：**延迟双删**、关键读**强制走主库**、或用 binlog 方案（binlog 到达时说明已落盘）    |
| Canal 挂了怎么办？      | Canal 支持**集群部署 + ZooKeeper 做 HA**，并**持久化 binlog 位点（position）**，重启后从断点续读，所以不会漏数据（可能重复 → 需**幂等**）      |
| MQ 方案要注意什么？       | ①**顺序性**：同一个 key 的变更要路由到**同一分区**，否则删除顺序乱；②**幂等**：重复删缓存本身天然幂等，但若做的是"更新缓存"就必须防乱序；③**重试上限 + 死信队列 + 告警** |
| binlog 方案的延迟能接受吗？ | 通常在**毫秒到百毫秒级**，绝大多数业务可接受；不可接受的业务应该重新评估"是否该用缓存"                                                       |
**读写分离**是数据库架构中一种非常常见的高并发应对策略。简单来说，就是**将“写数据”的操作和“读数据”的操作，分发到不同的数据库实例上执行**。

具体架构通常表现为：

-   **一个主库（Master）**：负责处理所有的**写入**操作（INSERT、UPDATE、DELETE），以及事务相关的读写。
-   **多个从库（Slave）**：负责处理大量的**查询**操作（SELECT）。从库通过**主从复制**机制，实时或近乎实时地将主库的新数据同步过来。

这样做最大的好处是**分摊压力**——当系统读远多于写时（比如刷微博、看商品详情），把读流量分散到多台从库服务器上，可以大幅提升系统的整体吞吐量，避免主库因为读压力过大而崩溃。

---

#### 为什么读写分离 + 旁路缓存会出现“脏数据”？

这正好对应你表格里提到的问题。因为主从复制**不是同步的，而是异步的**，存在毫秒级甚至秒级的**同步延迟**。

在高并发场景下，会发生这样一个“踩踏事件”：

1. **写请求**：线程A更新主库（比如把商品价格改为100元），然后**立刻删除了缓存**。
2. **读请求（踩坑）**：几乎在同一瞬间，线程B发起读请求。此时缓存已被删除，于是去从库查询数据。
3. **致命延迟**：由于主从同步延迟，此时从库里的价格**还是旧的（50元）**。线程B读到这个旧价格，并把它**回填到了缓存中**。
4. **结果**：缓存里又变成了旧数据（50元），并且可能很久都不会过期。主库虽然是最新的100元，但后续所有读请求都命中缓存，拿到了错误的价格——**数据又脏了**。

---

#### 你表格中的解法分别怎么理解？

针对这个“读写分离延迟”造成的新坑，你列出的三种解法原理如下：

- **延迟双删**：第二次延迟删除的时间，不仅要大于“读库+写缓存”的时间，还要**大于主从同步的延迟时间**。确保从库同步完成、旧数据被回填缓存后，再删一次。
- **关键读强制走主库**：对于**一致性要求极高**的数据（如库存扣减、余额查询），在代码里打标，强制让它**不查从库，直接查主库**。既然主库数据最新，读到旧数据的风险就消失了。
- **Binlog方案（如Canal）**：这个方案最优雅。因为从库同步数据依赖主库的Binlog日志，当程序**监听到Binlog到达从库**时，说明数据**已经落盘同步完毕**。此时再触发删除缓存的操作，就能确保删掉的一定是旧数据，不会误删刚同步好的新数据。

总的来说，**读写分离提升了性能，但引入了“主从延迟”这个时间差**，而所有缓存一致性的补丁（延迟双删、强制主库、Binlog监听），本质上都是在**想办法“覆盖”或“绕过”这个时间差**。

**延迟双删（Delayed Double Deletion）** 是一种在数据库与缓存（如Redis）并用的系统中，用于**缓解高并发场景下数据短暂不一致**的常见策略。

简单来说，它的核心思想是：**在更新数据库前后，不只删除一次缓存，而是删除两次，并且第二次删除是“延迟”执行的**。

#### 延迟双删核心步骤

延迟双删的标准流程通常如下：

1.  **第一次删除缓存**：在更新数据库**之前**，先删除缓存中对应的数据。
2.  **更新数据库**：执行数据库的更新操作。
3.  **延迟一段时间**：让当前线程“睡眠”（Sleep）一段预估的时间，例如500毫秒。
4.  **第二次删除缓存**：延迟结束后，再次删除缓存中相同的数据。

#### 延迟双删为什么要“延迟”删两次？

“延迟双删”是为了解决一个经典的并发问题：**“先删缓存（缩短“旧数据被用户读到”的时间窗口），再更新数据库”** 的策略下，在“删除缓存”和“更新数据库”这两个操作之间，可能会有其他读请求将数据库中的**旧数据**重新写入缓存，导致缓存和数据库数据不一致。

“延迟双删”通过第二次删除来兜底解决这个问题：

1.  线程A（写请求）先删除缓存。
2.  线程B（读请求）在缓存未命中后，从数据库读到旧数据。
3.  线程A完成数据库更新。
4.  **线程A等待一段预设的时间（此时间需大于线程B读取数据库并写入缓存的总耗时）**。
5.  线程B将旧数据写回缓存。
6.  线程A的**延迟删除**生效，将线程B刚写入的旧缓存再次删除。

这样一来，后续的读请求就会因缓存缺失而直接读取数据库，从而拿到最新的数据。


### 4.3 顺缓存模式追（考知识面）

| 追问 | 答题要点 |
|---|---|
| 除了 Cache Aside 还有哪些缓存模式？ | **Read/Write Through**：应用只跟缓存打交道，由缓存组件同步读写 DB（一致性好、实现复杂，如 Guava/Caffeine 的 loader）；**Write Behind（写回）**：先写缓存，异步批量刷 DB（性能最好，**宕机会丢数据**，典型如 OS 的 page cache、MySQL 的 Buffer Pool） |
| 能不能保证「双写原子性」？ | **不能**。Redis 和 MySQL 是两个独立系统，没有共同事务，所以只能追求**最终一致 + 补偿**。要真原子就得上分布式事务，性价比极低 |
| 一定要强一致怎么办？ | ①**别用缓存**，直接读 DB（首选）；②读写都加**分布式锁串行化**；③用 **NewSQL / 内存表**替代"DB+缓存"这套架构 |
| 缓存被删除后瞬间大量请求打到 DB？ | 那就是**缓存击穿**了，用**互斥锁**只让一个线程重建缓存 → 见 [[编程/数据库/redis/场景题/缓存雪崩、击穿、穿透是什么？怎么解决？]] |

### 4.4 顺落地追

| 追问 | 答题要点 |
|---|---|
| 你项目里用了哪种？ | 准备具体答案：如"改造成本考虑先用**先更 DB 再删缓存 + 短 TTL 兜底**，后来缓存下游变多，统一改成 **Canal 订阅 binlog → MQ → 各缓存消费者**，业务代码不再关心缓存" |
| 怎么监控不一致？ | **定时对账任务**抽样比对 cache 与 DB、缓存命中率监控、binlog 消费延迟（lag）告警——说不出监控会被认为没上过生产 |
| 缓存的过期时间怎么定？ | 按**数据变更频率 + 业务容忍度**定；再加**随机抖动**避免同时过期（→ 缓存雪崩） |
