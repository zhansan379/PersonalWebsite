# MySQL 索引分类

> MySQL 索引可按**四个角度**分类：数据结构（B+Tree/Hash/Full-text）、物理存储（聚簇/二级）、字段特性（主键/唯一/普通/前缀）、字段个数（单列/联合）。核心主线：**B+Tree 是主流，聚簇索引存数据/二级索引存主键，联合索引要守最左匹配。**

## 一、这是什么

回答"讲讲索引的分类"时，先亮出**四把尺子**，再按每把尺子细说。这是 MySQL 索引的地基题，联表/回表/覆盖索引都从这里来。

## 二、核心内容：四个分类角度

### 2.1 按「数据结构」分类

| 类型               | 说明                                                  |
| :--------------- | :-------------------------------------------------- |
| **B+Tree 索引**    | **最常用**，InnoDB（MySQL 5.5 后默认存储引擎）/MyISAM/Memory 均支持 |
| **Hash 索引**      | 等值查询快、不支持范围；常用于 Memory                              |
| **Full-text 索引** | 全文检索                                                |

在 MySQL 中，我们平时通过 ALTER TABLE 或 CREATE INDEX 创建的普通索引，底层默认都是 B+Tree 索引，它利用多路平衡树和叶子节点双向链表的结构，完美支持等值、范围查询和排序，这也是 InnoDB 引擎最核心的实现。
第二种是 全文索引（Full-text），通过 ADD FULLTEXT 创建，底层基于倒排索引实现，专门用来解决 LIKE '%...%' 这种前置模糊匹配导致的索引失效问题，不过在 MySQL 5.7+ 配合 ngram 分词器才能更好支持中文。
第三种是 哈希索引（Hash），这里有个大坑，虽然语法支持 USING HASH，但 InnoDB 引擎并不支持用户手动创建，写了会被静默降级为 B+Tree 并报警告，真正的 Hash 索引只存在于 Memory 引擎中，而且只适用于等值查询。
-- 先创建 Memory 引擎的表（重启后数据丢失）
CREATE TABLE temp_memory (
    id INT,
    user_id INT,
    INDEX USING HASH (user_id)
) ENGINE = MEMORY;
不过面试官需要注意，InnoDB 内部有一套自适应哈希索引（AHI）机制，会自动将热点等值查询的内存页映射为哈希表来加速，但这是数据库自动优化的黑盒，我们开发者无法干预。所以实际生产调优中，我一般会把 90% 的精力放在设计好 B+Tree 联合索引的顺序上

**InnoDB 选哪列做索引键**：
- 有主键 → 默认**主键**作聚簇索引键
- 无主键 → 选**第一个不含 NULL 的唯一列**
- 都没有 → 自动生成一个**隐式自增 id 列**作聚簇索引键

### 2.2 按「物理存储」分类（聚簇 vs 二级）

| 类型 | 叶子节点存什么 |
| :--- | :--- |
| **聚簇索引（主键索引）** | **实际数据**（完整用户记录都存主键 B+Tree 叶子） |
| **二级索引（辅助/非聚簇索引）** | **主键值**（不是实际数据） |

由此引出两个关键概念：
- **覆盖索引**：查询列都能从二级索引里拿到 → **不需回表**（高效）
- **回表**：二级索引查到主键值后，再查主键索引拿实际数据（Extra: Using index 表示覆盖、无需回表）

### 2.3 按「字段特性」分类

| 类型 | 特点 | 建法示例 |
| :--- | :--- | :--- |
| **主键索引** | 主键字段上，一张表最多一个，**不允许空值** | `PRIMARY KEY (col) USING BTREE` |
| **唯一索引** | `UNIQUE` 字段上，可多个，值唯一但**允许空值** | `UNIQUE KEY(col1,col2)` / `CREATE UNIQUE INDEX...` |
| **普通索引** | 普通字段，无主键/UNIQUE 要求 | `INDEX(col)` / `CREATE INDEX...` |
| **前缀索引** | 对**字符类型**字段的**前 N 个字符**建索引（char/varchar/binary/varbinary），**省空间、提升效率** | `INDEX(col(length))` |

### 2.4 按「字段个数」分类

- **单列索引**：建在单列上（如主键索引）。
- **联合索引（复合索引）**：多列组合成一个索引，如 `CREATE INDEX index_product_no_name ON product(product_no, name)`。
  - 联合索引用**多字段值**作 B+Tree 的 key：先按第一列排序，第一列相同再按第二列排序……（如 `product_no` 相同时再按 `name` 排）。

### 2.5 最左匹配原则（核心考点）

> 联合索引用**最左优先**方式匹配：不遵循最左匹配，联合索引会失效，无法利用索引快速查询。

以 `(a, b, c)` 联合索引为例：
- ✅ **可匹配**：`where a=1`、`where a=1 and b=2`、`where a=1 and b=2 and c=3`
  - 注意：因有**查询优化器**，a 在 where 子句中的**书写顺序不重要**
- ❌ **失效**：`where b=2`、`where c=3`、`where b=2 and c=3`
  - 原因：`(a,b,c)` 先按 a 排序、a 相同按 b 排、b 相同按 c 排；**b、c 是"全局无序、局部有序"**，脱离 a 无法利用索引

**范围查询的截断**（进阶）：最左匹配会一直向右匹配，**遇到范围查询就停止**——范围查询的字段能用上索引，但**它后面的字段用不上**。

## 三、可能追问

1. 「为什么选 B+Tree 而不选 B/BalanceTree/Hash？」→ B+树矮(减少 IO)、叶子有序(支持范围)、顺序/范围查询友好；Hash 不支持范围与排序
2. 「聚簇索引和二级索引为什么都存主键而非数据？」→ 避免数据冗余、便于维护数据一致性（见 2.2）
3. 「回表和覆盖索引什么关系？」→ 覆盖索引免回表(Using index)；回表=二级索引拿主键再查主键索引
4. 「最左匹配原则具体怎么判断？」→ 联合索引几你最左的连续列在条件里才会走索引，见 2.5
5. 「为什么建议用自增主键做聚簇索引？」→ 自增插入有序、避免页分裂；随机主键(UUID)导致频繁页分裂
6. 「前缀索引选多长？」→ 按区分度选长度（distinct 计数），既省空间又保选择性，避免过多字段截断
7. 「联合索引 (a,b,c) 和单列 a/b/c 怎么取舍？」→ 联合索引一个顶多个，但受最左匹配限制；按查询条件组合设计
