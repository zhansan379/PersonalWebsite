# MySQL 慢查询排查与优化方案

> "给你一张表，查询很慢，怎么解决？"——按 **分析（EXPLAIN）→ 索引 → SQL → 分页 → 表结构 → 缓存** 六层逐层排查，形成一套完整优化清单。核心主线：**先定位，再对症下药**。

## 一、这是什么

典型的**场景题/优化清单**题。回答时由内到外给层次，体现排查思路，而非零散背点。本文在六层清单基础上，展开 **EXPLAIN 逐字段定位** 与 **深分页详解** 两块必考干货。

## 二、核心内容：六层优化清单

### 1. 分析查询语句（先定位）
用 `EXPLAIN` 分析 SQL 执行计划，找出慢查询原因：**是否全表扫描、索引是否被利用**，据此调整索引。完整字段表见 [[MySQL EXPLAIN 详解]]，逐字段速查见 [三、EXPLAIN 关键字段速查](#三explain-关键字段速查)。

### 2. 创建/优化索引
- 为 `WHERE`、`ORDER BY`、`GROUP BY`、`JOIN`（连表）字段建索引。
- 多字段查询建**联合索引**，须符合**最左匹配原则**，否则索引失效。
- 覆盖高频查询字段用覆盖索引（见 EXPLAIN 的 Using index）。

### 3. 避免索引失效
不要使用 **左模糊匹配**（`%xx`）、**函数计算**（`where func(col)=...`）、**表达式计算**、隐式类型转换等——都会让索引失效。

### 4. 查询优化
- **避免 `SELECT *`**，只查需要的列。
- 用**覆盖索引**（索引包含所有查询字段，免回表）。
- **联表：小表驱动大表**，被驱动表关联字段要有索引；最优雅是**冗余字段设计避免联表**。

### 5. 分页优化（深分页详解）

针对 `LIMIT n,y` 深分页，把 `limit` 转成按**边界值**定位：

```sql
select * from tb_sku where id > 20000 limit 10;
```
> 适用于**主键自增**的表。

#### 5.1 深分页为什么慢？
执行 `select * from tb_sku limit 100000, 10` 时，数据库**不是**直接跳到第 100000 条，而是：
1. 按主键（或索引）顺序，**逐个扫描前 100010 条**；
2. 把前 100000 条全部丢弃；
3. 只返回剩下的 10 条。

→ **偏移量 M 越大、扫描行数越多**，磁盘 I/O 和 CPU 开销剧增，**耗时随翻页深度线性增长**。

#### 5.2 边界值方案 `id > 20000 limit 10` 怎么做？
- `20000` 是**上一页最后一条数据的 ID（书签/游标）**。
- 数据库利用主键索引 B+树结构**精确定位到 id=20000**，再沿链表顺序向后扫 10 条。
- **不需要扫描** id 1~20000 之间的任何数据，跳过大量无效扫描。

**对比：**
| 方案 | 扫描量 | 性能 |
| :--- | :--- | :--- |
| 原方案 `limit 100000,10` | 扫 100010 行、丢 100000 行 | 随深度线性变慢 |
| 新方案 `id > 20000 limit 10` | **只扫 10 行** | **恒定 O(1)，不随深度变慢** |

#### 5.3 为什么要求"主键自增"？
方案成立的前提是 **ID 大小顺序必须与数据的逻辑顺序完全一致**。
- **主键自增（无间隙回填）**：保证新插入的 ID 一定比旧的大；翻第二页时上一页末尾 ID 是 20000，下一页数据 ID 必然都 > 20000，`where id > 20000` 逻辑正确。
- **主键非自增**（如雪花算法有序 ID 或业务字段）：只要满足**排序有序**且能拿到上一页边界值，方案依然有效。官方强调"自增"是为了最简单直观地保证顺序连续性。

#### 5.4 ⚠️ 最大"坑"（适用场景限制）
> 致命代价：**无法直接跳转到第 100 页**。

要执行 `where id > 20000`，必须先知道第 99 页最后一条 ID。所以该方案**只适用于"下拉加载更多/瀑布流"**（每次只点"下一页"），**绝不适用于"页码跳转"**（如从第 1 页直接点第 100 页）。

#### 5.5 进阶：删除数据怎么办？
假设上一页末尾 ID=20000，但下一页前 5 条被物理删除，`where id > 20000 limit 10` 会返回接下来**现存**的 10 条（ID 20001 没了就返回 20002~20011）。显示上"跳过几个序号"但**数据不会遗漏也不会重复**——因为查询条件基于**逻辑顺序的"大于"**而非**物理位置的"偏移量"**，依然严谨可靠。

**一句话总结**：用**"记住边界值（上一页最大 ID）"**代替**"计算偏移量（limit M）"**，让数据库从边界值直接取数据，把深分页的 **O(N) 降为 O(1)**。

### 6. 优化数据库表结构
- 单表**超千万级**：考虑拆分为小表（分表分库），减轻单表压力。
- **字段多的表拆分**：把使用频率高的和低的字段分开建表，避免低频字段拖慢高频查询。

### 7. 使用缓存技术（架构层兜底）
- 引入 Redis 缓存**热点数据 / 频繁查询结果**。
- 但须考虑**缓存一致性**：
  - 读请求：**旁路缓存**（先查缓存，未命中查库并回填）
  - 写请求：**先更新 DB，再删除缓存**（配合过期兜底、MQ/Canal 重试）
> 详见 [[编程/数据库/redis/场景题/如何保证 redis 和 mysql 数据缓存一致性问题？]]

## 三、EXPLAIN 关键字段速查（逐字段定位）

| 顺序 | 看什么 | 判断要点 |
| :--- | :--- | :--- |
| 1 | `type` | 访问级别，判断**是否全表扫描**（All 最底、const 最高） |
| 2 | `key` | **实际**是否用到索引；区分 `possible_keys` 候选索引 |
| 3 | `key_len` | 联合索引**使用长度**，校验最左匹配 |
| 4 | `rows` | 预估扫描行数 |
| 5 | `Extra` | 有没有 Using filesort / Using temporary；是否命中覆盖索引 Using index |

**`key_len` 两个细节**：
- 例如 `DATE` 类型的 key_len 等于 3 字节。
- `key_len` **只统计被 `where` 用来过滤/定位行的字段**；只用于 `order by`/`group by` 的字段即使存在于联合索引中、不参与查找，**不计入 key_len**。

**优化方向**：避免 `type` 为 ALL → 让 `key` 不为 NULL → 增大 `key_len`（多用上联合索引列）→ 减少 `rows` → 消除 filesort/temporary。

## 四、可能追问

1. 「怎么定位到底慢在哪？」→ EXPLAIN（type/rows/extra）+ 慢查询日志 `slow_query_log` 抓慢 SQL
2. 「索引失效有哪些常见情况？」→ 左模糊、函数/表达式、隐式转换、`OR`、`!=`、联合索引不满足最左匹配
3. 「深分页为什么慢？怎么解？」→ `LIMIT n,y` 要回表扫 n+y 行再丢前 n；改用 `id > n`（边界值）或子查询/覆盖索引；代价是**不能页码跳转**
4. 「`id > n` 深分页有什么局限？」→ 只能"加载更多/瀑布流"，无法直接跳页（见 5.4）
5. 「分表和分库怎么选？」→ 数据量/单表压力：垂直拆（字段拆分）、水平拆（行拆分）、分库（读写/多库）
6. 「**为什么要避免 SELECT \*？**」→ 回表多、占用 IO/内存、无法走覆盖索引
7. 「索引建了很多，为什么还是慢？」→ 排查是否失效、是否有联合索引最左匹配、是否产生 filesort/temporary、数据量是否过大需分表/缓存
8. 「缓存一致性问题怎么彻底解决？」→ 先更库再删缓存 + 过期兜底 + 删除失败 MQ 重试 / Canal 订阅 binlog 异步刷新
9. 「假如业务必须支持页码跳转，深分页怎么优化？」→ 延迟关联/子查询（先查符合条件的 id 子集再回表）、或扫描索引代替全表
