# 事务的特性是什么？如何实现的？

> 这题是**两段式提问**：前半段「是什么」几乎人人会背，真正的分水岭在后半段「如何实现」。高分答法是给出 **特性 ↔ 技术** 的一一映射（原子性→undo log、持久性→redo log、隔离性→MVCC/锁、一致性→前三者共同保证），并点明**一致性是目的，其余三个是手段**。只背 ACID 四个单词等于零分。

## 一、答题逻辑（骨架）

```
1. 四个特性各一句话 + 生活化例子      ← 转账/购物，说明你真理解而非背书
2. 直接抛出「特性 ↔ InnoDB 技术」映射表 ← 本题最大加分点，主动往深处走
3. 点明三者是手段、一致性是结果        ← 体现结构化理解，堵住"那一致性靠什么"
4. 主动补一层实现细节（WAL / 版本链 / ReadView） ← 留钩子，引导追问到你熟悉的地方
```

**关键心态**：面试官问"如何实现"，是在探你**看过 InnoDB 日志与并发控制**没有。答完映射表后**主动展开一到两个**你最熟的（通常是 redo log 的 WAL 或 MVCC 的 ReadView），把节奏握在自己手里。

## 二、核心答题点

### 2.1 四大特性（ACID）

| 特性                     | 定义                                                                        | 例子                                                                                           |
| ---------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **原子性**<br>Atomicity   | 一个事务中的所有操作，**要么全部完成，要么全部不完成**，不会结束在中间某个环节。执行中发生错误会**回滚到事务开始前的状态**，就像从未执行过 | 买商品：成功则付钱+拿货；失败则商品在商家手中、钱也没花出去                                                               |
| **一致性**<br>Consistency | 事务操作**前后**数据都满足**完整性约束**，数据库保持一致状态                                        | A 有 800、B 有 600（共 1400）；A 转 B 200 后必须是 A=600、B=800（仍共 1400），不会出现 A 扣了 200 而 B 没增加（共 1200）的情况 |
| **隔离性**<br>Isolation   | 允许多个并发事务同时读写数据，**防止并发交叉执行导致的数据不一致**；每个事务都有完整的数据空间，对其他并发事务是隔离的             | 一个消费者购买商品，不影响其他消费者购买                                                                         |
| **持久性**<br>Durability  | 事务结束后对数据的修改是**永久的**，即便系统故障也不会丢失                                           | 支付成功后即使数据库宕机重启，订单依然在                                                                         |

### 2.2 InnoDB 如何保证这四个特性（核心映射）

| 特性 | 实现技术 | 一句话原理 |
|---|---|---|
| **持久性** | **redo log**（重做日志） | 先写日志再刷盘（WAL），崩溃后靠日志重放已提交的修改 |
| **原子性** | **undo log**（回滚日志） | 记录每步操作的**反向操作**，回滚时逆序执行 |
| **隔离性** | **MVCC**（多版本并发控制）**或锁机制** | 快照读靠版本链 + ReadView，当前读靠行锁/间隙锁 |
| **一致性** | **持久性 + 原子性 + 隔离性** 共同保证 | 它是**结果/目的**，不是靠某个独立技术实现的 |

> 记忆口诀：**「持久 redo，原子 undo，隔离 MVCC 和锁，一致性是三者之和」**。

### 2.3 主动展开一层（准备 1~2 个即可）

**redo log 保证持久性**
- **WAL（Write-Ahead Log）**：修改先写 redo log，再由后台异步刷脏页到磁盘。
- 为什么不直接刷数据页？改数据页是**随机 IO**，写 redo log 是**顺序 IO**，快得多。
- 是**物理日志**（记录"某表空间某数据页某偏移改成什么"），**循环写**（ib_logfile0/1），空间固定。
- 崩溃恢复：redo 重放已提交事务 → 再用 undo 回滚未提交事务，即 **crash-safe**。

**undo log 保证原子性**
- 记反向操作：`INSERT` 记 `DELETE`、`DELETE` 记 `INSERT`、`UPDATE` 记**旧值**。
- 同一行的多条 undo log 通过 `roll_pointer` 串成**版本链**，所以 undo log 同时是 **MVCC 的基础**。

**MVCC 保证隔离性（快照读）**
- 每行有隐藏字段 `trx_id`（最后修改事务 ID）和 `roll_pointer`（指向 undo 版本链）。
- 事务快照读时生成 **ReadView**（含 `m_ids` 活跃事务列表、`min_trx_id`、`max_trx_id`、`creator_trx_id`），沿版本链找到**对本事务可见的那个版本**。
- **RC** 每次 SELECT 都生成新 ReadView（所以能读到别人的新提交）；**RR** 只在第一次 SELECT 生成并复用（所以可重复读）。

## 三、30 秒速答版

> 事务有 ACID 四个特性：原子性是要么全做要么全不做，中途出错回滚到事务开始前；一致性是事务前后数据都满足完整性约束，比如转账前后总额不变；隔离性是并发事务之间互不干扰；持久性是提交后即使宕机也不丢。
> InnoDB 的实现是：**持久性靠 redo log**，先写日志后刷盘，崩溃后重放；**原子性靠 undo log**，记录反向操作用于回滚；**隔离性靠 MVCC 和锁**，快照读用版本链加 ReadView，当前读加行锁间隙锁；**一致性没有独立技术，它是前面三个共同保证的结果**。

## 四、对方可能追问的问题

### 4.1 顺 redo log 追（概率最高）

| 追问                             | 答题要点                                                                                                                                                                                                      |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| redo log 和 binlog 有什么区别？       | ①**层级**：redo 是 InnoDB 引擎独有，binlog 是 **Server 层**所有引擎共用；②**内容**：redo 是**物理日志**（页的改动），binlog 是**逻辑日志**（SQL 或行变更）；③**写法**：redo **循环写**空间固定，binlog **追加写**不断新建；④**用途**：redo 用于**崩溃恢复**，binlog 用于**主从复制和归档恢复** |
| 什么是两阶段提交？为什么需要？                | 更新流程：写 redo（**prepare**）→ 写 binlog → 提交 redo（**commit**）。若不用 2PC，两个日志写入之间崩溃会导致**主库和从库数据不一致**（有 redo 无 binlog → 从库少数据；有 binlog 无 redo → 从库多数据）                                                             |
| redo log 什么时候刷盘？               | 参数 **`innodb_flush_log_at_trx_commit`**：`1`=每次提交都 fsync（默认，最安全）；`0`=每秒刷一次（宕机丢 1s）；`2`=写到 OS page cache（MySQL 挂不丢、机器挂才丢）                                                                                   |
| Buffer Pool、脏页、checkpoint 的关系？ | 修改先落 Buffer Pool 变**脏页** → 由后台线程按 **checkpoint** 推进刷盘；redo log 写满时会**强制推进 checkpoint 刷脏页**，此时业务会明显卡顿                                                                                                      |
| redo log 已经能恢复，为什么还需要 undo？    | redo 负责"**已提交的别丢**"，undo 负责"**未提交的要撤**"，职责相反、缺一不可                                                                                                                                                         |

### 4.2 顺 undo log 追

| 追问 | 答题要点 |
|---|---|
| undo log 什么时候被删除？ | 不是提交就删。要等**没有任何 ReadView 还需要这个版本**，由 **purge 线程**异步清理 |
| undo log 自己会丢吗？ | 不会。undo log 的写入**本身也会记 redo log**，所以它同样是 crash-safe 的 |
| undo log 和 MVCC 什么关系？ | 同一行的历史版本靠 `roll_pointer` 串成**版本链**，MVCC 的"多版本"就来自 undo log，二者是**同一套数据的两种用途** |

### 4.3 顺隔离性追（第二高频）

| 追问 | 答题要点 |
|---|---|
| 有哪几种隔离级别？分别解决什么？ | 读未提交（脏读）→ 读已提交（不可重复读）→ **可重复读（MySQL 默认）**（幻读）→ 串行化 |
| RR 是怎么解决幻读的？ | **两条路**：快照读靠 **MVCC**（复用第一个 ReadView）；当前读靠 **间隙锁 / 临键锁**锁住区间不让插入 |
| RR 完全解决幻读了吗？ | ❗**没有完全解决**。经典反例：事务先快照读，中间别人插入并提交，本事务再执行 `UPDATE`（当前读）后又 SELECT，就会看到那条新行。所以说法应是"**很大程度上避免**" |
| 快照读和当前读的区别？ | 快照读=普通 `SELECT`，走 MVCC 不加锁；当前读=`SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE` / `UPDATE` / `DELETE` / `INSERT`，读最新版本并**加锁** |
| MySQL 默认为什么是 RR 而不是 RC？ | 历史原因：早期 binlog 只有 **statement** 格式，RC 下会出现主从数据不一致，所以默认 RR。互联网公司实际**很多设为 RC**（间隙锁少、死锁少、并发高） |
| 行锁有哪几种？ | **记录锁**（Record Lock，锁单行）、**间隙锁**（Gap Lock，锁区间）、**临键锁**（Next-Key Lock = 记录锁 + 间隙锁，RR 默认） |

### 4.4 顺一致性追（常被忽略，容易加分）

| 追问 | 答题要点 |
|---|---|
| 为什么说一致性是靠其他三个保证的？ | 一致性是**目标状态**：原子性防"只做一半"，隔离性防"并发互扰"，持久性防"做完丢失"，三者都满足才谈得上一致 |
| 数据库能保证所有一致性吗？ | ❌ 不能。数据库只能保证它**知道的约束**（主键、非空、外键、唯一、check）；业务级一致（如"库存不能超卖"）仍需**应用层加锁或校验** |
| ACID 的 C 和 CAP 的 C 是一回事吗？ | ❗**不是**（高频陷阱）。ACID 的 C 是**单库完整性约束**；CAP 的 C 是**多副本间的数据一致**，是分布式概念 |

### 4.5 顺工程实践追

| 追问 | 答题要点 |
|---|---|
| MySQL 所有引擎都支持事务吗？ | ❌ 只有 **InnoDB** 支持；**MyISAM 不支持**事务、也不支持行锁 |
| 长事务有什么危害？怎么排查？ | 危害：**undo 无法 purge 导致表空间膨胀**、锁长时间不释放、主从延迟；排查：`information_schema.innodb_trx` 按 `trx_started` 找长时间运行的事务 |
| `@Transactional` 什么情况下会失效？ | ①**方法内自调用**（不走代理）②异常被 `catch` 吞掉 ③默认只回滚 `RuntimeException`，检查异常需 `rollbackFor = Exception.class` ④非 `public` 方法 ⑤类未被 Spring 管理 |
| 事务能跨库吗？ | 不能，本地事务只管单库。跨库要用**分布式事务**：2PC/XA、TCC、Seata、**本地消息表 + MQ 最终一致** |
| DDL 能回滚吗？ | MySQL 8.0 前 DDL 会**隐式提交**当前事务且不可回滚；8.0 引入 **atomic DDL**（依赖数据字典），但仍不建议把 DDL 放进事务 |
