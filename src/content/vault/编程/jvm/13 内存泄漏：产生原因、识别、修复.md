# 内存泄漏：产生原因、识别、修复

> 内存泄漏 = 对象不再使用但仍挂在 GC Root 引用链上、无法被回收，长期占用堆内存；持续泄漏会「滚雪球」般耗尽堆内存，最终引发 OutOfMemory 内存溢出。本页基于 B 站「实战篇-1-内存泄漏和内存溢出」（BV1r94y1b7eS）整理，覆盖概念与产生场景。

## 一、实战篇总览：内存调优解决什么问题

生产环境三类与 JVM 紧密相关的问题：

| 调优方向 | 解决什么问题 |
|---|---|
| **内存调优** | 内存泄漏与内存溢出 |
| **GC 调优** | 高峰期频繁 Full GC 导致 CPU 饱和、系统假死 |
| **性能调优** | 用 JMH 等框架做准确性能测试、优化线上性能 |

内存调优的学习路线：**理解概念 → 内存监控工具选型（如 VisualVM）→ 常见泄漏代码场景 → 项目实战还原**（项目最终部署在服务器 / K8S 容器平台上，尽量还原真实环境）。

## 二、概念

### 1. 内存泄漏（Memory Leak）

**定义**：一个对象我们不再使用，但它依然在 GC Root 引用链上。按可达性分析法，它不会被垃圾回收器回收，长期占用内存 → 可用内存变少 → 内存泄漏。

**图解案例**：GC Root 对象 A → 引用 List 集合 → 集合中存放学生对象。
- 学生对象 1（代表已退出系统的学生）没有从集合中 `remove` 掉，仍在 A 的引用链上 → GC 不回收它 → **内存泄漏**；
- **修复**：调用 `remove` 把它从集合移除；若整个集合都不再使用，把持有它的**静态变量置 null**，整条引用链断开，集合及其中所有对象都可被回收。

> 注意：工作中绝大多数情况是**堆内存**引起的内存泄漏，后续默认讨论的都是堆内存泄漏。

### 2. 内存溢出（OutOfMemory）

持续的内存泄漏像**滚雪球**：假设每秒钟创建 1 兆对象 → 1 分钟 60 兆 → 1 小时 3600 兆（超过 3G）→ 不管堆多大，迟早被耗尽。

**比喻**：网购囤快递箱，箱子堆满屋子后什么都放不下了。

### 3. 两者关系

堆内存中的对象分三类：

| 类型 | 说明 | 是否可回收 |
|---|---|---|
| 不再使用的对象 | 与 GC Root 引用链已无关联 | ✅ 可回收 |
| **内存泄漏对象** | 不再使用但仍在 GC Root 引用链上 | ❌ 不可回收 |
| 需要使用的对象 | 正在使用 | ✅ 用完可回收 |

最终堆里只剩「内存泄漏对象」+「需要使用的对象」两类，把整个堆占满 → 新对象无法分配 → 抛 `OutOfMemoryError`，系统瘫痪。

## 三、常见产生场景

### 场景 1：后端应用缓存未清理

Controller 用 `HashMap` 缓存用户信息（`userId → 300MB 字节数组`）：
- 登录接口：把数据放入缓存；退出登录接口：从缓存删除；
- 若**只登录、不调用退出接口**，300MB 数据长期驻留内存 → 内存泄漏；
- 演示：堆设为 1G，只登录不登出，放入 3 个用户即 OOM。

> 工作中常见写法：轻易把数据放进 `HashMap` 等容器，用完忘记删除 → 泄漏。

### 场景 2：定时任务 / 分布式任务调度中累积

大型系统的分布式任务调度（如 ElasticJob、xxl-job）会在固定时间（如凌晨 1 点）调用 Java 应用生成报表；若被调度的代码存在内存泄漏，**多次调度后**同样触发 OOM。重启后能恢复，但运行一段时间后还会再溢出。

**演示**：Spring 定时任务（`@EnableScheduling` + `@Scheduled(fixedRate=100)`），任务体某行代码存在泄漏，执行约 100 次即爆堆内存溢出。

### 重启为什么不能根治

重启让堆内存恢复初始状态，只是**暂时**解决；运行一段时间后泄漏继续累积，OOM 会再次出现，必须**从根源修复**。
