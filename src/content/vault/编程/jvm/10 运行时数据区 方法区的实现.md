# 方法区的实现 · 永久代与元空间

> 方法区是**线程共享**区域，存放三类数据：**类的元信息**、**运行时常量池**、**字符串常量池**。方法区只是虚拟机规范里的**虚拟概念**，HotSpot 有两种实现：**JDK7 及之前用「永久代」放在堆里**（大小受 JVM 参数限制，容易溢出），**JDK8 及之后用「元空间」放在直接内存里**（默认只受操作系统内存上限约束）。生产环境务必用 `-XX:MaxMetaspaceSize` 设一个上限，一般 **256M** 起。

> 来源：B站「基础篇-23-方法区的实现」（BV1r94y1b7eS）

## 一、方法区存放什么

方法区是一块**线程共享**的区域，每一个线程都可以获取方法区里共享的数据。它主要存放一些**基础信息**：

| #   | 存放内容       | 说明                  |
| --- | ---------- | ------------------- |
| 1   | **类的元信息**  | 每一个类的基本信息（metadata） |
| 2   | **运行时常量池** | 字节码文件中的常量池被读入内存后的形态 |
| 3   | **字符串常量池** | 单独拎出来讲 —— 见下方说明     |

**关于字符串常量池的定位**：网上很多资料把字符串常量池归类在运行时常量池中。但随着 JDK 版本升级，**字符串常量池的设计一直在变化**，所以本系列把它单独列出来讲（下一小节的内容）。

## 二、类的元信息

在[[编程/jvm/04 类加载器]]的加载阶段学过：JVM 通过类加载器把类的字节码信息读入内存，并创建一个 `InstanceKlass` 对象，把字节码中的**基本信息、常量池、字段、方法**等数据全部存放在这个对象中。

此外，为了实现 Java 语法层面的一些特定功能（比如**多态**），JVM 还会在 `InstanceKlass` 对象里存放额外信息，例如 **虚方法表（vtable）** —— 它是实现多态的基础。

> **重要提醒（图示与底层实现的差异）**：示意图上把常量池、方法这些信息都画在 `InstanceKlass` 对象里，但**真正的 JVM 底层实现会把常量池和方法单独摘出来，用另一块内存区存放**，`InstanceKlass` 中只保存指向它们的**引用**。

**所以方法区的第一个作用**：存放每一个类的基本信息（元信息）。

## 三、运行时常量池

字节码文件中有一块内容就是**常量池**。常量池在**加载阶段**被读到内存中，此时就由原来的**静态常量池**变成了**运行时常量池**。

| | 静态常量池（class 文件中） | 运行时常量池（内存中） |
|---|---|---|
| 访问方式 | **编号**引用，如 `#6`（符号引用） | **内存地址**直接访问 |
| 性能 | — | **更高** |

所谓运行时常量池，就是**每一个常量的数据都可以通过内存地址去访问** —— 原来用 `#6` 这种符号引用的方式，要转变成通过内存地址直接访问，整体性能会更高一些。

> 符号引用→直接引用的转换过程，即[[编程/jvm/07 运行时数据区 栈 操作数栈和帧数据]]中「帧数据 · 动态链接」所做的事情。

## 四、方法区只是规范：两种实现

**方法区只是 Java 虚拟机规范中设计的一个虚拟概念**，每一款 JVM 在实现上都各不相同 —— 甚至对 HotSpot 这一款虚拟机来说，**不同版本实现方法区用到的技术都可能不同**。

### 4.1 JDK7 及之前：永久代（PermGen）

- 方法区**存放在堆里**，这块空间叫做**永久代**
- 大小由**虚拟机参数**来控制

> 这一点可能出乎意料 —— 前面的运行时数据区总览图上，方法区和堆是**两块不同的区域**，但在 JDK7 及之前，方法区是设计**放在堆里**的。

**这样设计的问题**（用现代眼光看肯定不合适）：

1. 把两个概念揉在一起，**维护复杂度**高
2. 在堆上就必须设一个最大空间，**容量受限**，方法区数据量过多时会内存溢出

### 4.2 JDK8 及之后：元空间（Metaspace）

- 把方法区**单独摘出来**，放到一块叫做**元空间**的区域
- 元空间存放在**操作系统维护的直接内存**中（直接内存下一小节详细介绍）

目前可以这样理解直接内存：**它是操作系统拥有的内存，独立于 JVM 内存空间之外**。因此：

- 使用上更**灵活**，不受 JVM 内存的各种限制
- 默认情况下，**只要不超过操作系统承受的上限就可以一直分配**
- 于是可以拥有非常大的方法区内存空间

### 4.3 用 Arthas 的 memory 命令实测对比

分别在 JDK7 和 JDK8 上用 `memory` 命令打印内存情况：

**JDK7 —— 有一块 `ps_perm_gen`（即永久代）**

```
ps_perm_gen    used = 17M   total = 21M   max = 82M
```

类的基本信息与运行时常量池就存放在这块空间中。注意 `max = 82M` —— **永久代在堆上，必须设一个最大空间**。

**JDK8 —— `perm_gen` 消失，取而代之的是 `metaspace`**

```
metaspace      used = 19M   total = 19M   max = -1
```

读法：

| 现象 | 含义 |
|---|---|
| `used = total = 19M` | 当前使用量等于总量，说明**空间已经满了** |
| `max = -1` | **-1 代表不设上限** |

所以尽管 `total` 已经满了也没关系，**依然可以继续往这块空间分配内存** —— 因为它已经脱离了 JVM 内存的上限。当然这块空间如果一直增长，**最多不能超过操作系统的内存上限**，因为元空间用的直接内存由操作系统掌管。

**结论**：方法区是虚拟的概念，在 HotSpot 中的实现方式有两种 —— **永久代**和**元空间**。

## 五、代码验证方法区溢出

### 5.1 思路

让方法区溢出比较简单：**不停地往方法区添加类的信息**即可。用 **Byte Buddy** 框架**动态生成字节码信息**并加载到内存，用死循环不停地把这些字节码对象加载到方法区，方法区内存就会一直往上增长。然后分别在 JDK7 和 JDK8 上运行。

### 5.2 Byte Buddy 基本用法

Byte Buddy 是一个**基于 Java 的开源库**，可以用来生成、操作 Java 字节码。

**第一步：引入依赖**

```xml
<dependency>
    <groupId>net.bytebuddy</groupId>
    <artifactId>byte-buddy</artifactId>
    <version>1.12.23</version>
</dependency>
```

**第二步：创建 `ClassWriter` 对象**，传 `0` 表示默认设置

**第三步：调用 `visit` 方法创建字节码数据**，几个核心参数：

| 参数 | 说明 |
|---|---|
| 第 1 个：JDK 版本 | 最终影响字节码信息中的**主版本号和副版本号** |
| 第 2 个：访问标识 | 按示例写默认即可 |
| 第 3 个：全限定名 | **每次创建的类名必须不同** —— 如果把两个同名类交给同一个类加载器，它会认为这是同一个类 |
| 第 4/5/6 个：签名、父类名、接口 | 按示例写默认（父类 `java/lang/Object`）即可 |

**第四步**：通过 `toByteArray()` 拿到这个类的字节码数据，再交给类加载器成功加载即可。

> **补充**：`ClassWriter` / `Opcodes` / `toByteArray()` 其实是 **ASM** 的 API。Byte Buddy 内部依赖并**重打包**了 ASM，所以引入 byte-buddy 后 import 的是 `net.bytebuddy.jar.asm.ClassWriter`。这也是为什么依赖写的是 byte-buddy，代码里用的却是 ASM 风格的写法。

### 5.3 测试代码

```java
public class MethodAreaOOMTest extends ClassLoader {   // 继承 ClassLoader → 自定义类加载器
    public static int count = 0;

    public static void main(String[] args) throws IOException {
        System.in.read();                              // 阻塞，方便挂载 Arthas
        MethodAreaOOMTest test = new MethodAreaOOMTest();
        while (true) {                                 // 死循环，不停往方法区添加字节码信息
            ClassWriter classWriter = new ClassWriter(0);
            classWriter.visit(Opcodes.V1_7, Opcodes.ACC_PUBLIC,
                    "Class" + count,                   // 类名带上 count，保证每次都不同
                    null, "java/lang/Object", null);
            byte[] bytes = classWriter.toByteArray();
            test.defineClass("Class" + count, bytes, 0, bytes.length);  // 用自定义类加载器加载
            count++;
            System.out.println(count);                 // 统计溢出时总共创建了多少个类
        }
    }
}
```

**两个关键点**：

1. 测试类**继承 `ClassLoader`**，因此它是一个自定义类加载器，可以直接调用 `defineClass`
2. 类名由 `"Class" + count` 生成，**只要 count 每次递增，类名就每次都不相同**

## 六、实测结果对比

| 版本 | 结果 |
|---|---|
| **JDK7** | 类的数量达到 **11 万左右**时内存溢出 → `java.lang.OutOfMemoryError: PermGen space` |
| **JDK8** | 跑了**上百万次**都没有出现任何错误；打开任务管理器可看到该进程**内存一直直线增长** |

**JDK7 的错误信息读法**：`OutOfMemoryError` 这个错误与之前[[编程/jvm/09 运行时数据区 堆内存]]演示的堆溢出**完全一样**，但**后面打印的内容不同** —— 这里指的是 `PermGen`（永久代）这块区域溢出。

> 由此印证：**JDK7 中类信息确实存放在永久代**；而 JDK8 把方法区搬到了元空间，因为元空间位于操作系统的直接内存中，默认只要不超过操作系统内存上限就能一直分配，所以百万次也不报错。

## 七、控制方法区大小的参数

| JDK 版本 | 参数 | 说明 |
|---|---|---|
| JDK7 及之前 | `-XX:MaxPermSize=<size>` | 控制**永久代**的最大大小 |
| JDK8 及之后 | `-XX:MaxMetaspaceSize=<size>` | 控制**元空间**的最大大小 |

> **补充**：`-XX:MaxPermSize` 在 JDK8 中**已被废弃**，加了会打印警告并被忽略。另外别把 `-XX:MaxMetaspaceSize` 和 `-XX:MetaspaceSize` 搞混 —— 后者不是「初始大小」，而是**首次触发 Metaspace GC 的阈值**，是个很容易误解的参数名。

## 八、为什么元空间也要设上限

既然元空间默认可以用到操作系统的内存上限，为什么还要给它设一个最大大小？

**要考虑这种情况**：有些公司部署程序时，**一台服务器上会部署好几个程序**。如果其中一个 Java 程序在方法区的处理上出了问题（比如像上面这样用了不合理的循环，往方法区存放大量数据），那么这个程序占用的直接内存（也就是操作系统内存）就会一直上升；**到达操作系统内存上限时，有可能把其他程序的内存资源占用掉**，从而影响整个服务器上所有程序的运行。

**建议**：启动程序时最好给元空间设置一个最大大小。具体值根据程序情况而定，**一般没有过高要求，设置为 256M 就可以**。

### 8.1 实测：限制为 256M

在 IDEA 的运行配置里添加 JVM 参数：

```
-XX:MaxMetaspaceSize=256m
```

运行结果：执行了 **39 万次**之后出现 `OutOfMemoryError`，但这一次提示的错误发生在 **Metaspace**（元空间）里。

**结论**：256M 大小能够容纳 **30 多万个类**的加载，这个数量对一般程序来说足够用了。如果发现自己的程序需要更大的元空间，也可以往上调（比如 512M），只要满足程序要求即可。**但一定要为自己的程序加上元空间的最大大小，防止内存占用过高。**

> **补充**：生产环境中元空间 OOM 最常见的真实原因不是「类太多」，而是**类加载器泄漏** —— 大量动态生成类（CGLib 代理、脚本引擎、反射生成类）或频繁热部署，导致旧的类加载器无法被回收，它加载的类元信息也就一直留在元空间。排查思路见[[编程/jvm/13 内存泄漏：产生原因、识别、修复]]。

## 九、小结

1. 方法区是**线程共享**区域，存放**类的元信息**、**运行时常量池**、**字符串常量池**三类数据
2. 类元信息保存在 `InstanceKlass` 对象中，包含基本信息/常量池/字段/方法，以及实现多态的**虚方法表**；底层实现中常量池和方法**单独存放**，`InstanceKlass` 只存引用
3. 静态常量池在加载阶段变成**运行时常量池**：由 `#6` 这类**符号引用**转为**内存地址**直接访问，性能更高
4. **方法区只是规范中的虚拟概念**，HotSpot 有两种实现，且不同版本不同
5. **JDK7 及之前 = 永久代**，位于**堆**中，必须设最大空间（Arthas 里叫 `ps_perm_gen`）
6. **JDK8 及之后 = 元空间**，位于**直接内存**（操作系统内存）中，Arthas 里 `max = -1` 表示不设上限
7. 溢出实测：JDK7 约 **11 万**个类就抛 `OutOfMemoryError: PermGen space`；JDK8 上百万次不报错，但进程内存直线上升
8. 参数：JDK7 用 `-XX:MaxPermSize`，JDK8 用 `-XX:MaxMetaspaceSize`
9. **元空间必须设上限** —— 否则单个程序可能吃满操作系统内存，拖垮同一台服务器上的其他程序
10. **建议 `-XX:MaxMetaspaceSize=256m`**（可容纳 30 多万个类），不够再往上调到 512M
