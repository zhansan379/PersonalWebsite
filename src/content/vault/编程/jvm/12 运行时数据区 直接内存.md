# 直接内存 · NIO 零拷贝与运行时数据区总结

> 直接内存**不在 JVM 规范中**，也不属于 Java 运行时内存区域。它是为 **NIO** 服务的：一是让这部分内存的回收**不影响堆上对象**（避免 GC 卡顿），二是**省掉一次「直接内存 → 堆」的数据复制**从而提升 IO 效率；JDK8 之后它还承载了方法区（元空间）。用 `ByteBuffer.allocateDirect()` 分配，用 `-XX:MaxDirectMemorySize` 限制上限。本页最后附**整个运行时数据区的章节总结**与 **JDK6/7/8 三版演变对比**。

> 来源：B站「基础篇-25-直接内存」（BV1r94y1b7eS）

## 一、直接内存是什么

到目前为止，JVM 规范中提到的几块内存区域 —— **程序计数器、栈、堆、方法区** —— 已经全部学完。直接内存其实在之前的课程中已经提到过：[[编程/jvm/10 运行时数据区 方法区的实现]]中讲到，**JDK8 及之后方法区的内容就存在于直接内存中的元空间**这块区域。

**直接内存的定位**：

- **不在 Java 虚拟机规范中存在**
- **不属于** Java 运行时的内存区域
- 它的出现主要是为了解决一个特定的问题

## 二、为什么会出现直接内存

**背景**：JDK 1.4 之后引入了 **NIO** 这种 IO 机制。企业中用 Java 开发网络程序，底层一般都基于 NIO —— 包括现在 Java 里比较火的 **Netty** 网络框架，底层也整合了 NIO 机制。**NIO 机制就使用到了直接内存。**

它使用直接内存主要为了解决**两个问题**：

### 2.1 问题一：避免 GC 影响用户使用

Java 堆里的对象如果不再使用会被回收（垃圾回收机制后面章节详细讲）。但**回收的时候会影响对象的创建和使用**：比如用户正在使用系统，正好 JVM 要回收堆中不再使用的对象，**这个回收过程可能导致用户的使用出现卡顿**，用户感受非常不好。

所以直接内存希望做到：**这部分内存在回收的时候不会影响到堆上的对象**，这样就不会对用户的使用产生影响。

### 2.2 问题二：提升 IO 操作的效率

**NIO 出现之前 —— 阻塞 IO 读文件**：

```
本地文件 → ① 读到操作系统的直接内存 → ② 复制到 Java 堆内存 → 程序从堆上获取数据
```

**使用直接内存之后**：

```
本地文件 → ① 读到直接内存 → 程序在堆上只维护一个【保存直接内存地址的引用对象】→ 直接访问
                                    ↑ 第 ② 步的复制动作不再需要
```

**收益**：减少了**一次数据复制**的开销。

**写文件同理** —— 可以把数据直接写入直接内存，也少了一次「从 Java 堆复制到直接内存」的开销。

### 2.3 第三个作用

**JDK8 之后，直接内存还用来保存方法区中的数据**（元空间）。

## 三、如何在直接内存中创建数据

Java 提供了 `ByteBuffer` 类，它有一个静态方法 `allocateDirect()`，作用就是**在直接内存上分配内存空间**，参数传内存空间的大小：

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024 * 100);   // 分配 100MB 直接内存
```

## 四、用 Arthas 观察直接内存

`memory` 命令输出中，直接内存的属性名叫 **`direct`**。

> **重要区分**：通过 `direct` 看到的直接内存大小，是**我们通过 `ByteBuffer` 分配的内存空间**，**和元空间没有关系** —— 元空间用的是 `metaspace` 这个属性来展示大小。虽然元空间物理上也位于直接内存中，但在 Arthas 的输出里两者是分开统计的。

## 五、代码实测

### 5.1 观察直接内存递增

```java
public class DirectMemoryTest {
    // 1024 字节(1KB) × 1024 = 1MB，× 100 = 100MB
    private static final int size = 1024 * 1024 * 100;

    public static void main(String[] args) throws Exception {
        System.in.read();
        ArrayList<ByteBuffer> list = new ArrayList<>();
        int count = 0;
        while (true) {
            // 每轮循环创建 100MB 直接内存
            ByteBuffer buffer = ByteBuffer.allocateDirect(size);
            list.add(buffer);        // 放入集合保存，否则不再使用的内存会被回收
            System.out.println(++count);
            Thread.sleep(5000);      // 休眠 5 秒，方便在 Arthas 中观察
        }
    }
}
```

**观察方式**：因为每隔 5 秒增加一次，直接输入 `dashboard`（不加参数，默认就是每 5 秒刷新一次）。

**观察结果**：

```
程序进入循环前：direct = 0        （还没分配任何内存）
进入循环：      direct = 100M
5 秒后：        direct = 200M
……            每过 5 秒以 100M 递增
```

**证明**：往直接内存中分配对象是没有问题的。

### 5.2 观察直接内存溢出

把 `Thread.sleep(5000)` 去掉，让程序一直运行：

```
java.lang.OutOfMemoryError: Direct buffer memory
```

**程序执行了 72 次之后就溢出了**。但要注意两点：

1. 虚拟机配置中**并没有设置任何直接内存上限**
2. Arthas 中直接内存的 `max` 这一栏写的是一个**横杠 `-`**，说明它**没有办法获取到这个值**

**那为什么 72 次之后就溢出了？**

因为 **JVM 在通过 `ByteBuffer` 分配直接内存时做了一些限制** —— 不可能让程序向系统资源无限申请。但由虚拟机来制定这个值，对我们的程序来说毕竟还是不太合理，所以我们需要知道**如何手动设置直接内存的上限**，从而针对不同系统情况做定制化设置。

> **补充（72 这个数字从哪来）**：`-XX:MaxDirectMemorySize` 不设置时，**默认值约等于最大堆大小 `-Xmx`**。前面[[编程/jvm/09 运行时数据区 堆内存]]测出这台机器的默认 `max heap = 7G`，而 72 × 100MB ≈ **7.2G** —— 正好在 7G 附近失败。这就是「72 次」的由来，也说明这个默认值完全取决于机器和堆配置，不是一个固定数字。

## 六、手动设置直接内存上限

```
-XX:MaxDirectMemorySize=<size>
```

**单位**：`k`/`K`、`m`/`M`、`g`/`G`。

**实测**：在 IDEA 中添加 JVM 参数 `-XX:MaxDirectMemorySize=1g`，运行结果 —— **第 11 次时申请直接内存失败**。因为设置的 1G 最多只能容纳 10 次 100MB 的分配。

## 七、工作中的建议

| 情况 | 建议 |
|---|---|
| 工作中**没有使用**直接内存 | 这个参数**可以不设置** |
| 底层**使用了 NIO** | **建议设置 `-XX:MaxDirectMemorySize`**，把直接内存控制在合理范围内 |

**这个值怎么定**：需要在**测试环境中进行压力测试**，看当前直接内存最大能达到多少，**设置的值至少要比压测下的最大值大一些**。

> **补充**：直接内存有两个容易踩的坑，值得和上面的建议一起记：
> 1. **直接内存不受 GC 直接管理**。`ByteBuffer.allocateDirect` 分配的内存靠 `Cleaner`（虚引用）在 `DirectByteBuffer` 对象被回收时才释放，而这通常需要一次 **Full GC** 才会真正触发。所以如果加了 `-XX:+DisableExplicitGC`（禁用 `System.gc()`），直接内存可能迟迟不释放 —— 这是 Netty 应用的经典事故。
> 2. **直接内存泄漏很难排查**：它不在堆里，`jmap` 导出的堆快照中看不到这部分内存，只能看到进程 RSS 一直涨而堆很干净。排查要靠 `-XX:NativeMemoryTracking` 或 Arthas 的 `memory` 看 `direct` 这一项。

## 八、本章总结：运行时数据区

到这里运行时内存区域的所有内容就介绍完了。本章主要回答两个问题。

### 8.1 问题一：运行时数据区分成哪几部分，各自作用是什么

**五部分，按线程是否共享划分**：

| 区域 | 线程共享性 | 作用 | 会不会内存溢出 |
|---|---|---|---|
| **程序计数器** | 不共享（每线程独立） | 记录当前要执行的字节码指令地址，控制程序执行，实现**顺序/分支/跳转/异常**等逻辑 | **不会** |
| **Java 虚拟机栈** | 不共享 | 临时性结构，保存方法调用中的基本数据：局部变量表、操作数栈、帧数据；每个方法调用使用一个**栈帧** | **会**（`StackOverflowError`） |
| **本地方法栈** | 不共享 | 同上，用于本地方法 | 会 |
| **堆** | **共享** | 存放创建出来的对象 | **会**，且是**最容易**产生溢出的位置 |
| **方法区** | **共享** | 存放类的元信息以及常量池 | **会** |

**几点补充说明**：

- **栈溢出**：工作中比较少见，一般只可能出现在**递归调用没有控制好退出条件**的时候，抛出 `StackOverflowError` —— 详见[[编程/jvm/08 运行时数据区 栈 内存溢出与本地方法栈]]
- **堆溢出**：是整个内存区域中**最复杂**的，并且和**垃圾回收机制**有关系，**下一章节还会回来研究堆内存溢出的真实原因** —— 对应[[编程/jvm/09 运行时数据区 堆内存]]第七章留下的悬念
- **方法区溢出**：当方法区存放了**大量类的元信息**、且方法区大小**设置得过小**时会发生 —— 详见[[编程/jvm/10 运行时数据区 方法区的实现]]

### 8.2 问题二：不同 JDK 版本在运行时数据区设计上的区别

| 版本 | 方法区的实现 | 方法区在哪 | 字符串常量池在哪 |
|---|---|---|---|
| **JDK6** | **永久代** | **堆**里面 | **方法区（永久代）里** |
| **JDK7** | **永久代** | **堆**里面 | **从永久代拆出来，放到堆上自己占一块空间** |
| **JDK8** | **元空间**（永久代不再存在） | **直接内存**中的一块区域 | **依旧放在堆里** |

一句话记忆：**方法区从堆里搬到了堆外（永久代→元空间），字符串常量池则从方法区搬进了堆，而且再也没搬走。**

> 三阶段演变的完整推导过程见[[编程/jvm/11 运行时数据区 方法区 字符串常量池]]第二章。

## 九、小结

1. 直接内存**不在 JVM 规范中**，**不属于**运行时内存区域，是 JDK1.4 引入 **NIO** 后为其服务的机制（Netty 底层也用它）
2. 作用一：这块内存的回收**不影响堆上对象**，避免 GC 导致用户使用卡顿
3. 作用二：**减少一次数据复制** —— 传统阻塞 IO 是「文件→直接内存→堆内存」，用直接内存后堆上只需维护一个**保存直接内存地址的引用对象**；读写文件都受益
4. 作用三：JDK8 之后**承载方法区（元空间）的数据**
5. 用 **`ByteBuffer.allocateDirect(size)`** 在直接内存上分配空间
6. Arthas `memory` 中直接内存看 **`direct`** 一项，它统计的是 `ByteBuffer` 分配的空间，**与 `metaspace` 分开统计**
7. 直接内存**会溢出**，抛 `OutOfMemoryError: Direct buffer memory`；不设参数时 Arthas 的 `max` 显示 `-`（取不到），但 JVM 内部仍有限制（默认约等于 `-Xmx`）
8. 用 **`-XX:MaxDirectMemorySize`**（单位 k/m/g）手动设上限；实测设 1g 后第 11 次分配 100M 就失败
9. **建议**：不用直接内存可不设；**底层用了 NIO 就应该设**，值由测试环境压测的最大值再放大一些得出
10. 运行时数据区五部分：**程序计数器/虚拟机栈/本地方法栈**线程私有，**堆/方法区**线程共享；除程序计数器外**都可能内存溢出**
11. 版本演变：**JDK6 永久代在堆 + 字符串常量池在方法区 → JDK7 字符串常量池进堆 → JDK8 元空间进直接内存、字符串常量池仍在堆**
