# 方法区 · 字符串常量池与静态变量

> 方法区存放的第三部分内容是**字符串常量池**。它与运行时常量池的关系随 JDK 版本变了三次：**JDK6 及之前两者合一、都在永久代** → **JDK7 字符串常量池单独挪到堆** → **JDK8 运行时常量池随方法区进元空间，字符串常量池仍在堆**。核心考点有三个：**`+` 拼接时左右是变量还是常量**（变量走 `StringBuilder` 到堆，常量走编译期折叠到常量池）、**`intern()` 在 JDK7 后只存引用不再搬运字符串**、**静态变量 JDK7 起存放在堆中的 Class 对象里**（而非方法区）。

> 来源：B站「基础篇-24-方法区-字符串常量池」（BV1r94y1b7eS）

**1**.**元空间是什么（核心定义）**  
**元空间（Metaspace）是 HotSpot 虚拟机在 JDK 1.8 及之后版本中，对“方法区（Method Area）”的具体落地实现。** 它最本质的特征是：**不再使用 JVM 堆内的内存，而是使用操作系统的本地内存（Native Memory）**。

**2. 元空间里到底存了什么？**  
它主要存储**类的元数据信息**（即描述类本身长相的数据），具体包括：
- **类的结构信息**：类的全限定名、父类信息、实现的接口列表、访问修饰符（public/private等）。
- **类的方法和字段信息**：每个方法的字节码指令（`Code`属性）、异常表、方法签名；每个字段的名称、类型和访问标志。
- **运行时常量池**：也就是你上一个问题问到的所有内容（字面量、符号引用、直接引用等），它们作为类元数据的一部分，被保存在元空间中。
- **注解信息**：类、方法、字段上标注的运行时注解（`@Retention(RetentionPolicy.RUNTIME)`。
- **方法表与虚方法表（vtable）**：用于支持动态分派和多态调用的内部结构。
## 一、字符串常量池存什么

字符串常量池里存放的就是**代码中定义的常量字符串**。比如代码里写了一个字符串 `"123"`，这个常量就会被直接放入字符串常量池中。

### 1.1 入门案例

```java
String s1 = new String("abc");
String s2 = "abc";
System.out.println(s1 == s2);   // false
```

**逐步分析**：

| 步骤 | 发生了什么 |
|---|---|
| 编译成字节码 | `"abc"` 直接加入**静态常量池** |
| 字节码读入内存 | `"abc"` 被自动加载到**字符串常量池** |
| `new String("abc")` | 因为用了 `new`，对象最终放在**堆内存**中；栈里的局部变量 `s1` 保存堆中对象的地址 |
| `String s2 = "abc"` | **没有用 `new`**，所以 `s2` 里存放的是**字符串常量池中** `"abc"` 的地址 |
| `s1 == s2` | 一个在堆、一个在常量池，地址不同 → **false** |

**结论**：字符串常量池中存放的内容，就是通过字节码文件读取到的**静态常量池中的字符串**。

## 二、字符串常量池与运行时常量池的关系

字符串常量池和[[编程/jvm/10 运行时数据区 方法区的实现]]中介绍的运行时常量池，**用处基本接近**。

**最早的时候，字符串常量池就是运行时常量池的一部分** —— 因为运行时常量池除了存放字符串常量，还可以存放类名常量、整数常量等，它们的存储位置也都一样。但在后续 JDK 版本中做了调整，**把两者拆分开了**。

### 2.1 三个阶段的演变

| 阶段 | 运行时常量池 | 字符串常量池 | 方法区实现 |
|---|---|---|---|
| **JDK7 之前** | 包含字符串常量池 | **在运行时常量池内** | 永久代（两块内容都在永久代中） |
| **JDK7** | 在永久代 | **被拿出来，单独存放在堆中** | 永久代 |
| **JDK8 及之后** | **移动到元空间** | **仍在堆中** | 元空间（永久代不再使用） |

**所以现在可以认为：字符串常量池和运行时常量池已经不再是一个东西了。**

## 三、练习题一：变量拼接

用字节码指令分析下面这段代码的执行结果：

```java
String a = "1";
String b = "2";
String c = "12";
String d = a + b;
System.out.println(c == d);   // ?
```

### 3.1 常量池中的内容

字节码加载到内存后，字符串常量池中会放入**三个字符串**：`"1"`、`"2"`、`"12"` —— 因为这三个字符串在源代码中都用**常量**来声明。

### 3.2 字节码逐行分析

```
 0: ldc           #2    // String "1"     ← 把常量池中"1"的地址放入操作数栈
 2: astore_1                              ← 从操作数栈取出，存入局部变量表 1 号位（a）
 3: ldc           #3    // String "2"
 5: astore_2                              ← b
 6: ldc           #4    // String "12"
 8: astore_3                              ← c
 9: new           #5    // StringBuilder  ← 关键！d = a + b 从这里开始
12: dup
13: invokespecial #6    // StringBuilder.<init>()
16: aload_1                               ← 取出 a（"1"的地址）
17: invokevirtual #7    // append
20: aload_2                               ← 取出 b（"2"的地址）
21: invokevirtual #7    // append
24: invokevirtual #8    // toString       ← 生成新对象，放入【堆内存】
27: astore        4                       ← d 保存的是【堆】上"12"的地址
```

**关键点**：实现 `+` 对两个字符串进行连接时，**底层用到的是 `StringBuilder` 对象** —— 通过 `aload` 指令取出局部变量表中 `a`、`b` 位置上的字符串，用 `append` 连接，再用 `toString()` 转成字符串对象**存放到堆内存**中。

### 3.3 结论

`c` 指向**字符串常量池**中的 `"12"`，`d` 指向**堆内存**中的 `"12"` → **`false`**。

> **解题心法**：做这类字符串常量池的题目，一定要分析清楚 **局部变量表中存放的这个地址，到底是在字符串常量池中还是在堆内存中** —— 这个可以通过字节码指令判断出来。

## 四、练习题二：常量拼接

在第一题的基础上只改一个点 —— `d` 不再用变量 `a`、`b` 连接，而是**直接用常量连接**：

```java
String a = "1";
String b = "2";
String c = "12";
String d = "1" + "2";     // ← 改动点
System.out.println(c == d);   // ?
```

用 IDEA 的 **jclasslib** 插件查看 `main` 方法的字节码，前面几条指令完全一样，但偏移量 9 处**不再使用 `StringBuilder`**：

```
 9: ldc           #4    // String "12"    ← 直接从字符串常量池取地址
11: astore        4
```

**所以 `c` 和 `d` 都来自字符串常量池 → `true`。**

**原因**：**编译器在编译过程中直接把这个 `+` 去掉了**，最终编译出来的结果其实就是 `String d = "12";`，与上面 `String c = "12";` 完全一样。

### 4.1 两题对比小结

| 题目 | `+` 左右是什么 | 编译期行为 | 结果对象在哪 | `c == d` |
|---|---|---|---|---|
| 第一题 `a + b` | **变量** | 替换成 `StringBuilder` 处理 | **堆** | `false` |
| 第二题 `"1" + "2"` | **常量** | **直接拼接成 `"12"`** | **字符串常量池** | `true` |

**两题最大的区别就是：用 `+` 连接时，左右到底是变量还是常量。**

> **补充**：
> 1. 这种编译期直接算出结果的行为叫**常量折叠**，只对**编译期常量**生效 —— 字面量，以及被 `final` 修饰且用字面量初始化的变量。所以 `final String a = "1"; String d = a + "2";` 结果也是 `true`。
> 2. **JDK9 起，变量拼接的底层实现变了** —— 不再生成 `StringBuilder` 调用链，而是用 `invokedynamic` 指令调用 `StringConcatFactory`（字符串拼接工厂）。结论（结果对象在堆上）不变，但如果你在 JDK9+ 上用 jclasslib 看字节码，看到的是 `invokedynamic makeConcatWithConstants` 而不是 `StringBuilder`，不要以为自己看错了。

## 五、intern 方法

`intern()` 方法**允许我们手动将字符串放入常量池中**。此前常量池里的内容都是通过代码中的常量来定义、由字节码信息加载进去的，而 `intern()` 让我们可以手动把某个字符串放到常量池中。

### 5.1 基础用法

```java
Scanner scanner = new Scanner(System.in);
String input1 = scanner.next().intern();   // 收到输入后立即放入字符串常量池
String input2 = scanner.next().intern();
System.out.println(input1 == input2);      // 两次都输入"IT黑马" → true
```

**执行逻辑**：第一次输入 `IT黑马` 并放入常量池；第二次再输入 `IT黑马` 时，调用 `intern()` 就**直接从常量池里把它取出来**，所以 `input1 == input2` 返回 `true`。

**价值**：整个执行过程中**只往常量池里存放了一份数据**，所以 `intern()` 可以**减少相同字符串在内存中的存储空间**。

**适用场景**：从**文件或网络读取大量重复字符串**时，把这些字符串加入常量池然后多次复用。

> **注意**：`intern()` 在工作中的使用场景并不多，它主要是**在面试中被高频考到**。

### 5.2 经典面试题

```java
String s1 = new StringBuilder().append("sink").append("123").toString();
System.out.println(s1.intern() == s1);     // ?

String s2 = new StringBuilder().append("ja").append("va").toString();
System.out.println(s2.intern() == s2);     // ?
```

**很多人的第一反应是两个都 `false`** —— 因为 `intern()` 返回常量池里的地址，而 `s1`/`s2` 是堆上的地址，与前面讲的内容一致。但**在 JDK8 中实测结果是 `true` 和 `false`**。为什么？

#### 5.2.1 两个前提知识

1. **JVM 在启动过程中自己就要用到 `"java"` 这个字符串**，所以它会**直接把 `"java"` 加入常量池**
2. 源代码中的 `"sink"`、`"123"`、`"ja"`、`"va"` 等字符串也会被加入常量池，但**不影响最终结果**

#### 5.2.2 JDK6 的执行流程：false / false

JDK6 中，`intern()` 会把**第一次遇到的字符串实例复制到永久代的字符串常量池中**；第二次再调同样字符串的 `intern()`，直接返回常量池中的地址。

| 代码 | 过程 | 结果 |
|---|---|---|
| `s1` | 堆上创建新对象 `"sink123"`，`s1` 指向它；常量池里没有 `"sink123"`，`intern()` 把它**复制**进常量池并返回**常量池地址** | `s1` 在堆、`s1.intern()` 在常量池 → **false** |
| `s2` | 堆上创建 `"java"` 对象；`intern()` 发现常量池**本来就有** `"java"`，直接返回常量池地址 | 地址不同 → **false** |

#### 5.2.3 JDK7 及之后：true / false

**JDK7 及之后，由于字符串常量池放在堆上**，`intern()` 会把第一次遇到的字符串的**引用**放到常量池中 —— **不再是把字符串搬运到常量池里去，而只是把引用放进去**，这样可以节省一定的空间。

| 代码 | 过程 | 结果 |
|---|---|---|
| `s1` | 堆上创建 `"sink123"`，`s1` 指向它；`intern()` 在常量池里**直接存放一个指向堆上对象的引用**，返回的就是**堆上的地址** | 两者都指向堆上同一个对象 → **true** |
| `s2` | 堆上创建 `"java"` 对象；但 `"java"` 是**启动过程中就放进常量池的**，`intern()` 直接返回常量池里那个 `"java"` 的地址 | 地址不同 → **false** |

#### 5.2.4 记住这个核心结论

> **JDK7 及之后的版本中，在堆上创建的字符串如果调用了 `intern()`，只是在常量池中存放了这个对象的引用，而不再把字符串搬运到常量池中。**

记住这个结论，这类问题都可以很容易地解决。

**同时要提醒**：不同 JDK 版本在 `intern()` 实现上的差别还是比较大的，**或许未来版本的实现方案会和上面两种都不相同**。

> **补充**：第二问之所以是 `false`，唯一的原因就是 `"java"` 这个字符串**被 JVM 抢先放进了常量池**。这是这道题的陷阱 —— 把 `"ja" + "va"` 换成任何一个 JVM 启动时用不到的字符串（比如 `"he" + "ima"`），JDK7+ 上的结果就会变成 **`true`**。所以答这道题时一定要点出「`java` 是 JVM 启动时已入池的字符串」，否则说明只背了答案没理解机制。

## 六、静态变量存放在哪里

这是方法区这一小节的最后一个问题。

| JDK 版本 | 静态变量存放位置 |
|---|---|
| **JDK6 及之前** | **方法区中**（即永久代） |
| **JDK7 及之后** | 被挪到**堆中的 Class 对象**里，脱离了永久代 |

**所以网上有些资料说「静态变量存放在方法区里」，这个描述并不准确** —— 因为**静态变量存放的位置与 JDK 版本有关**。

### 6.1 用 HotSpot 源码验证（OpenJDK8）

虽然源码是 C++ 写的，但只需抓核心逻辑来验证结论：

JVM 实现了 `putstatic` 指令，**它的作用是给静态变量赋值**。核心代码逻辑是：

```
if (操作确实是 putstatic) {          // 存放静态变量
    从内存中获取到 Class 对象         // 即前面讲过的 InstanceKlass 对象
    → 通过 InstanceKlass 获取它的 mirror（镜像）对象
    → 在这个镜像对象上为静态变量赋值
}
```

**关于 `mirror` 镜像对象**：

| 叫法 | 场景 |
|---|---|
| **Class 对象** | Java 语言层面的叫法，存放在 **Java 堆**中 |
| **mirror（镜像）对象** | 虚拟机内部的叫法 |

之所以叫「镜像」，是因为**它里面的数据来源于 `InstanceKlass`**，就像是 `InstanceKlass` 的一个镜像。

**结论得到验证**：**JDK7 及之后的版本，静态变量确实存放在堆里面的 Class 对象中。** 面试中被问到就按这个回答。

> **补充**：注意区分两件事 —— **静态变量本身**（这个「槽位」）存哪里是随版本变化的；而**静态变量所引用的对象**从来都在**堆**上，与版本无关。这也是[[编程/jvm/09 运行时数据区 堆内存]]里「静态变量持有的引用能让对象被多线程共享」这一说法成立的前提。

## 七、小结

1. 字符串常量池存放的是**代码中定义的常量字符串**，来源是字节码文件里的静态常量池
2. `new String("abc")` 的对象在**堆**上，`String s = "abc"` 指向**字符串常量池** → `==` 比较为 `false`
3. 两个常量池的演变：**JDK7 前合一在永久代 → JDK7 字符串常量池单独进堆 → JDK8 运行时常量池进元空间、字符串常量池仍在堆**
4. **变量 `+` 变量**：编译期替换为 `StringBuilder.append().toString()`，结果对象在**堆**上
5. **常量 `+` 常量**：编译期**直接折叠**成一个字符串，结果在**字符串常量池**中
6. 判断此类题目的方法：看字节码，确认局部变量表里的地址指向**常量池**还是**堆**
7. `intern()` 可**手动把字符串放入常量池**，适合从文件/网络读取大量重复字符串以节省内存；工作少用、面试高频
8. **JDK6 的 `intern()` 把字符串实例复制进永久代常量池；JDK7+ 只把堆对象的引用放进常量池**
9. 经典题在 JDK6 是 `false/false`，JDK7+ 是 `true/false`；第二问为 `false` 是因为 **`"java"` 在 JVM 启动时已入池**
10. **静态变量**：JDK6 及之前在方法区（永久代），**JDK7 及之后在堆中的 Class 对象（虚拟机内称 mirror 镜像对象）里**，由 `putstatic` 指令的源码可验证
