# hashmap 的 put 过程介绍一下

> 答题主线：`put` 是一个"**查位 → 判空 → 判同 key → 遍历链/树 → 树化 → 扩容**"的决策流程（JDK8）。核心动作：由 key 哈希算出数组下标，下标空则直接放；否则找是否存在相同 key（是则更新值，否则新增），键值对数超阈值再触发扩容。

## 一、四步回答骨架

1. **算位**：由 key 的 hash 计算数组下标（索引）。
2. **空位直放**：若该位置无元素，直接新建 Node 放入；`modCount++`。
3. **冲突查找**：若位置已有元素，先比首个节点的 hash+key → 相同则更新值；否则沿链表/红黑树找同 key（找到更新，未找到则尾部/红黑树新增），链长超标则树化。
4. **扩容收尾**：检查负载因子，超阈值扩容（2 倍，元素按 `e.hash & oldCap` 分流）。

## 二、核心内容：put 详细流程（JDK 1.8）

1. **计算下标**：由 key 哈希算出数组中的位置（索引）。
2. **空位直放**：若该位置为空，直接新建 Node 存键值；`modCount` 加 1（供迭代器发现并发修改）。
3. **判首节点**：若位置已有元素，检查该桶**第一个**节点的哈希与 key 是否相同——
   - 相同 → 找到相同 key，用新值替换旧值，完成更新。
4. **遍历查找**：首节点不同，则沿链表或红黑树逐节点比较 hash + `equals`：
   - **链表**：从头比较，相同则新值换旧值；遍历完没找到→加在**链表尾部**。
   - **红黑树**：用 hash + `equals` 定位节点，相同则换值；没找到→插入红黑树。
5. **链表→红黑树**：检查链表长度是否达阈值（默认 **8**）——
   - 若**链长超 8 且数组长度 ≥ 64** → 链表转为红黑树提升查找效率。
6. **检查负载因子**：判定元素数 `size` 与数组长度比值是否超阈值（默认 **0.75**）→ 若超则扩容。
7. **扩容**：
   - 创建**两倍大小**的新数组。
   - 遍历旧数组每个键值对，按 **`e.hash & oldCap`** 结果重新分配：要么留原位置，要么移到 **原位置 + oldCap**（**无需重新计算 hash**）。
   - 更新数组引用与阈值。
8. **完成添加**。

## 三、如何应用 / 面试怎么讲

**加分表达：**
- 强调 JDK1.8 才有的**树化条件**（链长≥8 **且** 数组≥64，否则只扩容不树化）——这是"背"与"懂"的分水岭。
- 讲扩容要带上 **`e.hash & oldCap` 分流** 的巧妙：元素只在"原位"或"原位+oldCap"二选一，避免重算 hash，是 1.8 相对 1.7 的优化。
- 顺带点出 **`modCount`++ 用于并发修改检测**（fast-fail），自然引出"HashMap 非线程安全"。

**常见追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| 扩容为什么是 2 倍？ | 2 倍后 `e.hash & oldCap` 结果是 0/非0 决定原位或 +oldCap，天然支持原位迁移，且下标计算用 `& ` 替代取模更快 |
| 什么条件转红黑树？ | 链长 **≥8 且数组长度 ≥64**；数组<64 只扩容不树化 |
| 为什么 8 才树化？ | 哈希分布较好时链长很难到 8；到 8 说明冲突严重，用红黑树(查询 O(logn))控成本；且 8 是经验权衡阈值 |
| 数组长度 <64 为什么不树化？ | 桶太少冲突普遍，先**扩容**摊薄每个桶，比重建红黑树划算 |
| 扩容后元素位置怎么定？ | 按 `e.hash & oldCap` 结果为 0 → 原位；非 0 → 原位置 + oldCap；不用重算 hash |
| HashMap 为什么非线程安全？ | 并发 put 有数据错乱/链环/死循环(1.7)等问题；需并发用 ConcurrentHashMap |
| 为什么要有 modCount？ | 供 `Iterator` 快速失败检测，发现迭代中结构被改就抛 `ConcurrentModificationException` |
| 初始值/负载因子默认是多少？ | 初始容量 16，负载因子 0.75，`size/capacity > 0.75` 时触发扩容 |
