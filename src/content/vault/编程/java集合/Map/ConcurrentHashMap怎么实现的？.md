# ConcurrentHashMap 怎么实现的？

> 答题主线：ConcurrentHashMap 的进化本质是**锁粒度不断变细**。1.7 用 Segment（分段锁，锁大段数组，基于 ReentrantLock），1.8 用 **volatile + CAS + synchronized**（锁桶头节点，粒度最细）。核心记忆点：**1.8 对头结点加锁**，空位置用 CAS 无锁写入，非空位置 synchronized 锁桶遍历，冲突多时转红黑树。锁粒度越小 → 冲突越少 → 并发度越高。

## 一、四步回答骨架

1. **定调**：ConcurrentHashMap 是线程安全版 HashMap；线程安全的关键是"**控锁粒度**"，1.7 → 1.8 一路把锁越做越细、并发度越做越高。
2. **1.7 分段锁**：`Segment[]`（数组的大锁）+ 每段 `HashEntry[]`（存数据）。`Segment` 继承 ReentrantLock，一段一个锁；占锁只锁一段，其余段其他线程可访问 → **真正并发**。
3. **1.8 锁桶**：`volatile + CAS + synchronized`。空桶 CAS 直接放、无锁；非空桶 `synchronized` 锁**桶头节点**，粒度从"段"细到"桶"。数组+链表/红黑树。
4. **收尾**：锁粒度对比——1.8 冲突和加锁频率更低，查询 1.8 红黑树从 O(n) 优化到 O(logn)。

## 二、核心内容：1.7 与 1.8 的实现对比

### 1. JDK 1.7：Segment + HashEntry（分段锁）

- **结构**：大数组 `Segment`（扮演锁的角色，继承 **ReentrantLock**）套小数组 `HashEntry`（存键值）。一个 CHM 含一个 Segment 数组，一个 Segment 含一个 HashEntry 数组，每个 HashEntry 是链表结构。
- **原理**：**分段锁**把数据分成一段一段，给每一段配一把锁。某线程占用锁访问其中一段时，其他段仍可被其他线程访问 → 实现**真正的并发访问**。
- **局限**：底层是"数组+链表"，数据多时遍历整条链表，访问慢。

### 2. JDK 1.8：数组 + 链表/红黑树（锁桶）

- **结构**：用 volatile 保证可见性，用 **CAS 或 synchronized** 实现线程安全；链表长度超阈值转**红黑树**，查询从 O(n) 优化到 **O(logn)**。
- **put 流程**（添加元素）：
  1. 判断容器是否为空 → **空则用 volatile + CAS 初始化**（无锁）。
  2. 非空则据 key 哈希算目标位置是否为空：
     - **位置为空** → 用 **CAS 设置该节点**（无锁，乐观并发）。
     - **位置非空** → 用 **synchronized** 锁住，遍历桶中链表/红黑树，替换或新增节点，最后判断是否需要转红黑树。
- **一句话归纳**：ConcurrentHashMap 通过对**头结点加锁**保证线程安全。锁的粒度相比 Segment 更小，冲突和加锁频率更低，并发性能更高。

#### 为什么"已经用了 synchronized，还要用 CAS"？

两者不是二选一，而是**按锁竞争程度分工的权衡**——哪个操作竞争低、适合乐观自旋，就用 CAS；哪个操作步骤多、必须保护整段结构，就用 synchronized：

- **空槽位用 CAS（竞争低，乐观）**：`putVal` 里算出的 hash 槽**如果还没有元素**，直接用 CAS 设置该节点。原因是 key 的 hash 经过多次扰动后，**碰撞概率较低**，可以预期用**较少的自旋**就能完成"落槽"。竞争少 → 自旋成本低、无锁并发，是 CAS 的主场。
- **非空桶用 synchronized（碰撞后，悲观接管）**：当桶位**已存在节点（发生 hash 碰撞）**，需要遍历链表/红黑树做查找、替换或追加，**操作步骤较多**，且要保护**整条链/整棵树的结构**不被并发破坏——这时 CAS 的自旋已不适合，改用 **synchronized 锁住该桶的头节点**完成这部分逻辑。

> 一句话：**CAS 用于"单个槽位的低竞争落位"，synchronized 用于"冲突后多步遍历操作的结构保护"**。竞争小用乐观锁省开销，竞争大用悲观锁稳结构——这就是两者在一种策略里共存的理由。
> 大白话说就是非空桶里面涉及到的操作多，然后如果使用cas就会自旋重试，不合适。

> “桶”（Bucket） 是一个非常形象的比喻，它在底层代码中指的是 哈希表（数组）里的一个具体槽位（Slot）。这个数组中的每一个索引位置（如 table[0]、table[1]……table[n-1]）就是一个桶。

## 三、如何应用 / 面试怎么讲

**加分表达：**
- 主动给出**"锁粒度演变"**主线（段 → 桶），比罗列类名高级——体现"理解设计动机"。
- 强调 1.8 的**无锁读路径**：空位置 CAS 直放，不需要 synchronized，这是并发度提升的来源。
- 能点出"**CAS 适合竞争少的乐观场景，synchronized 适合冲突时接管**"的互补——两者不是二选一，而是分工。
- 串起红黑树优化：不只是线程安全，还把查询从 O(n) 提到 O(logn)，顺带回应"为什么要树化"。

**追问预案：**

| 追问 | 应答案点 |
| :--- | :--- |
| 1.7 为什么用 ReentrantLock 而不用 synchronized？ | 1.7 时代 synchronized 性能弱、不可中断，ReentrantLock 更灵活；到 1.8 synchronized 已被 JVM 重度优化（偏向锁/轻量锁），改用 synchronized 更简洁 |
| 1.8 为什么改用 synchronized？ | 锁粒度已细到"桶"，synchronized 在 JVM 优化后性能足够，且语法更简单、可自动释放；只需锁头节点即可 |
| 锁的粒度分别是什么？ | 1.7 锁 **Segment**（大段数组，最多 16 段）；1.8 锁**桶头节点**（细到单个桶） |
| put 时哪种情况不加锁？ | 容器为空的**初始化**、以及**目标位置为空**的首次插入——都用 **CAS** 乐观写入，无锁（hash 扰动后碰撞率低，自旋少） |
| 什么时候才会加锁？ | 目标位置**已有元素**（hash 冲突）时，synchronized 锁桶头节点再遍历细分（操作步骤多、要保护整条链/树结构） |
| 为什么有的操作用 CAS、有的用 synchronized？ | 按**竞争程度权衡**：空槽碰撞率低→CAS 乐观自旋省开销；冲突后要遍历链/树多步操作、且须保护结构→synchronized 悲观接管 |
| 1.8 为什么查询变快？ | 链表→**红黑树**，查询从 O(n) 降到 **O(logn)**；但链表短时红黑树反而有开销，故设阈值（同 HashMap 链长≥8 且数组≥64 才树化） |
| 为什么比 Hashtable 并发度高？ | Hashtable 方法级 synchronized 锁**整个表**，一个时刻只一个线程写；CHM 分段/锁桶，多线程可并行写不同段/桶 |
| 读需要加锁吗？ | 读靠 **volatile** 保证可见性、无锁读；并发度高场景读性能优于 Hashtable |
| 与 HashMap 有什么关系？ | 存储结构与树化逻辑一致（数组+链表/红黑树），只是额外加了**并发安全**机制，是 HashMap 的线程安全替代品 |
