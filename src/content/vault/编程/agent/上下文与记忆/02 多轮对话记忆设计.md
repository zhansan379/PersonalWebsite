# 多轮对话记忆设计

> 五种记忆策略的详细实现、Token 预算分配、RAG 场景实践和生产部署注意事项。关于"记忆机制要考虑哪些问题"的全局视角，见 [[01 Agent 记忆机制]]。

## 🎯 答题逻辑（骨架）

```
1. 先定位：记忆是"外挂"不是"内建"        ← 15 秒，锁定这是上下文工程问题
   LLM 每次请求都是无状态的
   → "记忆" = 应用层每轮把历史重新拼进 messages
   → 所以本质是一道 Token 预算题，不是模型能力题
2. 五种策略按演进讲，落点在混合策略        ← 证明有选型判断，不是只会一种
   完整历史 → 滑动窗口 → Token 截断 → 摘要压缩 → 摘要 + 最近 N 轮
   落点：摘要进 system 紧接角色定义，最近 1~3 轮原封不动
3. 报 Token 预算的具体数字                ← 有数字才像上过生产
   32K 窗口：System 1K / 历史 4K / 检索 5K / 问题 0.1K / 生成预留 2K ≈ 12K
   只用窗口 30%~50%：Token 越多延迟越高、越贵
4. 讲工程落地                            ← 证明不是只写过 demo
   Redis 主存 + MySQL 归档 / TTL 30 分钟 / 敏感信息优先"不入库" / 记忆命中率
5. 主动抛出"模型有记忆，但检索没有"        ← 抢占下一个问题，本题最高分的钩子
   会话记忆只修了生成端 → 检索端仍然失忆 → 必须再配 Query 改写
```

**关键心态**：这题不考"你会不会存 history"，考的是**Token 预算意识 + 选型判断 + 知不知道记忆的边界在哪**。面试官在听三件事：你有没有具体的预算数字、你知不知道摘要该放在 messages 的哪个位置、你知不知道会话记忆解决不了检索端的失忆。回答"我把历史全拼进去"或者只报一个框架的 Memory 类名（如 `ConversationBufferMemory`）而说不出丢弃/压缩规则，会被直接判定为没上过生产。

**分水岭术语**：**摘要 + 最近 N 轮（混合策略）**、**成对丢弃**、**Token 预算分配**、**摘要放 system 消息**、**模型有记忆但检索没有**。

## 一、五种记忆策略

### 1.1 完整历史（Full History）

**做法**：所有对话历史全部塞进 messages，一条不丢。

| 优点 | 缺点 |
|---|---|
| 信息零丢失 | Token 无限膨胀 |
| 实现极其简单 | 费用持续增长 |
| 无需额外推理 | 最终超出窗口上限 |

> 适用场景：对话轮数确定不超过 5 轮的简单 FAQ 场景。

### 1.2 滑动窗口（Sliding Window）

**做法**：只保留最近 N 轮对话，更早的直接丢弃。

```
N=3：
第 4 轮结束：[第2轮, 第3轮, 第4轮]  ← 第1轮被丢弃
第 5 轮结束：[第3轮, 第4轮, 第5轮]  ← 第2轮被丢弃
```

| 场景 | 推荐 N | 理由 |
|---|---|---|
| 简单 FAQ | 3~5 | 2~3 轮即得答案 |
| 电商客服 | 5~8 | 需要来回确认细节 |
| 技术支持 | 8~10 | 排查需要较长上下文 |
| 复杂咨询 | 10~15 | 需保留较多背景信息 |

**公式**：`保留消息数 = maxRounds × 2（user + assistant 各一条）`

> 经验法则：从 N=5 开始，根据实际效果调整。

### 1.3 Token 截断（Token Truncation）

**做法**：设 Token 上限（如 4,000），从最新消息往前算，超出即丢弃。

**与滑动窗口的区别**：按 Token 精确控制，而非按轮数。消息长度差异大时更有效。

**关键约束**：截断时必须**成对丢弃**——一轮的 user 和 assistant 要么都保留，要么都丢弃。

**Token 估算公式**（无需精确 tokenizer）：
```
Token ≈ 中文字符数 × 1.5 + 英文字符数 ÷ 4
```

### 1.4 摘要压缩（Summary Compression）

**做法**：用大模型把早期对话压缩成简短摘要（200~500 Token），关键信息不丢失。

**触发策略**：

| 策略 | 做法 | 推荐度 |
|---|---|---|
| 按轮数触发 | 每 N 轮压缩一次 | 简单但不灵活 |
| **按 Token 阈值** | 历史超过 M Token 时压缩 | **推荐** |
| 按话题切换 | 检测话题变化时压缩 | 效果最好但检测难 |

**摘要 Prompt 要点**：
1. 保留用户核心意图和关注点
2. 保留所有关键实体（产品名、订单号、日期、金额）
3. 保留已确认的结论和决定
4. 保留尚未解决的问题
5. 省略寒暄、重复确认、无关细节
6. 第三人称描述，控制在 200 字以内

> 可用小模型（如 Qwen2.5-7B-Instruct）做压缩，成本很低。

### 1.5 混合策略：摘要 + 最近 N 轮（推荐⭐）

**做法**：早期对话压缩成摘要作为长期记忆 + 最近 N 轮保留完整对话作为短期精度。

```
messages = [
  System Prompt（角色定义）,
  对话背景摘要（200~500 Token）,
  最近 1~3 轮完整对话（原封不动）,
  当前用户问题
]
```

**设计要点**：
- 摘要放在 system 消息中，紧接角色定义，让模型优先看到对话背景
- 最近几轮完整对话保证模型准确理解当前话题
- 总 Token 远小于保留全部历史的方案

### 1.6 五种策略对比

| 策略 | Token 控制 | 信息保留 | 实现复杂度 | 额外 API | 适用场景 |
|---|---|---|---|---|---|
| 完整历史 | 无 | 完整 | 极低 | 无 | ≤5 轮简单场景 |
| 滑动窗口 | 按轮数 | 丢早期 | 低 | 无 | 大多数客服 |
| Token 截断 | 精确控制 | 丢早期 | 中 | 无 | 消息长度差异大 |
| 摘要压缩 | 大幅压缩 | 保留关键 | 高 | 1 次/触发 | 长对话需记忆 |
| **混合策略** | **精确可控** | **长+短期** | **高** | **1 次/触发** | **生产级推荐** |

## 二、RAG + 会话记忆：Token 预算分配

### 2.1 上下文窗口的三样东西

以 32K 上下文窗口为例：

| 部分 | 推荐预算 | 说明 |
|---|---|---|
| System Prompt | 1,000 Token | 角色定义 + 行为规则 |
| 对话历史/摘要 | 4,000 Token | 摘要 + 最近 3~5 轮 |
| 检索上下文 | 5,000 Token | Top-3 到 Top-5 chunk |
| 当前用户问题 | 100 Token | 通常很短 |
| 预留生成空间 | 2,000 Token | 模型回答最大长度 |
| **总计** | **~12,100 Token** | **远低于上限，留有余量** |

> 为什么不用满窗口？Token 越多延迟越高、费用越贵。用到总窗口的 30%~50% 是最佳平衡点。

### 2.2 分配优先级（从高到低）

1. **System Prompt**：定义行为规则，不能省
2. **预留生成空间**：不够会被截断
3. **最近 2~3 轮对话**：理解当前意图至关重要
4. **检索上下文**：RAG 核心价值，没有则 RAG 失效
5. **更早的对话历史**：最低优先级，可用摘要或丢弃

### 2.3 动态调整策略

```java
int chunkBudget = totalBudget - systemPrompt - reservedForGeneration - historyTokens;
// 确保至少能放 1 个 chunk（约 500 Token）
return Math.max(500, chunkBudget);
```

对话初期（历史少）→ 多放 chunk，对话后期（历史多）→ 减少 chunk 或触发压缩。

## 三、存储方案

### 3.1 三种方案对比

| 维度 | 内存 (ConcurrentHashMap) | Redis | MySQL |
|---|---|---|---|
| 读写性能 | 纳秒级 | 毫秒级 | 毫秒~十毫秒 |
| 持久化 | ❌ | 可选 | ✓ |
| 分布式 | ❌ | ✓ | ✓ |
| 过期清理 | 需自己实现 | 原生 TTL | 需定时任务 |
| 实现复杂度 | 极低 | 低 | 中 |
| 适用场景 | 开发调试 | 生产主存储 | 审计/分析 |

### 3.2 推荐方案

**Redis 做主存储 + MySQL 做归档**：
- 对话进行时：消息存 Redis（快速读写）
- 对话结束后：异步写入 MySQL（持久化 + 审计）

## 四、生产注意事项

### 4.1 会话超时与清理

- **内存**：Caffeine/Guava Cache 的过期机制
- **Redis**：设置 TTL（如 30 分钟），自动过期
- **数据库**：定时任务清理或标记为"已关闭"

不做清理会导致 OOM 或 Redis 内存不足。

### 4.2 敏感信息处理

对话中可能出现手机号、身份证、密码、银行卡号，四条处理路径：

- **不入库规则**：匹配到敏感信息（密码、验证码等）**直接不存**——最彻底，能不存就别存
- **脱敏存储**：掩码处理（如 `138****1234`），保留可读性但不可还原
- **加密存储**：加密整个消息内容，需要时解密
- **访问控制**：限制查看权限，记录访问日志

金融、医疗等合规行业尤其重要。

### 4.3 可观测性指标

- **Token 消耗**：每轮总消耗，历史/检索/生成各占多少
- **压缩触发**：压缩次数，压缩前后 Token 变化
- **响应时间**：摘要压缩、检索、生成的耗时占比
- **记忆命中率**：用户追问时是否正确理解上下文

## 五、与 Query 改写的关系

会话记忆解决了"模型记住上下文"的问题。但在 RAG 场景下还有一层：**检索系统也需要"上下文"**。

用户追问"那它的保修期呢"→ 模型理解了"它=iPhone 16 Pro"，但检索系统拿到的 query 仍然是"那它的保修期呢"→ 向量化后语义稀薄 → 检索效果很差。

因此还需要 **Query 改写**：将"那它的保修期呢"改写为"iPhone 16 Pro 的保修期"，再拿去检索。

## ⚡ 30 秒速答版

> LLM 本身是**无状态**的，所谓"记忆"就是每一轮把对话历史重新拼进 messages，所以它本质上是一道 **Token 预算**题。
>
> 常见五种做法：全量历史、滑动窗口保留最近 N 轮、按 Token 截断、摘要压缩，以及生产上我推荐的**混合策略——早期对话压成 200~500 Token 的摘要放进 system 消息紧接角色定义，最近 1~3 轮原封不动保留**，这样长期记忆和短期精度都有。
>
> 截断有个必须提的细节：要**成对丢弃**，同一轮的 user 和 assistant 要么都留要么都丢。
>
> RAG 场景还要做预算切分，我按 32K 窗口分：System 1K、历史/摘要 4K、检索上下文 5K、生成预留 2K，总共约 12K，只用到窗口的三到五成——Token 越多延迟越高、费用越贵。
>
> 存储上 **Redis 做主存储并设 30 分钟 TTL**，对话结束后异步归档到 MySQL 做审计。
>
> 最后一点最关键：**会话记忆只让模型有了上下文，检索系统仍然是失忆的**——用户问"那它的保修期呢"，向量检索拿到的还是这句原话，所以还得配 **Query 改写**。

## 💬 对方可能追问的问题

### 顺着五种记忆策略选型追（概率最高）

| 追问 | 答题要点 |
|---|---|
| 你项目里用哪种？为什么？ | **混合策略**：摘要（200~500 Token）+ 最近 1~3 轮完整对话。理由：纯滑动窗口会丢早期关键实体（型号、订单号），纯摘要会丢当前话题的精度，混合才能兼顾 |
| 滑动窗口 N 取多少？ | 按场景定：简单 FAQ 3~5、电商客服 5~8、技术支持 8~10、复杂咨询 10~15。从 **N=5** 起按效果调。保留消息数 = `N × 2`（user + assistant 各一条） |
| 滑动窗口和 Token 截断的区别？ | 前者按**轮数**，后者按 **Token 精确控制**。消息长度差异大的场景（有人只发一句话、有人贴一整段日志）必须用 Token 截断，按轮数会失控 |
| Token 截断最容易踩的坑？ | **成对丢弃**——只留下没有对应 user 提问的 assistant 回答，模型会把它当成凭空成立的断言，甚至照抄已被推翻的结论 |
| 不想引 tokenizer 怎么估 Token？ | 用估算公式 `Token ≈ 中文字符数 × 1.5 + 英文字符数 ÷ 4`，做预算控制精度足够，省掉一个依赖 |
| 摘要压缩什么时候触发？ | 三种触发方式：按轮数（简单但不灵活）、**按 Token 阈值（推荐）**、按话题切换（效果最好但话题检测难做） |
| 摘要 Prompt 要写清什么？ | 保留用户核心意图、**所有关键实体（产品名/订单号/日期/金额）**、已确认的结论与决定、尚未解决的问题；省略寒暄和重复确认；第三人称、200 字以内。压缩本身用小模型（如 `Qwen2.5-7B-Instruct`）成本很低 |
| 摘要放在 messages 的哪个位置？ | 放进 **system 消息、紧接角色定义之后**，让模型优先看到对话背景。不要当成一条普通消息插在历史中间 |

### 顺着 Token 预算分配追

| 追问 | 答题要点 |
|---|---|
| 32K 窗口你怎么分配？ | System Prompt 1,000 + 对话历史/摘要 4,000 + 检索上下文 5,000（Top-3~Top-5 chunk）+ 当前问题 100 + 生成预留 2,000 ≈ 12,100 Token |
| 为什么不把窗口用满？ | 主因是 Token 越多**延迟越高、费用越贵**；其次长上下文中间位置的信息**可能**被弱化（lost-in-the-middle，Liu et al. 2023——注意这是任务与模型相关的现象，新一代长上下文模型已明显缓解，别当成固定规律讲）。用到总窗口的 **30%~50%** 是最佳平衡点 |
| 预算不够时先砍谁？ | 优先级从高到低：System Prompt → 预留生成空间 → 最近 2~3 轮对话 → 检索上下文 → 更早的历史。所以**先砍最早的历史**，砍不动再触发摘要压缩，最后才减 chunk |
| chunk 预算怎么动态算？ | `chunkBudget = 总预算 - system - 生成预留 - 历史 Token`，再取 `max(500, chunkBudget)` 保证至少放得下 1 个 chunk。对话初期历史少→多放 chunk，后期历史多→减 chunk 或触发压缩 |

### 顺着存储与生产运维追

| 追问 | 答题要点 |
|---|---|
| 会话历史存在哪？ | **Redis 主存储 + MySQL 归档**：对话进行中读写 Redis（毫秒级、原生 TTL、天然分布式），结束后异步写 MySQL 做持久化和审计。内存 `ConcurrentHashMap` 虽然纳秒级最快，但不持久化、不支持分布式（多实例下请求落到另一台就丢会话），只适合开发调试 |
| 不做清理会怎样？ | 直接 **OOM 或 Redis 内存打满**。Redis 设 TTL（如 30 分钟）自动过期；进程内用 Caffeine/Guava Cache 的过期机制；数据库用定时任务清理或标记"已关闭" |
| 对话里出现手机号、密码怎么办？ | 四条路径，优先级从高到低：**不入库规则**（密码、验证码直接不存，最彻底——能不存就别存）> 脱敏存储（`138****1234`，可读但不可还原）> 加密存储 > 访问控制 + 访问日志。金融、医疗等合规行业尤其重要 |
| 上线后要监控什么指标？ | ①Token 消耗：每轮总量及历史/检索/生成各占多少 ②压缩触发次数与压缩前后 Token 变化 ③摘要压缩、检索、生成的耗时占比 ④**记忆命中率**：用户追问时是否正确理解了上下文 |

### 顺着与 Query 改写的配合追

| 追问 | 答题要点 |
|---|---|
| 有了会话记忆，还需要 Query 改写吗？ | 需要。会话记忆只修好了**生成端**——模型知道"它 = iPhone 16 Pro"；但**向量检索拿到的仍是原始 query 字符串**"那它的保修期呢"，向量化后语义稀薄，召回一堆无关内容。断点在检索端，不在生成端 |
| 改写放在链路哪一步？检索和生成分别用哪个 query？ | 位置固定为 `用户提问 → 读会话记忆 → Query 改写 → 检索 → 生成`，必须在**记忆读取之后、检索之前**（以历史为输入、以检索为输出）。**检索用改写后的 query，生成 Prompt 里放用户原始问题**，改写只为提升检索精度，不该改变用户的问题 |
| 摘要压缩会影响改写质量吗？ | 会，两者强耦合。摘要压得太狠只剩"客户咨询手机售后"、丢了具体型号，下游就无法消解"它"。**会话记忆的摘要质量直接决定改写质量**，所以摘要 Prompt 必须硬性要求保留关键实体 |

### 高频陷阱题

1. **「多轮对话的记忆是模型自己记住的吗？」** → **不是**。LLM 的每次请求都是**无状态**的，记忆完全由应用层每轮重新拼装 messages 实现，模型侧不存在任何跨请求状态。答"模型会记住"直接出局。
2. **「加了会话记忆，多轮 RAG 检索不准的问题就解决了吗？」** → **没解决**，本题最高频的陷阱。记忆修的是生成端，检索端依然失忆，必须再加 **Query 改写**。
3. **「上下文窗口都 128K/1M 了，是不是不用做记忆管理了？」** → 仍然要做。①Token 越多延迟越高、费用近线性增长 ②长上下文中间信息容易被忽略 ③窗口再大也有上限，长会话终会撞墙。生产上依然只用到窗口的 30%~50%。
4. **「摘要是不是压得越省 Token 越好？」** → **不是**。目标是**保住关键信息**而非最小化字数，压太狠会丢型号、订单号这类实体，直接让下游改写和回答一起失准。所以摘要有 200~500 Token 的合理区间和"必留实体"清单。
5. **「滑动窗口的 N 调大点不就万事大吉了？」** → N 一大就退化成完整历史：Token 膨胀、费用增长、最终超窗；而且早期无关话题会干扰对当前意图的理解。正解是**摘要 + 最近 N 轮**，而不是无脑加 N。
6. **「按 Token 截断时，多出来的那半轮留着不浪费吗？」** → 不能留，必须**成对丢弃**。半轮（只有 assistant）会制造"孤儿回答"，破坏对话结构，得不偿失。
