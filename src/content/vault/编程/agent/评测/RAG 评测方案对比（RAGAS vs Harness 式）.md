# RAG 评测方案对比（RAGAS vs Harness 式）

> RAGAS 是代码级固定指标框架，Harness 式是将评测逻辑编码为 Prompt 的方法论。两者不矛盾，可以组合。
>
> **前置概念**：Harness（运行框架）的定义见 [[编程/agent/Agent 系统设计的三维框架：Prompt-Context-Harness]]；Harness 式评测的完整方法论见 [[编程/agent/评测/Harness 工程搭建式 Agent 评测]]。本页只做**两条路线的对比与选型**。

## 🎯 答题逻辑（骨架）

```
1. 先定性，别急着比指标            ← 一句话锁死"两者不在同一维度"
   RAGAS   = 一个 Python 库（代码级固定指标）
   Harness = 一套方法论（评测逻辑编码为 Prompt）
   → 一个是工具，一个是方法论，不是竞品
2. 用一个指标做落地对比            ← 证明你两边都真跑过
   以「答案忠实度 / faithfulness」为例
   ├─ RAGAS：传 question / answer / contexts → 得到一个分数
   │         内部逻辑（拆 claims → 逐条验证）不可见、不可改
   └─ Harness 式：把 1-5 分 rubric + 场景「特别注意」写进评测 Agent Prompt
3. 点出能力边界差在哪              ← 分水岭：报告能力
   RAGAS 只有分数；Harness 式有穿透归因 + 可操作建议 + 跨版本对比
4. 给出 RAG 指标体系映射            ← 证明你有体系，不是零散指标
   L1 格式合规 / 响应成功率
   L2 检索召回率 · 答案忠实度 · 答案相关性 · 上下文精确率
   L3 引用准确性 · 拒答率 · 表格数据还原度
   每个指标都配评测方式：硬规则 / 二元决策 / LLM-as-Judge
5. 落到选型与组合（收口）           ← 不站队，给务实方案
   RAGAS 跑 L1 baseline（社区认可、论文认）
   Harness 式跑 L2/L3（自定义维度、非标准输出、归因）
   RAGAS 答"多少分"，Harness 答"为什么这个分、怎么改"
```

**关键心态**：这题考的不是「你用过哪个库」，而是**你有没有亲手搭过评测体系**。面试官在听三件事：你会不会无脑站队；你知不知道 ragas 指标背后的**实现假设**（默认答案是文本）；你有没有**归因意识**（分数之后怎么落到改进动作）。只回答「ragas 有 faithfulness 等指标，很好用」——说不出指标内部怎么算、说不出非文本输出会失效、只报分数不谈归因，基本会被判定为「跑过 demo，没做过评测」。

**分水岭术语**：**LLM-as-Judge**、**rubric（1-5 分档）**、**L1/L2/L3 三层指标**、**穿透归因**、**评测即文档**。

## 一、本质区别

| 维度 | RAGAS | Harness 式评测 |
|---|---|---|
| **本质** | 一个 Python 库（固定的指标实现） | 一套方法论（评测逻辑编码为 Prompt） |
| **指标** | 预定义有限集合（faithfulness, relevancy 等 ~10 个） | 想评什么就描述什么，无限可扩展 |
| **评测逻辑** | 写在 ragas 源码里（Python），不可见不可改 | 写在评测 Agent 提示词里，完全透明可改 |
| **扩展方式** | 提 PR 给 ragas 仓库，或自己 fork | 在 Prompt 里加一段文字 |
| **你需要写的代码** | 数据准备 + 调 ragas API + 结果处理 + 报告生成 | 一个批量循环脚本（调评测 Agent） |
| **部署** | `pip install ragas` + 配 LLM | 平台 + 评测 Agent Prompt，零依赖安装 |
| **报告能力** | 只有分数，没有分析、没有建议 | **穿透归因**（"15 条漏检中，12 条因为查询改写环节丢失了品牌名称"）+ **可操作建议**（"在检索 prompt 中加入'保留产品名称原文'"）+ **跨版本对比**（"v3 vs v2：忠实度 3.2→4.1，但召回率 85%→78%"） |
| **非标准输出** | 默认指标假设文本输出，JSON、表格、多跳推理链场景可能直接失效 | 想评"表格数据还原度"，在 Prompt 里写一句就行 |
| **组织价值** | 评测逻辑埋在源码里，非技术成员看不懂 | **评测即文档**：评测 Agent Prompt 本身就是团队对"什么是好答案"的共识 |

## 二、以"答案忠实度"为例的实操对比

### RAGAS 做法

```python
from ragas import evaluate
from ragas.metrics import faithfulness
from datasets import Dataset

data = Dataset.from_dict({
    "question": ["什么是 Attention？"],
    "answer": ["Attention 是一种机制..."],
    "contexts": [["Attention 机制由 Vaswani 等人在 2017 年提出..."]]
})

result = evaluate(data, metrics=[faithfulness])
print(result)  # 得到一个分数
```

**局限性**：ragas 内部的 faithfulness 判断逻辑（让 LLM 生成 claims → 逐条验证）你无法干预。如果你的 RAG 输出是表格而非文本，这套逻辑可能直接失效。

### Harness 式做法

```markdown
你是一个 RAG 评测专家。对以下数据，评测答案忠实度：

### 评分标准（1-5）
5：所有陈述均在检索文档中有直接支持
4：主要陈述有支持，1-2 处轻微推断
3：存在未经文档验证的推断，但方向正确
2：多处与文档矛盾或虚构信息
1：答案与检索文档完全无关

### 特别注意
- 本场景的答案常包含表格数据，逐行逐列核对
- 数值类信息必须精确匹配，±5% 以内算通过
- 如果答案引用了文档未提及的产品名称，直接判 1 分
```

**优势**：想怎么判就怎么写。场景变了就改文字，不用等框架更新。评分标准的 rubric 设计原则（锚点要具体、分档要可判别）见 [[编程/agent/评测/Harness 工程搭建式 Agent 评测]]。

## 三、RAG 场景下的指标映射

### Harness 三层指标 vs RAG 场景

L1/L2/L3 三层指标体系的定义与设计原则见 [[编程/agent/评测/Harness 工程搭建式 Agent 评测]]，此处只做 RAG 场景的落地映射：

| 层 | 内容 | RAG 适配 |
|---|---|---|
| **L1 通用基础** | 输出格式合规率、字段完整率 | 如果是结构化输出则保留；另加响应成功率 |
| **L2 按能力选用** | 分类准确率、召回/精确率、MAE | **检索召回率、答案忠实度、答案相关性、上下文精确率** |
| **L3 专属指标** | 按需自定义 | **引用准确性**（是否引用不存在文档）、**拒答率**（不知道时是否诚实说不知道）、**表格数据还原度**（如有） |

### 具体指标对应的评测方式

| RAG 指标 | 评测方式 | 对应原文哪种评测 |
|---|---|---|
| 检索召回率 | GT 标注"应检索到的文档"，对比实际检索结果 | 二元决策（召回率/精确率） |
| 答案忠实度 | 逐条验证答案陈述是否在检索文档中有依据 | LLM-as-Judge（1-5 分 rubric） |
| 答案相关性 | 答案是否直接回应问题 | LLM-as-Judge |
| 引用准确性 | 引用的文档 ID/片段是否真实存在 | 硬规则自动检查 |

## 四、适用场景选择

| 场景 | 推荐 | 原因 |
|---|---|---|
| 快速跑 baseline，需要社区标准指标 | **RAGAS** | 开箱即用，论文引用 |
| RAG 场景非常标准（文本 QA） | **RAGAS** | 指标够用，集成简单 |
| 需要自定义评测维度 | **Harness 式** | 改 Prompt 比改代码快 |
| RAG 输出非标准格式（JSON、表格） | **Harness 式** | ragas 指标假设文本输出 |
| 频繁迭代 prompt，需要快速验证 | **Harness 式** | 小时级闭环 |
| 需要归因分析 + 可操作建议 | **Harness 式** | ragas 不提供分析能力 |
| 给非技术团队看评测标准 | **Harness 式** | Prompt 比代码可读 |
| 发论文需要社区认可的标准指标 | **RAGAS** | 审稿人认 ragas |

## 五、组合方案（推荐）

两者不矛盾，务实做法：

```
RAGAS 跑 L1 通用指标（格式合规、基础忠实度）
    → 自动化、标准化、社区认可
    +
Harness 式跑 L2/L3（归因分析、自定义维度、跨版本对比）
    → 深度、灵活、可操作
```

- RAGAS 回答**"多少分"**
- Harness 回答**"为什么这个分、怎么改"**

## ⚡ 30 秒速答版

> RAGAS 和 Harness 式其实不在同一个维度上比：**RAGAS 是一个 Python 库**，指标是**代码级固定**的——faithfulness、answer relevancy、context precision/recall 这十来个，判断逻辑写在源码里，看不见也改不了；**Harness 式是一套方法论**，把评测逻辑写进评测 Agent 的 **Prompt**，想评什么就描述什么。
>
> 拿**答案忠实度**举例：RAGAS 就是传 question / answer / contexts，拿回一个分数；Harness 式是把 **1-5 分的 rubric** 加上场景特别注意——比如「表格逐行逐列核对」「数值 ±5% 以内算通过」——写成一段提示词。
>
> 最大的差距在**报告能力**：RAGAS 只给"多少分"，Harness 式能做**穿透归因**、给可操作建议、做跨版本对比。
>
> 所以我的做法是**组合**：**RAGAS 跑 L1** 通用指标当 baseline，标准化、社区认可；**Harness 式跑 L2/L3**——检索召回率、忠实度、引用准确性、拒答率这些，顺带产出归因和改进建议。

## 💬 对方可能追问的问题

### 顺着 RAGAS 的具体指标追（概率最高）

| 追问 | 答题要点 |
|---|---|
| RAGAS 常用哪几个指标，各评什么？ | **faithfulness**（答案陈述能否被检索文档支撑）、**answer relevancy**（答案是否直接回应问题）、**context precision**（相关片段是否排在检索结果靠前位置）、**context recall**（参考答案所需信息是否被检索到）。是**预定义有限集合**（~10 个），不是想加就能加 |
| faithfulness 内部是怎么算的？ | 让 LLM 先把答案**拆成一条条 claim**，再逐条回到检索文档验证。但这套逻辑写在 ragas 源码里，**不可见、不可干预** |
| 我想加一个「表格数据还原度」指标，RAGAS 怎么加？ | 只能**提 PR 给 ragas 仓库或自己 fork** 改源码；Harness 式在 Prompt 里加一句话就完成 |
| RAGAS 在什么场景会直接失效？ | 默认指标**假设文本输出**。JSON、表格、多跳推理链场景可能直接失效，因为 claims 拆解那套逻辑不适配 |
| 哪些 RAG 指标必须有标注 GT？ | **检索召回率**和 **context recall** 需要——本文的做法是标注「应检索到的文档」再对比实际检索结果，属**二元决策**；忠实度/相关性可无参考，走 LLM-as-Judge |

### 顺着两种方案的本质区别与选型追

| 追问 | 答题要点 |
|---|---|
| 两者是竞争关系吗？ | **不是**。一个是库、一个是方法论，**不在同一维度**，务实做法是分层组合 |
| 什么时候必须选 RAGAS？ | ①快速跑 baseline，要社区标准指标 ②场景非常标准的文本 QA ③**发论文**——审稿人认 ragas |
| 什么时候必须走 Harness 式？ | ①需要自定义评测维度 ②输出非标准格式（JSON、表格）③频繁迭代 prompt，要**小时级闭环** ④需要归因分析 + 可操作建议 ⑤要给非技术团队看懂评测标准 |
| 两边各要写多少代码？ | RAGAS：数据准备 + 调 API + 结果处理 + 报告生成，还要 `pip install ragas` 配 LLM。Harness 式：**一个批量循环脚本**调评测 Agent，零依赖安装 |
| 评测逻辑写在 Prompt 里，怎么保证不漂移？ | 这恰恰是优势——**评测即文档**：Prompt 本身就是团队对「什么是好答案」的共识，可版本化、可评审。前提是 **rubric 的锚点要具体、分档要可判别** |

### 顺着组合方案落地追

| 追问 | 答题要点 |
|---|---|
| 组合方案具体怎么分工？ | **RAGAS 跑 L1**（格式合规、基础忠实度）→ 自动化标准化；**Harness 式跑 L2/L3**（归因分析、自定义维度、跨版本对比）→ 深度灵活可操作 |
| 每个 RAG 指标分别用什么方式评？ | 检索召回率 → 对比 GT 的**二元决策**；引用准确性 → **硬规则自动检查** ID/片段是否真实存在；忠实度、答案相关性 → **LLM-as-Judge**（1-5 分 rubric）。能确定性判的不交给 LLM |
| L3 专属指标在 RAG 里放什么？ | **引用准确性**（是否引用不存在的文档）、**拒答率**（不知道时是否诚实说不知道）、**表格数据还原度**（若输出含表格） |
| 跨版本对比的报告该长什么样？ | 要能给出双向变化 + 归因 + 建议，例如「v3 vs v2：忠实度 3.2→4.1，但召回率 85%→78%」，再配「15 条漏检中 12 条因查询改写丢失了品牌名称」和「在检索 prompt 中加入'保留产品名称原文'」 |

### 高频陷阱题

1. **「RAGAS 和 Harness 式，你到底选哪个？」** → 直觉答案是站队，正确答法是**先拒绝二选一**：指出一个是库一个是方法论、不在同一维度，再给分层组合（RAGAS 跑 L1，Harness 跑 L2/L3）。
2. **「Harness 式是不是全面强于 RAGAS？」** → 不是「更强」，是**更透明、更可扩展**。RAGAS 的不可替代价值在**开箱即用 + 社区认可**（论文、审稿人认）；而 Harness 式的质量完全取决于 **rubric 设计**，写不好反而比固定指标更不稳定。
3. **「忠实度能用 LLM 打分，那检索召回率也让 LLM 打吧？」** → **不要**。召回率是标注 GT 后的**二元决策**，引用准确性是**硬规则自动检查**，都能确定性算出来；把它们交给 LLM 只会引入无谓噪声。
4. **「跑通 ragas 拿到 faithfulness 分数，接下来怎么优化？」** → 分数**本身不指向动作**。需要**穿透归因**（哪个环节丢了什么）+ 可操作建议，而这正是 RAGAS 不提供的能力，得靠 Harness 式评测 Agent 输出。
5. **「我的 RAG 输出是 JSON / 表格，直接上 ragas 就行吧？」** → 默认指标假设文本输出，**可能直接失效**。要么 fork 改源码，要么走 Harness 式在 Prompt 里补一句「逐行逐列核对、数值 ±5% 以内算通过」。
