# Harness 工程搭建式 Agent 评测

> 用一个顶级 Agent（Claude Code）作为评测 Harness 的搭建者和运行者，将评测逻辑从"代码"升级为"Prompt"，实现业务 Agent 的系统性快速评测。

来源：[[raw/编程笔记/agent/测评方案/基于顶级 Agent（Claude Code）的 Harness 工程搭建式业务 Agent 评测方案]]

## 🎯 答题逻辑（骨架）

```
1. 先说矛盾，别直接说方案            ← 证明你知道 Agent 评测真正难在哪
   业务 prompt 天级迭代 vs 传统评测工程周级启动
   五个痛点：启动成本高 / 人力密集 / 迭代慢 / 可复现性差 / 工程化沉重
2. 抛出核心洞察（一句话定调）        ← 这题的最高分点，先抛出来抢占印象
   评测 Harness 的本质 = 结构化评估规则 + 执行流程
   传统把它编码成 test_runner.py，Harness 式把它编码成「评测 Agent 提示词」
3. 讲三层架构 + 输出层               ← 证明你真搭过，不是听说过
   规则层（评测方案）→ 数据层（评测集 + GT）→ 执行逻辑层（评测 Agent Prompt）
   之上是输出层：归因分析、跨批次对比、可操作建议
   顺带说职责分工：人只做 GT 标注 + 方案审核 + 决策
4. 讲统一指标框架 L1/L2/L3           ← 证明这是可复用资产，不是一次性活儿
   L1 全员必报（格式合规率、字段完整率）→ L2 按能力类型从菜单勾选
   → L3 Agent 专属 → 每个指标配目标阈值
5. 用数字收口                        ← 量化收益，避免全程讲概念
   单 Agent 全流程 ~1.5 周 → ~1-2 天，整体 ~5x；方案设计和评测逻辑开发单点 ~10x
6. 主动讲局限                        ← 辩证思维，同时抢占面试官的下一个问题
   LLM-as-Judge 本身有偏差 → 关键决策人工抽检兜底
   评测集规模受人工 GT 限制 → 小而精优于大而糙
   依赖评测平台稳定性 → token 截断、API 超时要做容错
```

**关键心态**：这题考的**不是你会背几个评测指标，而是你有没有真把评测跑成闭环**。面试官在听三件事：①你的指标体系是不是**分层可复用**的（换个 Agent 还能不能用）；②你的**评测逻辑落在哪**（散在脚本里，还是收敛成一份可读可改的 Prompt）；③你**知不知道 LLM-as-Judge 不可靠**、怎么兜底。只说「我们用大模型给 1-5 分，准确率 90%」会被判定为只跑过一次 demo——因为你既没讲评测系统自己也会有 bug，也没讲怎么区分「评测系统 bug」和「被测 Agent bug」。

**分水岭术语**：**评测 Agent 提示词（执行逻辑从代码变 Prompt）**、**`system.question` 列（输入 + `ground_truth` 内嵌一列）**、**L1/L2/L3 三层指标框架**、**GT⊆AI 超集匹配**、**LLM-as-Judge + 可区分 rubric**。这几个词能自然说出来，面试官基本确认你亲手搭过；说不出来就是转述别人的方案。

## 一、核心问题

### 1.1 矛盾

业务 Agent 的 prompt 迭代快（天级），但传统评测工程搭建慢（周级）。每次 prompt 变更后需要快速验证效果，而传统做法：

| 痛点 | 表现 |
|---|---|
| 启动成本高 | 搭工程、写脚本、部署服务，一周还没开始评 |
| 人力密集 | 标注数据、写分析脚本、出报告，每个环节都需人工 |
| 迭代慢 | prompt 改一行，等半天才能看到效果 |
| 可复现性差 | 评测逻辑散落在各种脚本和 Notebook 里 |
| 工程化沉重 | 每换一个 Agent 就要新写一套评测代码 |

### 1.2 解法

用 Claude Code 搭建完整的评测骨架（Harness），包括评测方案、数据集、评测逻辑（以 Agent 提示词形式表达）、分析流程。人只需提供被测对象和做关键决策。

**为什么是 Claude Code？**

| 能力 | 在 Harness 中的作用 |
|---|---|
| 深度理解 prompt | 分析被测 Agent 逻辑，设计针对性评测维度 |
| 代码生成 | 数据获取/处理脚本，评测辅助工具 |
| 结构化输出 | 方案文档、评测 Agent 提示词、评测报告 |
| 多轮协作 | 跨版本持续迭代，保持上下文连贯 |
| 数据分析 | 对跑批结果做统计、归因、对比 |

关键洞察：评测 Harness 的本质是一套结构化的评估规则 + 执行流程。传统做法把它编码为 Python 脚本，Harness 式把它编码为 **Agent 提示词**——更灵活、更可读、更易迭代。

## 二、Harness 工程整体架构

### 2.1 三层架构

| 层         | 内容                  | CC 角色       | 输入 → 输出                       |
| --------- | ------------------- | ----------- | ----------------------------- |
| **规则层**   | 评测方案、评测维度、评估标准、目标阈值 | 方案架构师       | 被测 prompt → 评测方案文档            |
| **数据层**   | 评测集构建（含 GT 标注）      | 数据工程师       | 候选数据 → 评测集 Excel              |
| **执行逻辑层** | 评测 Agent 提示词（评测逻辑）  | Harness 工程师 | 评测方案 → 评测 Agent System Prompt |

三层之上是**输出层**：CC 作为数据分析师，对跑批结果做归因分析、跨批次对比、给出可操作建议。

### 2.2 职责分工

| 角色              | 职责                   | 不做什么            |
| --------------- | -------------------- | --------------- |
| **人**           | GT 标注、方案审核、最终决策      | 不写评测脚本、不手动计算指标  |
| **Claude Code** | Harness 全链路搭建 + 结果分析 | 不做批量推理主循环（交给平台） |
| **评测平台**        | 批量执行引擎（逐行调用）         | 不做方案设计和指标汇总     |

### 2.3 与传统评测工程的类比

| 传统评测工程 | Harness 式评测 | 变化 |
|---|---|---|
| `test_config.yaml` | 评测方案.md | 规则从配置文件变为自然语言文档 |
| `test_data.json` | 评测集 Excel（system.question） | 数据格式统一，人可直接看懂 |
| `test_runner.py`（数百行） | 评测 Agent 提示词（数千字） | 执行逻辑从**代码**变为**Prompt** |
| `conftest.py` + fixtures | GT 标注 + ground_truth 字段 | 预期结果内嵌在数据中 |
| `report_generator.py` | CC 实时分析 | 报告生成从脚本变为交互 |
| `requirements.txt` + CI | 评测平台一键跑批 | 零部署成本 |

## 三、统一评测指标框架

经过 6 个不同类型 Agent 的实战，沉淀出三层指标体系：

### L1：通用基础指标（所有 Agent 必报）

| 指标 | 含义 |
|---|---|
| 输出格式合规率 | JSON 可成功解析的比例 |
| 字段完整率 | 必要字段均存在的比例 |

### L2：按能力类型选用（从菜单按需勾选）

| 能力类型 | 指标                 | 适用场景        |
| ---- | ------------------ | ----------- |
| 分类判断 | 分类准确率              | 枚举值选择       |
| 二元决策 | 召回率 / 精确率          | 过滤 / 准入决策   |
| 数值提取 | 精确匹配率              | 离散数值的精确提取   |
| 连续评分 | MAE + 分档一致率        | 内容质量打分      |
| 文本生成 | LLM-as-Judge 1-5 分 | 文案、描述等开放式输出 |

### L3：Agent 专属指标（按需自定义）

每个 Agent 可在 L1+L2 基础上追加专有指标，如违禁词清洁率、关键信息保留率等。

### 新 Agent 接入时的指标选型流程

```
确定 Agent 涉及的能力类型 → 从 L2 菜单勾选对应指标 → 按需追加 L3 专属指标 → 设定每个指标的目标阈值
```

## 四、Harness 各层搭建方法

### 4.1 规则层：评测方案设计

**输入**：被测 Agent 的 prompt 文件 + 业务上下文描述

**CC 输出**：
- 完整评测方案文档（维度、指标、阈值、数据集要求、错误分类体系）
- 边界用例建议（CC 分析 prompt 逻辑后主动提出应覆盖的场景）

**实际效果**：从一个 prompt 文件到一份完整评测方案，约 10 分钟交互。

### 4.2 数据层：黄金评测集构建

CC 的工作流：
1. **数据获取**：编写脚本调用业务接口，批量拉取候选数据
2. **数据处理**：格式化为评测所需的 JSON 结构
3. **GT 辅助标注**：对分类型指标，CC 先给建议标注，人工复核
4. **评测集打包**：生成评测平台可直接消费的 Excel

**关键设计：`system.question` 列**

每行数据都有一列 `system.question`，格式为 JSON，包含：
- 被测 Agent 所需的全部输入字段
- `ground_truth`（人工标注的黄金答案）

评测 Agent 读取这一列即可获得输入和预期输出，无需额外配置。

### 4.3 执行逻辑层：评测 Agent 提示词（最核心创新）

这一层是前面"代码 → Prompt"这个洞察的落地：一份提示词同时承担了 test_runner 的执行流程、断言逻辑和输出契约三件事。

**评测 Agent 提示词结构模板**：
- **角色定义**：严谨的 AI 评测专家
- **工具声明**：调用被测 Agent 的接口
- **约束**：必须先调用工具再评测、只输出合法 JSON、数值精确计算
- **工作流程**：解析输入 → 调用 Agent → 解析输出 → 硬规则检查 → LLM 打分 → 错误归因 → 输出 JSON
- **输出 Schema**：完整的 JSON schema 定义

**为什么这样设计？**

| 优势 | 说明 |
|---|---|
| 逻辑可读 | 评测逻辑以自然语言写在提示词里，无需读代码 |
| 快速迭代 | 发现评测逻辑有误，改一段文字就行 |
| 统一执行 | 所有 Agent 的评测逻辑结构一致 |
| 评测即文档 | 提示词本身就是评测标准的完整说明 |

### 4.4 输出层：结果分析与报告

CC 在分析中的增值：
1. **自动识别 pattern**：不只报数字，还归因（如"18 条误过滤中，12 条是把评分维度误用为过滤条件"）
2. **跨批次对比**：和上一版结果对比，明确哪些指标进步/退步
3. **可操作建议**：不只说"分数低"，而是"建议在 prompt 第三段加入明确的过滤条件边界"

## 五、关键实践经验

### 5.1 评测集设计原则

| 原则 | 说明 | 反例 |
|---|---|---|
| 小而精 | 20-55 条足够，覆盖所有边界场景 | 200+ 条但都是简单 case |
| 分布均衡 | 正/负例比例合理，边界场景必须有 | 全是正例 |
| GT 可复核 | 每条 GT 标注有据可查 | GT 靠感觉打分 |
| 版本化管理 | 评测集跟随被测 prompt 版本变更 | 用 v1 评测集评 v3 prompt |

### 5.2 评测 Agent 提示词的迭代策略

评测 Agent 本身也需要迭代——评测系统 bug ≠ 被测 Agent bug：

| 常见问题 | 表现 | 修复方式 |
|---|---|---|
| 匹配逻辑过严 | 语义等价的判定被判错 | GT⊆AI 超集匹配 |
| 硬编码规则误报 | 排除列表不全 | 改为动态语义比对 |
| Token 截断 | 输出超长被截断 | 正则容错提取关键字段 |
| GT 覆盖缺口 | 新增选项未体现 | 更新 GT 标注 |

**迭代节奏**：v1 调试模式（带推导过程）→ v2 跑批模式（纯 JSON）+ 修复 bug → v3+ 持续调优

### 5.3 LLM-as-Judge 使用心得

对文本生成类 Agent，用 LLM 做评委——在评测 Agent 提示词中嵌入 1-5 分 rubric。

**有效 rubric 的设计要点**：
- 每个分值必须有具体、可区分的判定标准
- 避免"好/较好/一般"这类主观描述
- 分值之间的差异一个正常人也能判断

### 5.4 "评测 Agent 调被测 Agent"的踩坑

| 坑 | 解法 |
|---|---|
| 评测 Agent 忘记调用工具 | 在 Constraints 中强调"必须先调用工具" |
| 工具参数传递失败 | 在提示词中显式写明参数构造逻辑 |
| 评测 Agent 重试耗尽 token | 添加"禁止重试"约束 |
| 输出截断 | 减少推导过程，只输出最终 JSON |

## 六、效率对比

| 阶段 | 传统方式 | CC 协助 | 加速比 |
|---|---|---|---|
| 评测方案设计 | 1-2 天 | 10-30 分钟 | ~10x |
| 评测集构建 | 2-3 天 | 半天（含人工标注） | ~5x |
| 评测脚本/Agent 开发 | 2-3 天 | 1-2 小时 | ~10x |
| 跑批执行 | 同（平台执行） | 同 | 1x |
| 结果分析 + 报告 | 半天-1天 | 10-20 分钟 | ~5x |
| **单 Agent 全流程** | **~1.5 周** | **~1-2 天** | **~5x** |

## 七、适用场景与局限

### 适用场景

| 场景 | 适合度 | 原因 |
|---|---|---|
| Prompt 迭代验证 | ⭐⭐⭐⭐⭐ | 改 prompt → 跑批 → 看报告，闭环最快 |
| 多 Agent 横向对比 | ⭐⭐⭐⭐⭐ | 统一指标框架 + 相同评测流程 |
| 新 Agent 上线前验收 | ⭐⭐⭐⭐ | 系统性覆盖，不依赖人工抽检 |
| 线上问题复盘 | ⭐⭐⭐ | 可快速构造问题用例验证 |

### 局限

| 局限 | 建议 |
|---|---|
| LLM-as-Judge 本身有偏差 | 关键决策用人工抽检兜底 |
| 评测集规模受限（人工 GT） | 小而精优于大而糙 |
| 依赖评测平台稳定性 | token 截断、API 超时需做容错 |
| 首次搭建有学习成本 | 第二个 Agent 起复用率很高 |

## 八、范式转变总结

```
传统：人写评测代码 → 跑脚本 → 人看结果 → 人改代码 → 再跑
      （周级启动，天级迭代）

Harness 式：CC 搭建 Harness → 平台跑批 → CC 分析 → CC 调整 Harness → 再跑
           （天级启动，小时级迭代）
```

核心收益：从周到天、一人成军、可持续迭代、零部署、方法论可沉淀复用到任何 Agent。

## ⚡ 30 秒速答版

> 我们的背景是**业务 Agent 的 prompt 天级迭代，但传统评测工程周级才能启动**——搭工程、写脚本、部署服务，一周还没开始评。所以我们换了个思路：**评测 Harness 的本质就是「一套结构化评估规则 + 执行流程」，传统做法把它编码成 `test_runner.py`，我们把它编码成一份「评测 Agent 提示词」**，让 Claude Code 来搭。
>
> 具体分三层：**规则层**是评测方案（维度、指标、阈值、错误分类体系），**数据层**是黄金评测集，每行一个 **`system.question`** 列，里面 JSON 装着被测 Agent 的全部输入加人工标注的 **`ground_truth`**；**执行逻辑层**就是那份评测 Agent 提示词，它一份东西同时承担了 test_runner 的**执行流程、断言逻辑和输出契约**——工作流是解析输入 → 调用被测 Agent → 解析输出 → **先做硬规则检查，再做 LLM 打分** → 错误归因 → 输出 JSON。跑完批 CC 再当数据分析师做归因和跨批次对比。
>
> 指标上我们沉淀了 **L1/L2/L3 三层框架**：L1 是所有 Agent 必报的格式合规率和字段完整率，L2 是按能力类型从菜单勾选（分类准确率、召回/精确率、MAE + 分档一致率、LLM-as-Judge 1-5 分），L3 是 Agent 专属指标。新 Agent 接入就是「勾菜单 + 加专属指标 + 设阈值」。
>
> 效果是**单个 Agent 全流程从大概 1.5 周压到 1-2 天，约 5 倍**，其中评测方案设计和评测逻辑开发这两段能到 10 倍。局限我也清楚：**LLM-as-Judge 自己有偏差，关键决策还得人工抽检兜底**；评测集受人工 GT 限制，我们坚持**小而精（20-55 条覆盖全部边界场景）优于大而糙**。

## 💬 对方可能追问的问题

### 顺着「把评测逻辑从代码升级为 Prompt」这个范式转变追（概率最高）

| 追问 | 答题要点 |
|---|---|
| 写成 Prompt 比写成代码到底好在哪？ | 四点：①**逻辑可读**，评测标准就是自然语言，不用读代码；②**快速迭代**，评测逻辑有误改一段文字就行，不用改代码重新部署；③**统一执行**，所有 Agent 的评测逻辑结构一致；④**评测即文档**，提示词本身就是评测标准的完整说明 |
| 一份提示词具体替代了原来哪些文件？ | 做过一一映射：`test_config.yaml`→评测方案.md、`test_data.json`→评测集 Excel、`test_runner.py`（数百行）→评测 Agent 提示词（数千字）、`conftest.py`+fixtures→GT 标注内嵌到 `ground_truth` 字段、`report_generator.py`→CC 实时分析、`requirements.txt`+CI→平台一键跑批、**零部署成本** |
| Prompt 不比代码更不可靠吗？确定性怎么保证？ | 承认这点，所以**不是全交给 LLM**：提示词的工作流里**硬规则检查和 LLM 打分是分开的两步**。凡是能确定性判定的（JSON 能否解析、必要字段是否存在、枚举值合法性、数值精确匹配）都走硬规则，只有开放式文本才交给 Judge。另外用**输出 Schema** 约束返回格式、约束里写明「数值精确计算」 |
| 那评测平台在这套里做什么？ | 只做**批量执行引擎**（逐行调用），不做方案设计和指标汇总。分工是：人做 GT 标注 / 方案审核 / 最终决策，CC 做 Harness 全链路搭建 + 结果分析，**平台做批量推理主循环**——CC 不适合当主循环 |
| 评测 Agent 提示词自己有 bug 怎么办？ | 关键认知：**评测系统 bug ≠ 被测 Agent bug**，评测 Agent 本身也要迭代。节奏是 **v1 调试模式（带推导过程，方便看它为什么判错）→ v2 跑批模式（纯 JSON）+ 修 bug → v3+ 持续调优** |

### 顺着统一评测指标框架追

| 追问 | 答题要点 |
|---|---|
| 为什么要分成三层？ | 分层是为了**复用**：L1 是不变量（所有 Agent 必报），L2 是**菜单**（按能力类型勾选，避免每个 Agent 重新发明指标），L3 才是定制。这样第二个 Agent 接入时上层完全复用 |
| L2 的菜单具体怎么勾？ | 按被测 Agent 的**能力类型**映射：分类判断→分类准确率；二元决策（过滤/准入）→召回率+精确率；数值提取→精确匹配率；连续评分→**MAE + 分档一致率**；文本生成→LLM-as-Judge 1-5 分。一个 Agent 可能同时命中多个类型 |
| 连续评分为什么要 MAE **和**分档一致率两个？ | MAE 衡量数值偏差绝对量，但业务上真正用的是**分档结果**（比如高/中/低）。MAE 小但恰好卡在档位边界上反复跨档，业务还是错的；两个一起看才能既管住偏差量又管住决策一致性 |
| 二元决策为什么要召回和精确两个，不用准确率？ | 过滤/准入场景**正负样本天然不均衡**，准确率会被多数类掩盖。而且业务上两类错误代价不对称——误过滤（漏召）和误放行（误报）要分别定阈值 |
| 新 Agent 接入的完整流程是什么？ | 四步：确定 Agent 涉及的能力类型 → 从 L2 菜单勾选对应指标 → 按需追加 L3 专属指标（如违禁词清洁率、关键信息保留率）→ **给每个指标设定目标阈值**。最后一步不能省，没阈值的指标等于没结论 |

### 顺着 LLM-as-Judge 的可靠性追（最能拉开差距）

| 追问 | 答题要点 |
|---|---|
| 同一份输入让 Judge 打两次分数不一样，怎么办？ | 分三层处理：①**先把 rubric 修到能收敛**——每个分值要有具体可区分的判定标准，避免「好/较好/一般」，标准是「分值之间的差异一个正常人也能判断」；②**降低采样随机性**：Judge 调用用低温、固定模型版本和参数，保证跨批次可比；③**残余漂移用多次采样聚合**（取多次打分的中位数/众数）。同时承认这是本方案写明的局限之一——**LLM-as-Judge 本身有偏差，关键决策用人工抽检兜底** |
| 怎么防止 Judge 被又长又漂亮的答案迷惑？ | 这是公认的 **verbosity bias（冗长偏好）**。做法：①rubric 里**显式声明长度不是加分项**，只对指定维度打分；②把「文本质量」**拆成多个细维度分别打分**再汇总，而不是给一个笼统总分；③**长度约束、格式合规这类可判定项交给硬规则**，不要混进 Judge 的打分里；④对同一 case 做人工抽检校准，看 Judge 是否系统性偏向长答案 |
| 什么时候必须回退到代码化断言，不能用 Prompt 评测？ | 判据是**「这条指标有没有唯一确定的判定」**：有 → 硬规则。具体包括 L1 的输出格式合规率（JSON 能否解析）、字段完整率、枚举值/分类判断的对错、数值提取的精确匹配、违禁词命中这类可枚举检查。只有**开放式生成**（文案、描述）才必须用 Judge。本方案的评测 Agent 工作流本来就是「硬规则检查 → LLM 打分」两段式，不是二选一 |
| 怎么验证你的 Judge 打分是对的？ | 拿它**和人工标注对齐**：小批量双标，看分档一致率 / 打分偏差，不一致的 case 逐条看是 rubric 描述模糊还是 Judge 理解偏了，然后回去改 rubric。这也是「评测系统 bug ≠ 被测 Agent bug」的具体体现 |
| 让 Judge 先写理由再给分不是更准吗？ | 是更准，但和跑批有冲突——**带推导过程会把输出撑到 token 截断**。所以我们做成两个模式：**v1 调试模式带推导过程**（用来定位评测逻辑问题），**v2 跑批模式只输出最终 JSON**。这是精度和稳定性的显式 trade-off，不是没想到 |
| 语义等价但字面不同，Judge 判错怎么办？ | 这是我们踩过的具体坑，两个修法：匹配逻辑过严 → 改成 **GT⊆AI 超集匹配**（GT 是 AI 输出的子集即算命中）；硬编码排除列表不全导致误报 → 改为**动态语义比对** |

### 顺着评测集与 GT 构建追

| 追问 | 答题要点 |
|---|---|
| 评测集为什么只有 20-55 条？会不会不够？ | 原则是**小而精优于大而糙**：20-55 条**覆盖全部边界场景**，比 200+ 条全是简单 case 有信息量。约束来自 GT 必须人工标注且**可复核**（每条标注有据可查，不能靠感觉打分）。规模不够的部分靠**分布均衡**（正负例比例合理、边界场景必须有）补 |
| 边界用例谁来想？ | CC 读完被测 Agent 的 prompt 后**主动提边界用例建议**——它分析 prompt 的判断逻辑，指出应该覆盖哪些场景，人再复核。这一步和评测方案一起产出，大约 10 分钟交互 |
| GT 标注让模型做，不是自己评自己吗？ | 所以是 **CC 先给建议标注、人工复核**，人保留最终决定权。人的职责就是 GT 标注、方案审核、最终决策——**人不写评测脚本、不手动算指标**，但 GT 这条线不交出去 |
| 评测集怎么版本化？ | 评测集**跟随被测 prompt 版本变更**。反例就是拿 v1 的评测集去评 v3 的 prompt——prompt 改了枚举选项、加了新分支，旧 GT 就有覆盖缺口，跑出来的错都是假错 |

### 顺着你自己怎么落地和收益追（最容易露馅）

| 追问 | 答题要点 |
|---|---|
| 具体加速了多少？分阶段说 | 评测方案设计 1-2 天 → 10-30 分钟（~10x）；评测集构建 2-3 天 → 半天含人工标注（~5x）；评测脚本/Agent 开发 2-3 天 → 1-2 小时（~10x）；结果分析+报告 半天到 1 天 → 10-20 分钟（~5x）；**跑批那一段不变（1x，本来就是平台执行）**。合计 ~1.5 周 → 1-2 天，~5x |
| 报告里 CC 比人工强在哪？ | 三点增值：①**自动识别 pattern 并归因**，不只报数字——例如「18 条误过滤中，12 条是把评分维度误用为过滤条件」；②**跨批次对比**，明确哪些指标进步/退步；③**可操作建议**，不说「分数低」而说「建议在 prompt 第三段加入明确的过滤条件边界」 |
| 评测 Agent 调被测 Agent 时踩过什么坑？ | 四个具体坑：评测 Agent **忘记调用工具**（在 Constraints 里强调「必须先调用工具再评测」）；**工具参数传递失败**（提示词里显式写明参数构造逻辑）；**重试耗尽 token**（加「禁止重试」约束）；**输出截断**（减少推导过程只输出最终 JSON，并用正则容错提取关键字段） |
| 这套方法什么场景最适合、什么场景不适合？ | 最适合 **prompt 迭代验证**（改 prompt → 跑批 → 看报告，闭环最快）和**多 Agent 横向对比**（统一指标框架 + 相同评测流程）；**新 Agent 上线前验收**也好用（系统性覆盖，不依赖人工抽检）；**线上问题复盘**一般（能快速构造问题用例，但复现真实上下文有限）。不适合的是需要大规模统计显著性的场景，因为评测集规模受人工 GT 限制 |
| 这套东西可复用的资产有哪些？ | 6 个 Agent 实战沉淀出的模板：三层指标框架模板、评测方案文档模板、评测 Agent 提示词模板、评测集 Excel 格式规范、评测报告模板、错误分类体系。**首次搭建有学习成本，第二个 Agent 起复用率很高** |

### 高频陷阱题

1. **「跑批准确率掉了，是不是就说明新 prompt 变差了？」** → 不能直接下结论。**先排查评测系统自己是不是有 bug**：匹配逻辑过严、硬编码排除列表不全、输出被 token 截断、GT 有覆盖缺口——这四种都会让好 prompt 被判差。**评测系统 bug ≠ 被测 Agent bug**，这是这套方法最核心的一条纪律。
2. **「评测集是不是越大越好？」** → 不是。约束在**人工 GT 的成本和可复核性**上，200+ 条简单 case 不如 20-55 条覆盖全部边界场景。判据是覆盖度和分布均衡，不是条数。
3. **「既然评测逻辑都能写成 Prompt，那是不是不用写代码了？」** → 错。代码没消失，只是**换了位置**：数据获取/处理脚本还是代码，L1 的格式合规、字段完整、精确匹配这类**硬规则断言必须是确定性判定**，批量执行主循环交给评测平台。Prompt 取代的是 `test_runner.py` 里的**编排和开放式断言**那部分。
4. **「LLM-as-Judge 给 1-5 分，是不是就能当客观指标用了？」** → 不能。Judge 有偏差是本方案明确写下的局限，兜底是**人工抽检**。而且 Judge 分数只适合**同一 rubric、同一模型版本下做相对比较**（版本 A vs 版本 B），不适合当跨项目的绝对分。
5. **「rubric 写『5 分优秀、3 分一般、1 分差』够了吧？」** → 不够，这正是典型反例。有效 rubric 的三条要点：每个分值有**具体、可区分**的判定标准；避免「好/较好/一般」这类主观描述；**分值之间的差异一个正常人也能判断**。做不到这点，打分漂移是必然的。
6. **「让 Claude Code 直接把这批数据全跑一遍出报告不就完了？」** → 不行。CC 的角色是**搭 Harness + 分析结果**，**批量推理主循环交给评测平台**。让 CC 当主循环会遇到 token 消耗、上下文长度、中途重试和结果不可复现的问题。
