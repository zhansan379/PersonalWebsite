# IoC 控制反转与依赖注入

> **IoC（控制反转）** 是把对象生命周期的控制权从程序员反转给容器；**DI（依赖注入）** 是它最核心的实现手段。三者易混：IoC=设计思想、DI=编码技巧、DIP=设计原则。核心主线：**把 new 和依赖关系交给容器，解耦代码。**

## 一、这是什么

回答"怎么理解 IoC / 依赖注入 / 依赖倒置 / 设计一个 IoC"等问题时，先讲清思想，再讲清实现方式，最后展示架构设计思维。**IoC 是地基中的地基**，几乎必问。

## 二、核心内容

### 2.1 怎么理解 IoC

> "IoC（Inversion Of Control）是一种设计思想：把对象生命周期的控制权从程序员手中**反转给容器**。"

所谓"控制" = 对象的**创建、初始化、销毁**：

| 生命周期 | 原来（自己控制） | Spring 容器 |
| :--- | :--- | :--- |
| 创建 | `new` 一个 | 容器创建 |
| 初始化 | 构造器/setter 给依赖赋值 | 容器自动注入 |
| 销毁 | 置 null / 手动 | 容器管理生命周期 |

所谓"反转"：**反转的是控制权**——程序员由"对象控制者"变成"被动接收者"。本质收益：**解耦**，摆脱繁琐的对象生命周期操作。

### 2.2 控制反转 / 依赖注入 / 依赖倒置 三者区别

| 概念 | 层级 | 一句话 |
| :--- | :--- | :--- |
| **控制反转（IoC）** | 设计思想（框架层面） | 程序执行流程的控制权从程序员"反转"给框架 |
| **依赖注入（DI）** | 编码技巧（实现手段） | 不 new，把依赖对象外部建好后**传进来**（构造器/参数注入） |
| **依赖倒置（DIP）** | 设计原则（SOLID·D） | 高层不依赖低层，共同依赖抽象；抽象不依赖细节，细节依赖抽象 |

> 关键区分：**IoC 是"思想"，DI 是"做法"**（IoC 的具体落地），DIP 是"设计原则"。三者不冲突，是不同视角。

### 2.3 依赖注入的实现方式

| 方式 | 特点 | 生产建议 |
| :--- | :--- | :--- |
| **构造器注入** | 对象初始化时依赖已就绪，`final` 不可变 | ✅ 推荐（Spring 官方首选） |
| **Setter 注入** | 灵活，但依赖可能未完全初始化 | 可选 |
| **字段注入**（`@Autowired` 字段） | 代码最简洁，但**隐藏依赖、不易测试** | ❌ 生产不推荐 |

加分点：Spring 4.3+ 对单构造器自动识别，无需显式 `@Autowired`。

### 2.4 如果让你设计一个 Spring IoC

回答要点（设计题，展示架构思维）：
- **Bean 生命周期管理**：创建/初始化/销毁，用工厂模式 + 单例模式
- **依赖注入**：属性/构造器/方法注入 → 用**反射**解析依赖
- **Bean 作用域**：单例/原型/会话/请求 → 用 **Map** 按作用域存实例
- **AOP 支持**：需要代理机制
- **异常处理**：Bean 创建异常、依赖注入异常 → try-catch 兜底
- **配置加载**：XML / 注解 / Java 配置类

## 三、可能追问

1. 「构造器注入和字段注入选哪个？」→ 构造器（不可变、易测试、DI 明确）
2. 「`@Autowired` 找不到或找到多个 Bean 怎么办？」→ 找不到抛异常、多个抛 `NoUniqueBeanDefinitionException`，用 `@Primary`/`@Qualifier`/`Map` 注入解决
3. 「`@Autowired` vs `@Resource` 区别？」→ Autowired 按类型、Resource 按名称
4. 「IoC 和反射是什么关系？」→ 容器靠反射动态加载类/实例化/调用方法，见 [[IoC 与 AOP 的实现机制]]
5. 「单例默认作用域，多线程安全吗？」→ 单例 Bean 被共享，无状态安全、有状态需注意并发
