## 1. 问题背景
原有验证逻辑分为三类，混在一起导致：
- 代码职责不单一
- 修改或新增逻辑时容易影响现有代码
- 流程不清晰，不利于理解和维护

三类验证：
1. **非空/空值校验** — 简单基础
2. **字段间依赖关系校验** — 数据基本逻辑
3. **数据真实性校验**（如商品编码是否正确）— 依赖外部服务

## 2. 解决方案：责任链模式
核心思路：将三类验证拆分为**三个独立的处理器**，按顺序执行，每个处理器只关注自己的逻辑。

优势：
- **单一职责** — 每个处理器只做一类校验
- **易扩展** — 新增校验只需添加新处理器，不改旧代码
- **流程清晰** — 代码阅读者一眼能看出有哪几步校验，便于理解业务

## 3. 责任链模式简介
- 定义：将请求沿一条处理链传递，直到链中某个对象处理它（或所有对象依次处理）。
- 类比：用户拦截器（多个拦截器顺序执行，异常时中断）。
- 核心思想与验证逻辑一致：多个处理步骤顺序执行。

## 4. 实现细节（基于Spring环境）

### 4.1 类结构（共5个类）
| 类名 | 作用 |
|------|------|
| 责任链抽象接口 | 定义处理方法和分组标识 |
| 上下文容器（Context） | 聚合所有处理器，提供执行入口 |
| 三个具体实现类 | 分别对应三类校验逻辑 |

### 4.2 接口设计
- 包含两个核心方法：
  - `handle()`：执行处理逻辑
  - `getMark()`：返回分组标识（如“创建优惠券模板”）
- 各实现类继承接口，封装自己的校验逻辑。

### 4.3 上下文容器（核心）
- 实现 Spring 的 `ApplicationContextAware` 和 `InitializingBean` 接口。
- 在 Spring Boot 启动后，通过 `ApplicationContext` 获取该接口的所有实现类。
- 使用 `Map<String, List<Handler>>` 存储：
  - Key：`mark` 分组标识
  - Value：该分组下的处理器列表（List）
- 聚合流程：
  1. 遍历所有实现类
  2. 根据 `mark` 获取或创建 List
  3. 将当前处理器加入 List
  4. 放回 Map

### 4.4 排序（Order）
- 处理器需要排序，原因是**性能优先**：
  - 先执行性能好、无外部依赖的校验（如非空校验） → `order` 值小
  - 后执行性能差、有 RPC 调用的校验（如商品真实性） → `order` 值大
- 好处：避免先做昂贵的校验，若后续简单校验失败则白白浪费性能。

### 4.5 执行调用
- 业务代码引入上下文容器，调用 `handle(mark)` 方法。
- 方法内部：根据 `mark` 获取处理器列表，按顺序依次执行（若某个处理器抛出异常则中断）。

## 5. 开闭原则的讨论
- **传统责任链**：新增处理器需要手动修改注册逻辑，不符合开闭原则。
- **Spring环境下的优化**：利用 Spring 的 IOC 和 `ApplicationContext` 自动扫描所有实现类，自动注册，无需手动修改注册代码。
- 结论：在 Spring 框架下，这种实现**符合开闭原则**（新增处理器只需新增类，不改已有代码）。若不用 Spring，可能需要自己实现注册逻辑。

## 6. 总结
- 该方案通过责任链模式将复杂验证逻辑拆解为多个独立处理器，提升了代码可维护性和可扩展性。
- 利用 Spring 的容器管理能力，实现了自动注册和排序，兼顾性能和开闭原则。
- 适用场景：任何需要**多步骤顺序处理**且步骤可能动态增减的业务逻辑。
