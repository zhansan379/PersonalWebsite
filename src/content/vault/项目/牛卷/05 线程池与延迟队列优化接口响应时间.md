> 面试考的是 先执行再延迟确认 这套可靠性设计：为什么用线程池异步？线程池被 `Executors` 手写有哪些坑？任务可能投递后应用宕机怎么办？延迟队列怎么兜底？为什么拿 Redis 而不用 MQ？这套逻辑讲清胜过堆几个类名。

## 一、一句话定位

> 用**线程池异步** + **Redis 延迟队列兜底**，把 EasyExcel 解析百万数据 Excel 的接口从 **5 秒优化到毫秒级**，同时用"先执行、延迟确认"保证解析条数不丢。

## 二、项目技术路线（第13小节精华，按决策链记忆）

### 1. 业务背景 / 优化什么
- EasyExcel 解析百万行 Excel 需要约 **5 秒**，虽是后管接口，但**能优化还是优化**。
- 解法：把最耗时的"统计 Excel 行数 → 刷新发送条数"从同步改成**异步**，接口立刻返回。

### 2. 为什么不用 MQ？（这题常被追问）
- 完全可以用 RocketMQ，但**不是每个项目都有消息队列**。
- 用"线程池 + 延迟队列"作为**无 MQ 环境下的替代方案**，是扩展思路的加分点。

### 3. 线程池手写（核心，含 Executors 对比）
```java
ExecutorService executorService = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors(),       // core = CPU核数
        Runtime.getRuntime().availableProcessors() << 1,  // max = 2×CPU核数
        60, TimeUnit.SECONDS,
        new SynchronousQueue<>(),                          // 不存任务
        new ThreadPoolExecutor.DiscardPolicy()             // 满了丢弃，靠延迟队列兜底
);
```
- **corePoolSize = CPU 核数**：后管任务不频繁。
- **maximumPoolSize = 2×核**：IO 密集型（解析文件）所以翻倍。
- **SynchronousQueue + DiscardPolicy**：理论不阻塞、满了直接丢——因为**有延迟队列兜底**，丢弃无害。
- **为什么不用 `Executors`**（高频反问）：
  - `newFixedThreadPool` / `newSingleThreadExecutor`：无界 `LinkedBlockingQueue`，任务积压 → **OOM**。
  - `newScheduledThreadPool`：无界延迟队列，任务堆积 → OOM。
  - `newCachedThreadPool`：`SynchronousQueue` + 无限线程，高并发下**创建海量线程耗尽资源**。

### 4. 线程池异步的致命问题 → 引出延迟队列
> **致命问题**：任务刚投递线程池还没跑完，应用宕机，任务就丢了。
> 所以需要延迟队列**兜底**。

### 5. Redis 延迟队列兜底
- 用 Redisson 的 `RBlockingDeque + RDelayedQueue`。
- 投递线程池后，**再往延迟队列投一个延迟 20 秒的任务**（笃定线程池 20 秒内跑完）。
- 消费逻辑（`CommandLineRunner` 启动的无限循环线程）：
  1. `blockingDeque.take()` 取**已到期**元素；
  2. 查 `couponTaskId` 对应的 `sendNum`——**若已有值说明线程池跑了，无需处理；为空才重新解析兜底**。
- 一句话：**"先执行，延迟确认；确认成功则不再做，失败才兜底。"**

### 6. 事务保证 DB 与异步投递一致性
- 方法加 `@Transactional(rollbackFor = Exception.class)`：把"插入 CouponTaskDO + 投递线程池 + 投递延迟队列"绑在一起。
- 不加的话，DB 插入成功而异步投递失败 → **发送条数永远不会被刷新**。
- > 注意：延迟队列兜底理论上也依赖同一事务完成，若要更强保障应由消费者自行判断，这里作为入门兜底是够用的。

### 7. 为什么只拿 Redis 当兜底而非主力？
- Redis 是**缓存**：持久化（AOF）为异步，最好情况也会丢一条；主从同步未同步到从节点时节点故障也会丢。
- 所以**只作兜底，不作全部方案**；真正要保证不丢，仍应上 MQ。

## 三、面试回答主线（三段式）

**1. 抛出问题（体现主动性）**
> "解析百万 Excel 接口耗时 5 秒，我用线程池把耗时的行数统计异步化，接口秒回毫秒级。"

**2. 主动暴露可靠性问题 + 解法（核心加分）**
> "但异步投递有致命缺陷——任务没跑完应用宕机就丢了。所以我加了一个 Redis 延迟队列兜底：投完线程池再投一个 20 秒后的兜底任务，消费时先查 DB 的 sendNum，**有值说明跑完了，为空才重新解析**，也就是'先执行、延迟确认'。"

**3. 讲清选型取舍（体现批判性）**
> "线程池不手写 Executors 有 OOM/资源耗尽坑；Redis 只作兜底因为会丢数据、真要保证不丢得上 MQ；并且用事务把 DB 写入和异步投递绑在一起保证一致。"

## 四、必须能说出的记忆锚点

1. **核心思想**：先执行、延迟确认（先快把接口吐出去，再用兜底任务校验收尾）。
2. **线程池手写五参数**：core=核数、max=2×核、SynchronousQueue、DiscardPolicy、60s。
3. **Executors 三个坑**：无界队列 OOM / 无界延迟队列 OOM / 无限线程资源耗尽。
4. **兜底逻辑**：消费延迟任务先查 sendNum，有值即成功、为空才重做。
5. **延迟 20 秒理由**：笃定线程池 20 秒内跑完；若没跑完才轮到兜底复核。
6. **Redis 只兜底不主力**：AOF 异步会丢、主从不一致会丢 → 真正可靠要上 MQ。

## 五、被追问清单（面试官会往这打）

### Q1：为什么不用 `Executors` 直接创建线程池？
**答**：它给的默认配置常有隐患——
- 固定/单线程池用**无界队列**，提交速度超过处理速度任务无限积压 → OOM；
- Scheduled 用无界延迟队列，同样堆积 OOM；
- Cached 用同步队列+无限线程，高并发下**狂建线程耗尽系统资源**。
推荐**手写 ThreadPoolExecutor** 结合业务显式设置 core/max/队列/拒绝策略。

### Q2：为什么不直接用 MQ，而要线程池 + 延迟队列？
**答**：功能上 MQ 完全可以做，但**不是每个项目都引进了消息队列**。在无 MQ 的轻量场景，用"线程池异步 + Redis 延迟队列兜底"是零额外重型依赖的替代方案，达到类似"异步后置 + 补偿确认"的效果。**但**——如果要求不强丢、可回溯、支持多消费者，仍需上 MQ（本题暴露你对"MVP 方案 vs 生产级方案"的取舍）。

### Q3：任务投到线程池，应用突然宕机了怎么保证不丢？（此题必被追问）
**答**：
- 单靠线程池投递**必丢**（内存中，进程死即消失）。
- 用**延迟队列兜底**：投线程池的同时投一个延迟任务，宕机重启后消费者从兜底队列恢复，查 DB 发现 `sendNum` 为空就重新解析补上。
- 更彻底的做法（升级建议）：真正保证不丢 / 不重复，需引入 **MQ + 手动确认 + 消费端幂等**；或用**本地消息表 + 定时任务重推**。本项目是以轻量为目标做的兜底。

### Q4：这个 Redis 延迟队列的原理是什么？
**答**：Redisson 的 `RDelayedQueue` 底层是 `zset` + `RBlockingDeque`：元素先按到期时间戳进 **zset**，有专门线程到点把到期元素 `transfer` 到 `blockingDeque`，消费者 `take()` 阻塞取到即可。好处是**到点精确触发、消费端只阻塞等待不需要轮询**。

### Q5：为什么延迟 20 秒？怎么定的？
**答**：是"节奏预估"而非硬标准——**笃定正常路径线程池 20 秒内跑完**，所以延迟任务到点时 sendNum 大概率已有值，直接跳过，兜底逻辑基本不触发。若实际解析耗时波动大，这个值要根据压测重定（太长兜底不及时、太短频繁触发无谓复核）。

### Q6：Redis 会丢数据吗？用 Redis 做可靠队列靠不靠谱？
**答**：Redis 本质是缓存，**可靠投递不是它的强项**：
- 持久化（AOF/快照）是**异步**的，最好情况也会丢部分数据；
- **主从同步未完成时主节点故障**，未同步的写操作会丢；
- 所以本项目**只把 Redis 延迟队列当兜底**而非主力，真正要求不丢必须上 MQ（带持久化、ACK、偏移管理）。

### Q7：为什么加 `@Transactional`？里面组合了什么？
**答**：把"**插入任务 DB 记录 + 提交线程池 + 投递延迟队列**"放进同一事务。不加的话存在中间态——DB 插入成功、异步投递却失败（或未执行），发送条数永远刷新不了。加事务后要么一起成、要么一起滚。

### Q8：固定大小可用线程会不会成为瓶颈？要不要动态调？
**答**：本项目场景是后管低频任务，固定 core/max 即可。若任务量大且波动明显，应考虑**可调参**（运行时 set core/max）或**队列 + 拒绝策略组合**兜底，避免海量任务瞬间击穿。

### Q9：和普通 CompletableFuture / 异步注解比，这套有什么特别？
**答**：`@Async`/CF 只解决"异步执行"，**不解决"异步后丢任务"的可靠性**。本项目的增量是**补了一个补偿确认层**（延迟队列兜底），把"异步化"升级成"异步 + 最终一致"。面试上强调这一点，能把你和"会用 @Async"的申请人区分开。

## 六、代码记忆模板（背这份即可）

```java
// 1. 手写线程池：core=核数、max=2×核、不缓存、满了丢（靠延迟队列兜底）
ExecutorService executorService = new ThreadPoolExecutor(
        Runtime.getRuntime().availableProcessors(),
        Runtime.getRuntime().availableProcessors() << 1,
        60, TimeUnit.SECONDS, new SynchronousQueue<>(),
        new ThreadPoolExecutor.DiscardPolicy());

// 2. 异步执行 + 3. 延迟队列兜底
executorService.execute(() -> refreshCouponTaskSendNum(jsonObject));

RBlockingDeque<Object> blockingDeque =
        redissonClient.getBlockingDeque("COUPON_TASK_SEND_NUM_DELAY_QUEUE");
RDelayedQueue<Object> delayedQueue =
        redissonClient.getDelayedQueue(blockingDeque);
delayedQueue.offer(delayJsonObject, 20, TimeUnit.SECONDS);  // 延迟20秒兜底

// 4. 消费端：到点取，若 sendNum 已有值=线程池跑完，为空才重新解析
JSONObject delay = blockingDeque.take();
if (couponTaskMapper.selectById(delay.getLong("couponTaskId")).getSendNum() == null) {
    refreshCouponTaskSendNum(delay);   // 兜底重做
}
```
