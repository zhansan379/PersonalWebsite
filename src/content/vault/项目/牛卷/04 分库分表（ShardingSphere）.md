> 面试问分库分表，考察的不是"会不会配 ShardingSphere"，而是**你有没有"数据量到多大该拆 → 拆成几张表 → 按什么拆 → 拆完有哪些代价"这套完整决策链**。本文先把项目（牛券 oneCoupon）的技术路线讲清，再给面试回答主线、记忆锚点与被追问清单。

## 一、一句话定位

> 单表数据量大到影响读写性能后，按一定规则把一张表**水平**拆成多张、甚至分布到多个库，分散存储与读写压力。本项目用 **ShardingSphere** 把优惠券模板表按"店铺编号"分片到 2 库 × 8 表。

## 二、项目技术路线

### 1. 为什么拆（数据量估算）
- 电商渠道非官方数据：商家约 **3000 万**，每家平均创建 **100** 张券 → 优惠券模板表 **≈30亿** 数据量。
- 单表超过经验值 **2000 万**（不复杂 SQL、全走索引）就建议拆 → **30亿 ÷ 2000万 = 150 张表**
- > 取 2000 万是经验值：数据不多时约 3 次磁盘 IO 即可拿到，再多 IO 变多，且不利于数据库表备份。

### 2. 拆不拆库（并发决定）
- 优惠券模板**并发不高**（创建券是商家低频操作），所以**只分表、不分库**。
- 判断要不要分库：单 MySQL Server 写瓶颈实测约 **4000-5000 TPS**；若业务 TPS 到 **1 万**，就至少要分 2 个库。
- 本项目为便于演示/后续扩展，仍用 2 个库展示分库形态。

### 3. 按什么拆（分片键选择）
- 分片键三原则：**数据均匀性 / 业务关联性 / 数据不可变**。
- 分片键答案呼之欲出：**店铺编号 `shop_number`**——管理的查询都是"按当前店铺分页查自己创建的券"，天然适合承载。
**分片键（Sharding Key）**：就是用来决定一条数据落到哪个分片（哪个库 / 哪张表）的字段。 分片中间件（Sharding‑Sphere 等）根据分片键的值，通过分片算法（取模、范围、哈希），计算出这条数据路由到哪个分片。 例：以`user_id`作为分片键，`user_id % 4`，id=10 的数据就落到分片 2。


### 4. 用什么拆（框架选型）
- **ShardingSphere**（Apache 顶级，社区活跃、分片策略全：范围/哈希/复合）> **MyCat**（社区小、基础策略）为主流选择。
- **不用分布式数据库**（TiDB / PolarDB / TDSQL）三大理由：
  - 兼容性：部分不能 100% 兼容 MySQL，业务无法平滑迁移；
  - 技术储备：线上出问题缺专家兜底；
  - 使用成本：阿里/腾讯无开源版、付费高出 MySQL 一大截；TiDB 开源版 bug 多。

### 5. 拆完踩了什么坑（分片不均匀）
- 用默认 **HashMod**：`库 = hash(shop_number) % 库数`、`表 = hash(shop_number) % 表数`。因 shop_number 的 hash 值奇偶已定，导致 **0 库奇数表空、1 库偶数表空**，数据严重倾斜。
- 解法：自定义分片算法（`CLASS_BASED`），用 `hash % 16 / (16/2)` 的**扰动式取模**把奇偶先混合再分摊到库和表，5 万条 Mock 数据验证无明显倾斜。

### 6. 拆完的代价（读扩散）
- 查询**不带分片键**时节节点：ShardingSphere 会把 SQL 用 `UNION ALL` 广播到所有库所有表再合并 → **读扩散**，极端情况性能深渊。
- 结论：**业务查询必须带上分片键 `shop_number`**。

## 三、面试回答主线（三段式 + 一个流程图）

**1. 先回答"为什么拆 + 拆到什么程度"**
> 单表数据量大了（本项目估算 30 亿）读写变慢，按经验阈值 2000 万拆成 150 张表；是否分库看并发（单实例约 4000-5000 写 TPS）。

**2. 再回答"按什么拆 + 用谁来拆"**
> 分片键选 shop_number（均匀+业务关联+不可变），框架用 ShardingSphere（社区与策略优于 MyCat，且不贸然上分布式数据库）。

**3. 最后主动暴露"拆完的坑"**（面试加分点）
> HashMod 会因奇偶导致分片倾斜 → 自定义扰动算法解决；查询不带分片键会读扩散 → 强制带分片键。**主动说坑，比被问才答高一个段位。**

## 四、必须能说出的记忆锚点

1. **经验值**：单表 2000 万、单 MySQL 约 4000-5000 写 TPS。
2. **分片键三原则**：均匀 / 业务关联 / 不可变。
3. **分片算法两种**：HashMod（均匀）vs 时间范围（有热不均）。
4. **选型一句话**：ShardingSphere > MyCat；分布式数据库有三座大山（兼容/储备/成本）。
5. **分片不均匀根源**：分片键 hash 后奇偶锁定，模数没法打散 → 需扰动哈希（`hash % 16 / (16/2)`）。
6. **读扩散**：不带分片键 → `UNION ALL` 广播全库全表。

## 五、被追问清单（面试官会往这打）

### Q1：为什么 2000 万就拆？有什么依据？
**答**：是经验值而非硬性标准。数据少时索引查询约 **3 次磁盘 IO** 就能命中；再大会让 B+Tree 层数变高、IO 增多，且**单表过大不利于备份、DDL、归档**。具体阈值要结合**行大小**（每行太多 TEXT/BLOB 就应更早拆）压测来定。面试要说"2000 万是业界参考，不是绝对"，比悠悠背一个数字更专业。

### Q2：分片键选错了会有什么后果？为什么 `shop_number` 合适？
**答**：分片键决定数据能否**精准定位单表**。选错会导致大量请求必须广播（读扩散）或跨片查询。`shop_number` 合适因为①管理查询天然按店铺过滤、②商家数据相对均匀、③店铺编号不会变。对应**均匀/关联/不可变**三原则。

### Q3：分片不均匀了怎么办？（项目里的坑，必背）
**答**：
- 现象：HashMod 下 shop_number 取模后奇偶锁定，表/库出现"一半空一半满"。
- 根因：库表和分片键的模数关系固定，无法打散奇偶。
- 解法：**自定义扰动分片算法**——先用一个更大的模 `hash % 16`，再除以「每库表数 `16/2`」落库，把奇偶先混合再均匀分摊；并用 Mock 大数据量（5 万）验证倾斜度。

### Q4：查询不带分片键会怎样？（读扩散）
**答**：ShardingSphere 无法定位单表，只能把 SQL 广播到**所有库的所有表**，用 `UNION ALL` 合并结果 → **读扩散**。分片越多扩散越狠，高并发下是性能深渊。所以**业务侧强制要求所有查询带上分片键**；实在不能带的场景考虑**冗余表/ES/汇总层**。

### Q5：MyCat 和 ShardingSphere 怎么选？为什么不用分布式数据库？
**答**：
- MyCat：社区小、更新慢、只支持水平分表+垂直分库/基础分片策略。
- ShardingSphere：Apache 顶级项目、社区活跃、支持范围/哈希/复合分片，JDBC 层代理侵入小。
- 分布式数据库（TiDB 等）三大顾虑：**兼容性**（非 100% MySQL，迁移不平滑）、**技术储备**（线上问题缺专家）、**使用成本**（云厂商闭源贵、开源版 bug 多）。**中小团队自建 sharding proxy 往往比整套分布式 DB 更可控。**

### Q6：分库分表后会带来哪些新问题？（加分题，考你是否真做过）
**答**：
- **跨分片 JOIN 不支持/性能差** → 尽量冗余字段、反范式、或在应用层聚合/用 ES。
- **分布式事务变难** → 用 TCC/最终一致性/本地消息表，不能再依赖单库事务。
- **全局唯一 ID** → 不能用自增，改用雪花算法/号段。
- **扩容是最大痛点** → 固定 mod 后扩表需**哈希迁移**或一致性哈希/基因法（推荐回答"基因法"和"新增从库+读流量切换"两种平滑扩容思路）。
- **数据倾斜** → 看 Q3。

### Q7：扩容时原来取模的规则变了，历史数据怎么办？
**答**：三种主流思路——
- **哈希（mod）重分布**：最直接但全量迁移、停机风险大。
- **一致性哈希**：加节点只影响附近少部分 key，但引入虚拟节点与数据分布控制复杂度。
- **基因法（推荐项目答案）**：分片键末尾带"基因位"，扩容时**只用原表数取模定位，新表走新的余数规则**，实现**增量扩容、历史数据零迁移**。高并发分布式场景常用。

### Q8：能不能不分库分表，用别的方式抗大表？
**答**（考察批判性，避免被"动不动就分表"带偏）：数据量还没到阈值时先做——**索引优化、归档冷热分离、历史大表分表/分区、读写分离**；真到单表瓶颈才上分库分表，因为**分库分表是最后手段，代价最大**（JOIN/事务/ID/扩容全变复杂）。**面试加分：说出"能通过归档和分区解决的，就不值得上分库分表"。**

## 六、代码配置记忆模板（背这版即可）

```yaml
rules:
  - !SHARDING
    tables:
      t_coupon_template:
        actualDataNodes: ds_${0..1}.t_coupon_template_${0..7}  # 逻辑表 → 2库×8表
        databaseStrategy:      # 分库：standard 单分片键
          standard:
            shardingColumn: shop_number          # 分片键 = 店铺编号
            shardingAlgorithmName: coupon_db_mod
        tableStrategy:         # 分表同理
          standard:
            shardingColumn: shop_number
            shardingAlgorithmName: coupon_tbl_mod
    shardingAlgorithms:
      coupon_db_mod:
        type: CLASS_BASED      # 默认 HASH_MOD 会奇偶倾斜，改用自定义扰动算法
        props:
          algorithmClassName: com.xxx.DBHashModShardingAlgorithm
          sharding-count: 16
          strategy: standard
```
