# ragent 线程池使用规范与设计思想

> 这是 ragent 项目**并发模型背后的设计思想**（而非具体配置清单）：四条核心约定 + 每一步"为什么这样做"的动机。核心是**按业务形态选并发工具**——RAG 是「单请求 → 多并行子任务 → 汇总」的扇出-扇入结构，所以用 `CompletableFuture` 统一提交；是分布式可观测系统，所以线程池统一经 TTL 包装跨线程透传 trace；按业务失败语义分两派选队列/拒绝策略；统一优雅停机。供后续引入新并发场景时保持一致。

## 一、这是什么

这是 ragent 项目线程池相关代码梳理出的**设计原则层**总结。与之相对的是"具体实现层"（每个池的 bean 名、核心/最大线程数、队列、调用点等），本页只保留**可复用、可迁移的设计思想**：四条核心约定是什么、以及分别"为什么这样做"。遵循这些约定，后续新增并发场景时就能与现有代码保持同一套心智模型。

## 二、核心内容：四条核心约定 + 设计动机

### 约定 1 · 业务线程池统一集中配置，并经 TTL 包装

- 所有业务线程池在**一处集中声明**，统一经 `TtlExecutors` 包装 + 具名线程工厂。
- **动机（跨线程上下文）**：ragent 是分布式、可观测系统，traceId 需贯穿一次请求的完整日志；而 `CompletableFuture` 在线程切换处会丢失 `ThreadLocal`。对策是**每个池都经 TTL 包装** + 用 `TransmittableThreadLocal` 存 trace 上下文，让子任务继承父任务的 traceId/用户上下文，汇聚成完整 trace。
- 关键认识：**「集中配置 + TTL 包装 + CompletableFuture 提交」三者配套、缺一不可**。只集中配置而不 TTL，跨线程仍丢上下文；只 TTL 而不统一提交，也无法覆盖扇出-扇入。

### 约定 2 · 任务提交统一走 CompletableFuture

- 提交统一用 `CompletableFuture.supplyAsync/runAsync`，并**显式传入线程池**，不用裸 `Executor.submit/execute`（全项目仅限流器通知分发一类"火射即弃、无需结果"的场景例外）。
- **动机（扇出-扇入编排）**：RAG 检索、意图识别、记忆加载都是「单请求 → 并行拆成多个子任务 → 汇总聚合」的扇出-扇入形态。这类需求要**拿结果 + 组合 + 异常传递**：
  - 裸 `execute()` 拿不到结果；
  - 普通 `Future`（submit 返回）无法表达多结果组合；
  - `CompletableFuture` 的 `supplyAsync + join / allOf / whenComplete` 恰好覆盖「扇出-扇入 + 异常传递 + 拒绝兜底」三类需求。

### 约定 3 · 队列/拒绝策略按"业务失败语义"分两派

| 风格                                     | 适用业务                                  | 设计理由                                                   |
| :------------------------------------- | :------------------------------------ | :----------------------------------------------------- |
| `SynchronousQueue + CallerRunsPolicy`  | 检索 / 意图 / 记忆加载等**子任务结果必须 join 返回**的场景 | 「给池执行还是回落调用线程执行」差别不大；宁可扩线程或让调用者亲跑，也**不让请求失败**          |
| 有界 `LinkedBlockingQueue + AbortPolicy` | 流式输出 / SSE 入口 / 分块等**调用者不能被阻塞**的场景    | 调用者（如 Tomcat 线程）不能阻塞在池里；缓冲满时**快速失败**，把压力**上交限流器**做优雅降级 |

- **关键认识**：先问"这个任务的失败语义是什么"再选队列策略，而不是拍脑袋填参数。可回落的 → CallerRuns 兜底；必须快速失败、可被降级的 → Abort 上抛。
- **易混淆提醒**：名字带 `Executor` 的类很多（路由、工具执行器等）多是**顺序执行的业务执行器，并不使用线程池**——不要仅凭类名判断它是并发组件。

### 约定 4 · 统一优雅停机 + 协作式中断

- 关闭统一走优雅停机，绝不使用已废弃/危险的 `Thread.stop()`。
- **动机**：MinerU 轮询、调度锁心跳、限流等存在**跨请求的进行中任务**，强杀会打断业务，所以要给正常任务留收尾时间。
- 配套规范：`catch (InterruptedException)` 后**恢复 `Thread.currentThread().interrupt()` 标记**，保证中断状态不丢失。
- 调度类长驻线程用**守护线程 + 具名工厂**，既不阻塞 JVM 退出，又便于日志定位。

## 三、如何应用：引入新并发场景时的约定

> 下面 6 条是"新代码怎么保持一致"的可操作性结论，直接迁移到任何新并发场景。

1. **先复用已有池**，不要新建裸池；确需新池时优先在**集中配置处**声明，并 TTL 包装 + 具名线程工厂。
2. **提交统一用 `CompletableFuture`** 并显式传 executor；需要聚合用 `join` / `allOf`，异常传递在 future 上处理。
3. **按失败语义选队列/拒绝策略**：结果必须返回且可回落的用 `CallerRunsPolicy`；绝不能阻塞调用者且压力可上交限流器的用 `AbortPolicy`。
4. **停机统一走优雅停机模板**（shutdown → 宽限探测 → shutdownNow 兜底），`catch` 中断后恢复 `interrupt()` 标记。
5. **不能裸 `Executor.execute/submit` 提交**（除"火射即弃、无需结果"的例外场景）。
6. **守护线程**是长驻调度线程的默认选择，避免阻塞 JVM 退出。
