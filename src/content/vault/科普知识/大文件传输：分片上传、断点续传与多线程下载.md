> 大文件传输的完整图景：**上传**（前端分片 + 断点续传）↔ **下载**（HTTP Range + 多线程 IDM 式下载）↔ **存储**（S3 Multipart / MinIO / RustFS），三者在协议层与工程上是同构的——都是"**切片 → 独立传输 → 合并**"的思想在不同层的体现。

## 一、为什么大文件传输是个问题

小文件上传下载很简单，一个 HTTP 请求搞定。但文件一大，问题就来了：

- **请求超时**：网关、Nginx、浏览器都有超时限制，一个几百 MB 的文件很难在一个请求里传完
- **网络波动**：传了 90% 断线，单体传输只能从头再来，前功尽弃
- **内存压力**：整个文件读进内存再发，客户端和服务端都吃不消
- **并发受限**：单连接单线程，带宽利用率低

吐槽一句：阿里云套餐固定带宽改为流量计费，然后想要再改回固定带宽，居然还要花钱！！！！

解决思路可以浓缩成三个关键词：

| 关键词 | 解决什么 |
|---|---|
| **分片（chunk）** | 太大 → 切小，化整为零 |
| **断点续传（resume）** | 怕断 → 记进度，断了接着来 |
| **并行（parallel）** | 太慢 → 多路并发，吃满带宽 |

## 二、核心概念与协议基础

### 2.1 三个核心概念

- **分片**：把文件按固定大小（如 5MB）切成多个块，每块独立传输
- **断点续传**：记录已完成的进度，中断后从断点继续，而非从头开始
- **秒传**：先算文件 hash 发给服务端比对，服务端已有相同文件则直接返回成功，跳过传输

### 2.2 HTTP/1.1 Range 请求

断点续传和多线程下载在协议层的根基就是 HTTP/1.1 的 **Range 请求**（RFC 7233）。它允许客户端只请求资源的一部分字节。

一次完整的 Range 请求/响应：

```http
GET /bigfile.zip HTTP/1.1
Host: example.com
Range: bytes=1048576-2097151
```

```http
HTTP/1.1 206 Partial Content
Content-Length: 1048576
Content-Range: bytes 1048576-2097151/10485760
Accept-Ranges: bytes
ETag: "abc123"
```

四个关键头：

| 头 | 方向 | 作用 |
|---|---|---|
| `Range: bytes=start-end` | 请求 | 指定要下载的字节区间（左闭右闭，可省略一端） |
| `206 Partial Content` | 响应 | 状态码，表示返回的是部分内容 |
| `Content-Range: bytes start-end/total` | 响应 | 说明本次返回的区间及资源总大小 |
| `Accept-Ranges: bytes` | 响应 | 服务端声明自己支持 Range（值为 `none` 或不返回则不支持） |

补充要点：

- 可以用 `HEAD` 请求先探测：看响应里有没有 `Accept-Ranges: bytes`，并拿到 `Content-Length`（总大小），这是多线程下载分段的前提
- 续传时应配合 **`If-Range`**（携带上次的 `ETag` 或 `Last-Modified`）：若文件在中途被改过，服务端返回 200 全量内容而非 206，避免拼出一个新旧混合的坏文件
- Range 也支持一次请求多段（`Range: bytes=0-99,200-299`），响应为 `multipart/byteranges`，但实际下载器很少用

## 三、大文件上传：前端分片上传

整体流程一句话：**切片 → 计算唯一标识（md5）→ 逐片上传 → 服务端记录 → 全部到齐后合并**。

```js
// 1. 切片
const CHUNK_SIZE = 5 * 1024 * 1024; // 5MB 一片
const chunks = [];
for (let start = 0; start < file.size; start += CHUNK_SIZE) {
  chunks.push(file.slice(start, start + CHUNK_SIZE));
}

// 2. md5 放 Web Worker 里算，避免阻塞主线程（大文件算 hash 很耗时）
// 3. 并发控制：请求池，最多同时 N 个分片在传
async function uploadWithPool(tasks, limit = 3) {
  const pool = new Set();
  for (const task of tasks) {
    const p = task().finally(() => pool.delete(p));
    pool.add(p);
    if (pool.size >= limit) await Promise.race(pool);
  }
  await Promise.all(pool);
}
```

工程细节清单：

- **并发控制**：请求池限制并发数（常见 3~6），避免瞬间几百个请求打满浏览器连接
- **失败重试**：单个分片失败只重传该片，带指数退避
- **进度持久化**：`md5 + 已传分片序号` 存 localStorage，刷新页面后先问服务端"这个 md5 传了哪些片"（ListParts 思路），跳过已传部分
- **暂停**：`xhr.abort()` 中断在传请求，恢复时从未传分片继续
- **秒传**：上传前先发 md5 比对，命中则秒过

详细实现与面试答法见 [[wiki/编程/前端开发/JavaScript/07 工程实战与安全/面试官：大文件上传如何做断点续传？|面试官：大文件上传如何做断点续传？]]，本节只做主线串联。

## 四、大文件下载：Range 与多线程下载

### 4.1 断点续传下载

思路与上传对称：**记录已下载的字节数，中断后用 Range 从断点继续**。

```js
// downloaded = 本地已持久化的已下载字节数
const res = await fetch(url, {
  headers: {
    Range: `bytes=${downloaded}-`,
    'If-Range': lastETag, // 文件变了就退回 200 全量重下
  },
});
// 206 → 追加写入本地；200 → 文件已变化，从头重下
```

### 4.2 多线程下载原理（IDM / aria2）

IDM（Internet Download Manager）、aria2 这类下载器的"加速"并不神秘，核心就是**把一个文件拆成多段，每段一个连接并发 Range 下载，最后合并**：

```
1. HEAD 请求：拿 Content-Length（总大小）+ 确认 Accept-Ranges: bytes
2. 分段：总大小 ÷ 线程数 N，算出每段的 [start, end]
3. 并发：N 个连接各自 Range: bytes=start-end 下载自己的段
4. 合并：各段完成后按偏移量拼成完整文件（或预分配文件按偏移随机写入）
```

要点与限制：

- **前提**：服务端必须支持 Range（`Accept-Ranges: bytes`），否则只能单线程全量下
- **不适用**：动态内容（接口实时生成、gzip 压缩响应）——`Content-Encoding` 会改变字节布局，字节区间失去意义
- **加速的本质**：绕过单连接的 TCP 拥塞控制与服务器单连接限速，吃满客户端带宽；对阿里云那种按固定带宽计费的小水管无效（瓶颈在服务端出口）
- **动态分段**：IDM 会监控各段速度，把慢段再切小分给空闲线程，避免"最后一个慢线程拖全局"
- **浏览器端**：没有原生多连接下载 API，可用 Streams API + 多个 fetch(Range) + Service Worker 拼接做近似实现，但落地复杂、收益有限，所以网盘都要你做客户端

### 4.3 文件磁盘缓存问题

多线程分片下载到浏览器后还有一个现实问题：**刷新网页，已下载的分片就没了**。若想"边下载边落盘"、获得类似网盘客户端的体验（关了明天接着下），有三种思路：

| 方案 | 思路 | 缺点 |
|---|---|---|
| IndexedDB 存储 | 分片持久化在浏览器，刷新甚至关闭网页后已下载分片不丢失 | 写入速度慢，分片下载时同步写入会让**下载时长翻倍以上**；大文件存储还可能拖累浏览器运行 |
| FileSystem API（OPFS / showDirectoryPicker） | 浏览器直接申请文件夹权限进行读写 | 交互体验差、API 兼容性差（Chrome 系为主）；一次性写入可行，**分片读写能力有待探索** |
| Electron 客户端 | 直接操作 Node 进行文件读写 | 理想情况下的**最佳方式**（真正的流式写盘、断点持久化），但脱离了纯 Web 形态 |

一句话：**纯浏览器想做"网盘式下载"目前处处受限，这也是为什么百度网盘、阿里云盘都推桌面客户端**——Electron 方案本质上就是把 Node 的文件能力搬进"浏览器"。

## 五、服务端视角：S3 Multipart Upload

分片上传不是前端的专利——S3 对象存储把"分片"做成了一等公民 API，即 **Multipart Upload**。前端的分片上传方案，很多就是对着这套协议设计的。

### 5.1 三步核心流程

```
1. CreateMultipartUpload      → 拿到 uploadId（本次上传任务的唯一标识）
2. UploadPart × N             → 每片带 uploadId + partNumber 上传，各自返回 ETag
3. CompleteMultipartUpload    → 提交 [partNumber, ETag] 完整列表，服务端按序合并
```

配套接口：

- `AbortMultipartUpload`：**主动中止并清理已上传的分片**。已传未合并的分片不会出现在对象列表里，但**照样计存储费**——任务放弃时必须 Abort，否则存储费悄悄泄漏（也可配生命周期规则自动清理）
- `ListParts`：列出某 uploadId 已成功的分片——**断点续传时问它"我传到第几片了"**
- `ListMultipartUploads`：列出所有未完成的任务

### 5.2 关键约束与细节

| 约束 | 值 |
|---|---|
| 分片大小 | 5MB ~ 5GB（**最后一片除外**，可小于 5MB） |
| 分片数量 | 最多 10000 片 |
| 单对象上限 | 5TB |

- **ETag 校验**：每个分片上传后返回的 ETag 是该片的 MD5，Complete 时必须把全部分片的 ETag 按序提交，服务端逐片校验后合并——ETag 列表错了合并直接失败
- **合并后的对象 ETag 不是纯 MD5**：格式为 `分片MD5拼接后再MD5-分片数`（如 `xxx-3`），所以不能直接拿它跟本地文件 MD5 比对验完整性
- **预签名 URL 直传**：业务后端用密钥对每一步（Initiate、每个 Part、Complete）生成带签名的临时 URL，客户端拿着 URL 直连 S3 上传，**文件流量不经过业务服务器**（详见第七节方案 B）

## 六、S3 兼容的开源对象存储：MinIO 与 RustFS

S3 协议已成对象存储的事实标准，自建场景下有两个主流的开源 S3 兼容实现。

### 6.1 MinIO

- Go 实现的高性能分布式对象存储，**S3 兼容的事实标准**，绝大多数 S3 SDK 开箱即用
- 单机一行命令就能起，也支持分布式纠删码部署
- **注意许可证**：社区版为 **AGPLv3**，商用闭源集成有合规风险（需买商业许可）；且近年社区版功能有所收缩（管理控制台精简），部分能力转向付费版

```bash
docker run -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=admin -e MINIO_ROOT_PASSWORD=password \
  minio/minio server /data --console-address ":9001"
```

### 6.2 RustFS

- Rust 实现的新兴 S3 兼容对象存储（2024 年起开源），对标 MinIO
- **Apache 2.0 许可证**——这是它相对 MinIO 社区版最大的合规优势，商用无 copyleft 顾虑
- 卖点：Rust 带来的低内存占用与高性能，轻量部署
- 短板：项目年轻、生态和生产案例少，核心存储引擎的稳定性需要时间验证

```bash
docker run -p 9000:9000 rustfs/rustfs
```

### 6.3 选型对比

| 维度 | MinIO | RustFS |
|---|---|---|
| 实现语言 | Go | Rust |
| 许可证 | **AGPLv3**（社区版） | **Apache 2.0** |
| 成熟度 | 高，生产验证充分 | 新兴项目，生产案例少 |
| 性能/资源占用 | 性能好，内存占用中等 | 官方宣称更低内存占用（需自行压测验证） |
| 生态/社区 | SDK 全、文档全、社区大 | 生态建设中，基本兼容 S3 SDK |
| 适用场景 | 生产自建对象存储的默认选择 | 对许可证敏感、愿意尝新的团队；边缘/资源受限场景 |

## 七、端到端实战的三种架构方案

### 方案 A：业务服务器中转（最简单）

```
前端分片 → 业务后端 → 转发到 MinIO/RustFS（multipart）
```

- 优点：后端完全掌控（鉴权、病毒扫描、进度入库），前端逻辑简单
- 缺点：文件流量全部经过业务服务器，带宽和连接数压力大，大文件场景是瓶颈
- 适合：内网系统、文件量不大、需要严格审核的场景

### 方案 B：预签名 URL 直传（主流推荐）

```
前端 ←申请预签名→ 业务后端（只签发，不过流量）
前端 →直传分片→ MinIO/RustFS（multipart）
```

- 优点：业务服务器零文件流量，只负责鉴权和签发；客户端直连存储，可分片并行
- 缺点：前后端交互复杂（Initiate → 逐片签名 → Complete 三步都要协调）；断点状态（uploadId + 已传分片）需前端持久化或后端记录
- 适合：公网大文件、流量大的场景——也是 AWS 官方推荐模式

### 方案 C：tus 协议（标准化断点续传）

```
前端（tus 客户端，如 Uppy）→ tus 服务端（tusd，可接 S3/MinIO 后端）
```

- 优点：断点续传、暂停恢复、并发都是协议内置的，不用自己造轮子；tusd 可直接以 S3 为存储后端
- 缺点：引入额外组件和协议约束，定制自由度低，生态较小众
- 适合：想快速获得生产级断点续传能力、不愿自研细节的团队

### 三方案对比与选型

| | A 业务中转 | B 预签名直传 | C tus 协议 |
|---|---|---|---|
| 服务器流量 | 全量经过 | 零文件流量 | 经过 tusd |
| 前后端复杂度 | 低 | 高 | 中（协议内置） |
| 断点续传 | 自己实现 | 自己实现 | 开箱即用 |
| 适用 | 内网/小流量/强审核 | 公网大流量（推荐） | 快速落地、不想自研 |
