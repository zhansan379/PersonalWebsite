> 一句话概述：**互联网是基础设施，Web 是跑在它上面的服务**。计算机经交换机→路由器→ISP 连成互联网；用**域名**代替难记的 IP（靠 DNS 翻译）；用 **URL** 精确定位资源；**Web 服务器**（硬件 + HTTP 软件）接收浏览器请求并返回网页。

## 一、互联网是如何工作的

**互联网是把计算机互相连接起来的巨大网络**，是 Web 的支柱。它始于 1960 年代美国军方资助的研究项目，1980 年代演变为公共基础设施。技术在变，但工作方式没变：**确保所有计算机保持连接，无论发生什么**。

### 1. 从两台电脑到一张网

- **两台计算机**通信：一根网线（或 WiFi/蓝牙）直连即可。
- **十台计算机**两两直连需要 45 条网线——不可行。于是引入**交换机（switch）**：它像火车站调度员，确保一台计算机发出的消息只到达目标计算机。每台电脑只需一条线连到交换机。
- **成百上千个网络**互连：不能把交换机无限级联（路径长、单点故障导致大面积断网）。于是把每个网络保持小规模，用**路由器（router）**连接各个网络——它像邮局，读取数据包的收件地址，直接转发给正确的网络。
- 路由器之间借用已有的**电话网络**基础设施连接，需要**调制解调器（modem）**把网络消息转成电话设施可处理的形式（家用"路由器"通常集成了交换机+路由器+调制解调器三合一）。
- 最后通过 **ISP（互联网服务提供商）**接入互联网：ISP 管理着彼此互连、并能访问其他 ISP 路由器的特殊路由器。你的消息经由 ISP 的网络层层接力到达目标网络——**整个互联网就是由这样的网络基础设施构成的**。

一句话：中国ISP就是在中国境内提供互联网接入的运营商，核心是中国移动、中国电信、中国联通、中国广电四家基础运营商。
中国的公网IP是谁给的？
公网IP不是“中国自己造”的，而是按全球互联网注册体系逐级分配：IANA → APNIC（亚太）→ CNNIC / 国内各大ISP → 最终用户。
所以，你家的公网IP最终是运营商分配给你的；国家层面的地址块主要由CNNIC和三大运营商等从APNIC获得。

```
电脑 → 交换机（局域网内分发）→ 路由器（跨网络转发）→ 调制解调器（接入电话设施）→ ISP（骨干网络）→ 目标网络
```

### 2. 如何找到一台计算机：IP 地址与域名

- 每台连网计算机有唯一地址——**IP 地址**（如 `192.0.2.172`）。
- IP 对人难记且会变，于是用**域名**（如 `google.com`）作为可读别名，由 DNS 系统把域名翻译成 IP。

### 3. 互联网 ≠ Web

- **互联网是基础设施**（连接计算机的技术）；**Web 是建立在其上的服务**——互联网上的部分计算机（Web 服务器）能发送浏览器可以理解的信息。
- 互联网上还跑着其他服务：邮箱、IRC 等。
- 顺带区分：**内联网（Intranet）**是组织内部专用网络；**外联网（Extranet）**把专用网络部分开放给合作组织。两者与互联网跑在相同的基础设施和协议上。

## 二、域名：人类可读的地址

### 1. 域名的结构（从右往左读）

以 `developer.mozilla.org` 为例：

| 部分 | 名称 | 说明 |
| :--- | :--- | :--- |
| `.org` | **TLD（顶级域名）** | 表明服务的一般目的。`.com/.org/.net` 无特殊要求；`.gov` 仅政府、`.edu` 仅教育机构；`.us/.fr` 等地区域名可能要求当地托管 |
| `mozilla` | **二级域名（SLD）/ 标签** | 紧挨 TLD 的标签，1–63 个字符（字母、数字、`-`，`-` 不能在首尾），大小写不敏感 |
| `developer` | **子域名** | 域名持有者可自由创建（如 `developer.mozilla.org`、`iot.mozilla.org`），标签数量没有强制上限 |

### 2. 域名不是"买"的，是"租"的

- 你不能真正拥有一个域名，只能花钱获得**一年或多年的使用权**（续期优先于他人申请）——这样未使用的域名最终能回到市场。
- **域名注册商**负责登记你和域名的技术与管理信息。
- 查域名是否可用：注册商网站的 whois 服务，或命令行：

```bash
whois mozilla.org        # 已注册：返回注册人、到期时间等详细信息
whois afunkydomainname.org   # 未注册：返回 NOT FOUND，可以申请
```

### 3. DNS 请求如何工作

在浏览器输入 `mozilla.org` 后：

1. 浏览器先查**本地 DNS 缓存**，命中则直接拿到 IP，结束。
2. 未命中则询问 **DNS 服务器**，由它告诉你该域名对应的 IP。
3. 拿到 IP 后，浏览器与 Web 服务器开始协商内容。

> DNS 数据分布在全球服务器上，注册信息的变更需要一段时间才能刷新到所有服务器（这就是改 DNS 后要"等生效"的原因）。

## 三、URL：资源的精确地址

**URL（统一资源定位符）是互联网中唯一资源的地址**，是浏览器检索资源（HTML、CSS、图片等）的关键机制。一个 URL 的完整结构：

```
https://www.example.com:80/path/to/myfile.html?key1=value1&key2=value2#SomewhereInTheDocument
\___/   \______________/ \__/ \________________/ \___________________/ \___________________/
 方案        域名        端口        路径                参数                     锚点
 \________________________/
          权威
```

| 部分 | 必须？ | 说明 | 邮寄地址类比 |
| :--- | :--- | :--- | :--- |
| **方案（scheme）** | ✅ | 请求资源用的协议，网站通常是 `https`（或 `http`）；浏览器也认识 `mailto:` 等 | 用哪家邮政服务 |
| **域名** | ✅ | 指示被请求的 Web 服务器（也可用 IP，但少见） | 城市 |
| **端口（port）** | 可省略 | 服务器的技术"门户"。HTTP=80、HTTPS=443 为标准端口时省略 | 邮编 |
| **路径（path）** | ✅ | 服务器上资源的位置。早期对应物理文件，如今多是服务器处理的抽象 | 哪栋楼 |
| **参数（query）** | 可选 | `?key=value&…`，键值对，服务器可用它做额外处理（如搜索词） | 公寓号 |
| **锚点（fragment）** | 可选 | `#` 后的**片段标识符**，是资源内部的"书签"；**不会发送给服务器**，由浏览器自行定位 | 收信人 |

### 绝对 URL 与相对 URL

- **绝对 URL**：包含定位资源的全部必要部分（如地址栏里输入的）。
- **相对 URL**：浏览器用当前文档的 URL 补全缺失部分。假设当前文档是 `https://developer.mozilla.org/zh-CN/docs/Learn`：

| 写法 | 类型 | 浏览器解析结果 |
| :--- | :--- | :--- |
| `//developer.mozilla.org/zh-CN/docs/Learn` | 方案相对 | 沿用当前协议 |
| `/zh-CN/docs/Learn` | 域相对（以 `/` 开头） | 沿用当前协议+域名，从站点根目录取 |
| `Common_questions/Web_mechanics/What_is_a_URL` | 子资源（不以 `/` 开头） | 拼到当前目录下 |
| `../CSS/display` | 返回上级（`..`） | 解析为 `.../zh-CN/docs/CSS/display` |
| `#语义_url` | 仅锚点 | 当前文档内跳转 |

**最佳实践：语义 URL**——用有含义的单词而非随机字符（易操作、让用户知道自己在哪、利于搜索引擎分类）。

## 四、Web 服务器：硬件与软件的合体

"Web 服务器"一词可指硬件、软件，或二者协同的整体：

1. **硬件**：一台存储了网站文件（HTML、CSS、JS、图片）和服务器软件、接入互联网的计算机。
2. **软件**：至少是一台 **HTTP 服务器**——能理解 URL 和 HTTP 协议，通过域名被访问，把托管内容传给用户设备。

**一次请求的流程**：浏览器通过 HTTP 请求文件 → 请求到达正确的服务器（硬件）→ HTTP 服务器（软件）检查 URL 是否匹配现存文件 → 匹配则返回文件；不匹配则看是否动态生成；两者都不行则返回错误（最著名的是 `404 Not Found`）。

**HTTP 的两个特点**：

- **文本化**：命令是纯文本、人类可读的。
- **无状态**：服务器和客户端都不记住之前的交流（记不住你的密码、业务进度——那是应用服务器的事）。
- 只有客户端发请求、服务器必须应答（至少回一个错误）；请求文件必须提供 URL。

### 静态服务器 vs 动态服务器

| | 静态 Web 服务器 | 动态 Web 服务器 |
| :--- | :--- | :--- |
| 组成 | 计算机 + HTTP 服务器 | 静态服务器 + 应用服务器 + 数据库 |
| 工作方式 | 把托管文件"**保持原样**"传给浏览器 | 应用服务器先**更新/生成**内容（如用数据库填充 HTML 模板）再传给浏览器 |
| 典型形态 | URL 直接对应文件路径，内容固定 | `/product?id=123`、按用户/参数生成 |
| 代表 | 纯静态站点 | MDN、维基百科（几个模板 + 巨大数据库，而非成千上万的静态页面） |

> 自建网站通常把文件托管在专用服务器上：始终在线、始终联网、有固定 IP、由第三方维护。

## 五、延伸：静态还是动态，对爬虫意味着什么

关键不在服务器软件是 Nginx 还是 Apache，而在于**请求后拿到的内容是现成文件还是后端临时生成的**：

- **静态网站**通常更好爬：`requests.get()` 拿 HTML 直接解析；分页是固定链接。但注意有些静态站也用 JS 异步加载数据。
- **动态网站**更复杂：要处理 GET/POST 参数、headers/cookies/token，可能要登录、过验证码、处理 CSRF 和频率限制；内容可能不在初始 HTML 里，需抓包找 API 或用 Playwright/Selenium 渲染。
- 但如果动态站直接暴露 JSON API，反而比解析 HTML 更简单。

**爬虫真正关心的四件事**：① 数据在不在初始 HTML 里；② 请求能不能直接构造；③ 有没有反爬；④ 返回 HTML 还是 JSON（JSON 更好解析）。

**快速判断三步**：查看网页源代码搜数据 → 搜得到多半可直接解析；开发者工具 Network 筛 XHR/Fetch → 找返回 JSON 的接口；禁用 JS 刷新 → 内容还在说明服务端返回了完整 HTML。

**实战原则**：能直接请求 API 就不要渲染页面；能解析 HTML 就不要开浏览器。
