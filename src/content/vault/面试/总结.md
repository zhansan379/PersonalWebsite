# 项目口稿

面试官最想听的不是你做了什么，而是遇到什么复杂问题 -> 为什么选这个方案 -> 如何权衡利弊 -> 最终怎么验证。

建议采用 **“总-分-总”的STAR叙事结构**

我是从两个方面去设计这个系统的，一方面是要保证系统的高并发和高可用，另一方面是解决如何搜的准。
就拿我之前看过的一些开源项目，graphrag来说，这种框架是通过图的方式来提高这个检索的精度。但在实际运行过程中，首先得能够抗住流量，比如说在deepseek刚上线或者同意千问出那个抢奶茶的活动时，就都有这个 “服务器繁忙，请稍后再试”的响应。同样的我为了实现高可用和高并发，在检索之前做了三件事，首先是幂等提交拦截，通过切面+注解，使用用户id实现了分布式锁限流。然后是通过信号量实现队列限流，确定说最多能有多少请求在处理，避免资源耗尽。最后就是通过TransmittableThreadLocal实现这个在线程池中的值传递一个Id，用来实现模型调用过程中的监控

> 基于 Redis 信号量 + ZSET + Pub/Sub 实现分布式排队限流，Lua 脚本保证原子性，支持公平排队与超时拒绝，SSE 实时推送队列状态。

> 基于 TTL + TtlExecutors 实现用户身份与 TraceId 跨线程透传，按业务域隔离 8+ 独立线程池（检索/重写/工具调用等），保障异步并发以及链路追踪完整性。

除此之外的话，还有三态熔断器实现的模型降级。这块的话是指说，假如说，请求的时候模块挂了，这时候系统并不知道说模型服务是否可用，还以为是模型还在响应，可能说有一个超时时间....

> 自研三态熔断器监控 LLM 模型健康度，结合优先级降级链 + 流式首包探测，故障自动切换备选模型用户无感，保障多模型混合调度高可用。

> ModelSelector 的选择算法分四步：确定首选 → 过滤禁用和不支持的候选 → 按首选优先 + priority 三级排序 → 熔断预过滤。每一步都有明确的职责
> 
> 为什么需要熔断器
> 
> 假设你的电商客服系统配了四个 Chat 模型：`qwen3-max`、`glm-4.7`、`qwen-plus`、`qwen3-local`。某天百炼平台出了故障，`qwen3-max` 连接超时。如果不做任何处理，每次用户提问都会先尝试调 `qwen3-max`，等 30 秒超时（或者直接失败），然后才切换到 `glm-4.7`。用户的每一个问题都要多等 30 秒——这显然不可接受。
> 
> 熔断器的作用就是：连续失败达到阈值后，直接标记这个模型为不可用，后续请求跳过它，不再白等。等一段冷却时间过去，再试探性地放一个请求过去看看恢复了没有。恢复了就重新启用，没恢复就继续熔断。

### 🎤 面试开场白（基于“防崩溃”视角，约 1.5 分钟）

> “面试官您好，关于这个智能客服项目，我想先说明我的**设计出发点**。
>
> 现在开源社区像 LlamaIndex、GraphRAG 解决得非常好的问题是 **‘检索准不准’**，这属于算法层面。但现实是，很多 AI 应用上线扛不住流量——就像 DeepSeek App 刚上线时的‘服务器繁忙’，或者千问抢奶茶活动时的瞬间崩溃。**如果服务都宕机了，检索得再准用户也访问不到。**
>
> 所以，我在设计这个项目时，**没有把精力花在调优 Embedding 或 Reranker 上（这些直接用成熟模型就行），而是把‘高并发下的稳定性’和‘高可用’当作架构的一等公民**。
>
> 基于这个出发点，我并没有照搬 LlamaIndex 那种单次调用的脚本写法，而是从头设计了一套 **‘管道-阀门’架构**。核心思路是：**在大模型这个昂贵且缓慢的资源前面，建三道防护坝，拦住突发流量，保证系统不雪崩，同时把有限的算力用在刀刃上。**”

---

### 🧠 接下来怎么把“高并发设计”揉进八阶段里（不要让面试官觉得你在背课文）

说完开场白，面试官肯定好奇你具体怎么做的。这时候不要平铺直叙八个阶段，而是**按“防御层级”来归类**，让面试官知道你心里有张“流量防护网”：

**第一层防线：流量入口（削峰填谷）**

> “我在 Service 层实现了 **队列式并发限流**。这就好比大模型推理是只有 3 个灶台的后厨，外面排了 100 个点餐的客人。
> - 我用 Redis 信号量严格控制同时进后厨炒菜（推理）的并发数；
> - 超出的请求在 Redis 里排队，设置最大等待超时。
> 
> 这就直接避免了像 DeepSeek 那种瞬时流量把 GPU 服务打挂的情况。**这在纯 Python 的 RAG 脚本里是绝对没有的，那是面向单用户的设计，我这是面向多租户生产环境的设计。**”

**第二层防线：中间逻辑（短路止损）**

> “光限流还不够，每个请求都去调大模型成本太高。所以我在流水线里设置了 **3 个短路点**，相当于‘快速通道’：
> 1. **歧义反问**：意图模糊时我不调大模型，直接反问用户，省掉一次昂贵的生成；
> 2. **纯闲聊直答**：用户说‘你好’，我直接跳过向量库检索，秒回；
> 3. **空结果兜底**：库没查到东西，我直接返回固定话术，**绝对不让模型瞎编，这既是为了准确率，也是为了节省 Token 费用**。
> 
> 这三个短路点让至少 30% 的请求不需要走完完整链路，极大地释放了后厨（GPU）的压力。”

**第三层防线：底层基建（可观测与防重）**

> “最后，在基建层面：
> - 我用分布式锁做 **幂等拦截**，防止用户手抖连点导致内存里写了两份一样的记忆，造成数据错乱；
> - 我接入了基于 `TransmittableThreadLocal` 的 **全链路 Trace**。在高并发异步线程池里，链路追踪经常断掉，我特意解决了跨线程传递的问题。这样一来，如果某次请求突然慢了 3 秒，我能精准定位是卡在了检索、MCP 工具调用，还是 LLM 生成，这是生产环境排障的生命线。”

### 🏁 结尾升华（回应“为什么不用开源现成的”）

最后一定要把这句话抛出来，彻底堵住面试官“你为什么不直接用 LangChain 或 LlamaIndex”的疑问：

> “所以，总结来说，**LlamaIndex 和 GraphRAG 解决的是‘能回答’的问题，我这个项目解决的是‘能扛住’和‘回答得稳’的问题。** 我参考了它们检索流程的合理性，但在架构上，我是按照互联网高并发微服务的标准去设计的。这也是我从 DeepSeek 和千问的故障中得到的启发——**算法决定体验的上限，但工程决定系统的生死。**”

### 💡 关键避坑提醒

- ✅ **一定要把“Redis 信号量”和“DeepSeek 繁忙”绑定起来说**，这会让面试官觉得你很有产品 Sense。
- ✅ **提到 `TransmittableThreadLocal` 时要加一句“解决异步线程池传递丢失问题”**，证明你懂 Java 并发的坑。
- ❌ **不要**把 GraphRAG 贬得一文不值，要承认它“检索准”的优势，只是侧重点不同（你可以说“我们互补”）。
- ✅ 如果面试官追问“你的限流队列如果积压太多怎么办？”，回答：设置超时熔断，返回友好提示“当前咨询人数较多，请稍后再试”，宁可牺牲这一次请求，也要保住整个服务的可用性。

把这个开头背熟，面试官立刻会意识到：**这小子不是来背八股文的，是真正上过生产战场，见过服务器冒烟的。** 加油！如果面试官追问具体某个限流或 Trace 的细节，你随时问我。
