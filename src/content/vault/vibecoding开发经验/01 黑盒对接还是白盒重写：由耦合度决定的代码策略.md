> 「要不要读源码」不由项目是开源还是公司项目决定，而由**功能与核心域的耦合度**决定。

## 一、这是什么

一个常见的困惑：在开源项目里做「Markdown 导入 / 图片导出」如鱼得水，几乎不用读源码；回到公司项目做「简历生成编辑」却寸步难行，读了源码还是改不动。

结论：差异的根因不是「读不读源码」，而是**功能在系统中的生态位**不同。

- 加「外挂」不需要看主机说明书。
- 改「内脏」必须先解剖。

## 二、核心内容

### 2.1 两类功能：附加型 vs 侵入型

| 维度 | 附加型功能 | 侵入型功能 |
|---|---|---|
| 典型例子 | MD 导入、图片导出 | 简历生成编辑器 |
| 位置 | 管道末端 | 心脏地带 |
| 边界 | 清晰的 Input / Output | 无边界，与数据模型/路由/权限交织 |
| 依赖形态 | 数据流经过 | 状态联动、生命周期耦合 |
| 类比 | 独立插件，插卡槽 | 在盖好的房子里砸承重墙改户型 |
| 代码策略 | **黑盒对接**（喂入口、取出口） | **白盒改造**（读透后重写） |

### 2.2 为什么开源项目「感觉不需要读源码」

不是因为开源，而是因为优秀项目提供了两个前提：

1. **约定大于配置**：扩展点（Extension Points）设计清晰，例如「实现某个 `Exporter` 接口，放进指定目录即可自动识别」。开发者在*插卡槽*，而不是*焊电路板*。
2. **数据与 UI 解耦**：导入只涉及「文件流 → 文本」，导出只涉及「画布渲染」，不触碰前端状态管理（Vuex / Redux）。

反之，公司项目里「编辑区一变，预览区跟着变」属于**状态联动**，必须深入生命周期，源码无法回避。

一句反向理解：

> 开源项目让人觉得轻松，是因为作者已经替使用者承担了「架构清晰」的成本；
> 公司项目让人觉得艰难，是因为前手把「架构清晰」的成本转化成了后人的**维护债务**。

### 2.3 底层原则

- **依赖倒置**：依赖接口而不依赖实现。能黑盒对接，是因为存在可依赖的接口；改不动，是因为没有接口可依赖。
- **防腐层（Anti-Corruption Layer）**：对边界清晰的能力隔离对接，避免核心域被外部细节污染。
- **耦合度决定策略**：策略选择的自变量是耦合度，不是项目性质。

## 三、如何应用

### 3.1 拿到需求先问三个问题

1. **它是 IO 型还是状态型？**（导入导出 = IO；编辑预览 = 状态）
2. **它有标准接口/扩展点吗？**（有 → 黑盒；无 → 白盒）
3. **它失败会影响主流程吗？**（导不出图可重试；简历存不上则系统崩）

三问的答案直接映射到策略：**IO 型 + 有接口 + 失败可降级 → 黑盒对接**；**状态型 + 无接口 + 影响主流程 → 白盒重写**。

### 3.2 面试表述范式

> 「复盘后发现，并不是我不愿读源码，而是我本能地遵循了**防腐层原则**：对边界清晰的导入导出功能采用『黑盒模式』快速对接；对与系统核心状态深度耦合的编辑功能采用『白盒模式』彻底重写。我的代码策略不由『是否开源』决定，而由『功能与核心域的耦合度』决定。」

### 3.3 可迁移的追问

在动手前追加一句设计层面的提问：

> 「这块功能能否设计成插件模式挂接？」

能，则把侵入型需求降级为附加型，成本大幅下降；不能，则提前预算解剖源码的时间。
